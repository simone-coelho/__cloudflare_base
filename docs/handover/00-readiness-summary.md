## Part 1 — State of the codebase

**What's actually here.** One Cloudflare Workers app (Hono) serving six built demo surfaces off a single shared D1 database, isolated by table-name prefix discipline (`coach_*`, `bh_*`, `mrd_*`, `funnel_*`) rather than separate schemas or databases: the Coach/Tapestry retail storefront, a First National Bank visual demo, Revenue Radar (checkout funnel), Bright Hour (QVC live-shopping), Meridian (shown on-screen as "Calder" — the Opticon demo), and an operator console — plus a 13-month-stale generic landing page at `/` that links to none of them. A seventh surface, Pizza Hut/`/restaurant`, is planning-only: **verified directly** — zero implementation exists in `src/` or `public/` beyond two comments referencing its build spec (`src/demos/registry.ts:4`, `src/demos/brighthour/surface.test.ts:4`); `src/demos/registry.ts:25` types `DemoSurface` as `'coach' | 'brighthour'` only. `docs/pizzahut/README.md` itself says "pursuit stage, nothing customer-facing yet" — treat it that way, not as a fourth live demo. `npx tsc --noEmit` is clean (R1 §5, run live). `@ts-ignore`/`eslint-disable` usage is low and narrowly scoped (5 hits total — R1 §4). Debt is tracked, just not inline: only 1 TODO exists in the whole tracked repo, but `ONBOARDING.md` §6 enumerates 9 known divergences with file:line citations — debt lives in one doc, not scattered comments (R1 §4).

The two newest, most-presented surfaces are also the best-documented: Meridian's isolation charter (`src/demos/meridian/README.md`) names ~10 specific coupling traps and how each is avoided, and Bright Hour's presenter runbook pair (`BrightHour-Demo-Runbook.md` + `Cheat-Sheet.md`) is the strongest "hand this to someone who didn't build it" documentation in the repo (R2 §3). Neither pattern has propagated to the rest of the codebase yet.

**What's not ready, one line per track:**

- **Push to the shared repo (Track A):** blocked by one live-shaped credential sitting in tracked git history (`.cursor/mcp.json:14`, duplicated inside an accidentally-committed 96-file worktree snapshot) — **verified directly**: both copies are tracked in git today, and no `.gitignore` entry covers either path. Plus a non-functional test harness and lint config, and a ~90-file customer-doc manifest that needs executing. Every item is individually small; none is optional.
- **Hand to engineers/SEs (Track B):** blocked by an onboarding path that actively misdirects rather than merely under-documents. The root `README.md`'s own Quick Start references `wrangler.toml.example`, which does not exist (**verified**: `find . -maxdepth 1 -iname "wrangler*"` returns only the real, pre-filled `wrangler.toml`), and describes a product with zero mentions of any demo actually in the repo. A stranger following it literally cannot reach a working demo. This needs a rewrite, not a patch — but a bounded one (R2 §2).
- **Tapestry delivery (Track C, internal):** the largest gap of the three, and the only one with an external deadline and a named technical reviewer. The customer-facing Solution & Algorithm document (`docs/content-personalization-design-tapestry.html`) currently tags three capabilities `built v1` — parameter control via UI/API, priors import, full data egress — that have **zero** corresponding code anywhere in the repo. **Verified independently**: no route, KV key, or UI control anywhere in `src/routes/operator.ts` or `public/operator-console.*` implements a weight, decay, or threshold control. This needs a decision before the document's next round with the customer, separate from and faster than the underlying build (R3 §0).

**A note on trusting numbers in this repo right now.** The three source audits report the same total test-case count (430) but disagree on the Meridian subtotal (R1: 120, R3: 153). A direct recount during this synthesis got a third figure — 443 total (56 reflex / 235 brighthour / 152 meridian) — because grep-based counting is sensitive to `it.skip`/`it.each` patterns and the suite is genuinely moving under concurrent development. None of the three counts is simply wrong; it means the repo cannot currently produce its own authoritative test count, because the one thing that would settle it — actually running `vitest run` — doesn't execute (item 5 below). All three audits independently converged on fixing that as the single highest-leverage item in the repo; treat that convergence as the strongest signal in this whole synthesis.

**Bottom line.** The shared-D1/prefix-discipline architecture is a deliberate design and, with one documented exception (item 8 below), holds up under inspection — this is not a pattern failure. What blocks each track is enumerated below, mostly small per item, and mostly mechanical. The two exceptions worth reading as genuinely urgent rather than routine backlog: the leaked credential (Track A — fix now, independent of any push timeline) and the Tapestry documentation-vs-code gap (Track C — resolve the label or the code before the next customer round, on a clock this team doesn't control).
