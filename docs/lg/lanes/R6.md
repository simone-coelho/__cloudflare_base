## Findings

### 1. DEFECT: a fence refusal that is not a 401 is remembered as the tenant's datafile failure, across shoppers

**Where.** `src/services/OptimizelyService.ts`:
- `:111` — `refusal` recognises only `HTTPException` 401;
- `:279` — the `fetchDatafile` catch;
- `:319` — the `createFreshClient` catch;
- `:269` and `:313` — the remembered failure is re-thrown to later callers.

**Why it happens.**
1. `ownerFetch` → `ownerEffect` rechecks the owner before and after the fetch (`src/identity/sessionAuthority.ts:279`, `:282`).
2. That recheck runs `requireRetention` on every pinned retention guard (`sessionAuthority.ts:320`).
3. `requireRetention` throws `RetentionUnavailable` (`src/retention.ts:96-99`), which extends `Error`, not `HTTPException` (`retention.ts:38`).
4. The memory is keyed by the backing binding and the tenant's connector (`:144-150`), not by the shopper. So one shopper's lapsed profile-retention stamp is stored as the whole tenant's datafile failure.
5. For 60 s, every other shopper's decision seam and feature-variable probes in that isolate degrade at once, and nothing is fetched.

**Evidence.** My probe `scratchpad/r6/probe-retention.test.ts` runs on the lane's code with the real `runOwnerOperation`, `retentionBirth` and `pinRetention`:
- Shopper A's pinned stamp lapses while the fetch is in flight, and A's operation rejects with `RetentionUnavailable`.
- 59 s later, shopper B (outside any owner operation, nothing lapsed) gets the same error instance, with 1 fetch in total.
- Control: after `forgetRememberedDatafiles()`, B fetches (2 fetches) and gets the datafile's own 503.
- Result: 1 passed.

**Why the test missed it.** `OptimizelyService.datafileMemory.test.ts` case (d) simulates the refusal as a global `fetch` that throws `SessionAccessError`, so it never reaches the fence's other refusal.

**How likely.** It needs a retention stamp that lapses, or a retention policy revision, during a datafile fetch. That is rare. The effect is up to 60 s of fallback decisions for every shopper of an FX tenant in the isolate.

**What would close it.** Remember only failures of the fetch, the response or the datafile validation. Never remember anything the owner fence raises.

### S1. Finding 1: the datafile's own failures only

**The rule now** (`src/services/OptimizelyService.ts`):
- `fetchedDatafile` (`:183-195`) is the only fetch for `createFreshClient` and `fetchDatafile`.
- A bad status, bad JSON or a failed validation is remembered (`:194`).
- A rejection from `ownerFetch` is remembered only if `ownerFenceRefuses()` (`:120-122`) is false at the catch (`:188`).
- A 401 is still never remembered (`rememberFailure`, `:124-126`).

**Can a fence condition fail during the fetch and pass at the recheck? No, given a clock that does not step back.** The fence's check is `recheckOwnerInvocation` (`src/identity/sessionAuthority.ts:314-321`). It does no I/O at all:
- **No grant re-read.** The admitted principals are compared on `exp` only, through `assertSessionTarget`.
- **No retention read.** `requireRetention` compares the pinned stamp against `env.RETENTION`, a static variable it parses each time.
- **Deadlines are pinned numbers.** Consent and recovery deadlines are compared to `Date.now()`.

**Every input only moves towards failing.**
- The guard collections are append-only: pushes at `:312`, `:324`, `:382`, `:402`, and no removal anywhere in `src`.
- `held.active` only goes from true to false (`:486`).
- Every time comparison except one can only start failing as time advances.
- The exception, a stamp whose `bornAt` is after now, is validated when the stamp is pinned (`:323-324`), so it cannot fail later on a clock that does not step back.

**There is no I/O between the two rechecks.** The fence refuses either at `:279` (before the fetch) or at `:282` (after it). Between that refusal and the catch's recheck there is only promise settlement, and workerd does not advance `Date.now()` without I/O, so both reads see the same instant. Under Node, time can only advance, which can only add failures.

**Network failures and the conservative side.** A network failure while the grant lapses during a slow fetch is not remembered, so the next caller simply fetches again.

**The constructible counterexample needs a clock that steps back.** I wrote `scratchpad/r6/probe-clock.test.ts`, which scripts `Date.now()` around the post-fetch recheck. It passes 2 of 2:

| clock after the post-fetch recheck | what shopper B gets | fetches |
|---|---|---|
| holds past expiry | `Failed to fetch datafile: 503` | 2 (fixed) |
| steps back one read later | the remembered `RetentionUnavailable` | 1 |

So the rule depends on exactly that assumption and on nothing else.

**Can the recheck throw inside the catch and change what the caller sees? No.**
- `ownerFenceRefuses` wraps `currentOwnerIdentity()` in try/catch and returns a boolean.
