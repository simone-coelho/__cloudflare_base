### 2. The design, and why it keeps the contracts

**(a) The day merged once.** Before, `reportFromHours` summed the hours with `hb = mergeBrand(hb, hour)`, which
builds a new total from the old one every time. `admitHours` charged each visited member `4 × aggs.length` for that
copy, counting every folded hour of the day, empty ones included.

`mergeBrandInto` adds an hour into the running total in place:

- It uses the same functions on the same numbers in the same order (`mergeCounter`, `mergeEntry`, `addCounts`,
  `maxCounts`), so every value and every key order is what `mergeBrand` made.
- A member the hour does not carry is left as it is, instead of being copied unchanged.
- Admission charges each member once: 4, exactly what a one-hour day was always charged.

No limit moves, and admission still refuses what it refused for size:

- `hourly.test.ts`'s W32.03 day of 24 hours of 11,000 items is still refused (1,056,000 and more).
- Its 16,384-cell and 8 MiB-output refusals still refuse.
- The input hours are still never mutated.

**(b) The open hour's working aggregate**, the brief's shape, with segments at object granularity.

What each five-minute run does (`foldOpenHours`, after `catchUp`, inside the tenant's existing scheduled task):

- It folds the hour that is open, and also the hour before it while that hour's own fold is not yet due.
- It uses `buildHour`'s fold, step for step, against the shards as they stand, cleaned in memory exactly as
  `cleanupHourlyState` would clean them.
- It never writes a shard or the hour's aggregate.
- It writes under `aggregates/<tenant>/open/<date>/<hh>`:
  - `.json`: the working aggregate, an `HourAggregate`;
  - `.ledger.<id>`: one segment of the hour's ledger copy, for each run that read something from the ledger. A
    segment is a header line, then each object's text as the ledger holds it, unescaped.

How the copy is used:

- The next run reads the segments, and from the ledger only the objects they do not hold under the same etag.
- A segment that holds an object storage has since changed or no longer lists, or an object naming an erased
  visitor, is removed. Its still-good objects go into the run's new segment, which is written first.
- Every object, copied or read, is charged to the same raw budgets in the same order. So the rows, the refusals and
  the aggregate are the ones a read of the ledger gives.
- A segment is what the queue has written by the run, not a five-minute slice of record times. An object can
  straddle two slices, and a record can land in a later object than its time. Cutting by object means no record is
  folded twice or skipped.

Why the copy is the ledger's text and not a partly folded state: a decayed accumulator cannot have an erased
shopper subtracted from it, and a credit already given cannot be re-ordered when a late object arrives. Only a
refold from the rows stays exactly the closed hour's fold. The cost is at most one hour's raw text per refold,
bounded by that hour's own fold budget, however busy the day is.

How a report build (`runDayReport`, built-in overlays) uses it:

- It refreshes the working aggregates the job has started, reading only the raw written since the job's last run.
- It then sums the final hours and the working ones.
- The hours summed from a working aggregate are named in `hours.open`, and such a day's coverage says `incomplete`.
- A day with neither a folded nor a working hour is read raw exactly as before, with the same refusals.

| Contract | How it holds |
|---|---|
| The hour's final aggregate is byte-equal to today's for the same records | `buildHour` is unchanged except that three blocks moved verbatim into helpers the working fold shares. Golden hashes captured at 272ede8 before the move still match: both hour aggregates, all 64 shards, and the canonical day. A store folded open every ten minutes through hour 12 ends with the hour aggregate and every shard byte for byte those of a store that never was |
| Erased visitors leave at the next fold | The working fold reads the tombstones on every run. The run after an erasure drops her rows from the counts and names them in `rows_hidden`. After that run, the copy never keeps an object that names an erased visitor: such an object is read from the ledger at each fold, as the final fold reads it |
| Provenance-less records write the bytes they always did | The final fold is unchanged (the golden fixture mixes rows with and without `experiment`). The working fold is the same code |
| Row conflicts still refuse | A conflict in the open hour refuses its working fold with `conflicting rows under one logical id`, as the final fold refuses the hour, and the last good working aggregate stands. A refused hour leaves the in-memory shards as they stood, so the next open hour is still folded. The raw path's filing and resolution (W22 D1.03) are untouched |
| `foldedHours` still names the hours | Only the final fold writes shards. After it, each shard holding rings names hour 12 once |
| No budget rises | `REPORT_LIMITS` is untouched. A segment is written only when it fits `aggregateBytes`, and the segments are read back under one `aggregateBytes` budget. Any doubt about one, and the ledger is read instead |
| The answer's shape | Every member is unchanged. `hours.open` is added, only when an hour is open, and while it is the coverage says `incomplete`. The kit's route passes the report through and is unchanged |

The working objects of an hour are removed by the first run after the hour's fold is due, so the copy outlives its
hour by one run at most. W22 R1.03's rule stands: a closed hour past its grace with no final aggregate is listed in
`missing`, and it is not summed from its working aggregate.

### 6. What is not fixed, and what it needs

**The fold stops folding once the 48-hour rings are busy (case 2). This is the first thing for the lead.**

- **The mechanism.** `buildHour` stages all 64 shards. Shard 0's pending plan carries every staged body, plus the
  hour's aggregate, JSON-escaped. The bound then adds the larger of each shard's old and new body, for the mix a
  restart could find. So two copies of the ring state, plus the aggregate, must fit 16 MiB: the rings can hold
  about 7.5 MB.
- **On this rig.** The rings held 6,652,548 bytes in 61 shards after hour 10. Hour 11 then needed 22,205,992 bytes.
- **What follows.** From then on every busy hour's fold is refused, and the catch-up tries each again every run
  for 26 hours, reading its raw every time. Two such hours at the front of the lookback stop every newer hour from
  folding (`catchUp` stops after two other failures).
- **What the report does now.** With this lane the day still answers: the open hour from its working aggregate,
  the hours that folded, and the refused hours named in `missing`. But it is not the whole day.
- **What fixing it needs.** Something that changes what is written or kept: a smaller plan that does not carry
  every unchanged shard, a shorter horizon or smaller ring entries for a demo tenant, or a different recovery
  format. That is W30.04's transaction and W22's horizon, so it is not this lane's to decide. The ruling is the
  lead's; the lane can build whichever is chosen.

**The other limits:**

- **One hour past its own fold's raw budget.** A closed hour's fold reads at most 600 objects and refuses past
  16 MiB of raw. That is unchanged, and the working fold refuses at the same point. On this rig an hour holds about
  four rounds of both suites before it gets there; hour 11 reached 98%. Such an hour is listed in `missing` once its
  grace has passed. Truncating an hour at its byte budget, as it is truncated at its object cap, would change what
  an over-budget hour's fold writes. That is the lead's to rule.
- **A day the job never folded.** On a rig whose cron is not run, the day is read raw as before and refuses as
  before once it passes 16 MiB. RESUME-oh's rule stands: run the cron. On a fresh state it takes thirteen runs
  (two hours a run, oldest first, over the 26-hour lookback) before today's closed hours are folded. From the first
  run the open hour has its working aggregate, so the date is read from its hours.
- **The kit's report panel misreads the window.** `public/demo-kit/panels.js` line 458 writes "the hour in progress
  is not in it until it closes" whenever `hours.source` is `aggregates`. With this lane the hour in progress is in
  the report, named in `hours.open`. The sentence should read `hours.open`. That file is not this lane's.
- **A refold costs about what a closed hour's fold costs.** Each five-minute run, and each build, refolds the open
  hour from its copy: at most an hour's raw, which the hour's own fold reads once. For a busy hour that is about
  50 MB of heap and about a second of CPU (§4).
  - **On wrangler dev** everything shares one process, so a scheduled run holds requests behind it. In case 2 it
    re-tries every refused hour as well, which made each run take 9–10 s.
  - **What the late rounds failed on came from that.** The 503s and broken images in them landed inside those
    runs. Two builds during one of them made workerd restart the worker mid-request.
  - **A hosted isolate** has 128 MB. A build that lands in the same isolate as a run folding a busy hour can meet
    that limit; the closed hour's fold already lives at that size.
  - **Not built:** a run, or a build, with nothing new could skip the refold by recording what the working
    aggregate was folded from (the hour's listing, the shards' etags and the tombstones).
- **The ledger copy.** It is a copy of the open hour's ledger rows, visitor ids included. It lives one run past the
  hour's grace, and keeps no object that names an erased visitor after the fold that first sees the erasure.
- **The hosted worker.** It runs 272ede8's engine until `edge-platform-oh` gets a code deploy (the owner's step).
  Whether its catch-up has been refusing hours is in its logs (`hourly fold hours failed and skipped`), not on this
  rig. After a deploy:
  - the first five-minute run starts the open hour's working aggregate;
  - the day report answers from its hours;
  - while case 2 lasts, the refused hours are listed in `missing`.
