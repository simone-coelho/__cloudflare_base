# Lane E2: a tenant with no priors document is served as "no priors"

**Status, 2026-10-02: built and tested locally; nothing committed, pushed or deployed.** The fix is in the engine. A publication set with no priors member now reads as "no priors" wherever priors are read. It no longer reads as an authority error. The kit is unchanged, for the reason in §3.

On both rigs the error is gone from the logs:
- OH request-level suite: 223 of 223 on its first run after the fix.
- Vantage request-level suite: 115 of 115.
- Vantage DOM suite: 298 of 298.

The full vitest run adds no failure. The typecheck passes. Built on `92c60cf`. During the lane the head moved to `9e35b51`, M1's OH commit. That commit touches none of this lane's files, and my OH runs used its files as they then stood, uncommitted, in the working tree.

## 1. Cause

The demo bootstrap (`src/routes/demoBootstrap.ts:46`, `MEMBERS = ['reflex', 'catalog', 'slots', 'learn']`) creates a publication set with four members and no `prior` member. Every demo tenant (OH, Vantage) has this set.

`LearnStats.priorsFor` (`src/durable-objects/LearnStats.ts:855` before the fix) reads the prior member without a guard, through `readPinnedPublication`. That function throws `required(ref)` (`src/config/publication.ts:339`) when the set has no ref for the member. The thrown message is `Configuration publication authority unavailable`.

`priorsFor` is called from `snapshot()`, so every lift snapshot of a demo slot failed:
- **`/snapshot`** answered 503 "statistics acknowledgement unavailable".
- **The publication alarm** threw out of `alarm()`. In `publish()` (`:801`) the snapshot is built outside the `try`, and `alarmScoped` (`:432`) rethrows. Workerd logged this as `Uncaught Error`, then retried the alarm on its backoff, and the next attempt failed the same way. That is the stream of errors every lane saw.

A demo slot therefore never published a lift snapshot.

The rigs also saw the ledger consumer stall, with receipts answering 202 or 503. The link from these errors to that stall comes from earlier lanes (Vantage RESUME findings 3 and 5; lane P finding 4). My "before" run did not reproduce the stall, at a load average of 13 to 16. Nothing I measured contradicts the link, and with the fix no throwing alarm is left to restart anything.

The comment in `priorsFor` already stated the design: an authority that cannot be read is not an empty prior document. A set that simply lists no prior member is a different case. That set has been read, and its digest checked. A member cannot be removed without breaking that digest, so the missing member is the authority's own answer: this tenant imported no priors.

The engine already draws this line for proposals. `publishedProposals` (`src/routes/decisions.ts:77`) answers "no proposals" when the set has no proposals member. It still refuses when the set itself cannot be read. Priors had no equivalent.

**The priors document.**
- **Kind:** `PRIORS_KIND` (`src/learn/priors.ts`), named `prior`. Its shape is `{ version?: string, cellGrammar?: { name, version, order }, rows: PriorRow[] }`, where a row is `{ slot, item, cell, p_prior, n_equiv, measurementBasis? }`.
- **An empty valid instance:** `{ rows: [] }`. The engine's own is `EMPTY_PRIORS = { version: 'prior-empty', rows: [] }`.
- **The snapshot convention for "no priors":** `priorVersion` 0 (`src/learn/stats.ts:461`, `priors?.version ?? 0`). Receipts carry the same 0 (`src/content/decide.ts:513`, `:544`).

## 2. The fix, by file

| File | Change |
|---|---|
| `src/config/publication.ts:355-376` | New `readOptionalPinnedPublication(env, kind, scope, set)`. It returns `null` when the pinned set lists no member for `kind` and `scope`. In every other case it behaves exactly like `readPinnedPublication`: a set of another scope refuses (503), and so does a member the set lists whose document is missing or does not match its ref. A set that cannot be read never gets this far, because `pinPublication` refuses first |
| `src/durable-objects/LearnStats.ts:851-878` | `priorsFor` reads the prior member through the new function. It still runs the configuration check against the published learn document, so a missing priors member excuses nothing else. It then returns `null` (no priors; the snapshot's `priorVersion` is 0) when the member is absent. A member that is present goes through the unchanged path: capacity, unit refusal, the ladder grammar, the bounded index |
| `src/config/publication.optionalMember.test.ts` (new, 3 tests) | Uses the four-member bootstrap set. The optional read answers `null`; the required read still refuses with exactly the logged message; a member that is present reads identically through both functions. A prior document that is present, empty or full, is read as published. Never "absent" when unreadable: a listed member missing from storage, a listed member whose bytes break the digest, a storage outage, and a set pinned for another tenant all refuse with 503 |
| `src/learn/priorsAbsent.test.ts` (new, 3 tests) | A real `LearnStats` over the four-member set. `/snapshot` answers 200 with `priorVersion` 0, and `alarm()` resolves and publishes the lift snapshot to KV. Forced `/publish` publishes. With the clock pinned, the same evidence learns exactly what it learns under a published `{ rows: [] }`: identical items, slot rates and events, with prior version 0 against 1. Negative controls: a listed prior member gone from storage, or an authority outage, still answers 503, `alarm()` still throws, and nothing is published |

On the code before the fix, the first two `LearnStats` tests fail (`expected 503 to be 200`) and the negative-control test passes. I proved this by reverting the one read in place, running the tests and restoring. A version that caught every error and answered "no priors" would fail the third test.

## 3. The kit: no change, and why

The kit could not publish an empty priors document at bootstrap without a route change, and with the engine fix it does not need one:
- **The bootstrap route takes four members, no more.** `src/routes/demoBootstrap.ts` builds its baselines from `MEMBERS` alone (`:46`, `:81`, `:106`) and ignores any other body key. A `priors` member sent by `scripts/demo-kit/lib/seed.mjs` would be dropped.
- **A later versioned write cannot add the member.** A set's membership is fixed when it is initialized. `publishSet` reads each change's base through `readPinnedPublication` (`src/config/publication.ts:461`), which refuses an absent member with 503. `validatePending` also requires the new set to list the same members as the old one (`:263`).

So `seed.mjs`, `lib/config.mjs` and the kit's config schema are unchanged. A demo needs no priors document now.

**For the owners** (outside this lane's paths; none of them blocks a demo):
1. **`src/routes/content.ts`.** `GET /content/priors`, `/history` and `/revisions/:n` still answer 503 on a set without a prior member. The handler is already written for a missing read (`:294`, `rev ? rev.value : k.fallback`, with `fallback: EMPTY_PRIORS` at `:73`), but `readPublication` never returns null. Reading the priors kind through `readOptionalPinnedPublication` would answer the compiled default, `source: 'compiled-default'`, revision 0. The console's "Imported priors" panel reads `/content/priors/history` (`public/console/views-measure.js:247`).
2. **Importing priors into a demo.** A demo tenant cannot import priors at all, because its set has no member to write. If a demo is ever to show imported priors, `src/routes/demoBootstrap.ts` would accept an optional `priors` member, validated by `PRIORS_KIND`, with `EMPTY_PRIORS` as the default. Then the kit's bootstrap would send it, from a `seed.documents.priors` entry in the config.
3. **`publishedProposals` (`src/routes/decisions.ts:77-83`)** can call the new function. The semantics are the same. This is a tidy-up, not a defect.
