# Lane E4 — the hosted action answers at the profile read's speed

Engine lane, briefed by the lead on 2026-10-03 after the OH store's first live verification of the
persistence and panel-redraw commit (`bbf8a9d`, hosted as version `cd3775e2` on `edge-platform-oh`).
The ruling it serves is Simone's: a click registers at once; the panel redraws after every click.
The page now does that (it re-reads her profile the moment the action answers), so the only thing
between her click and the panel is the engine's `POST /realtime/action`, and on the hosted worker
that call takes one to two seconds.

## What the lane does

Make `POST /realtime/action` on a hosted worker answer in about the time `GET /realtime/reflex`
answers, for the same visitor, with the **same response body** it answers today (the update's
affinity dims and changed list, the decisions where it carries them, the session id, the cookies
flag). Nothing about what is stored, learned, ledgered, broadcast or decided changes; only when the
caller is answered relative to that work and how often the same configuration is fetched.

1. **Measure first, in the object.** Instrument the ingest path with `performance.now()` marks
   around each awaited step and log one structured line per action (`action_timing`, with the
   step names and milliseconds) under a flag or at debug level, deploy that to the lane's own
   measurement by tailing — no: the lane does not deploy. Instead, reproduce hosted conditions on
   the rig as far as possible (a `DecisionProvider` whose datafile fetch takes 800 ms and fails;
   KV reads with 60–120 ms latency through a wrapper in the test harness) and show where the time
   goes with a table in the lane note. Keep the instrumentation if it costs nothing and is quiet
   by default; otherwise remove it.
2. **The datafile.** A tenant whose `OptimizelyService` has no Feature Experimentation key, or whose
   `DECISION_SOURCE` is not `optimizely`, never fetches a datafile; `getCtx()` resolves to the
   fallback immediately. Where a key exists, the datafile fetch is memoised per object (or per
   isolate) with a short TTL and never blocks an action's answer when it is already known to fail
   (a failed fetch is remembered for a minute). `src/connectors/index.ts` lines 35, 47 and 58 are
   where the provider is chosen.
3. **Configuration reads.** `resolveTenantReflexConfig`, `resolveTenantCatalog`,
   `bufferedEventAllowed` and `bufferedInterest`: whichever of them reads KV, the configuration
   store or another object on every event gets a per-object cache keyed by the publication revision
   (the object already knows the revision through `resolveTenantReflexConfigRevision`, line 166),
   so an unchanged publication costs no read after the first. A new publication (a republish, a
   beat's press) is honoured on the next event, so the cache is validated against the revision
   cheaply or expires within a few seconds. The suites press beats and then act within the same
   second; they must keep passing.
4. **Fan-out after the answer.** The region ingest, the learn outcome, the websocket broadcast and
   the ledger delivery run after the response is built, through `ctx.waitUntil` or the object's
   equivalent (`this.state.waitUntil`), never awaited in front of the caller, unless a step's
   result is part of the body. Ordering guarantees that exist today (the ledger's sequence, the
   outcome's attribution) are preserved: say in the note which ones exist and how each is kept.
5. **Tests.** Unit tests for the memoised datafile (no fetch without a key; a failed fetch
   remembered; a fresh fetch after the TTL), for the configuration cache (served from cache on the
   same revision; refreshed on a new one), and for the answer-before-fan-out order (the response
   resolves before the region ingest is awaited). Run the files you touch plus
   `src/routes/realtime.sdkContract.test.ts`, `src/durable-objects/*.test.ts`, `src/demos/**/*.test.ts`,
   `src/routes/oh.test.ts`; then `npm run check:generated` and the app typecheck
   `npx tsc --noEmit --incremental false --composite false`. The four pre-existing failures named in
   LANE-LOG (W19.F3.04 ×2, W22.R1.03, realtime.sdkContract's one) are not yours; name any you see.
6. **Prove the speed on the rig.** With `scripts/demo-kit/rig.mjs` or `npm run dev` on your own
   port (9140), run `node scripts/demo-kit/check-demo.mjs --config oh --base http://localhost:9140`
   and the two OH suites (`scripts/rehearse-oh-page.mjs`, `scripts/rehearse-oh-dom.mjs --only store`)
   as the gate; then time ten `POST /realtime/action` calls before and after your change with the
   same rig and the same slow-datafile and slow-KV wrappers, and put both columns in the note. The
   hosted figure is the lead's to take after the deploy.

### 2. What changed, by file

| File | Change |
|---|---|
| `src/config/publication.ts` (`pinPublication`, caching only) | **When:** a serving read whose storage handle has no resident entry. **What it still does:** reads and validates the head, every time. **What is new:** if the head's committed identity (revision and digest) is one this isolate already holds a set for, the read uses that set and the documents already read under it instead of reading them again. It takes the newest such entry, so each operation starts from what the previous one held. **Why that is safe:** the identity is the digest of the sealed set, and the set and its documents are immutable and were validated against it when first read. **Unchanged:** a head that cannot be read or does not validate refuses as before; a new identity reads its own set; the administrative (non-serving) read, the 30-second lifetime, the byte and entry bounds and the invalidation at publish are as they were; lane E2's optional-member rule is untouched. **Effect per action:** one R2 read instead of four, and the vocabulary cache now hits |
| `src/services/OptimizelyService.ts` | **What is remembered,** per isolate, per backing KV binding (`ownerBindingIdentity`) and per the tenant's datafile identity: a fresh client, reused for `FRESH_DATAFILE_MS` (10 s), so freshness stays "within seconds" (doc 09 §6.1); and a failed fetch, remembered for `FAILED_DATAFILE_MS` (60 s). **During that minute** `createFreshClient` and `fetchDatafile` fail at once with the same error, so callers degrade exactly as they did after waiting. **Never remembered:** an authority refusal raised while fetching (an owner fence's 401). **Forgotten on refresh:** the datafile webhook's `refreshDatafileCache` and the explicit `refreshDatafile` forget the tenant's entry. **New:** `hasFxKey()`. **Unchanged:** a tenant with no key still throws before anything is read or fetched |
| `src/connectors/DecisionProvider.ts` | `LiveDecisionProvider.getCtx()`: a tenant with no FX key degrades at once, with nothing read, fetched or logged |
| `src/connectors/AudienceStore.ts` | **What:** `KvAudienceStore.listPublished` remembers the tenant's published audiences per backing binding and tenant for `AUDIENCE_LIST_MS` (10 s). **Writes here:** every write through any store in the isolate (publish, seed, archive, rename, pin) forgets the list at once, and a list that a write overtook is never remembered. So an audience authored in this isolate qualifies on the next event, as before. **Writes elsewhere:** an audience written by another isolate is seen within 10 s, inside the 60 s that KV itself allows a write to reach every reader. **Callers** receive copies |

### 3. Step 4, the fan-out after the answer: built, then taken out

**What I built.** In `ShopperReflex`'s `/authority/request` branch, for `POST /realtime/action`:
- the response resolved as soon as the route had built it;
- the operation went on draining its retained work, under the same owner fence;
- the object's chain still held the next operation until the drain settled.

This moved the region ingest and the outcome behind the answer, and with the broadcast retained instead of awaited, the frame too.

**Two existing tests encode the current order.**
- **`W05.02 resolved action consent`: "persists only necessary cold refusal hints and fails on unreadable/malformed state or failed refusal persistence before configured effects"** (`src/routes/realtime.sdkContract.test.ts:5673`).
  - At `:5686` it sends one consenting `add_to_cart` and does not drain it.
  - It then re-arms the destinations (`destinations(f)`), clears the effects, and asserts that the next action, which is refused, produced none.
  - With the answer first, the first action's outcome reaches the re-armed queue and ring after the clear, and the test sees `['outcome', 'learning']`.
  - It fails with the early answer alone.
- **`W06.12`: "propagates the original profile deadline into the actual delayed relay send boundary"** (`:793`).
  - It requires the action whose broadcast meets the expired profile deadline to answer not-ok (`:828`).
  - With the broadcast retained, the answer is built before the refusal, so it is 200.
  - It passes again when the broadcast stays awaited.

The method does not let me edit either test or leave the failure, so the change is out.

**What it would buy, measured on the rig:**
- **Reward-bearing actions** (`add_to_cart`): about 170 to 230 ms, the outcome's erasure read plus `DecisionRing /learn/outcome`.
- **Product views:** close to nothing, because the region ingest already runs beside the main path.
- **Click to panel:** less than the answer gains. The object admits its next operation only after the drain, so the profile read the page sends straight after would still wait for that work.

**For the lead.** Two rulings would let it land:
- the specifier amends W05.02 at `:5686` to drain the first action;
- W06.12 keeps the broadcast awaited, as the version I built did.

The change is then about 25 lines in the `/authority/request` branch of `ShopperReflex.fetchScoped`. Ordering would hold:
- the drain stays inside the owner operation;
- every effect still rechecks grant, consent and retention at its binding;
- the object's chain still serializes this shopper's operations, so frames, region counts, outcomes and ledger messages keep their per-shopper order.

### 7. Ordering guarantees

None changed, because nothing moved relative to the answer. For the record, these exist:
- **The object's serialization chain** (`ShopperReflex.serialize`) admits one owner operation at a time, and the next only after the previous one has drained everything it retained. So this shopper's frames, region counts, outcomes and ledger messages keep the order of the actions.
- **The outcome's attribution** (its session, its decision reference, its event id and its time) is fixed in `emitOutcome`, from the action and the host's answer, before its delivery starts.
- **The ledger's own sequence** is the record id (tenant, engine-stamped time, visitor, event id), set at that same moment. The queue itself promises no order.
