## 4 · What the audit missed

### 4.1 The overstatement it warns about is already in the customer's kit
`docs/kit/00-README.md:3` — "**Prepared for:** Tapestry (platform and front-end teams, Coach first)". It is
a customer-facing document. And `docs/kit/04-staging-connection.md`:
* `:61–63` — "**The scripted acceptance run in your lower environment is M4**; it uses the same requests as
  this check, extended to the loop. It exists as `scripts/acceptance-run.mjs` …"
* `:86` — "It stops on the first failure and prints the transcript, **which is the acceptance evidence**."

And internally, `docs/architecture/21:333` — "**The acceptance run exists (M4).**" — sits **ten lines above**
`:343`'s rule that a script is not the acceptance. The audit says "'acceptance passed' *would* overstate";
the correct tense is that it **already does**, in writing, in a document prepared for Tapestry. That is the
sharpest form of this finding and the cheapest thing to fix.

### 4.2 A shipped-SDK defect: graceful absence never reaches slot subscribers
`src/sdk/listen.ts:53`:
```ts
function notifyAbsence(): void { for (const cb of setSubs) { try { cb(null); } catch { } } }
```
`setSubs` holds only `onDecisions` callbacks. Slot subscribers (`slotSubs`) are notified **only** from
`apply()` (`:55–66`), which runs only when a decision set actually arrives. So on a hydrate timeout, a
failed snapshot or a malformed one, a per-slot subscriber is never called.

The kit's headline section — "**The ten lines that personalize a page**",
`docs/kit/01-integration-guide.md:46–58` — puts the default render inside the slot callback:
```js
client.listen.subscribe('hero', (decisions) => {
  const d = decisions[0];
  if (!d) return renderDefaultHero();     // never reached on absence
  renderHero(d.customerContentId);
});
```
A customer who writes those ten lines and does not additionally copy the separate `onDecisions` block
eleven lines further down (`:69–71`) renders **nothing at all** in the hero when the platform is slow or
down — measured, §3 R3, `paints: []`.

This contradicts three of the platform's own statements:
* `src/sdk/listen.ts:3–4` — "the page never waits on us and **never shows a hole**".
* `src/sdk/listen.ts:22–24` — `subscribe` is "Called with the slot's decisions … **every time a set
  arrives** — with an empty array when the set has nothing for the slot, so a page can revert to its
  default." True for a set that arrives; absence is not a set.
* `src/sdk/README.md:10` and `docs/Tapestry-BTI-System-Architecture.md:267` — "**guaranteed** graceful
  absence".

It ships: `public/sdk/edge-personalization.js` has the same shape at `:535` (`notifyAbsence`), `:576–578`
(the timer) and `:589`. This is precisely the class of defect a real browser acceptance against a customer
page would surface, which is F29's own argument, made concrete.

### 4.3 A test that reads as proof and is not
`src/sdk/listen.test.ts:41` ("declares graceful absence on the deadline, then applies a late snapshot") and
`:55` ("a failed or malformed snapshot is absence, not an error") both assert absence **only** through
`onDecisions`. No test in the file subscribes to a slot and asserts what that callback receives on absence.
The suite passes, and reads as proof of the graceful-absence contract, while never touching the path the
kit tells customers to use.

### 4.4 One leg of the acceptance bar has no owner, and no editor
`docs/architecture/20-scope-truth-ledger.md:66`, row B4, still open: "**Who delivers the tuning UI**, when
the acceptance bar requires weights live-tunable by a business user … Name the deliverer and the date, **or

And the editor does not exist for the right weights. `src/content/kinds.ts:149–153` requires each slot
strategy to carry `weights: Record<dimension, 0..1>`. The console's slot view
(`public/console/views-config.js:333–360`) edits `take`, the pin, stage, freshness, fatigue and diversity —
**never `st.weights`**. The weights editor at `views-config.js:156–174` is on a different document: event-signal
weights, as `:182`'s `D.weights.product_view` shows. So the audit's remedy step "business weight edit and
rendered consequence" **cannot be executed today**; F27 is a hard prerequisite for F29's remedy, and the
audit does not say so.

### 4.5 Both-host parity is pinned off in configuration, not merely unproven
`wrangler.toml:231` and `:330` both set `REFLEX_HOST = "session"` with the comment "Session until the object
host passes the acceptance run". Parity is a configuration commitment blocked on the very run that F29 says

## 7 · Remedy assessment, and the smallest safe fix

**The remedy is right in direction, over-scoped as one item, and under-scoped on its dependencies.**

* Right: execute the real acceptance with customer content and agreed scenarios; separate delivery
  acceptance from the scientific experiment and commercial entitlements; rebaseline against the actual
  kickoff and freeze; do not invent a revenue guarantee.
* Over-scoped as one unit: it bundles an engineering pack (M), a customer-content and environment
  dependency the customer owns, both-host parity (separate engineering), and a commercial rebaseline (S).
  Estimating them as one M hides the parity work and the fact that the pack is an extension of two
  existing harnesses, not a new build.
* Under-scoped: it does not name **F27** as a hard prerequisite. "Business weight edit and rendered
  consequence" cannot be demonstrated until a per-slot dimension-weight editor exists
  (`public/console/views-config.js:333–360` vs `src/content/kinds.ts:149–153`), and doc 20 row B4 has not
  even named who delivers that surface. It also does not name the misrepresentations as the urgent part.

**Smallest safe fix that closes the launch-blocking part** — roughly one engineer-day, and it closes the
representation risk without waiting on the customer, the kickoff, or F27:

1. **Stop calling the script the acceptance.** Edit `docs/kit/04-staging-connection.md:61–63` and `:86`, and
   `docs/architecture/21:333`, so no document — least of all one prepared for Tapestry — says the script
   *is* M4 or that its transcript *is* the acceptance evidence. Use `21:343`'s own words: the engineering
   check that precedes acceptance. (~1 hour.)
2. **Fix `notifyAbsence()` so the kit's ten lines are correct.** In `src/sdk/listen.ts:53`, also notify each
   slot subscriber with an empty array on absence, and add a `listen.test.ts` case that a slot subscriber
   receives `[]` on timeout and on a failed snapshot. Rebuild `public/sdk/edge-personalization.js`.
   Five lines plus a test; it is the difference between a customer's hero showing their default and showing
   nothing. (~half a day including the bundle.)
3. **Make the no-flash sentence true or make it honest.** Either document the server-injected-snapshot
   pattern in `docs/kit/01-integration-guide.md` — resolve `GET /v1/{tenant}/decisions/snapshot` at the
   origin, inline the JSON, call `client.listen.apply(payload)` before first paint, which the SDK already
   supports at `listen.ts:29–30` — or correct all eight lines listed in §1.6 to say that the default may
   paint first and the decision repaints within `hydrateTimeoutMs`. Documenting the `apply()` path is the
   better answer: it delivers the promise instead of retracting it. (~2–3 hours.)
4. **Delete the SSO baseline.** `docs/Tapestry-Implementation-Plan.md:74` → "API-key + email-and-password
   operator auth; SSO (OIDC) on request, about two engineer-days plus your identity team's time", per
   `docs/architecture/30:48–54`. (~10 minutes, and it stops a security reviewer from finding it first.)
5. **Rebaseline the dates.** Remove the unreachable "Mid-September"/"End of September" M1/M2 wording and the
   "~6 Nov" example at `docs/architecture/21:28`; state acceptance as landing **before** the customer's
   November freeze, with M3 (mid-October SDK + docs) as the hard line per `docs/architecture/19:112`.
   (~1 hour, and it is a decision to record, not work to do.)

The full acceptance pack — 20–30 customer assets, the cold / third-interaction / return-visit / channel
matrix, weight edit and rendered consequence, pins/defaults/inventory, consent, identity, reconnect,
both-host parity, recorded IDs and timings — remains **M**, follows F27, and should be built by extending
`scripts/rehearse-storefront.sh` and `scripts/acceptance-run.mjs` rather than starting over.
