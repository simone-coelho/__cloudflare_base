# F17 verification — "Hourly folding loses late data and cannot honestly represent the seven-day policy"

Verifier: independent reviewer. Date: 2026-09-06.
Repository: `/mnt/c/Users/LAH/Documents/__Development/Optimizely/__cloudflare_base`, branch `feature/real-time-personalization`.
**HEAD is `c10ccff7303d06492e4acdf932fc70273d7159ac` — the same commit the audit names.** `git status` shows one
modified file (`public/meridian/engine.bundle.js`) and two untracked docs; nothing under `src/` differs from the
audited commit. So every line number below is both HEAD and the audited state, and nothing in this finding has
been fixed since.

**Verdict: CONFIRMED, and understated.** Every mechanical claim holds at HEAD. Four of the five reproductions I
attempted reproduced; one (the ring-cap counterexample) reproduced exactly as described. I found three further
defects in the same code path that the audit did not name, one of which — a silently frozen distinct-visitor
count — corrupts a headline number in the day report rather than an attribution edge case.

## 2 · Reproductions

All probes are read-only, run from the repository root with `npx tsx`, against an in-memory `FakeR2` modelled on
the repo's own test double. Files: `/tmp/audit-verify/F17/probe.ts`, `probe2.ts`, `probe3.ts`.
The repo's own suite passes first: `npx vitest run src/learn/hourly.test.ts` → 10 passed.

### P1 — late outcome into an already-folded hour (the audit's own scenario)

`catchUp` at 13:05 folds hour 12 (one decision at 12:10). At 13:06 a click that *happened* at 12:30 is written to
the ledger; `hourPrefix` files it under `coach/2026-09-03/12/outcome/…`. `catchUp` at 13:10 then:

```
catchUp@13:05 built: [[12,1,0]] pending: 0
catchUp@13:10 built: [] failed: 0 pending: 0
hour 12 aggregate: outcomes = 0  credits = 0  truncated = false  ringsFolded = true
the late object exists in the ledger: 1 object(s)
day report: counts = {"decisions":1,"outcomes":0,"visitors":1,"truncated":false} credits = 0
            hours = {"source":"aggregates","built":[12],"missing":[0..11],"horizonMs":172800000}
```

**Reproduced exactly.** The outcome is durably in R2, is never read again, is counted nowhere, and no field of the
report says a repair is pending. (My first attempt failed to reproduce because `catchUp`'s default `maxHours: 2`
had not yet reached hour 12; with the fold actually performed, the loss is deterministic.)

### P2 — the ring is trimmed before the same hour's outcomes are attributed

Three decisions for one visitor at 12:01/12:02/12:03, then a click on the **first** item at 12:20, all in hour 12:

```
ringCap=2   -> credits: 0
ringCap=200 -> credits: 1
online attribute() over the untrimmed ring -> credits: 1
```

**Reproduced.** `foldShard` keeps the newest `ringCap` entries at `:256` and only then attributes at `:260`, so a
credited decision that the online path already paid is dropped by the batch. The audit's "the production 200-record
cap changes the volume threshold, not the defect" is correct. The threshold is concrete: a visitor needs more than
200 decisions inside the 48-hour horizon before the outcome, which at the Coach page shape (§3.1) is roughly 23 page
views in 48 hours.

### P3b — a failed hour retried after a later hour: `ringsFolded: false`, credit lost forever

Decision for `v3` at 12:59 (item `a`), another for `v3` at 13:05 (so the shard is persisted with `through = 13:00`),
click on item `a` at 14:01. Hour 12's `get` throws on run 1:

```
run 1 built: [11,13,14]  failed: [12]
run 2 built: [12]  pending: 0
hour 12 ringsFolded: false | hour 14 credits: 0
v3 batch ring items: ["z"]        <- the 12:59 decision never entered the ring
day report credits: 0 | counts: {"decisions":2,"outcomes":1,"visitors":1,"truncated":false}
            hours: {"source":"aggregates","built":[11,12,13,14],"missing":[0..10],"horizonMs":172800000}
report mentions ringsFolded anywhere: false
```

**Reproduced.** `folded = ctx.from > state.through` (`:231`) is a monotonic high-water mark, so a repaired hour can
never put its decisions into the rings. `ringsFolded` is recorded on the aggregate (`:126`, `:400`) and read by
nothing: `reportFromHours` (`:322-328`) does not carry it, and `grep` finds no other reader.

### P4 — the 48-hour batch horizon against the seven-day purchase policy

Story served 2026-09-03 12:00, purchase of a featured product 3 days later in the same session; every hour folded
in order as the cron would:

```
DEFAULT_POLICY.windowsMs.purchase = 604800000 = 7 days
batch day report on 2026-09-06: credits 0, outcomes 1, horizonMs(days) 2
online attribute() same session, 3 days later -> 1 credit
```

**Reproduced.** The engine learns from a credit the report cannot show. This is disclosed in doc 31 §3 and brief §6
("Known limit, documented"), and the report payload does carry `hours.horizonMs` — but see §3.4 for where that
disclosure stops.

### P6 — a truncated hour is unrepairable for attribution even by hand *(not in the audit)*

Five decision objects in hour 12, cap 2, then a click in hour 13 on the item served in the 5th object:

```
fold with cap 2 -> objects: 5 read: 2 truncated: true decisions: 2
v1 ring after the truncated fold: ["item0","item1"]
hour 13 credits (the click on item4): 0
manual rebuild with cap 600 -> decisions: 5 truncated: false ringsFolded: false
v1 ring after the rebuild: ["item0","item1"]
```

The rebuild recovers the *counts* and clears the `truncated` flag, but `folded` is false, so the three recovered
decisions never enter the rings and the credit stays lost — now with no flag at all, because `truncated` has flipped
to false. Raising `MAX_HOUR_OBJECTS` after the fact makes the report look *more* complete while attribution stays
broken. Also note `loadHourRecords` (`:350-352`) sorts by the object name's minimum timestamp and slices the first
`cap`, so truncation always discards the **end** of the hour: the loss is time-biased, not random.

### P7 — the day's distinct-visitor count freezes after an out-of-order repair *(not in the audit)*

Two visitors served in each of hours 12–15 (8 distinct), plus one hour on the previous day that is repaired late:

```
after hours 12,13            -> day visitors: 4   (truth 4)
[repair of 2026-09-02 23h]
after hours 14,15            -> day visitors: 4   (truth 8), decisions: 8
```

`foldShard:232` wipes `state.seen` on every shard whenever `state.seenDate !== ctx.date`, and `mergeBrand:175` takes
`Math.max` of `visitorsDay` across hours. So one out-of-order repair across a date boundary — exactly the failed-hour
path the audit already identified — freezes `counts.visitors` at its pre-repair value for the rest of the day. The
report showed **4 distinct visitors where 8 were served**, with `truncated: false` and no missing hours. This is a
headline number on the operator's Measurement view, not an attribution edge case.

## 3 · What the audit got wrong

**3.1 The page-size number is wrong by about 2.5–3×.** The audit writes: "An online ring of 200 content-item receipts
is also only about 7–10 full 20–30-item pages." One `DecisionRecord` is emitted per (slot, position)
(`src/content/decide.ts:245-248`), and the configured home pages are:

- `DEFAULT_SLOTS` (`src/content/kinds.ts:229-238`): hero 1 + story 2 + rail 5 = **8** records
- the Coach seed (`scripts/seed-coach-content.mjs:39-46`): merch 1 + chero 1 + story 2 + carousel 5 = **9**
- the acceptance run (`scripts/acceptance-run.mjs:80-83`): 1 + 2 + 3 + 1 = **7**

So 200 receipts is roughly **22 page views**, not 7–10. A 20–30-item page is *configurable* (`take` is validated to
1..50 at `src/content/kinds.ts:148`) but is not what this system serves. The direction of the claim survives — the
200-record cap binds long before seven days for an engaged shopper — but the figure should be corrected before this
goes to the customer, because it is checkable in a minute and being wrong on it costs the rest of the finding.

**3.2 "Late outcomes, failed hours, and truncation yield incomplete reports that can appear final" is too broad.**
Two of those three *are* declared in the report payload:

- a failed or never-folded hour is listed permanently in `hours.missing` (`loadHours:461-471`, `:327`);
- truncation raises `counts.truncated` (`:324`), which the console does render.

What is genuinely silent is (a) late data into an already-folded hour (P1), (b) `ringsFolded: false` (P3b), (c) the
frozen visitor count (P7), and (d) a truncated hour rebuilt at a higher cap, which clears the flag while leaving
attribution broken (P6). The finding is stronger stated that way, because those four are unfalsifiable from the
report.

**3.3 "does not automatically correct an already-written truncated hour" understates it.** There is no correction
path at all — automatic *or* manual — for the attribution half. P6.

**3.4 The audit does not credit `hours.horizonMs`, and then misses the better complaint.** Doc 31 §3 says "the
report says so (`hours.horizonMs`)", and it does: `reportFromHours:327` carries it. The real gap is one level up.
Neither operator surface renders it, nor `hours.missing`: `public/learning.js:280` and
`public/console/views-measure.js:143` print only `counts.truncated`. And the artifact a lift claim would actually be
made from — `windowReport` (`src/measure/window.ts:48-86`), reached by `GET /:tenant/learn/report/window` and
described in the console's own header as "This is the number, and the only one that answers 'did it work'" — pools
`report.holdout[slot]` rows across days and **drops every honesty signal except missing days**. `WindowReport` has no
`truncated`, no unfolded-hours count, no horizon. That is the precise sense in which the system "cannot honestly
represent the seven-day policy", and it is a stronger argument than the one the audit made from the 48-hour ring.

**3.5 Minor.** The five-minute grace is at `:411`, not `:435`; `:435` is the existence filter. Both sentences in the
audit's clause are true, of two different lines.

## 4 · What the audit missed

1. **The distinct-visitor freeze (P7).** `foldShard:232` + `mergeBrand:175`. Measured 4 where 8 were served. Same
   trigger as the finding's own failed-hour path.
2. **Client-supplied event time is trusted without bound.** `src/routes/realtime.ts:101` —
   `timestamp: validatedEvent.timestamp || Date.now()`; `outcomeFromAction` puts it in the outcome id
   (`src/ledger/records.ts:131,134`), and `writeBatches` partitions on it (`src/ledger/writer.ts:51`). "Late data" is
   therefore not bounded by queue latency: a device with a slow clock, or an SDK flushing a buffered beacon, writes
   straight into an hour that was folded hours ago and is silently dropped; a fast clock files the event in a future
   hour and lands it on the wrong day. There is no clamp and no skew check anywhere on that path.
3. **Truncation loses the end of the hour and is unrepairable (P6).** Time-biased loss, and the repair clears the
   flag without fixing the data.
4. **`ringsFolded` is written and never read.** Dead honesty. `hourly.ts:126,396,400` are the only occurrences
   outside the test file.
5. **A test that passes for the wrong reason.** `src/learn/hourly.test.ts:217-229` ("the run continues past an hour
   whose fold throws") asserts `built: [11,13]`, `failed: [12]`, `pending: 1` and stops there. It never folds hour 12
   afterwards, so it never observes that the repaired hour returns `ringsFolded: false` and that the credit is gone.
   `:114` does assert `again.ringsFolded === false` on a same-hour rebuild — the flag is tested; nothing asserts it
   reaches a report. The suite's headline test (`:79`, "the day from its hours is the day from its records") only
   ever compares a fold performed in strict order against records read in one pass, so no test in the file exercises
   out-of-order or late delivery at all.
6. **`max_retries = 2` with no dead-letter queue** (`wrangler.toml:34`, and the same in `[env.staging]` and
   `[env.production]`). A message whose retries are exhausted is dropped with no hour object to blame and no counter
   anywhere. Adjacent to F16 as much as to F17, but it is the second way the same day report comes out short.

## 5 · Severity and size

**Severity: blocks the pilot.** I agree with the audit. Under the brief's scale this is not live-data safety, so it
is not "blocks launch"; it is the measurement artefact the pilot is judged on. But it sits at the top of that band,
for a reason the audit did not give: the failures are *silent*, so the customer's analyst has no way to detect them
from the report, and one of them (P7) corrupts a headline count rather than an attribution tail. Any lift number
handed to Tapestry from `GET learn/report/window` today is unaccompanied by the evidence needed to trust it.

The 48-hour-vs-7-day horizon on its own I would rate lower — it is disclosed in doc 31 §3, in brief §6, and in the
report payload. It becomes pilot-blocking only because the disclosure dies before it reaches a human (§3.4).

**Size: L for the audit's full remedy; S for the launch-blocking part.** I agree the end state the audit describes —
event-time ordering, stable ids, checkpointed contiguous progress, delivery/maturity watermarks, explicit late-data
correction — is multiple engineer-weeks and touches the queue, the ledger and the fold. But the audit's single "L"
hides that the silent-failure half can be closed in days, and a team reading "L" may defer all of it.

## 6 · Remedy assessment

The audit's remedy is **right in direction and over-scoped as a gate**. Watermarks and checkpointed progress are the
correct end state, and the audit is right to refuse "a million decisions requires a database" as a law and to ask for
the volume, retention, join and recovery numbers first. But "never mark a truncated/failed hour final" is under-
specified: the aggregate already carries `truncated` and `ringsFolded`, and the problem is that neither reaches the
day report, the window report, or a screen. And the remedy does not mention the completeness check that actually
closes the late-data hole cheaply.

### Smallest safe fix (S, ~2–3 engineer-days, no schema migration)

1. **Re-fold an hour whose ledger has grown.** `HourAggregate` already stores `objects` — the true object count in
   the hour prefix at fold time (`loadHourRecords:367`, `:400`). In `catchUp`, for candidate hours whose aggregate
   `builtAt` is inside a maturity window (say the last 2–3 hours), `list` the hour prefix and rebuild when the count
   exceeds `agg.objects`. Cost: 2–3 extra `list` calls per five-minute run, well inside `RUN_BUDGET = 700`. This
   alone closes P1 for the ordinary queue-delay case.
2. **Make a repair actually repair the rings.** Replace `ShardState.through` (a monotonic high-water mark, `:80`,
   `:231`, `:279`) with a small set of folded hour-starts pruned to the horizon, so `folded` becomes per-hour
   idempotent. Without this, steps 1 and 3 recover counts but not attribution (P3b, P6). S–M on its own.
3. **Stop the visitor-count wipe.** Key `seen` by date — `Record<date, Record<brand, string[]>>` pruned to two days —
   instead of resetting the whole map when `state.seenDate !== ctx.date` (`:232`). Closes P7.
4. **Carry the honesty forward.** Add the unfolded/`ringsFolded:false`/truncated hour lists to `DayReport.hours`, add
   the same fields to `WindowReport`, and render `hours.missing`, `hours.horizonMs` and the incomplete-hours list in
   `public/learning.js:280` and `public/console/views-measure.js:143`. Nothing here is new computation; it is
   plumbing three booleans that already exist to the two screens a customer reads.
5. **Clamp ingest time.** Reject or clamp `timestamp` at `src/routes/realtime.ts:101` to server-now ± a stated skew
   allowance, and record the clamp. One line plus a counter.

Items 1, 3, 4 and 5 are the pilot-blocking minimum and are genuinely S. Item 2 is the one that must not be skipped
if the team wants a repair path at all. The watermark/checkpoint architecture and the storage decision for the
seven-day window remain L and should be scheduled, not gated on.

### Tests that should exist and do not

Fold hour N, deliver a record for hour N, fold again, assert it is counted. Fail hour N, fold N+1 that touches the
same shard, repair N, assert the cross-hour credit survives. Repair a previous-day hour after a current-day hour and
assert `counts.visitors`. Truncate an hour, rebuild at a higher cap, assert the rings hold the recovered decisions.
Assert that a report built over an incomplete hour cannot render as complete.
