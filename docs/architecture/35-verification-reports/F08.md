Verifier: independent. Repo `/mnt/c/Users/LAH/Documents/__Development/Optimizely/__cloudflare_base`,
branch `feature/real-time-personalization`, **HEAD = `c10ccff` — the audited commit itself**, so there is
no drift between the audit and the tree I checked (`public/meridian/engine.bundle.js` is the only

## 3 · The number that matters: items × cells, not cells

The audit reports the threshold as "15,000 distinct affinity cells for **one slot/item**". A reader
translates that into "not our problem". The stored value is `items × levelKeys`, so the ceiling falls
linearly in the number of content pieces eligible for the slot.

Using a Coach-shaped cell space (4 channels × 4 visit buckets × 4 stages × 51 US regions × 49 affinity
tokens — 49 is the count of distinct `dim:value` tokens in the repository's own
`public/data/coach-content.json`), that space is **159,936 reachable cells from US traffic alone**, and
(`frontier.ts`, `frontier2.ts`, `v8.serialize` vs 2 MiB):

| eligible pieces in the slot | cells at which the object dies |
|---|---|
| 1 | ~14,800 |
| 5 | 3,868 |
| 18 (**the seeded `chero` slot**) | **1,203** |
| 20 | 1,083 |
| 40 | 537 |

The customer's own seeded catalog has 26 pieces, 18 of them eligible for `chero`. That object stops
accepting exposures at **0.75 % of the cell space its own configuration can produce**, with no attacker
and no unusual traffic — just ordinary US shoppers across states, channels, stages and interests.

## 4 · What the audit got wrong

1. **`2,618,613 bytes` is not a real measurement.** The true figure at 15,000 cells is 2,468,636 B
   (JSON) / 2,228,518 B (v8). Right order of magnitude, wrong number, and not reproducible from the
   audit's own scratch files. Delete it or replace it.
2. **"Severity: blocks launch *of enabled learning* at unbounded cardinality" is the wrong qualifier
   and the most dangerous sentence in the finding.** `DEFAULT_LEARN` (`src/content/kinds.ts:376-385`)
   runs every slot at γ = 0 — shadow mode, learning does not influence any decision — and exposures are
   still fanned on every request: `service.ts:242` gates `fanDecisions` on `consent.tracking` alone,
   never on γ. Shipping with learning "off" does **not** avoid this. The gate is tracking consent.
3. **"returned HTTP 500"** — it throws. Nothing returns 500; the audit's 500 is an artefact of its own
   harness. The consequence is identical because the call site swallows both, but a remediating
   engineer looking for a 500 in logs will find nothing, which matters (see §5.2).
4. **`wrangler.toml:121`** is the `[[migrations]]` header; the assertion is line 123. And "the
   configured Durable Objects are SQLite-backed" is false for three of the nine classes.
5. **`DecisionRing.ts:69`** is the ring push; the unbounded index push is line 70.
6. **"Its risk is source-confirmed, not the object exercised by this storage-limit probe"** — the audit
   under-claims its own work. `DecisionRing` fails the same way at 20,300 decisions for one visitor;
   I reproduced it in one run.

## 5 · What the audit missed, in the same code path

### 5.1 The published lift snapshot carries a second copy of the entire raw state — on the decision path

`LearnStats.publish()` (line 110) and `/snapshot` (line 56) call
`buildSnapshot(d.stats, d, …)`, passing the whole `Stored` where the parameter is declared
`ids: { tenant; brand; slot }`. `buildSnapshot` ends with `return { ...ids, … }` (`stats.ts:164`), so
**`config` and the complete raw `StatsState` are spread into every published snapshot.** Verified
directly (`leak.mjs`):

```
top-level keys of the published lift snapshot:
  tenant, brand, slot, config, stats, reward, objective, version, publishedAt,
  events, n0, nMin, liftMin, liftMax, priorVersion, items, slotRates
carries the raw StatsState? true   raw stats bytes 827 of total 2138  (39 %)
```

At 14,500 cells the KV value is 5,528,711 B of which 2,385,470 B is the redundant raw state — the
proper snapshot alone is 3,143,166 B. TypeScript does not complain because excess-property checking
does not apply to a variable argument. This document is what the **decision path** reads:
`readLift()` in `src/content/service.ts:47-52` does `env.CACHE.get(key, 'json')` on every isolate cache
miss, `LIFT_TTL_MS = 60_000`, per slot. So every isolate, every minute, per slot, parses roughly twice
the bytes it needs. This is a one-line fix that halves the hot-path payload and is worth doing
independently of F08.

### 5.2 The failure is completely silent, and permanent until eviction

`post()` in `src/learn/fan.ts:26` is `catch { return null; }`, and `fanDecisions` wraps every job in
`.catch(() => undefined)` at line 84. `SQLITE_TOOBIG` therefore reaches no log, no metric, no alarm and
no response field. Worse (probe **g**): after the first failed `save()` the object's **in-memory
`this.data` keeps the oversized map**, so every subsequent write fails *including writes that add no new
key* — I reproduced exactly that. And `arm()` is never reached, because it is sequenced after `save()`
in the same block (`LearnStats.ts:41`, `:51`), so once the pending alarm fires the object never
re-arms: publishing stops permanently while the decision path keeps serving the last KV snapshot as if
it were fresh. Learning goes quietly dead and every dashboard still shows a valid, versioned lift
snapshot.

Two things that would otherwise have caught it cannot:

* `scripts/load-test.mjs:52` sends `channel=load`, one constant channel from one region, and a new
  visitor per iteration. It creates many shopper objects and exactly one cell shape. It is structurally
  incapable of finding this — which is precisely the audit's "load-test hot slots" remedy, and worth
  citing as evidence rather than advice.
* `src/ops/monitor.ts:68` — the five-minute self-monitor — passes
  `opt_tracking_consent=false; opt_personalization_enabled=false`, so `write` is false and it never fans
  an exposure. The production monitor can never observe this failure.

### 5.3 `channel` is an unvalidated, caller-supplied cardinality lever

`src/routes/decisions.ts:328`: `const channel = (c.req.query('channel') ?? '').trim() || null;` —
free text, no allow-list, only lower-cased and cut to 32 chars in `cellFor` (`src/content/cell.ts:63`).
It appears in **five of the six level keys** (`levelKeys`, `stats.ts:35`), so each distinct value adds 5
item counters *and* 5 slot counters. A caller holding the public site key — it ships in a `<meta>` tag
on the demo pages, it is not a secret — can kill a named tenant/brand/slot object in a few thousand
requests. `/v1/*` is not rate-limited: `rateLimiter()` is mounted on `/api/*` only (`src/index.ts:81`).
The audit's scratch (`v8size.ts`, `bracket.ts`) explored channel cardinality; the written finding does
not mention it, and the remediation team reads the finding.

### 5.4 The 90-day index that kills `DecisionRing` is dead weight

`d.index` is pushed at line 70 and aged at line 72, and its **only** read is `d.index.length` in
`/recent` (line 49). `outcome()` attributes against `d.ring` alone (line 81). Nothing in `src/`
consumes the `index` field; the sole consumer is an assertion in `learn.test.ts:116`. The structure that
takes the visitor's object down at 20,300 decisions buys nothing.

### 5.5 The suite passes for the wrong reason

`learn.test.ts:110`: `class FakeStorage { map = new Map(); async put(k, v) { this.map.set(k, v); } … }`.
It stores the object **by reference**. It never serializes, never structured-clones, and has no size
ceiling — so it cannot express the failure mode under test, and it would also miss any non-cloneable
value. Eight tests, 19 ms, green. A Miniflare run of the same class, same inputs, fails.

### 5.6 Smaller adjacent defects

* `/reset-item` (`LearnStats.ts:68-79`) deletes `d.stats.items[item]` but never prunes `st.slot`. The
  slot map — half the bytes — cannot be shrunk by any operator action. The only escape is `/reset`,
  which destroys the slot's entire learning history.
* Write cost scales with stored size (probe **f**): a single exposure POST goes from ~10 ms to ~30 ms
  median between 0 and 12,000 cells because the whole value is re-serialized per request. The Durable
  Object is single-threaded and further serialized by `this.chain`, so one hot slot object caps near
  ~33 exposure writes/second at that size. That is the throughput concentration the audit mentions only
  inside its remedy paragraph, unquantified and without a severity.
* Same pattern elsewhere: `PersonalizationWebSocket.ts:290` stores every connection as one value on a
  **KV-backed** class — a 128 KiB ceiling, sixteen times tighter.

## 7 · Severity, size, remedy

**Severity: blocks launch. I agree with the label and would strike the qualifier "of enabled
learning"** — the ingest path is unconditional on γ, so it is not opt-out by leaving learning in shadow.
The failure is silent, permanent for the affected object, and reachable by ordinary traffic on the
customer's own seeded configuration at ~1,200 context cells.

**Size: the audit says M–L. The full remedy is L. The launch-blocking part is S.** Those should be
stated separately; as written, "M–L" invites deferral of a three-day fix.

The audit's remedy is right in direction and over-scoped as a launch gate. Bounded rows/chunks,
retention, migration, sharded ingest and recovery testing are all correct and all belong before scale —
but none of them is needed to stop the object dying.

**Smallest safe fix (S, roughly 1–3 engineer-days, no migration, no schema change):**

1. **Bound the write.** In `recordExposure`/`recordSuccess`, cap distinct keys per item and in
   `st.slot` (2,000 each is ~300 KB). At the cap, record a new cell only at levels 0–3 and evict the
   least-recently-touched level-4/5 key — the `t` on every `ReflexEntry` already gives you LRU for free.
   This degrades gracefully **by design**: `liftFor` walks finest-to-coarsest and simply answers at a
   coarser level, which is what the pooling ladder is for.
2. **Bound the input.** Allow-list `channel` against a configured set, mapping anything else to
   `other`. Closes 5.3 and removes the injection lever in the same change.
3. **Make it loud.** `try/catch` around `save()`; on failure re-load the last durable state instead of
   keeping the poisoned map, still call `arm()`, emit one Analytics Engine point and set a `degraded`
   flag on the published snapshot so the console can show that learning is capped.
4. **`DecisionRing`:** cap `index` by count as well as age — or delete it; nothing reads it (5.4).
5. **One line:** pass `{ tenant: d.tenant, brand: d.brand, slot: d.slot }` at `LearnStats.ts:110` and
   `:56` instead of `d`. Halves the KV lift snapshot and the decision path's parse (5.1).
6. **One test:** replace `FakeStorage` with a double that structured-clones and refuses over 2 MiB, or
   add a Miniflare test of `LearnStats`. Without this the fix has nothing holding it in place.

Then, before real scale (M–L, not a launch gate): per-key or `storage.sql` rows keyed by item and
level, explicit retention, and a load test that varies cells rather than shoppers.
