# F09 verification — "Re-provisioning silently rotates identity, authentication, and all site keys"

Independent verifier's report. Repository `/mnt/c/Users/LAH/Documents/__Development/Optimizely/__cloudflare_base`,
branch `feature/real-time-personalization`, HEAD `c10ccff7303d06492e4acdf932fc70273d7159ac` — which is the
audited commit itself. Working tree clean for every file this finding touches
(`git status --porcelain scripts/ src/identity/ src/middleware/edgeAccess.ts wrangler.toml migrations/` is empty).

**Verdict: confirmed, and understated.** Every evidence claim holds at HEAD. The audit describes a hazard;
the reproduction shows the hazard is the *default* outcome of the second run and that it ends worse than the
audit says — the freshly generated site key is never printed, because the script dies one step after writing it.

Three facts follow, and only the first is in the audit:

1. All three secrets are replaced on a run whose visible message says ids "could not be read" and asks the
   operator to fix the file **and re-run** — which rotates them again.
2. The guard at line 40 (`grep -q "<$ENV-" wrangler.toml && exit 1`) cannot fire once the ids are filled, and
   they are filled and committed for both provisioned environments. The guard protects exactly one state in
   the environment's lifetime, and it is not the state anyone re-runs from.
3. **The new site key is never printed.** `operator-seed.mjs`'s plain `INSERT` collides with
   `email TEXT NOT NULL UNIQUE` (`migrations/0010_operator_accounts.sql:15`), the script exits 1, and
   `set -e` kills `provision-stamp.sh` at line 54 — after the three `secret put` calls (48–50) and before the
   echo block that discloses the key (56–60). Production is left enforcing a site key that no human or file
   has ever held.

The same account on the same brand becomes a different person. `IdentityStore.link` classifies the returning
customer as **`relinked`** — the platform's own word for *a different person took over this browser*
(`src/identity/store.ts:102–108`) — files the real shopper under `previous`, the trail meant for shared
computers, and mints a new record with `createdAt = now`, resetting tenure. The old record survives in KV with
nothing pointing at it: `resolveVisitor('vis-1')` now answers the new id. On the object host the same rename
orphans the per-shopper Durable Object, which is named by that id (`src/tenancy/objects.ts:43–54`,
`src/durable-objects/ShopperReflex.ts:975`). The only route back is a full warehouse re-import through
`applyHistory` (`src/identity/history.ts:117`) — a data migration, exactly as the audit's remedy says.

The second line also shows that an absent or blank salt collapses every id onto the constant
`edge-identity-unsalted` (`shopperId.ts:23`), a namespace anyone with this public repository can compute.

## 3 · Severity and size

**Blocks launch — I agree.** The brief reserves that label for live-data safety and production reliability.
This is the documented recovery path for a production stamp; the state it destroys is the customer's site
credential, every operator session, and the identity graph; and the abort leaves no record of the credential
it just installed. It is operational rather than request-path, so nothing breaks while no one runs the
script — but the script's own failure message tells the operator to run it again, and it is the only tool in
the repository that can add a second brand's site key.

**Size: audit says M; I agree for the remedy as written, but the launch-blocking part is S.** See §6.

## 4 · What the audit got wrong

1. **Line 8 → lines 8–9.** The claim "a rerun continues past existing resources" is completed on line 9.
2. **"Silently" is the wrong word, and it makes the finding easier to dismiss.** The script does announce
   "Secrets, generated / JWT_SECRET, IDENTITY_SALT and SDK_KEYS set on the worker." What is unstated is that
   existing values were *replaced*, and — the sharper fact — on the re-run path the replacement key is never
   disclosed at all. "Unprompted and unrecoverable" is both true and harder to argue with.
3. **The remedy step "merge site-key entries rather than replacing them" cannot be implemented as written.**
   Worker secret values cannot be read back: wrangler 4.105.0 ships `secret put`, `secret list`, `secret
   delete` and `secret bulk`, and no `secret get` (verified against `node_modules/wrangler/wrangler-dist/cli.js`;
   `secretGetCommand` is absent). A merge needs a source of truth outside the secret — a manifest, a D1 row, or
   an operator-facing key-management route. As stated, the step reads like a script tweak; it is a design change.
4. No overstated consequence found. If anything the consequence section is conservative: it says the rotation
   "can" invalidate integrations; with `AUTH_MODE = "enforced"` on all three environments, it does.

## 5 · What the audit missed (adjacent, same code path)

1. **The guard is inert exactly when it matters** (§2.1, point 2). Worth stating explicitly because a reader
   scanning the script sees `exit 1` and assumes a re-run is stopped.
2. **The abort before disclosure** (§2.1, point 3) — the strongest fact in the finding and it is absent from
   the audit. `SDK_KEYS` is written at line 50 and printed at line 59, with a step that fails by construction
   in between.
3. **There is no other way to add a brand's key.** `SDK_KEYS` is written only by `provision-stamp.sh:50` and
   `provision-staging.sh:39–41`; nothing in `src/` manages the key map, and no runbook describes adding a
   tenant to a live stamp. So the "provisioning exercise rather than another build" that scope §1.7 promises —
   quoted back in `src/tenancy/tenant.ts:20–25` — currently means: replace brand #1's key and rename brand #1's
   shoppers.
4. **This is a regression from the script it replaced.** `provision-staging.sh:38–41` loops
   `wrangler secret put "$s"` *interactively* and prompts a person for each value. `provision-stamp.sh` removed
   the prompt ("No prompts: every value is generated", line 3) and with it the only thing standing between a
   re-run and a rotation. `provision-staging.sh` also never sets `IDENTITY_SALT` at all, so staging may still be
   minting ids in the fixed unsalted namespace; not checkable from here without touching the host.
5. **The codebase already knows how to version a secret — for the wrong one.** `IDENTITY_SECRETS` accepts
   `tenant:secret|previous` and verifies against both (`src/identity/assertion.ts:33–47`), giving assertion
   signing a clean overlap window. `IDENTITY_SALT`, the one secret whose change *renames people*, has no
   previous-value support anywhere.
6. **Latent id-parsing hazard.** `id32()` (`grep -o '[0-9a-f]\{32\}' | head -1`) will capture a Cloudflare
   **account id** out of wrangler's error text: `throwFetchError` embeds `/accounts/<32 hex>/…` verbatim
   (no redaction — `extractAccountTag` confirms the shape), and the non-interactive multi-account error prints
   `` `<name>`: `<account_id>` `` for every account. It does not bite today because the KV "already exists"
   path is a `UserError` carrying no hex and the `[ -n CACHE ] && [ -n SESSIONS ] && [ -n D1 ]` condition needs
   `id36` to match too — but a partial failure that satisfies all three would write a bogus namespace id into
   `wrangler.toml` and print "▸ wrangler.toml: production ids filled".
7. **No test covers either provisioning script.** Grepping `*.test.ts` for "provision" returns only
   `src/routes/auth.test.ts` fixtures. The idempotency test the remedy asks for has nothing to build on.
8. **`sed -i` on line 36 edits a tracked file.** Provisioning mutates version-controlled configuration and, by
   committing the ids, permanently disarms its own guard.

## 6 · Remedy assessment and the smallest safe fix

The audit's remedy is the right shape and correctly scoped as M *as a programme* — manifest, reconcile,
dry-run/diff, identity material with a versioning and recovery plan, an idempotency test. Two corrections:
the "merge site-key entries" step is not implementable inside the script (§4.3), and the programme is larger
than the launch gate.

**Smallest safe fix that closes the launch-blocking part (S, hours):**

1. Gate lines 47–51 behind an explicit `--rotate-secrets`, and default to skipping them when
   `npx wrangler secret list --env "$ENV"` already names `JWT_SECRET`, `IDENTITY_SALT` or `SDK_KEYS`.
   Print what was skipped and why.
2. Drop the blanket `|| true` on lines 23–33: fail on any create error unless `--reconcile` is passed, and
   never print "ids filled" on a path where an id was not read.
3. Print the site key at the moment it is generated, not after the seed; nothing that can fail may sit between
   writing a credential and disclosing it.
4. Make the seed idempotent — `INSERT … ON CONFLICT(email) DO NOTHING` in `operator-seed.mjs`, reporting
   "already seeded" — so the admin step stops being a landmine.
5. One test: run the script twice against a stubbed wrangler and assert the second run performs no
   `secret put` and no `sed`. The harness in `/tmp/audit-verify/F09/repro/` is that test, minus the assertions.

Steps 1 and 3 alone remove the unrecoverable outcome. The manifest, the identity-rotation-as-migration plan and
the key-management surface that lets a second brand be added without touching the first remain M and should be
scheduled before the second tenant, not before the first deploy.
