### 1.2 "Sort … ignores its accepted client session ID" — confirmed, with the fix location

This is the sharpest code claim in the section and it is exactly right. At HEAD:

- `src/routes/sort.ts:37` parses `sessionId: z.string().optional()`, and line 86 destructures
  `{ userId, surface, candidates, weights }` — `sessionId` is never read again.
- `src/routes/sort.ts:75` calls `engine.getOrCreateSessionFromCookies(c.req.header('Cookie') ?? null, userId)`
  with **neither** of the two parameters CW37/CW39 added: no `defer`, no `clientSessionId`.
- The decision path does pass both: `src/content/service.ts:113` calls the same function with the
  deferral callback and `clientSessionId ?? undefined` (fed from `r.sessionId` at `service.ts:157`).
- Without `defer`, the session write is awaited on the response path:
  `src/services/SessionManager.ts:297` — `if (defer) defer(writes); else await writes;`

That accounts for the shape of the numbers: sort's fresh row fell only from 616.3 ms to 464.4 ms
(it inherited CW37's "two writes go together" batching) while the snapshot's fell to 285.3 ms
(it also got the deferral). The remaining ~429 ms gap between fresh and returning sort
(464.4 vs 35.4 ms) is that awaited write plus the same three missing KV reads.

### 1.6 `decide: 0 ms` — right conclusion, imprecise mechanism

Two facts sharpen this:

1. The stage is rounded to whole milliseconds in code: `src/content/service.ts:133-134`,
   `timings[name] = Math.round(t - mark)`. Anything under 0.5 ms prints 0.
2. On a deployed Worker the clock does not advance during synchronous, I/O-free execution, so a stage
   containing no I/O — which `decideContent` is, by design ("No I/O, no clock, no randomness",
   `src/content/decide.ts:1-6`) — cannot register at all, at any catalog size. A local workerd probe
   (`/tmp/audit-verify/S3/timer-probe.mjs`, Miniflare) shows the *local* runtime does advance during a
   busy loop (170 ms for 60M `Math.sqrt` iterations), so this is a production-runtime property, not a
   resolution property, and it is invisible in local dev.

Either way the audit's conclusion — "not zero cost at any catalog size" — is correct, and I can now
quantify both halves. The measured staging population is the seeded Coach catalog:
`public/data/coach-content.json` holds **26 pieces**, on which the real composer costs **0.026 ms per
call warm** in Node. At 100,000 pieces the same function costs ~150 ms. So `decide: 0` is uninformative
twice over: the work is invisible to the instrument, and the corpus it was measured on is 26 items.

## 5 · Corrections

1. **"forty measured calls after five warmups (`scripts/latency.mjs:129`)."** The script's default is
   `--n 60` (line 48); forty comes from doc 32's `--n 40` invocation. Line 129 is the warmup loop; the
   measured loop is line 131. And it is forty per route × population — six rows, 240 measured calls.
2. **The doc 31 object-host row is unlabeled.** 192 / 665 / 795 ms are caller wall time, because
   `scripts/load-test.mjs` never reads `Server-Timing`. The section's own preamble requires the label.
   The conclusion is unaffected (network is ~35 ms, so the server P95 is still far above 200 ms).
3. **`decide: 0 ms` is not a resolution artifact.** It is `Math.round` to whole milliseconds
   (`src/content/service.ts:133`) over a stage that, on a deployed Worker, cannot advance the clock at
   all because it performs no I/O. Say "the instrument cannot see CPU-only work", not "below the timer's
   resolution" — the stronger statement is also the true one.
4. **The composer-time column is not reproducible to the tenth.** My repeats span 17–40 ms at 10,000
   and 588–780 ms at 300,000, with worse outliers under load. Publish it as a range or as an order of
   magnitude; the byte and heap columns are far steadier.
5. **"Keep error/timeout requests in the report" should name `latency.mjs`.** `load-test.mjs` already
   keeps them.
