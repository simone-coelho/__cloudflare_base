## 2 · Reproductions

Harnesses: `/tmp/audit-verify/F24/repro.ts`, `/tmp/audit-verify/F24/repro2.ts`. Run from the repo root with `npx tsx <file>`. They import the real modules (`src/learn/cycle.ts`, `src/learn/autonomy.ts`, `src/config/versionedStore.ts`, `src/content/kinds.ts`, `src/learn/stats.ts`) against an in-memory KV double. Nothing in the repo was written to; no network was used.

### R1 — the audit's headline scenario, verbatim
Day 1: `hero.occasion = 0.10`, slot in `assisted`. Cycle proposes `occasion 0.1 → 0.15`.
Day 30: a merchandiser sets `occasion = 0.90`, adds `occasion` to `autonomy.pinned`, and sets `mode: 'configured'` (autonomy **off**).
Day 31: an operator clicks Apply on the day-1 proposal.

```
current weights before apply: { occasion: 0.9, line: 0.25 }
decideProposal -> {"ok":true,"revision":3}
weights after apply:          { occasion: 0.15, line: 0.25 }
```

The applied change is **0.75, fifteen times the configured `step` of 0.05**, in the opposite direction to the proposal, on a slot whose autonomy is off, on a dimension the operator pinned, from a proposal 30 days old. Nothing warned, nothing failed, and the revision note reads `proposal … applied by ops: occasion 0.1 → 0.15` — a note that describes a move that did not happen.

### R4 — the false applied receipt
Autonomous slot; the KV double throws on `slots:config:*` puts.

```
runCycle threw?  Error: KV put failed for slots:config:coach:rev:2
slot weights on disk:    { occasion: 0.35, line: 0.25 }   (unchanged)
proposal receipt on disk: [{"status":"applied","note":"applied autonomously within bounds","from":0.35,"to":0.4}]
```

The durable receipt says applied; the weights never moved. The non-throwing variant is worse: `cycle.ts:77` sets `r.revision` only when `res.ok`, but `r.action` stays `'applied'` either way, and `POST /v1/:tenant/learn/cycle` (`src/routes/decisions.ts:287–293`) returns `{ok:true, results:[{action:'applied'}]}` with no error. The cron's log line (`src/index.ts:216`) prints only `"N action(s) across M slot(s)"` — no slot, no dimension, no from/to, no success flag.

### R5 — the evidence gate
Synthetic (as the audit ran it): `a` with `n=1, lift=1.001`; `n` with `n=9999, lift=1.000`.

```
evidence: [{"dimension":"occasion","values":{"evening":{"meanLift":1.001,"n":1,"items":1},
                                            "weekend":{"meanLift":1,"n":9999,"items":1}},"spread":0.001}]
proposal: occasion 0.35 -> 0.4 | reason: occasion separates outcomes most (spread 0.001)
```

Through the **real** `buildSnapshot` it is worse, not better. One exposure with one click gives a shrunk root lift of **1.29** against 1.00 from 9,999 exposures:

```
real root stats: a = {n:1, s:1, p_hat:0.129, lift:1.29}   n = {n:9999, s:1000, p_hat:0.1, lift:1}
real evidence:   evening meanLift 1.29 (n=1) vs weekend 1.00 (n=9999); spread 0.29
real proposal:   occasion 0.35 -> 0.4
gate: slotRates["*"].n = 10000  >=  minN 500   ← passed on the other item's 9,999 exposures
```

The `minN` gate is satisfied entirely by exposures that have nothing to do with the comparison driving the move. The only threshold on the comparison itself is `spread > 0` after rounding to three decimals.

### R6 — the ratchet, with no new data at all
Autonomous slot, **one frozen lift snapshot**, twenty daily cycles:

```
occasion: 0.4, 0.45, 0.5, 0.55, 0.6, 0.65, 0.7, 0.75, 0.8, 0.85, 0.9, 0.95, 1, 1, 1, 1, 1, 1, 1, 1
```

0.35 → 1.00 (the bound) in **13 days**. Weights are absolute multipliers — `score += a * w` at `src/reflex/contentCompose.ts:145`, never renormalized — so this is a real change to what ships: the slot converges on ranking by one dimension.

### R7 — `applyProposal` is a two-sided clamp and nothing else
```
cfg.pinned = ["occasion"], cfg.step = 0.05, current occasion = 0.9
applyProposal({occasion:0.9,line:0.25}, {dimension:"occasion", to:0.15}, cfg) = {occasion:0.15, line:0.25}
applyProposal({occasion:0.9,line:0.25}, {dimension:"occasion", to:1.7 }, cfg) = {occasion:1,    line:0.25}
applyProposal({occasion:0.9},           {dimension:"ghostDim", to:0.5 }, cfg) = {occasion:0.9, ghostDim:0.5}
```
The last line: a proposal re-introduces a dimension a merchandiser has since deleted from the slot.

## 3 · What the audit got wrong

Nothing material. Four precision defects a remediating engineer could trip on:

1. **Three line anchors are off.** `cycle.ts:89` should be `:90–:92` for the loads (`:93` for the apply, which is exact); `autonomy.ts:102` should be `:103`; `cycle.ts:72` should be `:73`. All inside the right function; none changes the finding. Worth fixing because HEAD *is* the audited commit, so these are the audit's own imprecision, not drift.
2. **"pinned" is ambiguous in this codebase.** `AutonomyConfig.pinned` is a list of **dimension names**; `SlotStrategy.pinnedPieceId` is an unrelated per-slot content pin. R1 confirms the first. The second is a *separate* hole (§4.1) with a different fix. The sentence should name `autonomy.pinned`.
3. **The audit names only one direction of the receipt/write split.** `runCycle` writes the receipt first (`:73`) and the slots second (`:76`). `decideProposal` does the opposite and correct order (`:94` slots, `:95` bail on failure, `:99` receipt) — so its failure mode is the mirror: the weights move and the proposal is left `'proposed'`, re-appliable. Both need the same atomicity fix; the audit's remedy line covers both, its evidence line covers one.
4. **One remedy item already exists as a mechanism.** "reversible trials, and a rollback policy" — `POST /v1/content/slots/rollback/:n` is wired (`src/routes/content.ts:53`, `KINDS.slots` at `:35`) and `versionedStore.rollback` rolls forward as a new revision. What is missing is the *policy* and the *detection*, not the button. Saying "build rollback" would over-scope the work.

The audit also **understates** twice:

- **The ratchet needs neither selection bias nor sparse outliers.** R6 drives 0.35 → 1.00 on a single unchanging snapshot. The mechanism is simpler than the audit says: the cycle never asks whether the *previous* raise helped, so any fixed positive spread yields an unbounded sequence of raises. Selection bias makes it worse; it is not required.
- **This is a gap against the team's own design document, not only against good practice.** Doc 22 §11 defines `assisted` as *"A scheduled job evaluates the attributed reward **under small perturbations of the weights** and proposes a change, with the evidence."* No perturbation is evaluated anywhere. §11 also defines `step` as *"Maximum change to any weight per cycle"* — R1 applies 15× it. And §11 lists a `cadence` bound that has no field in `AutonomyConfig` and no implementation. Delivery ledger 19 rows 14 and 15 trace "configured AND autonomous modes" and "tune themselves" to the customer's own words, so the audit's severity condition ("if assisted/autonomous tuning is represented as safe") is **met**.

## 4 · What the audit missed — same code path

### 4.1 A proposal built from one page is applied to every page carrying that slot name (new, and the same class of defect)
`Proposal` has no `page` field. `cycle.ts:93` applies to **every** page: `list.map((s) => (s.slot === p.slot ? …))`. Reproduced (R3), `hero` on `home` (0.35) and `category` (0.80):

```
cycle produced 2 results, ids: coach:hero:m0gcgmio  /  coach:hero:m0gcgmio   ← IDENTICAL
after applying the HOME proposal:
  home     : { occasion: 0.4,  line: 0.25 }
  category : { occasion: 0.4,  line: 0.1  }   ← was 0.80. Never proposed. Halved.
proposal statuses: [applied, applied]          ← both, from one click
```

Three defects in one: (a) cross-page bleed of an absolute target; (b) **duplicate proposal ids** — `id` is `${tenant}:${slot}:${now.toString(36)}` (`autonomy.ts:94`) and `now` is constant across a cycle, so `find(x => x.id === id)` at `:85` can never reach the second, while `:98` marks *both* applied; (c) the autonomous path (`cycle.ts:61`) correctly scopes to one page while the operator path does not — the two paths disagree about what a proposal means. `learn.slots[slot].autonomy` and `liftKey(tenant, brand, slot)` are likewise keyed by slot name only, so two pages share one autonomy config and one lift snapshot. `validateSlotCatalog` scopes its duplicate-slot check per page (`kinds.ts:214`), so this configuration is legal and expected.

### 4.2 `runCycle` skips a `pinnedPieceId` slot; `decideProposal` does not
`cycle.ts:54` returns `action:'none', reason:'pinned slot'`. The operator path never looks. Reproduced (R2): the same slot, now non-personalizable, took the weight change silently — latent until the content pin is removed.

### 4.3 A saturated top dimension silences the whole cycle for ever
`autonomy.ts:91` `return`s instead of falling through to the next candidate. Probe A1: `occasion` at max 1.0 with spread 0.75, `line` at 0.25 with spread 0.15 → `proposeFor` returns **null**, "occasion is already at its maximum 1". Because §4.4's ratchet always saturates the top dimension, every autonomous slot eventually reaches a permanent silence that reads in the console as "no evidence yet".

### 4.4 `spread = max − min` is a count of tag values, not a measure of signal
Probe A2: 40 items, lift drawn from one identical noise distribution, no signal in either dimension; `line` has 2 tag values, `priceBand` has 8. Over 400 trials: **`priceBand` won 400, `line` won 0.** The "most discriminating dimension" is, under noise, whichever dimension has the most values. A real registry mixes 2-value and 8-value dimensions, so the cycle has a systematic preference for high-cardinality ones regardless of outcome.

### 4.5 The receipt's exposure number is not the move's support
Probe A3: 30 items at `n=500` all with lift 1.0, plus one item at `n=2` clamped to lift 2.0 on its own tag value. Spread 1.0, proposal issued, and `proposal.exposures` reads **15,002**. The move rests on 2. The console renders exactly that number (`public/learning.js:317`, `${Math.round(p.exposures)} exposures`), so the operator is shown a support figure three orders of magnitude larger than the evidence.

### 4.6 The console cannot show the operator that a proposal is stale
`public/learning.js:317` renders `${p.dimension}: ${p.from} → ${p.to}` — `from` is the value at *proposal* time. In R1 the card reads "occasion: 0.1 → 0.15" while the live weight is 0.90. The relative timestamp is shown (`when(p.at)`), but the card offers nothing that would make an operator hesitate. Only the last 12 proposals are rendered (`:313`), and `PROPOSALS_KIND.validate` slices to the last 200 **on read as well as write** (`cycle.ts:26`, via `coerce`), so still-`'proposed'` entries silently vanish from the audit trail — roughly ten days for a twenty-slot tenant.

### 4.7 No role gate on the apply route
`POST /v1/:tenant/learn/proposals/:id/:decision` (`src/routes/decisions.ts:302`) is `jwt({ required: true })` with no `roles`/`permissions`. A non-admin `operator` account carries `permissions: ['read']` (`src/auth/accounts.ts:84`). The only edit gate is client-side (`canEdit = () => Boolean(S.token)`, `public/learning.js:26`). *Overlaps audit F03*, which makes the general point but does not cite this route.

### 4.8 The lost update is a second, independent way the same failure happens
`versionedStore.write` has no expected-revision precondition (`:233–:246`) and `read` serves a 30-second isolate cache (`:37`, `:144`). A merchandiser saving weights while the 03:00 cron runs loses one of the two writes with no error. *This is audit F15's mechanism*; F24 does not cross-reference it, and it is the reason a from-precondition (§6) is the right shape of fix rather than a second read.

### 4.9 The autonomy cycle's tenant list is borrowed from another job
`src/index.ts:213`: `(env.TREND_ROLLUP_TENANTS ?? 'coach').split(',')` — every *other* job in the same handler uses `tenantConfig(env).provisioned`. A new customer's slots are never cycled unless someone remembers to edit a variable named for the regional trend roll-up, and the fallback is a hardcoded `'coach'`.

### 4.10 Nothing observes any of this
`src/ops/monitor.ts` has no reference to proposals, autonomy, or the cycle; the five-minute self-monitor and `ALERT_WEBHOOK_URL` never fire on an autonomous weight change, a failed application, or a slot ratcheting to its bound.

### 4.11 A test that passes for the wrong reason
`src/learn/phase2.test.ts` is the only coverage (7 tests, all passing: `npx vitest run src/learn/phase2.test.ts` → 7 passed). Line 134 asserts `applyProposal(weights, {dimension:'occasion', to:1.7}, cfg)` → `{occasion:1, line:0.25}` and reads as a governance test. It passes because `cfg.pinned` defaults to `[]` and `cfg.max` is 1 — it proves the clamp and nothing else. Lines 132–133 verify that `pinned` and `mode:'configured'` block a **proposal**; no test verifies they block an **application**, which is the actual defect. Line 152 (`already applied` → `ok:false`) is the only apply-time guard in the code and the only one under test.

## 5 · Severity and size

**I agree with the audit: blocks the pilot. Size M for controls, L for validated optimization.**

Reasons to hold it there rather than raise it to *blocks launch*:
- `DEFAULT_AUTONOMY.mode` is `'configured'` (`autonomy.ts:24`), the console's mode selector *deletes* the autonomy block when set to configured (`public/learning.js:388`), and nothing in `scripts/` or the seeds sets `assisted`/`autonomous`. Blast radius today is zero.
- The brief's own scale allows it: *"Optional learning/model/autonomy features may remain disabled, but their capabilities must then be reported as undelivered."*

Reasons it is not merely an *improvement*:
- Doc 22 §11 **recommends launching every slot in `assisted`**, which is the mode R1 breaks; the pilot plan turns this on.
- Delivery ledger 19 rows 14 and 15 trace "configured AND autonomous modes" and "tune themselves" to the customer's words, so the audit's conditional is satisfied — the capability is represented as delivered.
- Turning it on is one dropdown, with no confirmation step and no alerting.

**The condition attached to remediation:** if the controls are not built, `assisted` and `autonomous` must be removed from the console (not just defaulted off) and rows 14/15 reported as partly undelivered. Leaving a working dropdown next to a broken apply path is the worst of the three options.

Size, checked against the work: the governance controls are one file each and are covered by the existing `phase2.test.ts` harness — I would call the controls **S–M**, at the low end of the audit's M, because `Proposal.from` already exists (§6). The validated-optimization half is genuinely **L** and independent.

## 6 · Remedy assessment and the smallest safe fix

The audit's remedy is **right but bundled**. It reads as one work item spanning a one-day precondition fix and a multi-week causal-inference programme. Bundled that way it will be scheduled as an L and deferred past the pilot, leaving R1 live. Split it.

**Smallest safe fix — closes the pilot-blocking half. Two functions, ~25 lines, no schema change.**

In `decideProposal` (`src/learn/cycle.ts:89–96`), before `applyProposal`, refuse with a reason when any of these fail:

1. `cfg.mode === 'configured'` → the slot's autonomy is off.
2. `cfg.pinned.includes(p.dimension)` → the dimension is pinned.
3. `now - p.at > MAX_PROPOSAL_AGE_MS` (7 days is the natural value: proposals are daily).
4. **`s.weights[p.dimension] !== p.from`** — a compare-and-swap precondition, evaluated **per slot entry**.
5. `Math.abs(p.to - s.weights[p.dimension]) > cfg.step + 1e-9` → the move exceeds the documented per-cycle bound.

Check 4 is the load-bearing one and costs nothing: **`from` is already on the `Proposal` (`autonomy.ts:42`)**. It closes R1 (0.90 ≠ 0.10), the cross-page bleed in §4.1 (0.80 ≠ 0.35, so only `home` moves), and the F15 lost update in this path — one condition, three defects. Applying it per entry rather than per document is what makes the cross-page case fall out for free.

Then, for the receipt (`cycle.ts:72–78`): move the `PROPOSALS_KIND` write **after** the `SLOTS_KIND` write, mark `status:'applied'` only when `res.ok`, and set `r.action = 'none'` with the error as the reason otherwise, so the route stops returning `ok:true` on a failed application. Mirror it in `decideProposal` (`:99`): if the receipt write fails after a successful slots write, return `ok:false` with the revision, so the operator is told the trail is inconsistent rather than shown a silent success.

Also in the same pass, both cheap: add `page` to `Proposal` and to its `id` (fixes the duplicate ids in §4.1); add `roles`/`permissions` to the apply route (§4.7); log the slot, dimension, from→to and outcome in the cron line (`src/index.ts:216`).

**Under-scoped in the audit:** the page identity (§4.1) and the `pinnedPieceId` asymmetry (§4.2) are not named, and both survive an expected-revision check written at document granularity — which is what "expected-revision checks" most naturally means. Say "per-slot-entry expected value" explicitly.

**Over-scoped in the audit:** "reversible trials and a rollback policy" reads as build work; the rollback route exists (§3.4). The deliverable is a written policy plus an alert on any `autonomous` application, not a mechanism.

**Correctly scoped and correctly deferred:** everything after "Demonstrate beneficial coefficient changes through controlled perturbation/holdout evaluation". That is the L, it is a real gap against doc 22 §11's own definition of `assisted`, and it must not gate the S-sized safety fix. Until it exists, the honest framing for the customer is that `assisted` proposes a **heuristic** — "these tags differ in outcome" — not a measured improvement, and the console should say so where it currently says "separates outcomes most".
