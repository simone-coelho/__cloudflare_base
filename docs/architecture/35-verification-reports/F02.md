# Verification of F02 — "Refresh tokens bypass the advertised fifteen-minute access boundary"

Independent verifier's report. Repository `/mnt/c/Users/LAH/Documents/__Development/Optimizely/__cloudflare_base`,
branch `feature/real-time-personalization`. **HEAD is `c10ccff7303d06492e4acdf932fc70273d7159ac` — the exact
commit the audit names**, so no line numbers can have drifted, and nothing in the working tree touches any
auth file (`git status` modifies only `src/learn/*`, `src/content/*`, `src/ledger/*`, `src/durable-objects/*`,
`public/learning.js`, `public/meridian/engine.bundle.js`).

**Verdict: confirmed, with the consequence understated.** Every evidence claim holds at the cited line, and
every behavioural claim reproduced on the first attempt in an isolated harness. Three things the audit did
not say make it worse, and one thing in its remedy would break the delivery tooling if applied literally.

## 3 · Verdict, severity, size

**Confirmed.** Not partly: every cited line is right, the probe reproduces, and the audit was careful not to
overclaim about roles.

**Severity: blocks launch — agree.** On the brief's scale this is live-data safety plus a representation:
`/v1/:tenant/visitors/:id/receipts`, `/v1/:tenant/identity/shopper/:id`, `/v1/:tenant/ledger/erasures` and
`PUT|PATCH /config/reflex` all sit behind a role-free `jwt()`. The refresh token lives in the console's
`localStorage` (`public/operator-session.js:33`, mirrored into `sessionStorage` as `tuning-token`), so one
script on the console origin buys **seven days** of read/write access that sign-out, disable, reset, password
change and account deletion do not end. Doc 30 tells a customer's security team the opposite.

**Size: M — agree, with a split worth knowing.** The launch-blocking core (deny `type:'refresh'` at the
verifier, plus a regression test) is **S — under a day**. M is the honest number for the whole remedy
because of the tail: session-bound access tokens, a revocation check, `must_change_password` as a
server-side restricted state, migrating the self-minted machine tokens (below), negative tests across 34
guards, and a redeploy of both stamps.

**Already fixed at HEAD: nothing.** HEAD *is* the audited commit; the last change to any auth file is
`b71c355` ("Operator accounts move to D1"), before it.

## 4 · What the audit got wrong

1. **The algorithm allowlist is hygiene, not the hole.** jose 5.10 already rejects `alg:none` and any
   asymmetric algorithm against a `Uint8Array` secret (measured: both 401). Listing it beside the real
   defect invites a team to ship the allowlist, tick the finding, and leave refresh-as-access open. Say
   plainly that the typed check and the revocation check are the fix and the allowlist is defence in depth.
2. **"beyond fifteen minutes" undersells it by a factor of 672.** The stolen artefact that matters is the
   refresh token, and its ceiling is seven days, not "more than fifteen minutes". Sign-out does not shorten it.
3. **Anchor nit.** `src/middleware/auth.ts:49` is the secret; the validation is at 50–53. Immaterial, but a
   remediating engineer will look one line down.
4. **"Temporary-password onboarding similarly depends on client cooperation" is generous.** There is no
   server-side dependency on cooperation at all: `must_change_password` is never read by any route. The
   console merely unhides a form the operator can ignore while every API call continues to work.

## 5 · What the audit missed, adjacent to this finding

1. **A second, wider path to the same failure: `src/middleware/edgeAccess.ts:119–121`.** In enforced mode a
   `Bearer` header makes the SDK-key gate delegate to `jwt()`, so the refresh token also opens `/realtime/*`
   and `/operator/*` writes with no site key and no tenant binding. Fixing only the route guards leaves this
   one open. (Shares remediation with F01/F03; do not double-count the estimate.)
2. **Revocation is missing in five directions, not one.** Measured: logout, disable, role change, account
   deletion and password change all leave live tokens fully functional. Role demotion is the sharp one — a
   demoted admin keeps `roles:['admin']` in a live token for fifteen minutes and passes `jwt({roles:['admin']})`.
3. **`POST /auth/password` never calls `revokeSessions`.** The one action a compromised operator takes on
   their own does not evict the attacker. Doc 30's table does not list it either, so the doc is consistent
   and the behaviour is still wrong.
4. **The tests pass for exactly the wrong reason.** `src/routes/auth.test.ts:55`, `:131` and `:136` assert
   401 from `/auth/refresh` after logout, reset and disable. That proves only that the `operator_sessions`
   row is gone. No test presents a revoked token to any *other* route, and none presents a refresh token as
   a bearer. Eleven green tests read as "revocation works".
5. **Eight tooling scripts self-mint bearer tokens with no session and no `type` claim** —
   `scripts/dev-token.mjs`, `acceptance-run.mjs`, `import-content.mjs`, `seed-coach-content.mjs`,
   `console-operator.mjs`, `holdout-proof.mjs`, `identity-proof.mjs`, `rehearse-storefront.sh` — several with
   `roles:['admin']` or `['operator']`. The audit's remedy as written ("require intended claims", "enforce
   session revocation") breaks all of them, including `scripts/acceptance-run.mjs`, which brief §6 names as
   the gate the object host still has to pass. They need their own token type with an explicit exemption, or
   real service accounts.
6. **`wrangler.toml:159` commits `JWT_SECRET = "development-secret-key-change-in-production"` in the
   top-level `[vars]`.** `[env.staging.vars]` / `[env.production.vars]` replace rather than merge, and
   `scripts/provision-stamp.sh:48` puts a random secret on those two stamps — but the default (non-env)
   worker inherits the committed value unless a secret was set by hand, and `scripts/deploy.sh:49` checks
   only for `SDK_KEYS`, never `JWT_SECRET`. Measured: a token forged offline from those values passes
   `jwt({required:true, roles:['admin']})`. On any stamp in that state, token semantics are moot. I did not
   and must not call the deployed hosts, so this is a source finding, not an attested one.
7. **The `sub` claim is never required.** `src/routes/auth.ts:54` promises "never a request whose token
   carries no id"; a `sub`-less token with `roles:['admin']` passed (measured 200), and `actorOf`/`actor()`
   would then write `null` into the audit trail.

## 6 · Remedy assessment, and the smallest safe fix

The audit's remedy is **right in direction, under-scoped in two places and mis-weighted in one**.
Right: typed access/refresh validation, revocation where the privilege model requires it, a restricted
password-change state, and the test list. Under-scoped: it never mentions `edgeAccess.sdkKey`'s bearer
delegation (finding 1 above), and it never mentions the machine tokens the typed check would break
(finding 5). Mis-weighted: the algorithm allowlist reads as co-equal with the actual defect and is not.

**Smallest safe fix that closes the launch-blocking part — one line, no migration, breaks nothing:**

in `src/middleware/auth.ts`, immediately after `jwt.jwtVerify` returns (line 53), before the payload is cast:

```ts
if ((payload as { type?: string }).type === 'refresh') return c.json({ error: 'Invalid token' }, 401);
```

A *deny* on `type === 'refresh'`, not a *require* of `type === 'access'`. It is the difference between a
one-line change and a change that breaks eight scripts and every token already in an operator's browser:
`mintAccess` emits no `type` claim today, so requiring one rejects every live access token and every
self-minted tooling token the moment it deploys. Ship the deny now; then, in order: add `type:'access'` and
`sid: <session jti>` to `mintAccess`, add a `service` type for the scripts, switch the verifier to an allow
of `access|service`, look the `sid` up in `operator_sessions` on privileged routes, call `revokeSessions`
from `POST /auth/password`, and gate privileged routes on `must_change_password` server-side. Add the
negative tests from §5.4 with the first commit, not the last.
