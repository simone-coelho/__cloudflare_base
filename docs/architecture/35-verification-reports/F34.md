## 2 · Reproductions

All harnesses are under `/tmp/audit-verify/F34/`. Nothing in the repository was modified; no network host
was contacted.

### A · The duplicate is real, and a *correct* integration produces it
`/tmp/audit-verify/F34/sdk-lifecycle.mjs`, run with `node`. It imports the **shipped bundle**
`public/sdk/edge-personalization.esm.js` (not the TypeScript source) and drives it against a real
**jsdom** DOM, so the elements accumulate listeners the way a browser's do.

```
A  mount -> detach -> mount, ONE click on each element:
   { content_click: 2, add_to_cart: 2, observers_created: 2, observers_live: 1 }
A2 four correct mount/detach cycles, ONE click:  { content_click: 4 }
```

The integrator did everything right: called the returned detach before re-mounting. The observer *was*
released (`observers_live: 1`), exactly as the audit says. The click listeners were not, so one human
click produced two `content_click` events and two `add_to_cart` events. Growth is linear in mounts.

React 18 StrictMode in development double-invokes effects (mount → cleanup → mount), so a correct React
integration reproduces this on the first render without any route change.

### B · A second way in, which the audit missed: re-scan without detach
```
B  re-scan without detach:
   { impressions_after_scan1: 1, impressions_total: 2, content_click: 2,
     observers_created: 2, observers_live: 2 }
```
Calling `declarative()` again to pick up newly rendered content — the obvious reading of the integration
guide, which never mentions the detach function — duplicates **impressions** too, because the `seen` set
(line 89) is per-call, and leaks the IntersectionObservers as well. So the audit's "removes observers but
not those listeners" is true of the documented path and too generous about the undocumented one.

### C · The existing test cannot see any of it
`src/sdk/emit.test.ts:52-81` is the only test of `declarative()`. Its fake element is
`addEventListener: (t, fn) => { listeners.set(t, fn); }` — a `Map` keyed by event type, so the second
listener **replaces** the first. Running the identical mount→detach→mount scenario against that fake:
```
C  same scenario, emit.test.ts fake element: { content_click: 1, listener_slots_held: 1 }
```
The test passes for the wrong reason. It also calls `detach()` at line 80 and asserts nothing afterwards,
and its `observe` stub returns a no-op detacher, so neither half of the cleanup contract is tested.

### D · `listen.rendered()` never releases its observer
`src/sdk/listen.ts:121-131`: `off()` is called only in the branch where the element leaves the viewport
after a dwell. An element that stays on screen until the route changes keeps its IntersectionObserver
forever, and `Listen` exposes no detach handle. Measured: one observer created, one still live, no way to
release it. This is milder than A — the `impressed` set (line 116) means three `rendered()` calls create
one observer, not three — but it is unbounded across client instances and the audit did not mention it.

### E · The duplicate actually moves what the engine learns
`/tmp/audit-verify/F34/bias-entry.ts`, bundled with the repo's own esbuild and run in Node. Two content
pieces, 100 exposures each, ten genuine clicks each, the shipped `attribute()` → `recordSuccess()` →
`buildSnapshot()` path with `DEFAULT_POLICY` and `DEFAULT_STATS`. Only piece A sits on a DOM node that
survived a remount.

```
one mount  (no duplication) : A lift 1.000 (n 100, s 10)  ·  B lift 1.000 (n 100, s 10)
two mounts (audit scenario) : A lift 1.256 (n 100, s 20)  ·  B lift 0.744 (n 100, s 10)
four mounts                 : A lift 1.462 (n 100, s 40)  ·  B lift 0.538 (n 100, s 10)
```

Exposures are unaffected because they are recorded server-side from the decision path
(`src/learn/fan.ts:69` `fanDecisions`), not from SDK events. Only the numerator inflates, so the rate and
the lift move. One remount gives piece A a **69% relative lift advantage** over an identical piece; four
give it 2.7×. Note the second-order effect the audit did not state: piece B is *pushed down* to 0.744,
because shrinkage is toward the slot's rate in the same cell and the duplicates raise that rate. The harm
is not confined to the duplicated item — it reorders the whole slot.

There is no downstream defence. `ActionEnvelope` (`src/sdk/types.ts:109-119`) carries no event id, so the
ingest cannot dedupe; `DecisionRing.outcome()` (`src/durable-objects/DecisionRing.ts:77-98`) attributes
every outcome independently with no per-decision credit ledger; `LearnStats` `/credits` calls
`recordSuccess` once per credit with no idempotency key. A duplicated click is indistinguishable from a
real one at every layer, and cannot be cleaned out of the accumulators afterwards.

### F · The measurement path at cardinality — the server breaks before the browser
`/tmp/audit-verify/F34/report-entry.ts`, calling the real `buildReport()` on synthetic ledger records.
Node on a laptop, not a Worker isolate; the orders of magnitude are the point, not the milliseconds.

| Scenario | decisions / outcomes | slots × pieces | `buildReport` | `GET /learn/report` payload | `JSON.parse` | cells the UI renders for **one** slot |
|---|---|---|---|---|---|---|
| demo today | 500 / 50 | 3 × 20 | 30 ms | 0.24 MB | 2 ms | 320 |
| small pilot | 5,000 / 500 | 20 × 60 | 151 ms | **4.7 MB** | 20 ms | 960 |
| mid pilot | 20,000 / 2,000 | 50 × 150 | 1.05 s | **28.8 MB** | 112 ms | 2,400 |
| `REPORT_CAP` | 50,000 / 5,000 | 100 × 295 | 5.5 s | **112.5 MB** | 457 ms | 4,720 |
| `REPORT_CAP`, outcome-heavy | 50,000 / 25,000 | 100 × 295 | **32 s** | 111.8 MB | | |
| `REPORT_CAP`, outcome-saturated | 50,000 / 50,000 | 100 × 295 | **160 s** | 110.6 MB | | |

**Caveat on the shape.** The two largest rows assume 100 slots each serving ~295 distinct pieces in one
day — an aggressive but not absurd reading of doc 28's "thousands of items, hundreds of slots". The
defensible headline is the mid-pilot row: 50 slots × 150 pieces gives a **28.8 MB** report and a 1.05 s
build. The demo shape in use today (0.24 MB, 30 ms) is fine, which is exactly why this has not been seen.
Node on a laptop is not workerd; the CPU and memory limits below are read from Cloudflare's documented
limits (30 s CPU on paid, 128 MB per isolate) and were not tested against a real Worker.

Three separate failures fall out of this, none of them in the audit:

1. **The report object exceeds a Worker.** 99.9% of the payload is `grids` — `slots × 5 policies ×
   pieces × 6 pooling levels` `LevelStat` objects (`src/learn/report.ts:120-123`, `stats.ts:147-163`).
   `runReport` does `JSON.stringify(report)` and `r2.put(...)`, then `routes/decisions.ts:557` returns the
   whole thing with `c.json`. A 112 MB string in a 128 MB isolate does not survive. At the mid-pilot shape
   it is 28.8 MB, which survives but is not a web response.
2. **`buildReport` is quadratic in the wrong variable.** `src/learn/report.ts:113` does
   `i.decisions.find((x) => x.decision_id === c.decision_id)` inside the loop over outcomes, inside the
   loop over five policies. Cost is `policies × credits × decisions`. That is the whole difference between
   5.5 s and 160 s in the table. `REPORT_MAX_OBJECTS = 800` guards the number of R2 objects opened; nothing
   guards the number of records, and `REPORT_CAP = 50_000` per stream is the only ceiling. A one-line fix
   (build a `Map` of decision_id → record once) removes it.
3. **The window endpoint parses whole day reports to read one small field.**
   `src/measure/window.ts:60-63` loops up to `MAX_WINDOW_DAYS = 92` days, doing `await obj.json()` on each
   day report and then reading only `report.holdout` (a few hundred bytes). The console's default window is
   28 days (`views-measure.js:28`), and `enter()` fires it on every visit to the view. Twenty-eight
   sequential full parses of multi-MB — potentially 28 MB+ — objects, in a Worker, to produce a page.

For the browser half the audit is right but the leverage is elsewhere: at the mid-pilot shape the operator
downloads **28.8 MB** to render **2,400 table cells** for one slot, plus one card per slot in the window
section (50 cards at mid pilot, 100 at cap). `views-measure.js:163` reads only the `'*'` level of each
item, so five sixths of what it downloads is never displayed at all.

### G · A third way to duplicate, in the same file: the dataLayer adapter
`/tmp/audit-verify/F34/datalayer.mjs`, again against the shipped bundle. `emit.dataLayer()`
(`emit.ts:124-147`) is the path the integration guide calls "the cheapest path where a tag layer exists",
and it needs no DOM node to survive anything.

```
1  dataLayer() twice, one historical entry + one purchase: { product_view: 2, purchase: 2 }
2  attach A, attach B, detach A, then one push: { add_to_cart: 0 }
   after detaching B as well:                   { add_to_cart: 1 }
```

Line 1: attaching twice without detaching double-captures every push *and* replays the existing layer a
second time (`opts.replay !== false` defaults to on), so historical purchases are re-sent.
Line 2 is worse and is a plain correctness bug. `return () => { layer.push = original; }` restores the
`push` captured *at attach time*. Detach in mount order and A's restore clobbers B's wrapper: capture
stops silently (`add_to_cart: 0`). Then B's detach restores *A's wrapper*, so after the integrator has
fully torn everything down the layer is left instrumented, closed over a client the page has discarded,
and still posting (`add_to_cart: 1`). The SDK keeps sending events after a complete, correct teardown.

### H · What could not be measured locally
Real-browser render timing (layout and paint at 2,400–4,720 table cells and 50–100 cards) was not
produced. A jsdom harness modelled on `src/console/console.render.test.ts`
(`/tmp/audit-verify/F34/console-cardinality.mjs`) boots correctly — a probe confirmed all seven console
scripts evaluate and the shell renders — but on this filesystem the `jsdom` import alone costs ~54 s and
the scaled runs (20 slots × 60 pieces, and 100 × 300) did not finish inside the time available; they were
stopped rather than left running. jsdom also performs no layout, so its timings would not represent a
browser. The DOM cell counts in §2F are derived from the code, not measured. No staging or production
host was contacted and no `wrangler dev` was started, per the brief.

The Worker CPU and memory limits referenced in §2F are Cloudflare's documented limits, not measurements
against workerd; the build times and payload sizes are measured, on Node 22 on this machine.

## 3 · What the audit got wrong

Nothing material is wrong. Four things are imprecise or incomplete:

1. **Two listener sites, one cited.** `:117` leaks the same way as `:109` and duplicates commerce events
   (`add_to_cart`, `wishlist_add`, `form_submit`, `button_click`). A remedy written against `:109` alone
   would leave half the defect in place.
2. **"cleanup removes observers" is true only of the documented path.** Re-scanning without detaching
   leaks observers *and* duplicates impressions (§2B). The sentence reads as if observers were safe.
3. **The remedy needs a type change the audit does not name.** `ElementLike` (`src/sdk/types.ts:56-59`)
   declares `getAttribute` and `addEventListener` only. "Register removable listener functions" is not
   possible without adding `removeEventListener` to that interface and to every fake that implements it
   (`emit.test.ts`, `memoryHost`). Small, but it is a public interface change in a shipped package.
4. **The consequence is put entirely on the browser.** "Large measurement reports can still overwhelm the
   browser" is true and is the least of it: at the same cardinality the report cannot be built inside a
   Worker's CPU budget, cannot be serialised inside its memory limit, and the window endpoint re-parses
   every day report to read one field (§2F). Sizing the fix as a UI-paging job under-scopes it.

The severity label is the one substantive disagreement. See §6.

## 4 · What the audit missed, adjacent to this finding

1. **`emit.dataLayer()` has the same class of defect, twice, and one of them keeps sending after teardown**
   (§2G). Same file, same lifecycle contract, and it is the integration path with the lowest barrier.
2. **`buildReport`'s linear scan inside a double loop** (`src/learn/report.ts:113`) turns a 5.5 s report
   into a 160 s one when outcomes approach decisions. One-line fix, large effect (§2F.2).
3. **`windowReport` parses whole day reports for `report.holdout`** (`src/measure/window.ts:60-63`), up to
   92 of them, on the view's default load (§2F.3).
4. **The report grids carry six pooling levels per item and the UI reads one.**
   `views-measure.js:163` reads `[...]['*']` only. Roughly five sixths of the largest payload in the
   product is downloaded and discarded.
5. **The report is written behind an operator token and read without one.**
   `POST /v1/:tenant/learn/report` carries `jwt({ required: true })` (`src/routes/decisions.ts:533`); the
   `GET` of the same report at `:580` and `GET /learn/report/window` at `:568` carry none. `/v1/:tenant/*`
   is gated only by `sdkKey()` (`src/index.ts:85`), which is pass-through when `AUTH_MODE=open` and
   otherwise checks the public site key that ships inside the storefront page. So the holdout result and
   every piece's learned lift are readable by anyone who views source. Two honest qualifiers: the reports
   are aggregates with no visitor id, and these two routes are *not* uniquely ungated — `/lift/rows:73`,
   `/learn/slots:125`, `/learn/exploring:151`, `/lift:251` and `/lift/history:467` are ungated too, so this
   is a router-wide pattern that belongs under F01's boundary finding rather than to F34 alone. What is
   specific to F34 is the write/read asymmetry on one endpoint and the dead handling it produces:
   `views-measure.js:38` renders "Sign in to read the measurement" on 401/403, which the server never
   returns.
6. **`src/sdk/emit.test.ts` passes for the wrong reason** (§2C), and the same fake-element shape would
   hide a re-introduction of the bug after any fix.
7. **The legacy unbounded page is still routed.** `public/learning.html:15` states the pre-doc-28 page "is
   still served, unchanged, at `/legacy/learning.html`". Bounding the new view leaves the old one.

## 6 · Severity, size, and the smallest safe fix

**Severity — the SDK half: blocks the pilot** (the audit says fix before the next customer).
The brief defines "blocks the pilot" as covering "the promised customer integration or a feature claimed in
that pilot". Declarative capture is the promised customer integration — ledger 19 §108 claims it as
delivered and `docs/kit/01-integration-guide.md:97` is the customer's instruction for it. The duplicate
fires on a *correct* integration, is silent, is asymmetric between pieces, cannot be deduped downstream,
and corrupts the click reward that the holdout comparison, the day report and the published lift snapshot
all rest on — which is to say, it corrupts the evidence the pilot exists to produce. The honest qualifier:
a classic multi-page-load storefront never triggers it. It needs an SPA, a re-scan, or React StrictMode. If
the launch brand's storefront is confirmed to be full page loads with a single `declarative()` call, the
audit's label is right. That is a fact worth establishing before the label is settled.

**Severity — the measurement half: fix before the next customer.** Agreed with the audit. It is not a
launch blocker at Coach's demo volumes (0.24 MB, 30 ms), and the promised cardinality is doc 28's, not a
signed clause. But it fails on the server before the browser, so it should be sized as a service fix.

**Size: M overall**, agreed. Within it: the SDK correction is **S** (half a day including a real-DOM
remount test); the measurement bounding done properly — project `grids` per slot at read time, page the
policy table, index the decision lookup, stop `windowReport` parsing whole reports — is **M**.

**Smallest safe fix that closes the launch-critical part** (≈20 lines, `src/sdk/emit.ts` only, no public
type change):

```ts
// module scope
const BOUND = new WeakMap<object, Set<string>>();          // element -> event keys already bound
const bindOnce = (el: ElementLike, key: string, fn: () => void): boolean => {
  const set = BOUND.get(el as object) ?? new Set<string>();
  if (set.has(key)) return false;
  set.add(key); BOUND.set(el as object, set);
  el.addEventListener('click', fn);
  return true;
};
```

Use it at both `:109` and `:117`. A `WeakMap` at module scope, not per-`Emit`, so it also holds when an SPA
builds a fresh client per mount. This makes attach idempotent — the duplicate stops — without needing
`removeEventListener` on `ElementLike`, so nothing in the published interface changes and no fake breaks.
Ship it with one test that uses a real jsdom element (the harness in §2A) instead of the `Map`-backed fake,
asserting one click after mount → detach → mount.

**Verified.** I applied exactly this to a scratch copy of `src/sdk` at
`/tmp/audit-verify/F34/sdkfix/emit.ts` (the repository was not touched), bundled it with the repo's own
esbuild, and re-ran the §2A harness against it:

```
A  mount -> detach -> mount, ONE click on each element:  { content_click: 1, add_to_cart: 1 }   (was 2, 2)
A2 four correct mount/detach cycles, ONE click:          { content_click: 1 }                    (was 4)
B  re-scan without detach:                               { content_click: 1, impressions_total: 2,
                                                           observers_live: 2 }                   (clicks were 2)
```

The guard-only version leaves the re-scan path's duplicate impressions and observer leak (§2B) in place.
Extending the same key set to the `dom.observe` call — claim the key before observing, release it in the
detach the closure pushes into `offs` — closes those too, still with no public type change. Verified:

```
B  re-scan without detach, extended fix: { impressions_total: 1, content_click: 1,
                                           observers_created: 1, observers_live: 1 }
                                  (was)  { impressions_total: 2, content_click: 2,
                                           observers_created: 2, observers_live: 2 }
A  mount -> detach -> mount:             { content_click: 1, observers_created: 2, observers_live: 1 }
```

That is roughly 25 lines in one file and it closes every duplication path §2A–§2B demonstrates.
One honest limit remains: a DOM node whose `data-op-content` changes in place keeps its first click
listener and will keep reporting the old content id. Only a real `removeEventListener` fixes that, which
is why the guard is the emergency fix and not the end state.

Then, as the proper fix and not the emergency one: add optional `removeEventListener` to `ElementLike`,
push real unbind closures into `offs`, key the `dataLayer` restore off "is the current `push` still mine"
rather than a captured original, and give `Listen` a detach handle for `rendered()`'s observers.

For the measurement half, the smallest useful server change is a `?slot=` projection on
`GET /v1/:tenant/learn/report` that returns the report with `grids` narrowed to the requested slot (and
`items` paged): 112 MB → about 1 MB at the cap shape, with no change to how the report is built or stored.
Do it together with adding `jwt({ required: true })` to that route and to `/learn/report/window`, and with
the one-line `Map` in `buildReport`. Those three together are well under a day and remove the failure
modes; the full paging/streaming redesign the audit describes can follow.
