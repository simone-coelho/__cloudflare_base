### R1 — the audit's headline replay (CONFIRMED)

Write one decision for `v1` on 2026-11-26 through `consumeLedger`; erase at 2026-11-27 14:00; run `rewriteErasures` at
`now = D + 1 day` with a 90-day window.

- `rows_removed = 1`, `retired = 1`, `erasures/coach/pending/` empty, ledger clean.
- Redeliver the **same queue message** (the exact `LedgerMessage` object) → the row is back in R2.
- `loadTombstones` now returns an empty map, `hidden()` is `false`, `withoutErased` keeps it, a later `rewriteErasures`

The delayed-delivery path is real code, not hypothetical: `src/index.ts:262` calls `m.retry()` on every message in the batch
when R2 fails, and `wrangler.toml:34` sets `max_retries = 2`.

### R2 — a second, worse route to the same place (NEW; stronger than the audit's version)

`done_through` marches monotonically backwards and the rewrite **never revisits a day it has cleaned** (`nextOf` at
`erasure.ts:163` = `prevDay(t.done_through)`). Reproduced: a capped run cleans 11-27 and 11-26 and stops with 88 days still to
walk and the tombstone **still pending**; a redelivery into 11-26 lands; the next run walks 11-25 and older, reports
`rows_removed = 0`, and retires. The row survives in R2 and is then visible.

So the exposure is not only "after retirement". **From the first nightly rewrite onwards, any late row for the erased visitor
dated on or before the erasure day is permanent**, whether or not the tombstone is still pending. The audit's replay
understates its own finding.

### R3 — the same failure reachable from an unauthenticated request (NEW)

`actionEventSchema` (`src/routes/realtime.ts:85`) accepts `timestamp: z.number().optional()` with **no bounds**, and `:101`
uses it verbatim. `outcomeFromAction` (`src/ledger/records.ts:131`) puts that number in `OutcomeRecord.ts` and in the
`outcome_id`, and `hourPrefix` files the R2 object under the day that number names.

Reproduced: erase `v1`, complete the rewrite, retire; then `POST /realtime/action` equivalent with
`{ type: 'purchase', userId: 'v1', timestamp: erasedAt - 2 days }` → one row lands under `coach/2026-11-25/`, and
`hidden()` is `false`. `POST /realtime/action` is gated only by `sdkKey()` (`src/index.ts:85`), which is pass-through in the
default open mode and, per brief §6, accepts the example key printed in the repository on staging. **Anyone who can call the
event endpoint can re-create pre-erasure rows under an erased visitor's id at a timestamp of their choosing.**

### R4 — the object cap (CONFIRMED, and it is the smaller half of the problem)

48 objects in one day, `maxObjects: 5` → `objects_opened = 48`, 101 storage operations in one run. The cap is advisory
between days only.

### R5 — an interrupted run loses the whole day (NEW)

`done_through` is set once per day at `erasure.ts:202`, after every object of that day. Simulating a throw after the third of
four objects: the run rejects, the persisted tombstone has `done_through: undefined` and `rows_removed: 0` — **no checkpoint
and no record of what was already removed** — while objects on disk have already been rewritten. The next run redoes the day
from scratch. A day that cannot be finished inside one invocation is therefore never finished at all.

### D1 — the `seen` identity map (CONFIRMED)

## 3 · Severity and size

**Severity: blocks launch.** I agree with the audit. Under the brief's own definition ("live-data safety … these safety
issues also precede any pilot with real customer data"), an erasure that a later delivery silently undoes, plus a receipt that
reports success when a stage failed, is a GDPR Art. 17 defect that also misreports itself — the second half is what makes it
unfixable by operational care. It is *not* contingent on the learning features being enabled: the ledger, the tombstone and
the identity route are on by default.

Sub-severities, so the team can sequence:

- **Blocks launch:** the delayed/back-dated delivery restoring rows (R1–R3); the receipt claiming success (E1); the rewrite
  not completing at volume (§4, new).
- **Blocks the pilot:** `/visitors/:id/recent` with no 410 (a documented operator surface for a person's own data); erasure
  covering one host only, given that the `REFLEX_HOST` flip to `do` is imminent (brief §5.7, §6).
- **Fix before the next customer:** the `seen` array; the `profile:*` CACHE key; the reversible `visitor_hash`; the
  50-visitor cap.

**Size: M for the launch-blocking core, L only for the audit's full remedy.** The audit says M–L, which is right, but the
label hides the decision. The launch gate — a durable erasure watermark consulted at ingestion, both hosts covered, an honest
receipt, the missing 410, and a bounded wire timestamp — is about 1–2 engineer-weeks with tests. The audit's full remedy
(durable job, per-object checkpoints, destination receipts, connector and raw-export reconciliation, backfill rejection) is L
and should not gate January.

## 4 · What the audit got wrong

1. **`src/ledger/writer.ts:53` is the wrong line.** `:53` is a map-key expression. The unconditional write is `writeBatches`
   at `:46`, `await r2.put(key, body)` at `:62`. The claim is right; the citation would send a reader to the wrong statement.
2. **The `RealtimeSegmentEngine` consequence is overstated.** The legacy `profile:{userId}` key is genuinely uncovered by
   erasure, but nothing on the shopper path writes it: `saveUserProfile` has exactly one caller,
   `assignSegment` (`RealtimeSegmentEngine.ts:821`, an operator/admin action). `getUserProfile` is read on the live path
   (`:418`, `:924`) and returns a cold-start object when the key is missing. So the residue exists only for visitors an
   operator manually segmented, in the `CACHE` namespace, with a 7-day TTL. Real, and much smaller than "the legacy cached
   profile is not covered" implies.
3. **"A busy day's rewrite can exceed its intended work budget" is a serious understatement.** Using the repository's own
   accepted volume constant — `MAX_HOUR_OBJECTS = 600` (`hourly.ts:46`), i.e. up to 14,400 ledger objects a day — a 90-day
   window is ~1,296,000 objects to list and open **for a single erasure**. At the rewrite's default `maxObjects = 5000`
   (`erasure.ts:156`) and one run a night (`wrangler.toml:212`, `0 3 * * *`), that is **~259 nights ≈ 8.6 months** to complete
   one person's erasure. GDPR Art. 12(3) allows one month, extendable to three. Worse, per R5 a day is checkpointed only when
   it finishes, so any day whose object count exceeds one Worker invocation's subrequest budget can never complete and the
   tombstone stays pending forever. (The exact Cloudflare per-invocation subrequest ceiling — 1,000 on paid plans, with
   binding calls counted — should be confirmed with the platform; the 259-nights arithmetic needs no external number.) This
   deserves to be its own launch-blocking line rather than a clause.
4. **The audit's replay understates itself.** It presents the exposure as "after the completed rewrite retired the
   tombstone". R2 above shows the row is already permanent from the moment the rewrite passes that day, tombstone pending or
   not, because the rewrite never revisits a cleaned day.
5. **Nothing in the finding is refuted.** No claim I checked failed.

## 5 · What the audit missed, adjacent to this finding

1. **The client sets the timestamp (R3).** `timestamp: z.number().optional()` with no bounds is the second, deliberate way to
   undo an erasure, and it needs no queue accident. It also lets any caller back-date outcomes into closed hours and into
   attribution windows. One-line fix, large blast radius. The audit's remedy mentions "reject pre-erasure backfills"; it does
   not identify that the ordinary event endpoint *is* a backfill endpoint.
2. **The tombstone list is the only erasure signal a downstream consumer gets, and it disappears within about a day.**
   Doc 22 §15 says the export listing "names the pending count and the list a warehouse job applies to what it loads"
   (`routes/decisions.ts:370`, `:381–:386`). A tombstone written today is normally retired at the first 03:00 run after the
   erasure day ends — roughly 3 to 27 hours (the first 03:00 UTC run on a later UTC date). A warehouse job that polls daily can miss the window entirely and will never learn
   to delete rows it already copied. The retired record carries only the (reversible) hash, so it cannot be joined on either.
   Erasure therefore does not propagate to the export the design calls the customer's warehouse feed.
3. **D1 `demo_events` holds per-visitor rows that erasure never touches and never discloses.**
   `captureDemoEvent` (`routes/realtime.ts:790–835`) inserts `ts, vuid, session_id, event_type, product_id, path, label,
   dwell_ms, raw_json` for **every** action when `demoEventCaptureEnabled` is true — which by `:778–:788` is **on in every
   environment that is not named `production`**, i.e. on staging, which the memory record describes as a real enforced-auth
   environment with real operator logins. `eraseSubject` does not delete these rows and `notReached` does not mention them,
   although `POST /operator/events/reset?vuid=` (`routes/operator.ts:345`) already deletes exactly this by vuid. Doc 22 §15's
   correction "D1 left the ledger path … so there is nothing to delete there" is true of the *ledger* and false of D1 as a
   whole.
4. **On the session host, erasure deletes one session record, not the visitor's session records.** `eraseProfile` deletes
   `session:{sid}` where `sid` is whatever `user:{id}` currently points at, plus the single `ownSessionId` the link
   remembered (`identity/store.ts:165` keeps only the most recent). Session ids are named by the browser's cookie, else the
   SDK's rotating browsing-session id (CW39, `53fd3ae`), and every record carries `userId`, `segments`, `attributes` and
   `metadata` with a 30-day TTL (`SessionManager.ts:151`). Any earlier session record for that visitor — created when the
   cookie was absent or blocked, or on a second link — is orphaned, unindexed and undeleted until its TTL. This is a larger
   residue than the legacy `profile:*` key the audit did name.
5. **The 50-visitor cap does more than truncate.** `store.link` keeps the newest 50 (`:122`) but never deletes the dropped
   browsers' `identity:visitor:{v}` keys, which carry `LINK_TTL_S = 400 * 24 * 3600` (`:31`). After `erase(shopperId)` a
   dropped browser still resolves to the erased shopper id for up to 400 days, so its next decision is attributed to the
   erased person and writes fresh rows under that id — a *third* way an erased subject reappears.
6. **Two tests pass for the wrong reason.** `src/routes/identity.test.ts:302` asserts
   `profiles.every(p => p.result === 'erased' || p.result === 'absent')` — a disjunction that cannot distinguish a real
   deletion from a no-op, and `SessionManager.deleteSession` returns `true` even when it deleted nothing (`:713–:728`,
   `readRaw` may be null). `:337` asserts the second, idempotent erase reports `absent` while verifying nothing about what
   still exists. And **no test in the repository sets `REFLEX_HOST: 'do'` for erasure** (the flag appears in
   `content/consent.test.ts:31`, `reflex/shopperReflex.identity.test.ts:75`, `routes/sort.test.ts:70`,
   `tenancy/routeEscape.test.ts:26` — never in an erase test), so the object-host branch of `eraseProfile` has zero coverage.
   `src/ledger/erasure.test.ts:89` documents the between-days cap as intended behaviour on a two-object day, which is why the
   defect in R4 survived review.
7. **`visitorHash` is reversible (E2)** and the retired records never expire.
8. **Retention is asserted, not enforced.** `LEDGER_RETENTION_DAYS` is set in no environment block of `wrangler.toml`, so
   every environment uses the 90-day constant; nothing in the repo applies an R2 lifecycle rule to
   `edge-platform-storage-{staging,production}`; ledger objects are written with no expiry (`writer.ts:62`); and the
   `DecisionRing` index keeps `{id, ts}` pairs for 90 days (`DecisionRing.ts:16`) inside an object that also holds the ring.
   The audit's sentence on this is correct and worth keeping as written.

## 7 · Remedy assessment

The audit's remedy is directionally right and over-scoped as a *gate*. "Create a durable erasure job that first snapshots
every linked subject/store, then checkpoints each deletion without discarding retry information … Cover both hosts, all
caches/rings/indexes, connectors, raw exports, and subject-level aggregate state … Publish incomplete/failed status honestly
until destination receipts reconcile" is the correct end state and is an L. Presented as one item it invites either a
half-built version or a slipped date.

It is also **under-scoped in four places**: it does not name the client-settable timestamp, the D1 `demo_events` table, the
orphaned session records, or the fact that the export consumer's only erasure signal expires. And one clause —
"Checkpoint per object, not just per day" — is necessary but not sufficient: without a bound on total work per run and a way
to *resume within* a day, checkpointing per object still leaves the 259-nights arithmetic in §4.3 untouched.

### The smallest safe fix that closes the launch-blocking part

Two changes, in `src/ledger/erasure.ts` and `src/ledger/consume.ts`:

1. **Never let the suppressive record disappear.** At `erasure.ts:214`, stop deleting the pending tombstone. Instead rewrite
   it in place with a `state: 'rewritten'` marker, keeping `visitor_id` and `erased_at`, and keep it for the full permitted
   replay/backfill horizon (at minimum the retention window). `loadTombstones` then keeps hiding the visitor's rows forever,
   which closes the read half of R1, R2 and R3 and restores the truth of doc 22 §15's "every reader hides".
2. **Consult it at ingestion.** In `consumeLedger` (`consume.ts:17`), load the tenant's erasure watermark once per queue
   batch and drop any record whose `visitor_id` is tombstoned with `ts <= erased_at` before `writeBatches` is called. That
   closes the write half: the row never lands, so no future rewrite has to find it. To keep this off the hot path, publish
   one compact `erasures/{tenant}/watermark.json` (id → `erased_at`) that `writeTombstone` updates and the consumer caches
   for a few seconds; that is the same shape the readers already want.

Together these are on the order of 40–60 lines and close "erasure can be undone", which is the part that blocks launch.

Then, in the same change set and still inside M:

3. `eraseProfile` (`erase.ts:48`): run **both** the DO reset and the session-host deletion unconditionally, not on the
   `REFLEX_HOST` branch, and report both in the receipt.
4. Snapshot the linked visitor list **before** `store.erase` (`:85`) and persist it as a retry job; do the profile and ledger
   deletions first and remove the links last. Make `erased` list only ids whose every stage succeeded, and have
   `routes/identity.ts:188` answer `ok: false` (or `status: 'partial'`) with the failures named when any stage failed.
5. Copy the four-token guard from `decisions.ts:237` into the `/visitors/:visitorId/recent` route at `:270`.
6. Bound the wire timestamp: `timestamp: z.number().optional()` → reject or clamp anything outside roughly ±24 h of `now`
   in `realtime.ts:85`. This also protects attribution windows and the hourly fold.
7. Filter `state.seen` by `ctx.tombs` in `foldShard` alongside the ring filter at `hourly.ts:233`.

Separately scheduled, not a launch gate: per-object checkpointing plus a work budget for the rewrite (the 259-nights
problem needs a different shape — a per-visitor day index, or a compaction that piggybacks on the hourly fold, rather than a
full-partition walk per subject); D1 `demo_events` deletion by vuid wired into `eraseSubject`; orphaned session records;
the 50-visitor cap; replacing `visitorHash` with a keyed digest and giving retired records an expiry; and an ODP-receipt
reconciliation so `notReached` becomes `reached, receipt id …`.
