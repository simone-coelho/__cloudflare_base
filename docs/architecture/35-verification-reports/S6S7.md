### 2.3 The closing paragraph

> "If learning is held in shadow, disable unsupported exploration/autonomous changes too and make the UI/status ledger reflect that restriction."

The factual premise is correct and I verified it in code rather than taking it on trust:

- Shadow is the default: `src/content/kinds.ts` `DEFAULT_LEARN` carries the comment "Every slot runs at γ = 0 (shadow) on the click reward until a person raises the dial", and γ is a per-slot dial validated 0..1 (`kinds.ts:321`).
- Exploration is **not** gated on γ. In `src/content/decide.ts:184`, the `explore` callback is built from `learning.exploreOf(slot)` with no γ test; γ is applied separately at `:172–179` as `base * lift^γ`. The only path that disables exploration is the `no_learning` holdout arm (`decide.ts:88`, which drops `exploreOf`).
- Consequence: a slot "held in shadow" at γ = 0 can still serve a different piece via `explorationPick` (`src/learn/explore.ts:83–115`, default `{ mode: 'rotation', share: 0.1, floor: 50 }`). The recommendation is therefore load-bearing, not rhetorical.

Seven distinct owner roles imply a staffing model that today's two-track, one-checkout arrangement does not have; the gates would be actionable if each row named the track (or the named human/customer role) that doc 21 already records.
