## 3 · Severity and size

**Severity: blocks launch. Agreed.** The brief's scale defines "blocks launch" as covering "representations that the full
contracted capability is delivered". A customer-facing appendix says twelve capabilities are "Built, tested, and active on
signature. This is what the platform does today", while two of the twelve were never entered in the register that exists
precisely to stop that, and two more are closed on components that do not meet the clause. That is the definition, met
literally. It is stronger than the audit claims, because v7 — already reviewed by the customer — carries the same twelve.

**Size: L for the whole remedy, S for the launch-blocking part.** The audit's L is right for building the four missing
workflows (enrichment review/publish; customer-catalog search with server-resolved affinity; typed attribute and audience
ingestion; a scheduled warehouse destination with retries/watermarks/reconciliation). But F11 bundles a one- to three-day
documentary and governance repair with multi-week engineering under a single L, which invites the representation fix to be
scheduled behind the builds. It should not be: the representation is what blocks launch, and it is the cheap half.

   transactions with a live proof. The destination-share conclusion is unaffected.
4. **F11's evidence paragraph never says the finding's own headline** — that doc 20 has no row for §1.9 or §1.10. A reader
   must infer the omission from a list of clauses. §5's table says it; the finding should.
5. **The consequence sentence is accurate but conservative.** "Action history is not typed CRM attribute ingestion" understates

## 7 · Remedy assessment and the smallest safe fix

and one L conflates a one-day governance repair with multi-week builds. "Verify Product Recommendations entitlement
separately" is correct and cannot be done in this repository. One item is missing: because the same claims now sit in at least
four documents, the register must be **regenerated from the customer-facing document set** and re-derived before any document
ships, rather than maintained alongside it.

**Smallest safe fix that closes the launch-blocking part (documentary; ~1–3 engineer-days, no code):**

1. Add doc 20 rows for **§1.9** (status: separate Optimizely entitlement, verified commercially, not by this repository) and
   **§1.10** (status: Coach demo only — compiled 71-item catalog, client-asserted affinity, no tenant), and split **§1.3** and
   **§1.12** into sub-capability rows so "import" cannot close "AI enrichment approval" and "R2 partitions" cannot close
   "scheduled Snowflake destination share" or "third-party attributes and audiences". Add the §2.3 widget clause.
2. Sweep the four customer-facing artefacts that carry the same claims — the v8 §1 lead-in, `Tapestry-BTI-Deliverables.md`
   items 11 and 14, `content-personalization-design-tapestry.html:815`, `PS-Implementation-Delivery-Guide.md:65` — and qualify
   or remove each before the next document leaves. Settle **B1** ("available on signature" vs the Implementation Plan's
   milestones) in the same edit; it is already an open decision in doc 20 §B.
3. Give each reopened row an owner and a date. The four builds then schedule as ordinary work (the L) instead of standing
   behind a sentence that says they are already done.

**Cheapest adjacent code fix, if one is wanted in the same pass (S, ~half a day):** pass the tenant scope into
`applyHistory` — replace `resolveReflexConfig(env, resolveSurface(null))` at `src/identity/history.ts:105` with the tenant's
own `readReflexConfigRevision(env, tenant, now)`, matching `src/content/service.ts:140`, and add one test at a non-`coach`
tenant. That closes reproductions D and E. It is a piece of F31, not of F11's representation problem, and does not by itself
make any clause true.
