### 1.1 The requirement (claim 1)

`docs/architecture/tapestry_requirements.txt`, §6.4.1 "Holdout Groups (The Foundation)":

- `:363` — "Size: 5-10% of traffic held out **permanently (not rotating)**"
- `:364` — "Assignment: Based on **persistent identifier** (customer ID for logged-in, device fingerprint for anonymous)"
- `:365` — "Duration: Holdout remains constant for the entire measurement period (**6+ months minimum**)"
- `:366` — "Experience: Holdout sees **current production experience (segment-based rules)**"
- `:367` — "A user who was in BTIE for 3 months and then moves to holdout carries learned behaviors with them — they are no longer a valid counterfactual."
- `:372–374` — the pre-set targets are **CVR lift vs. holdout**, **Revenue Per Visitor lift**, and **Return Rate delta**.

The audit cited line 366; lines 363–365, 367 and 372–374 are equally load-bearing and strengthen it.

### 1.2 The arm is drawn at decision time from the current id, and never persisted (claims 2, 3)

`src/content/service.ts:168`:

```ts
const arm = armUnder(consent, armFor(r.visitorId, { ...learn.holdout, salt: learn.holdout.salt || brand }));
```

`armFor` (`src/content/holdout.ts:37`) is a pure hash of `${salt}:${visitorId}`. A repository-wide grep for `armFor(`
outside tests returns **exactly one call site** — this one. **No enrollment record exists anywhere**: the arm is not on
the session, not on the shopper object, not on the identity link. It is recomputed on every request from whatever id the
browser is carrying at that moment.

The id changes at both identity boundaries:
- `src/sdk/identify.ts:67` — `core.setVisitorId(shopperId, 'identified')` after login; the server hands the id back at
  `src/routes/identity.ts:88` as `carry: result.shopperId`.
- `src/sdk/identify.ts:48` — `core.setVisitorId(freshVisitorId(core.host), 'logout')` on logout.

The shopper id is `shopperIdFor()` (`src/identity/shopperId.ts:43`), a salted SHA-256 of the account id — a hash entirely
uncorrelated with the anonymous id. The redraw is therefore independent, not sticky.

### 1.3 The default arm is not the customer's production experience (claims 4, 5)

`src/content/decide.ts:69` sets `affinity = NO_SIGNAL` for `arm === 'default'`. With no signal every candidate scores 0,
so `contentCompose.ts:156` falls through to the tie-break `(rank.get(x) - rank.get(y)) || id.localeCompare(...)`, where
`rank` (`:119`) is the position of the piece in the catalog document. Pins are applied before scoring and survive
(`:127–137`). Diversity, eligibility and dedup still apply (`:138`, `:176–204`).

Refinements the audit did not state, all of which *strengthen* it: on the default arm the journey-stage rule
(`decide.ts:105`), freshness (`:115`), fatigue (`:116`) and the external model (`decide.ts` `ext`) are all switched off,
and the merchandising multiplier is skipped because `base > 0` is false (`:164`). So the control is neither the
customer's segment rules *nor* an unpersonalised version of the treatment — it is a distinct third experience that
exists nowhere in Tapestry's production stack. The `slot.prefer` bonus (`contentCompose.ts:149`) would break this, but
`decideContent` never populates `prefer`, so it is a latent path only.

### 1.4 Consent traffic shares the arm field (claim 6)

`src/content/consent.ts:46` — `armUnder = (c, arm) => (personalizes(c) ? arm : 'default')`. A shopper who leaves tracking
on but turns personalization off is written into the ledger with `arm: 'default'`, indistinguishable in the report from a
hash-assigned control. `service.ts:242` gates `fanDecisions` on `consent.tracking`, so the tracking-off population is
written nowhere — which means the recorded default arm is exactly the union of (hash controls) ∪ (personalization-declined,
tracking-consenting visitors). `report.ts:127–131` groups purely on `d.arm` and has no way to separate them. The raw
ledger *does* carry `explain.note = "the site's defaults: personalization is off by the shopper's choice"`
(`service.ts:236`), so the mixing is recoverable in principle — but not by the shipped report.

### 1.5 The arithmetic (claims 7, 8)

`src/learn/policy.ts:74–96` (`attribute`) returns **one credit per slot per outcome**. Every outcome inside the window
credits the decision independently, so N outcomes against one decision produce N credits.

`report.ts:112–115` increments `armCredits` once per credit. `report.ts:129–131`:

```ts
const decisions = i.decisions.filter((d) => d.slot === slot && d.arm === arm).length;
const credited  = armCredits.get(`${slot}|${arm}`) ?? 0;
return { arm, decisions, credited, rate: decisions ? r3(credited / decisions) : 0 };
```

`credited` and `decisions` are counts of two different things. `report.ts:136` then hands them to `compareArms` as
`{ n, s }` — successes and trials of one Bernoulli process, which they are not.

`measure/holdout.ts:136`, inside `wilson()` declared at `:134`: `const S = Math.min(N, Math.max(0, finite(s)));`.

### 2.1 The audit's own probe — reproduced verbatim (`probe1.ts`)

One `default` decision with three clicks, one `personalized` decision with one click, through the real `buildReport`:

```
holdout rows      : [{"arm":"default","decisions":1,"credited":3,"rate":3},
                     {"arm":"personalized","decisions":1,"credited":1,"rate":1}]
control summary   : {"arm":"default","n":1,"s":3,"rate":{"p":1,"lo":0.2065,"hi":1}}
neededPerArm      : NaN
WORDS             : personalized 100.0% of 1 decisions vs default 100.0% of 1: +0.0 points (+0% relative);
                    ... a difference this size needs about NaN decisions on each arm to call ...
wilson(3,1)       : {"p":1,"lo":0.2065,"hi":1}
```

**rate 3 (300 %) in the day report, 100 % in the interval helper — exactly as the audit states.**

Two things the audit did not report: `compareArms` also emits `neededPerArm: NaN` (because `neededPerArm`,
`holdout.ts:167–172`, does **not** clamp: `pc = 3` makes `pc*(1-pc) = -6` and `Math.sqrt` of a negative is NaN), and the
`ArmSummary` publishes `s: 3, n: 1` un-clamped beside a clamped rate of 1. `public/learning.js:298` renders `cmp.words`
verbatim into the operator console, so an operator would read "needs about **NaN** decisions on each arm to call."

### 2.2 Identity churn destroys the control population (`probe2.ts`)

20,000 synthetic visitors, `share = 0.05`, salt `coach`, arm computed with the real `armFor` and the real
`shopperIdFor`:

```
control while anonymous            : 1060 of 20000 (5.30%)
still control after login          : 63 (5.9% of them)
leaked out of control on login     : 997
arm changed at least once across anon -> login -> logout : 14.9%
visitors whose arm changes if the salt is edited         : 9.74%
personalization opt-out  -> arm: default   (same field as a hash-assigned control)
```

**94.1 % of the anonymous control leaves the control the moment the shopper signs in**, and the 5.9 % that remain are
simply a fresh independent draw. Symmetrically, ~5 % of previously-treated visitors are pulled *into* the control at
login carrying months of treated exposure — precisely the contamination requirement line 367 forbids.

### 2.3 The variance is wrong: false-positive rate under a true null (`probe3.ts`)

Visitor-randomised, decision-analysed, **no arm effect whatsoever**, 20,000 visitors × 400 runs, nominal 95 %:

```
heterogeneous=no  share=0.05  -> a winner CALLED in  20/400 =  5.0%   (nominal 5%)
heterogeneous=no  share=0.5   -> a winner CALLED in  10/400 =  2.5%
heterogeneous=yes share=0.05  -> a winner CALLED in  94/400 = 23.5%   <-- 4.7x nominal
heterogeneous=yes share=0.5   -> a winner CALLED in  68/400 = 17.0%
```

With homogeneous visitors — where decisions genuinely are i.i.d. — the module is correct at 5.0 %. With ordinary
visitor-level heterogeneity in click propensity it calls a winner **23.5 %** of the time on null data. A "95 % interval"
that covers about 76 % of the time.

### 2.4 The same, through the real `buildReport` (`probe6.ts`)

Synthetic days with **no arm effect**, run through `buildReport`, beside the visitor-level analysis of the same data:

```
visitors=2000 decisions=16336 outcomes=1687
  SHIPPED : default 795/115 (rate .145), personalized 15541/1572 (rate .101) -> control_better  [-0.070, -0.020]
  VISITOR : default 100/47,             personalized 1900/719              -> undecided       [-0.191, +0.006]
```

**On data with no effect at all, the shipped report declares the engine worse than doing nothing at 95 % confidence**,
and `public/learning.js:298` would print "control_better ... and the holdout is the reason we can say so." The honest
visitor-level interval is ~4× wider and excludes nothing.

At 40,000 visitors the shipped sentence reads: *"a difference this size needs about **132,895 decisions on each arm** to
call, and the smaller arm has 16,508."* The correct visitor-level power number is 63,708 **visitors**, and the smaller
arm has 1,927. The module's advertised answer to "how long" (`holdout.ts:26–30`) is optimistic by roughly the
decisions-per-visitor factor — about **8×** here.

### 2.5 The denominator is itself an outcome (`probe4.ts`)

200,000 visitors, treatment changes browsing depth by 60 %:

```
A. Clicks per VISITOR identical (0.4985 control vs 0.4991 treated) -- no business effect
   SHIPPED report rate: control 0.0738  treated 0.0454
   -> verdict: control_better, relative -38.5%, targets: "below the minimum"

B. Clicks per VISITOR +59% (0.5488 -> 0.8744) -- a real business win
   SHIPPED report rate: control 0.0807  treated 0.0796
   -> verdict: undecided, relative -1.4%, targets: "below the minimum"
```

The metric moves in the wrong direction in both cases. A treatment that makes the site more engaging is punished; a
treatment that genuinely lifts clicks per visitor by 59 % is reported as no change.

## 3 · Severity and size

**Severity: blocks launch**, as the audit says — for the incrementality claim specifically, and for any pilot
representing scientific acceptance. I agree without qualification. §6.4 of the customer's paper is not a nice-to-have:
"This is the only methodology that Finance will accept" (`:358`). The platform currently produces a number that (a) is
not a Bernoulli proportion, (b) can declare a winner on null data 23.5 % of the time, (c) can invert the sign of a real
business effect, (d) is labelled against the customer's CVR targets while measuring something that is not CVR, and (e)
is rendered into an operator console with the sentence "the holdout is the reason we can say so."

Note the severity is correctly *scoped to the claim*, not to the engine. The deterministic scoring core, the arms
plumbing, the ledger and `compareArms`'s Wilson/Newcombe arithmetic are all sound in themselves. What is broken is the
mapping from the ledger to the counts, and the absence of enrollment.

**Size: L.** I agree. Persistent enrollment across identity boundaries, visitor-level or cluster-aware inference,
visitor-level CVR/RPV/return-rate collection, the customer's real production control, and pre-registration are
multi-week cross-component work spanning `src/content/`, `src/identity/`, `src/learn/`, `src/measure/` and the operator
console. It overlaps F02-style identity work and should not be added to it as an independent estimate.

## 4 · What the audit got wrong

Nothing material. Three points of precision:

1. **Anchor drift, three places.** `report.ts:129` defines the denominator; the division is at `:131`.
   `holdout.ts:134` is the `wilson` signature; the clamp is at `:136`. `contentCompose.ts:117` is the explanatory
   comment; the mechanism is the `rank` map at `:119` and the tie-break at `:156`. None changes the claim; all three
   are findable by symbol.

2. **The headline probe is the least representative failure.** "rate 3 (300 %)" is a degenerate one-decision case.
   In realistic traffic the aggregate `credited/decisions` rarely exceeds 1 (my 40,000-visitor day produced 0.099 and
   0.102). A team that reads the finding quickly could "fix" it by clamping the rate and believe the finding closed.
   It would not be. The damage is the variance (2.3) and the denominator (2.5), both of which occur at rates well
   under 1. The report should lead with those.

3. **"Attribution removes unlinked business outcomes"** is true but imprecise. `attribute` with `match: 'direct'`
   drops them from *both* arms; the problem is that the drop is not symmetric in expectation, because the treated arm
   is selected to serve items the shopper is more likely to name. The consequence is bias, not only loss.

## 5 · What the audit missed

1. **`src/learn/hourly.ts:307–313` repeats the identical construction** — and per doc 31 §3 this is the path actually
   used at Tapestry's volume (the day is the sum of hourly aggregates; `runReport` from the ledger is refused for a day
   too large to read). A remedy applied only to `report.ts` leaves the production path unchanged.

2. **`src/measure/window.ts:78–81` repeats it again for the cumulative window**, and additionally pools per-day counts
   across up to 92 days, so one person's three months of decisions become 90+ "independent trials". This is the module
   that answers §6.4.3, the customer's aggregate-over-windows requirement. Two further defects there:
   `MAX_WINDOW_DAYS = 92` **cannot express the customer's "6+ months minimum"** (requirement line 365) in a single
   reading; and because the arm is redrawn on identity change, the *same person* can be pooled into both arms across
   the window.

3. **`neededPerArm` returns `NaN` whenever an arm's raw rate exceeds 1** (`holdout.ts:167–172`, no clamp), and the NaN
   reaches the operator verbatim through `compareArms`'s `words` and `public/learning.js:298`. `compareArms` also
   publishes `ArmSummary.s` un-clamped (`:235–236`), so the JSON shows `s: 3, n: 1` beside `rate.p: 1`.

4. **The "how long" answer is on the wrong scale.** `neededPerArm` counts decisions. At 40,000 visitors it told me
   132,895 decisions per arm where the visitor-level requirement is 63,708 visitors per arm — roughly 8× optimistic.
   The module advertises this number as "the honest answer to how long" (`holdout.ts:26–30`).

5. **`src/identity/link.ts` never migrates the `DECISION_RING`.** It moves affinity, audiences, pipeline and the
   session (`:138–166`) but the ring is keyed `ringName(tenant, visitorId)` (`src/learn/fan.ts:34`, `:72`, `:89`).
   A login therefore orphans the ring: a decision served before sign-in can never be credited by a post-login purchase
   inside the seven-day window. The arm redraw and the attribution loss happen at the same instant, and the finding
   should name both.

6. **The test that passes for the wrong reason.** `src/learn/holdoutArms.test.ts:70–71` builds exactly **one decision
   and at most one outcome per visitor** (`p0..p39`, `h0..h39`) — the single data shape where decisions == visitors,
   `credited ≤ decisions` always holds, and the Bernoulli framing is accidentally correct. The suite therefore
   validates the model on the only inputs where the model is valid. Relatedly, no test in
   `src/measure/holdout.test.ts` ever passes `s > n` through `compareArms` — `:44` asserts the clamp on `wilson`
   directly — which is why the `NaN` has never been caught. All 35 tests pass at HEAD.

7. **The salt defaults to the brand, so the holdout is per-brand.** `kinds.ts:378` defaults `salt: ''`;
   `service.ts:168` substitutes `|| brand`. There is no Tapestry-wide control population — a shopper is held out on
   Coach and treated on Kate Spade. Per-brand experiments are a defensible design, but the requirement is written at
   the enterprise level ("5-10% of traffic"), and nothing records which salt a given result was measured under. Editing
   the salt silently re-randomises ~9.7 % of visitors (2.2) with no versioning and no freeze.

8. **`report.ts:113` is quadratic.** `i.decisions.find((x) => x.decision_id === c.decision_id)` sits inside the outcome
   loop, and the whole loop runs once per reporting policy (five by default via `presetPolicies`). Measured:
   34 ms at 4,204 decisions, 51 ms at 8,088, 151 ms at 16,336, 576 ms at 33,874, and **over 120 seconds at 317,374** —
   a wall reached inside the module's own `REPORT_CAP` of 50,000 once policies are counted. A `Map` keyed on
   `decision_id` is a one-line fix.

9. **`REPORT_CAP = 50_000` truncates the day at a time-ordered prefix.** `loadDay` (`report.ts:157–179`) sorts keys
   lexicographically and stops at the cap, so at Tapestry volume the incrementality number is computed from the
   earliest hours of the day. `truncated` appears in `counts` (`:151`) but neither the holdout rows, the comparison,
   nor `words` mention it — an operator reading `cmp.words` cannot tell.

10. **The targets are mislabelled.** `holdout.ts:55` documents `TAPESTRY_TARGETS` as the customer's §6.4.2 "CVR lift vs
    holdout", and `targetWords` prints "against the pre-set targets (minimum +10 %, target +40 %, stretch +60 %
    relative)" against a clicks-per-decision ratio. A repository-wide search finds **no computation of CVR, revenue per
    visitor, or return rate anywhere in `src/`** — the three metrics requirement lines 372–374 name. The report is not
    merely measuring the wrong quantity; it is presenting it under the customer's own metric names.

## 7 · Remedy assessment

The audit's remedy is **directionally correct and correctly sized at L**. Every clause is right: separating enrollment
from eligibility and from attribution; a persistent assignment anchor with an explicit anonymous→recognised merge
policy; preserving the salt for the agreed experiment; the real production control with recorded exposures; visitor-level
business outcomes collected independently of content matching; pre-registration of unit, metric, window, maturity,
target, allocation and stopping rules; cluster-aware inference; excluding or stratifying consent-ineligible traffic; and
keeping the attribution report but labelling it attribution. The closing sentence — that exploration and an evolving
policy do not invalidate a properly randomised permanent holdout — is correct and worth keeping, because it forestalls
the wrong fix.

Two scoping corrections:

- **Under-scoped in reach.** It names `report.ts` and `measure/holdout.ts` only. `src/learn/hourly.ts:307–313` and
  `src/measure/window.ts:78–81` carry the same construction, and `window.ts` additionally cannot express the six-month
  window. A remediation plan that does not name all three will ship a fixed daily report over a broken production path.
  Add the `DECISION_RING` migration in `src/identity/link.ts` — it is the same seam.

- **One clause is not ours to build.** "Implement/accept the actual production control" means running Tapestry's current
  segment-based rules as the control experience. That is a customer integration decision (whose rules, served from
  where, refreshed how), not platform engineering. It belongs on the joint implementation plan with a named Tapestry
  owner, not inside the L estimate — otherwise the engineering estimate absorbs a dependency it cannot discharge.

### The smallest safe fix that closes the launch-blocking part

The launch-blocking part is not the statistics; it is **the representation**. The platform is currently making a causal
claim it cannot support, in the customer's own metric vocabulary, in an operator console. Two moves, in order:

**(a) Stop publishing the number as incrementality — approximately 1 engineer-day.**
In `src/measure/holdout.ts`: delete the `targets` reading and `TAPESTRY_TARGETS` from the default path (or gate them
behind a visitor-level metric that does not yet exist), remove the clause "and the holdout is the reason we can say so"
from `compareArms`'s `words`, clamp `s` to `n` in `ArmSummary` and guard `neededPerArm` against rates above 1 so no NaN
can reach a reader. Rename the fields and the sentence to attribution-diagnostic language: `credited per decision`, not
a rate; "attribution diagnostic, not an incrementality result", not a verdict. Apply the same in `src/learn/report.ts`,
`src/learn/hourly.ts`, `src/measure/window.ts` and `public/learning.js:298`. Add one test that drives `compareArms`
with `s > n` and asserts no NaN and no causal wording. This costs no capability and immediately removes the false claim.

**(b) Persist the enrollment — M, and the prerequisite for everything later.**
Write the arm and a salt version **once**, on first decision, to the shopper record; read it back instead of
recomputing; and carry it through `linkVisitor` and detach in `src/identity/link.ts` so the arm survives login and
logout, alongside the `DECISION_RING` migration. Until this exists, no amount of statistical work produces a valid
result, because there is no stable population to analyse. Every day it is deferred is a day of ledger that can never be
analysed as an experiment.

The remaining L — visitor-level or cluster-aware inference, visitor-level CVR/RPV/return-rate collection, the customer's
real production control, pre-registration and stopping rules — cannot be shortcut and should be planned as the audit
describes. It is scientifically required before any number is shown to Tapestry's Finance function, which is the
audience §6.4 names.
