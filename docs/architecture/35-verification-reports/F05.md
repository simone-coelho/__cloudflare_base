## 3 · What the audit got wrong

1. **Line drift (trivial).** `src/content/service.ts:107` and `:120` are the `} catch {` lines; the `CONSENTING` returns are at 108 and 121.
2. **The demo-capture item cannot occur on the production stamp.** `demoEventCaptureEnabled` returns `false` for `ENVIRONMENT='production'` and for a missing `ENVIRONMENT`; `wrangler.toml:317` sets `ENVIRONMENT = "production"`. Listing it inside a *blocks launch* evidence block overweights it. It is real for **staging** (`wrangler.toml:218`), which is where a pilot with real Coach data runs — so it belongs in the finding, but as a pilot-data issue, not a production one.
3. **Regional fan-in and ODP are lumped together; their consequences differ by an order of magnitude.** The region object stores decayed aggregates keyed `tenant:region` with **no visitor identifier** (`src/reflex/regionTrend.ts:130–145`); the ODP call carries a stable pseudonymous `vuid` and the product ids to a third party. Only the second is a subject-data egress.
4. **On the object host the regional fan-in is inert, for an unrelated reason.** `ShopperReflex.normalizeEvent` (`src/durable-objects/ShopperReflex.ts:426–435`) rebuilds the event and drops `geo`, which the route attached at `src/routes/realtime.ts:98–105`. `fanInRegionTrend` at `ShopperReflex.ts:554` therefore always no-ops (`regionKeyOf(undefined) → null`). `RealtimeSegmentEngine.ts:468` is the only live instance today — and CW6's population prior silently never accumulates on the object host, which is a separate delivery defect.
5. **One remedy item cannot be delivered as a guard.** "Test … withdrawal during a session, … prior contribution" — a prior contribution to the region trend is unkeyed and irreversible by construction. Honouring withdrawal there needs a design change (per-visitor contribution keys, or accepting that aggregates are not withdrawable and saying so in the customer's policy), not a consent check.
6. **"Initialize SDK consent before automatic activity" understates the gap.** `public/storefront.js` contains no consent code at all — the single match is prose in a demo string. This is new SDK surface, not an initialization-order fix.

Nothing else in F05 is overstated. The severity, the direction of the remedy and the M–L size are right.

## 4 · What the audit missed (same code path)

1. **The strongest instance of its own finding.** With tracking explicitly refused, the refused behavioural event is sent to ODP on **both** hosts (`ShopperReflex.ts:590`, `RealtimeSegmentEngine.ts:501`), carrying the stable `vuid` and product ids in `recent_events`. Reproduced (R6, R7). The audit cites `odpLoop.ts:370` but frames it as "not all guarded by the same boundary" rather than "the refused event leaves the edge to a third-party CDP."
2. **The personalization switch is enforced in exactly one file.** `personalizes()`/`armUnder()` appear only in `src/content/service.ts`. `POST /realtime/action`, the WebSocket push and `POST /sort` all personalize a shopper with `personalizationEnabled=false` (R7, R8). The audit's title says "capture, scoring, and egress"; scoring is worse than described — it is not route-specific, it is one-route-only.
3. **No way for the contracted integration to express a refusal.** `ServeRequest` (`src/content/service.ts:27–40`) has no consent field, and neither `/v1/:tenant/decisions` (site-key gated, `src/index.ts:86`) nor `/sort` accepts a consent parameter. A customer calling server-side, which is the headless model in the Mandeep contract, is structurally unable to state that the shopper refused. R4 is that case.
4. **Logout erases the refusal.** `POST /:tenant/identity/detach` (`src/routes/identity.ts:98–105`, unauthenticated) calls `SessionManager.clearCookieHeaders()` (`SessionManager.ts:664–668`) and `POST /realtime/session/reset` (`src/routes/realtime.ts:376–382`) does the same, both expiring `opt_tracking_consent` and `opt_personalization_enabled`. Absence means consenting (`consent.ts:39`), and the reset also deletes the KV record that held the instruction. A shopper who refuses and then signs out is consenting again on her next request.
5. **A whole tracking ingress has never been inside the consent model.** `POST /track/event` and `POST /track/batch` (`src/routes/tracking.ts:33`, `:89`) and `GET /pixel/track/:pixelId` (`src/routes/pixel.ts:48`) write the full enriched event to Analytics Engine indexed by the visitor id — including `page.ip` from `CF-Connecting-IP` and the User-Agent (`src/utils/context.ts:9–26`) — and hand it to `EventDispatcher`, which always enqueues it (`EventDispatcher.ts:90`, `:147`) and POSTs it to any destination `WEBHOOK_ENDPOINTS` enables. No consent check anywhere. Mounted publicly at `src/index.ts:94–95`. This is the only path in the repository that stores an IP address.
6. **The self-monitor is a test that passes for the wrong reason, and becomes a false alarm.** `src/ops/monitor.ts:66–71` asserts `!out.write` for a synthetic refusing visitor. It passes on the session host and is cited as proof consent is honoured; it proves only that the session-host cookie mirror works. On the object host the identical check fails — `"a monitor decision was going to be written"` (R9) — so flipping `REFLEX_HOST=do` (brief §5 item 7, "three times faster on a decision") turns the five-minute self-check into a permanent webhook alert. The alert would be correct.
7. **`src/content/consent.test.ts` covers only the passing cases.** All four tests run with `REFLEX_HOST:'do'` against a stub that reports consent on the snapshot. There is no test for a cookie refusal on the object host, for a state-read failure, or for the session host at all.
8. **The consent cookies are script-writable.** `SessionManager.ts:569` sets `httpOnly: false` for every cookie except `opt_session_id`. Any script on the page can set `opt_tracking_consent=true`, and the outcome path (`realtime.ts:123`) believes it over the stored record.
9. **A hardcoded grant.** `RealtimeSegmentEngine.processActionEvent` creates a session with `preferences: { trackingConsent: true, personalizationEnabled: true, cookieConsent: true }` (`RealtimeSegmentEngine.ts:430–434`), reachable from `POST /realtime/demo/trigger` (`src/routes/realtime.ts:723`).
10. **A misattributed receipt.** `service.ts:236` writes `"the site's defaults: personalization is off by the shopper's choice"` whenever `!personalizes(consent)` — including `{tracking:false, personalization:true}`, where the shopper allowed personalization. The contract requires every decision to be explained; this one explains it wrongly. The builders' own test asserts the wrong string (`consent.test.ts:81`).

## 6 · Severity, size, remedy

**Severity: blocks launch — agreed.** Not because of the demo D1 capture, but because (a) a contracted capability (§1.11 sort) personalizes a shopper who refused, (b) a refused event is sent to a third-party CDP with a stable pseudonymous id on both hosts, (c) absence and failure both default to consenting, and (d) the site-key-gated API the customer will actually call has no way to say "she refused." These are live-data-safety issues, and the brief's own scale puts those before any pilot with real customer data.

**Size: M–L — agreed.** M for the resolver and the guards on the decision/event/sort paths; L once the SDK consent surface, `/track` + `/pixel` + the queue, the logout/reset paths, and the four-combination test matrix are included.

**Remedy assessment.** Right fix and right direction: one resolved consent value, taken once, carried through both hosts. Under-scoped in naming: it names `/sort` and ODP but not `/track`, `/pixel`, `EventDispatcher`'s queue, or the logout/reset paths that erase the instruction. One item (withdrawing a prior contribution from an unkeyed aggregate) is a design decision, not a guard. Not over-scoped anywhere.

### Smallest safe fix that closes the launch-blocking part

Roughly 3–5 engineer-days, three edits:

1. **`readShopper` (`src/content/service.ts:99–123`):** resolve consent as the *intersection* of the host's stored switches and `consentFromCookies(cookieHeader)` — an explicit `false` from either source wins — and return that same intersection from both `catch` blocks instead of `CONSENTING`. This alone fixes R1 and R2, and makes the self-monitor correct on both hosts instead of alarming on one.
2. **Make refusal expressible on the API:** add `consent?: { tracking?: boolean; personalization?: boolean }` to `ServeRequest` and to the `/v1/:tenant/decisions` and `/sort` request bodies, intersected with (1), so a server-side caller can state it. Closes R4.
3. **Put the three unguarded behavioural writes/egresses behind that one value:** `refreshOdpSeedIfDue` (`RealtimeSegmentEngine.ts:501`, `ShopperReflex.ts:590`), `fanInRegionTrend` (`RealtimeSegmentEngine.ts:468`, `ShopperReflex.ts:554`), `captureDemoEvent` (`realtime.ts:112`); and in `sort.ts` return the platform's order unchanged when `!personalizes(consent)`. Closes R6, R7, R8.

After that, no personalization and no third-party egress under a refusal, and a refusal that a customer can state. The rest of the M–L — the SDK consent API, `/track` + `/pixel` + the queue, preserving the instruction across logout/reset, `httpOnly` on the consent cookies, the misattributed receipt, and the four-combination × two-host × blocked-cookies test matrix — can follow behind the same resolver rather than gating the launch.
