## 3 · Bullet 2 — Deployed provenance and configuration

**Verdict: holds with drift.** The deployed version id, the secrets actually present on each stamp, and the
DNS/hostname routing genuinely cannot be seen from here. But the bullet sweeps in three things the repository
decides today, and the audit should not have left them open.

### 3.1 The binding manifest is in the repository and is complete

A script (`/tmp/audit-verify/S8/bindings-check.mjs`) extracted every `env.X` / `c.env.X` symbol the source
reads (57 of them) and compared them against the three scopes of `wrangler.toml`. Every store binding is
declared in all three environments: `CACHE`, `SESSIONS` (KV), `STORAGE` (R2), `EVENT_QUEUE` (producer and
consumer), `DB` (D1), `ANALYTICS` (Analytics Engine), `ASSETS`, and nine Durable Object classes
(`STATE_MANAGER`, `RATE_LIMITER`, `PERSONALIZATION_WEBSOCKET`, `OpalAgent`, `SHOPPER_REFLEX`,
`MERIDIAN_REFLEX`, `REGION_TREND`, `DECISION_RING`, `LEARN_STATS`), each with its `[[migrations]]` tag.
No `<staging-…>` or `<production-…>` placeholder remains.

Two deliberate asymmetries and one gap:

- `BROWSER` is declared for dev and staging, not production — consistent with "no screenshot route" in
  production, and the reason no headless check can ever run there (§5 below).
- `TREND_ROLLUP_TENANTS` is declared only in dev; staging and production fall back to the code default
  `'coach'` (`src/index.ts:213`, `:240`).
- `GEMINI_API_KEY` is typed **required** in `src/types/env.ts:139` and is declared in no environment and set
  by no provisioning script; the Opal agent path therefore runs with it undefined on every stamp.

What remains open is only the *linkage*: that the deployed Worker version was built from this manifest.
That needs `wrangler deployments list --env <env>` / the dashboard version id, from the Cloudflare account
owner.

### 3.2 The effective auth/consent/key settings, as declared, are decidable — and one of them blocks the customer

`wrangler.toml` sets `AUTH_MODE = "enforced"` in all three environments and `CORS_ORIGINS = ""` in staging and
production. Probing the real middleware (`/tmp/audit-verify/S8/tenancy-key-probe.ts`) with exactly that
configuration:

```
verifySdkKey("anything", "coach", {})              -> {ok:false, status:401, "SDK key not recognized"}
verifySdkKey("", "coach", {})                      -> {ok:false, status:401, "SDK key required"}
verifySdkKey("k1","kate-spade",{SDK_KEYS:"coach:k1"}) -> {ok:false, status:403, "SDK key is for a different tenant"}
originAllowed("https://www.coach.com", …)          -> false
originAllowed("http://localhost:9100", …)          -> true
```

So: the site-key gate **fails closed** when the `SDK_KEYS` secret is absent (no fail-open), cross-tenant key
use is refused, and — the operational point — with `CORS_ORIGINS` empty, an enforced stamp answers **no**
cross-origin browser caller. The customer's lower environment cannot call staging from a page until
`CORS_ORIGINS` is filled in and redeployed. That is a named input for the end-of-October connection, and it
is knowable now.

### 3.3 Customer/brand host mapping is not unverified — it is absent

`src/tenancy/middleware.ts:45` reads the stamp's brands from a `TENANTS` variable
(`{"provisioned":[…],"hosts":{…}}`). **No `TENANTS` is declared in any `[vars]` block of `wrangler.toml`**,
and `wrangler deploy` writes the toml's vars over whatever a dashboard held, so this is settled rather than
unknown. Probing the resolver with the declared configuration:

```
tenantConfig(staging as declared) = {"provisioned":["coach"],"hosts":{}}
  host shop.katespade.com   + X-Tenant: kate-spade  ->  tenant "coach"
  host www.stuartweitzman.com + X-Tenant: kate-spade ->  tenant "coach"
```

Safe (a caller cannot select a brand) and, at the same time, proof that no second brand is served today and
no host maps to one. The audit's `F33` conclusion is therefore reachable from the repository alone.

### 3.4 A methodological correction the record should carry

`src/middleware/auth.ts:49` computes the JWT key as `new TextEncoder().encode(c.env.JWT_SECRET)`. If the
secret is unset, WebIDL's default makes that a **zero-length** key. Under Node (which is what
`vitest.config.ts` runs, `environment: 'node'`) `jose` happily signs and verifies with it — an apparent
"anyone can mint an admin token" fail-open:

```
node:    encode(undefined).length = 0 ; signed: yes ; VERIFIED {"sub":"attacker","roles":["admin"],…}
```

Under real `workerd` (Miniflare, `compatibility_date 2025-06-01`) the same code throws:

```
workerd: {"keyLength":0,"threw":"DataError: Imported HMAC key length (0) must be a non-zero value …"}
```

So the deployed behaviour is fail-closed (a stamp missing `JWT_SECRET` is unusable, not exploitable). The
lesson for the audit record is the general one: this suite never sees the runtime it ships to, so
runtime-specific behaviour is invisible to it — and Miniflare probes, which need no network and no deploy,
can close a class of questions the audit filed as unverifiable.

## 6 · Bullet 5 — Scientific/business evidence

**Verdict: holds with drift.** "Replay and unit tests alone cannot prove lift" is right, and every
customer-data item in the bullet stands: historical data with provenance, CVR/RPV/margin/returns feeds,
production baseline parity, the customer's DS review and a valid experiment. But four sub-items are
decidable now, without one row of customer data, and the audit files them all under "needs the customer".

### 6.1 Allocation is correct (a positive result)

`/tmp/audit-verify/S8/holdout-probe.ts`, 200,000 synthetic ids per shape, `share = 0.05`:

```
[alloc uuid-like]   share=0.0510  sticky=true  uniform-blocks-of-10=11880/20000
[alloc sequential]  share=0.0500  sticky=true  uniform-blocks-of-10=12001/20000
```

Both match the configured share, assignment is deterministic, and consecutive ids are not block-sampled
(0.95¹⁰ = 0.5987 predicts ≈11,974 blocks; both shapes land on it). The `mix32` finalizer added on
2026-09-04 (`src/content/holdout.ts:22`) does what its comment claims.

### 6.2 Permanence is one config edit away

`HoldoutConfig.salt` is an operator-editable field documented as "Rotated to reassign"
(`src/content/types.ts:87`), and `src/content/service.ts:168` defaults it to the brand. Rotating it moves
**9,644 of 100,000 visitors (9.64%)** across arms — exactly the 2·0.05·0.95 = 9.5% the geometry predicts —
and nothing in the decision record marks the rotation. The customer's paper asks for a *permanent* holdout;
permanence here is a convention, not a mechanism.

### 6.3 The estimator is wrong independently of what the customer agrees

`src/learn/report.ts:129` counts **decisions** per arm and `:136` hands those two counts to
`compareArms`, which treats them as independent Bernoulli trials. Simulating a null effect with per-visitor
clustering (each visitor draws a propensity, both arms from the same distribution, so the true difference is
exactly zero) and asking how often a verdict is called at 95%:

```
 300 visitors/arm x 20 decisions: called in 136/400 runs (34.0%)   nominal 5%
1000 visitors/arm x 20 decisions: called in 120/400 runs (30.0%)   nominal 5%
2000 visitors/arm x  8 decisions: called in  62/400 runs (15.5%)   nominal 5%
```

Three to seven times the nominal false-positive rate. This quantifies `F07`'s qualitative sentence and needs
no customer agreement to establish: whatever unit the customer signs up to, the present routine will
manufacture winners.

Two adjacent facts, both from code: exploration cannot contaminate the control, because the default arm
disables learning and exploration entirely (`src/content/decide.ts:88`, `:69`) — a point in the design's
favour; but consent-declining traffic is recorded in the same `arm: 'default'` field
(`src/content/consent.ts:46`, `src/content/service.ts:168`) and `report.ts:127–136` groups on `arm` with no
filter, so the control mixes randomized visitors with a self-selected subpopulation. The only marker is a
free-text `explain.note` set at `service.ts:236`.

### 6.4 Doc 22's recomputability promise holds — to 1.0e-2, not exactly

Doc 22 promises a customer's data scientist can recompute the lift table from the ledger. Reimplementing
§5.2 and §5.4 **from the document alone** and running it against `src/learn/stats.ts` over the same 4,000
synthetic events (75 item/level rows):

```
WITHOUT the engine's per-level r3(p0):  max |Δp̂| = 1.00e-3, max |Δlift| = 1.00e-2
WITH    the engine's per-level r3(p0):  max |Δp̂| = 0.00e+0, max |Δlift| = 0.00e+0
```

The arithmetic is fully reproducible, and the constants match the document (`DEFAULT_STATS` in
`src/learn/stats.ts:20`: `n0 30`, `tau 21 days`, `liftMin 0.5`, `liftMax 2`, `nMin 30`; the six-level ladder
in `levelKeys` matches §5.4 Level 0–5 with the journey stage after the visit bucket). The one gap: the engine
rounds each level's p₀ to three decimals **and reuses the rounded value as the next level's shrinkage
target**, which doc 22 does not say. A DS working from the document gets the third decimal of p̂ and the
second decimal of lift, not the published number. One sentence in doc 22 §5.2, or round only for display,
closes it. That is a delivery-side fix, not a customer question.

## 8 · Bullet 7 — Operational/privacy completion

**Verdict: partly does not hold.** Four of this bullet's items are decidable from the repository, and three
of those are not "unverified" — they are absent or defective now.

### 8.1 Late-backfill suppression is broken (reproduced)

`src/ledger/erasure.ts` hides a row when its visitor is tombstoned and `rec.ts <= erased_at`, and the nightly
rewrite walks days newest-first from the erasure day back over the retention window, recording
`done_through` and **never revisiting a cleaned day** (`nextOf`: `prevDay(t.done_through)`). When the window
completes, the tombstone is *deleted* and replaced by a hashed audit row — so read-time suppression ends too.
Harness (`/tmp/audit-verify/S8/erasure-backfill.ts`, fake R2, erasure at 2026-09-06 12:00Z):

```
run1 {"days":91,"rows_removed":2,"retired":1,"remaining":0,"more":false}
tombstones pending after run1: 0
   … a pre-erasure row for the same visitor then lands in an already-cleaned day …
run2 {"tombstones":0,"days":0,"rows_removed":0}
late row hidden at read time? false
late row survives withoutErased? true
ledger objects still holding the erased visitor: [ 'coach/2026-09-04/13/decision/x-y-late.ndjson' ]
```

One nightly run retires the tombstone (the day after the request). Any row for that visitor timestamped at or
before the erasure that materialises afterwards — a retried or backlogged queue message, a re-import, a
replayed batch; objects are keyed by the record's own timestamp (`writer.ts`, `hourPrefix(id.tenant, id.ts)`),
not by arrival — is then neither hidden by any reader nor removed by any later pass. It stays in the R2
partition that is also the warehouse export. This is a finding, not an evidence request.

### 8.2 Erasure lag is computable from the team's own volume figure

The nightly job calls `rewriteErasures` with the default cap of **5,000 objects** per run
(`src/index.ts:231`, `erasure.ts:157`), sequentially listing, reading and rewriting each. Doc 31 states that
at the design's volume (a million decisions a day) "even hundred-record objects are thousands a day". A
90-day window is therefore of order 10⁵–10⁶ objects, so a single full pass takes roughly **18 to 180 nightly
runs**. All pending tombstones share one pass over a day, so this is a per-pass cost, not a per-erasure one —
but the physical deletion still lags the request by months at that volume, while the tombstone carries the
whole burden of hiding the rows. Worth stating before a privacy team asks.

### 8.3 Cross-host deletion: Analytics Engine does hold identifiers

`src/identity/erase.ts` states that "Analytics Engine holds aggregate points with no identifier worth
erasing", and the receipt's `notReached` lists only ODP. True of the learning ledger's points
(`src/ledger/enqueue.ts:29`, `:41` — tenant/brand/page/slot/item/arm, indexed by tenant). Not true of the
older ingestion routes: `src/routes/tracking.ts:33` writes `blobs: [JSON.stringify(enrichedEvent), …]` and
`indexes: [user.userId || user.anonymousId]`, and `src/routes/pixel.ts:48` writes the whole event plus
`indexes: [user.anonymousId]`. Analytics Engine has no per-row delete. Either those routes stop carrying
identifiers, or the receipt must say so. Separately, D1 `demo_events` holds `vuid` per action and no erasure
touches it; capture is off when `ENVIRONMENT = 'production'` (`src/routes/realtime.ts:778`) but **on for
staging**, which is where the customer's lower environment connects.

### 8.4 Non-rotating reconcile/restore does not exist

`scripts/provision-stamp.sh:48–50` unconditionally generates and puts `JWT_SECRET`, `IDENTITY_SALT` and
`SDK_KEYS` on every run; there is no `--reconcile`, no idempotent path, and no second script. The header's
"re-running reports already exists and continues" is about resources, not secrets. Rotating `IDENTITY_SALT`
changes every derived shopper id; rotating `SDK_KEYS` breaks every embedded site key. The evidence the audit
asks for cannot be produced because the artefact does not exist — this is delivery-track work, not a customer
or account question.

### 8.5 Migrations, retention and alert delivery

- **Rollback drills**: `migrations/` holds `0001`–`0010` and a `seed/` directory; a grep for `DROP TABLE`,
  `-- down` or `ROLLBACK` across it returns nothing. There are no down-migrations, so there is nothing for a
  drill to exercise.
- **Retention**: `LEDGER_RETENTION_DAYS` is declared in no environment, so the code default of 90 applies
  (`erasure.ts:56`, `:75`). `src/types/env.ts:32` says it "must match the R2 bucket's lifecycle rule", and no
  script or configuration sets one — bucket lifecycle is account-side. KV holds its own TTLs
  (`src/identity/store.ts` link TTL; `src/ops/monitor.ts` 7-day monitor rows), so the un-retained stores are
  R2 and Analytics Engine. Closing this needs the Cloudflare account owner (`wrangler r2 bucket lifecycle`)
  plus Tapestry's privacy team agreeing the number.
- **Alert delivery**: `ALERT_WEBHOOK_URL` is read at `src/ops/monitor.ts:92` and documented in
  `docs/kit/02-api-reference.md:214` as a worker secret — and is set by **no** provisioning script. Delivery
  and on-call ownership remain open, as the audit says; the reason is now specific.
- **Committed material**: the only secret-shaped literal in the tracked tree is the development placeholder
  `JWT_SECRET = "development-secret-key-change-in-production"` (`wrangler.toml:159`). Whether previously
  committed material was revoked is a Cloudflare/Optimizely account-owner record; no repository state can
  show it, and no secret value needs to be disclosed to produce that receipt.

### 8.6 Addition the audit does not raise anywhere: no dead-letter queue

None of the three queue consumers in `wrangler.toml` (`events`, `events-staging`, `events-production`)
declares a `dead_letter_queue`, and all set `max_retries = 2`. `src/index.ts:262` retries the **whole ledger
batch** when R2 fails. A message that exhausts its retries with no dead-letter queue configured is discarded
by Cloudflare, so a sustained R2 problem silently loses decision and outcome records — the substrate under
the day report, the lift table, the holdout comparison, replay and the DS export — and nothing counts the
loss. Unplaceable messages are also acknowledged and dropped by design (`consume.ts`, logged only). A
dead-letter queue plus a drop counter in the monitor is a small change and belongs on the evidence list.
