### 1.1 The truncation is real and the label is false

`datesBetween` caps at 92 dates. `windowReport` returns the **requested** `to`. The 89 dates it never opened are
not in `days` and **not in `missing`** — `missing` only ever lists dates the loop actually visited. Reproduced:

```
P1 report: from 2026-01-01 to 2026-06-30 | days read 92 | last day read 2026-04-02 | missing 0
           keys on the object: tenant,brand,from,to,days,missing,confidence,slots
P1 decisions pooled: 92000 of a true 181000 (51%)
```

A six-month request returns a document labelled `2026-01-01 → 2026-06-30` containing **51 %** of the period, with
an empty `missing` array asserting nothing was skipped. The console (`public/console/views-measure.js:112`) then
prints the card subtitle *"Every day from 2026-01-01 to 2026-06-30 that has a report, added together"* — a false
sentence, generated from the false label.

**92 days is exactly one calendar quarter** (Q3 = Jul 1–Sep 30 = 92 days). So monthly and quarterly work; the cap
sits one day above the largest quarter and roughly half of a bi-annual window. That is the crux for acceptance:
`docs/architecture/26-btie-requirements-gap-review.md:142` marks the requirement *"Aggregate over windows, not
point-in-time; **monthly, quarterly, bi-annual**"* as **✅ closed** by this route, and
`docs/architecture/21-tapestry-gap-closure-plan.md:146` records D4 as **Done 2026-09-05**. Bi-annual is not
delivered; it silently returns half.

### 1.2 The completeness flags exist and are thrown away

This is stronger than the audit says. `DayReport` already carries two completeness signals
(`src/learn/report.ts:45,57`):

- `counts.truncated: boolean` — set when any folded hour hit the 600-object cap (`hourly.ts:46,324`)
- `hours: { source, built: number[], missing: number[], horizonMs }` — the closed hours not yet folded

`window.ts` imports the very type that declares them and reads only `report.holdout`. The nightly job logs both
(`src/index.ts:226` prints *"(21 hour(s) unfolded) (truncated)"*), so incomplete days are a **normal operating
condition**, not a hypothetical. Reproduced:

```
P2 every day truncated with 21/24 hours unfolded -> days 31 missing 0
   any completeness field on the result? 0        (regex over the whole JSON: no match)
```

Thirty-one days each built from 3 of 24 hours pool into a clean-looking month with `missing: []`. Worse than a
precision loss: unfolded hours are the **late** hours of a day, so the surviving sample is a systematically
different traffic mix, which biases the arm comparison, not merely its width.

### 1.3 "Decisions still needed" — the number is fixed at 95 % and assumes equal arms

```
P3 neededPerArm at 90/95/99: 21109 21109 21109     (z used for the intervals: 1.645 / 1.960 / 2.576)
```

`compareArms` honours the operator's chosen confidence everywhere except here. Pick 99 % in the console and the
intervals widen while the "how long until we know" number silently stays a 95 % number.

The equal-arm assumption errs in **both** directions at once, which matters for how you describe it:

```
P3 equal-arm per arm:            80,682  => the sentence implies 161,364 decisions of traffic
P3 true 5 %-holdout control arm: 41,925  => total site traffic 838,500
P3 understatement of total traffic: 5.2x
```

(2.0 % control vs 2.2 % treatment — the contracted +10 % minimum, 19:1 allocation.) So the shipped number is
~1.9× **conservative** as a gate on the control arm ("not yet" for longer than necessary), while the plain reading
of the sentence — "we need about 161 k decisions" — is **5.2× optimistic** about the traffic and therefore the
calendar. Neither number is the one a pilot plan needs.

### 1.4 The relative-lift interval, and the target verdict built on it

`readTargets` scales the Newcombe absolute interval by the control **point** rate, which ignores all uncertainty
in the denominator. Reproduced against the standard Katz log method and against Fieller:

```
P4  control 30,000 @2.0 %, treatment 570,000 @2.4 %  (a month at 20k/day, 5 % holdout)
    shipped relative interval : +12.0 % to +28.0 %   standing: reached_minimum
    Katz relative interval    : +10.7 % to +30.1 %
    width: shipped 16.0 pts of relative lift vs Katz 19.4 pts  (18 % too narrow)
```

A 756-shape sweep over commercially realistic volumes (5 k/20 k/100 k decisions per day × 7/28/92 days × 0.5/1/2/5 %
control CVR × +10 %…+80 % lift × 90/95/99 %):

```
shapes 756 | target rung too GENEROUS 83 | too conservative 0 | agrees 673
relative-low end above the correct one (too narrow, flattering): 608 | below: 148
  conf 0.9  5000/d x28d cvr 0.02 lift 80%: shipped reached_stretch  low 65.0% vs correct 56.5%
  conf 0.9  5000/d x28d cvr 0.02 lift 60%: shipped reached_target   low 45.0% vs correct 39.1%
  conf 0.9  5000/d x7d  cvr 0.02 lift 45%: shipped reached_minimum  low 12.5% vs correct  9.5%
```

**Zero shapes err conservatively.** 11 % of them award a target rung the data does not support, and the sentence
that reaches the customer is *"against the pre-set targets … the target is reached, the low end of the interval is
+45 %."* That is the audit's "overstates statistical readiness", measured.

## 3 · Severity and size

**Severity: blocks the pilot.** I agree with the audit, and I would name the escalation condition it leaves
implicit: the brief's *blocks launch* category covers "representations that the full contracted capability is
delivered". `26-btie-requirements-gap-review.md:142` is exactly such a representation — a ✅ against the customer's
own "monthly, quarterly, bi-annual" line. **If that row goes to the customer as delivered, this becomes blocks
launch.** The other half of the finding — the flattering target verdict — is not gated on long windows at all: it
is reachable today in the nightly day report (`report.ts:136`) and the hourly build (`hourly.ts:313`), which call
`compareArms` with the same defaults.

**Size: M overall, but split differently than the audit implies.** The audit's own remedy paragraph contains a
clause that is not an M and not part of this defect: *"Separate CVR, RPV, profit, and returns targets."* The holdout
arm rows are unweighted counts — `report.ts:112–115` increments `credits += 1` per credit regardless of value —
so RPV and profit have **no data path into the arm comparison** even though `value` and `margin` exist on
`OutcomeRecord` (`records.ts:24,27`); and there is no return/refund reward type at all
(`RewardType` = click | dwell | video_complete | wishlist | add_to_bag | purchase | custom), with `creditWeight`
returning 0 for any non-positive value, so a return cannot even be credited negatively. That clause is a new
metric pipeline plus continuous-outcome uncertainty (Wilson and Newcombe do not apply to revenue per visitor) —
**L, and it belongs in its own finding.** What remains in F25 is M, and the pilot-blocking core inside it is S
(§7).

## 4 · What the audit got wrong

1. **The retention sentence names the wrong mechanism.** "Retention of ninety days also needs reconciliation with
   six-month-plus measurement" reads as though retention would starve a six-month window. It would not.
   `windowReport` reads **day-report aggregates** at `reports/{tenant}/{brand}/{date}.json` (`report.ts:182`), and
   nothing in this repository ever deletes them. `LEDGER_RETENTION_DAYS` / `DEFAULT_RETENTION_DAYS = 90`
   (`erasure.ts:56,75`) is used in exactly one place — to bound how far back `rewriteErasures` scans for a
   *tombstone* (`erasure.ts:153–205`). There is no time-based purge of ledger objects in code at all. The real
   reconciliation issues are different and should be stated as such: (a) a day whose report was never built can
   never be rebuilt once its raw ledger ages out under whatever R2 lifecycle policy exists outside this repo, and
   it stays in `missing` forever; (b) the nightly erasure rewrite touches the ledger only, so an erased visitor's
   rows remain inside already-built day-report aggregates and keep being pooled — aggregate-only and probably
   defensible, but undocumented.
2. **"Silently" is a shade too strong.** The API does return `days` and `missing`, and the console toolbar prints
   *"92 days read"*. A diligent operator comparing 92 against a 181-day request could catch it. What is genuinely
   absent is any *statement* of truncation, and the `to` label plus the card subtitle actively assert the opposite.
   Say "returns a truncated period under the full period's label, with no truncation flag" rather than "silently".
3. **The sample-size error is described as one-directional and is not.** "Estimates samples using equal arms" is
   correct, but the consequence is two-sided (§1.3): conservative as a gate on the control arm, ~5× optimistic as a
   traffic/calendar estimate. A remediator reading only the audit may "fix" it in the wrong direction.

Nothing else in the finding is wrong. Every line number is exact; the April 2 arithmetic is right for 2026 (it
would be April 1 in a leap year); the remedy list is otherwise sound.

## 5 · What the audit missed, adjacent to this finding

1. **The window report is not authenticated.** Every other sensitive route in `decisions.ts` carries
   `jwt({ required: true })` — `:178, :198, :223, :288, :295, :355, :381, :416, :434, :493, :513, :533`. The two
   report GETs, **`:568` (window)** and `:580` (day), carry none. The only gate is `app.use('/v1/:tenant/*', sdkKey())`
   (`index.ts:86`), and `sdkKey()` accepts the **public site key** from `X-SDK-Key` *or* the `?sdkKey=` query
   (`edgeAccess.ts:118`) — the key that ships inside the customer's storefront JavaScript — and returns `next()`
   unconditionally when `AUTH_MODE` is not `enforced` (`edgeAccess.ts:117`). So anyone who can view source on the
   storefront can read per-arm conversion rates, incrementality intervals and target standing for the brand. The
   console's own error handler expects 401/403 here (`views-measure.js:37`), so this looks unintended. The audit's
   authorization finding names `config.ts:123` and `identity.ts:175` as "only jwt"; it does not name these two as
   **no jwt**. Brief §6 records that staging still accepts the example key printed in the repo.
2. **The pre-set targets are hardcoded to one customer.** `TAPESTRY_TARGETS = {0.10, 0.40, 0.60}` is the only
   target definition in `src/`. All three call sites (`window.ts:81`, `report.ts:136`, `hourly.ts:313`) pass no
   `targets`, so the `undefined` default applies, and the route offers no way to supply one. Reproduced: a report
   for tenant `acme-outdoors` reads *"against the pre-set targets (minimum +10 %, target +40 %, stretch +60 %
   relative)"*. `21-tapestry-gap-closure-plan.md:146` claims "a tenant may set its own" — true only of the function
   signature; no configuration document, route or console field reaches it. This is the concrete form of the
   audit's "no versioned metric/target protocol", and it is a *fix before the next customer* portability gate in
   its own right.
3. **Visitor clustering has an evidence line the audit did not give.** The arm is assigned per **visitor**
   (`content/holdout.ts:36 armFor`, sticky hash), but `n` and `s` are per **decision** (`report.ts:112–115`,
   pooled at `window.ts:69` as `{ n: r.decisions, s: r.credited }`). Wilson, Newcombe and `neededPerArm` all treat
   correlated decisions from one visitor as independent trials, so every interval is too narrow by roughly
   √(1+(m−1)ρ). The day report carries `counts.visitors` for the day but **not per arm**, so the design effect
   cannot be computed from what is stored — this is the part of the remedy that actually costs weeks.
4. **A second, independent way the same failure happens: 4-decimal rounding of the divisor.** `wilson()` returns
   `p: r4(p)` (`holdout.ts:143`), and that rounded value is the denominator at `:190,192` and `:238`. Reproduced:
   control 3/40,000 (0.0075 %) vs treatment 95/760,000 (0.0125 %) — a genuine +67 % relative lift — reports
   `relative: 0`, `relativeLow: −1`, `relativeHigh: +1`, `standing: below`. At 2/100,000 the control rate rounds to
   `0` and the comparison answers *"the pre-set targets cannot be read against a control rate of zero"*. Harmless
   for click-rate slots at ~2 %; wrong by ≥10 % of the denominator below a 0.05 % rate — i.e. exactly the
   purchase-reward slots the customer cares about.
5. **A shipped test locks in the flattering verdict.** `src/measure/holdout.test.ts` (the *"judges on the low end
   of the interval, not the point estimate"* case, `big`) asserts `reached_target` for 3.0 % → 4.5 % at
   20,000/400,000. Re-examined:
   ```
   shipped standing: reached_target | shipped relative low 41.33 %
   Katz    low 38.46 %  ->  reached_minimum
   Fieller low 38.85 %
   ```
   The suite's other three rung assertions happen to sit on shapes where both methods agree, so the defect is
   invisible to the suite. Fixing `readTargets` will turn this green test red — that is the correct outcome, and
   whoever remediates must expect it.
6. **`window.test.ts` never exercises the failure.** `datesBetween` is tested for the cap
   (`expect(datesBetween('2020-01-01','2030-01-01')).toHaveLength(MAX_WINDOW_DAYS)`) but nothing asserts what the
   *caller* is told, and no `windowReport` test uses a window longer than 3 days. Its fixture (`window.test.ts:10`)
   builds day objects with no `counts` and no `hours` — the tests themselves document that those fields are never
   read. The cap itself was deliberate ("capped so a typo cannot ask for a decade", `window.ts:38`); the defect is
   that a deliberate cap was never given a way to announce itself.
7. **Heterogeneous days pool without a check.** `windowReport` sums `holdout` rows across days that may have been
   built under different attribution policies, slot rewards, objectives or holdout shares. `builtAt` and the policy
   list are on each `DayReport` and are discarded. A window spanning a configuration change silently mixes regimes.
8. **Minor:** a reversed range (`from` > `to`) yields `datesBetween → []`, so the route answers `200 ok` with an
   empty report rather than a 400.

## 7 · Remedy assessment, and the smallest safe fix

The audit's remedy is **right in direction, over-scoped in one clause, under-scoped in another.**

- Over-scoped: "Separate CVR, RPV, profit, and returns targets" is a new metric pipeline (§3), not a fix to
  `holdout.ts`. Split it out or F25 will never close.
- Under-scoped: "allocation-aware power/uncertainty calculations" quietly requires **per-arm visitor counts**,
  which the day report does not store. That is a schema change across `hourly.ts` → `report.ts` → `window.ts` with
  a version field, and it is the only genuinely multi-week item here.
- Missing from the remedy: per-tenant targets (§5.2) and authentication on the report GETs (§5.1).

**Smallest safe fix — 1–2 engineer-days, closes the pilot-blocking core:**

1. `window.ts` — when `datesBetween` truncates, stop lying about the period. Either return `400` at the route with
   the maximum stated, or set `to` to the last date actually read and add `requestedTo`, `requestedDays`,
   `readDays`, `truncated: true` to `WindowReport`; render it in `views-measure.js` (the card subtitle already
   interpolates `window.to`, so honesty propagates for free).
2. `window.ts:63` — carry completeness through: `incomplete: string[]` for any day with
   `counts.truncated || hours?.missing.length`, and **suppress the target `standing` (force `undecided`) whenever
   the window was truncated or any pooled day is incomplete.** That single suppression rule is what stops a
   three-month, partly-folded sample from producing "the target is reached".
3. `holdout.ts:188–199` — replace `difference.lo / controlRate` with the Katz log relative interval
   (`exp(ln(p_t/p_c) ∓ z·√((1−p_t)/s_t + (1−p_c)/s_c)) − 1`), computed from **raw** rates, not `r4`-rounded ones.
   Five lines. Re-baseline the one shipped assertion in §5.5.
4. `holdout.ts:165` — take `z` as a parameter so `neededPerArm` uses the operator's chosen confidence, and either
   state the number allocation-aware ("at the current 5 %/95 % split, ≈N decisions of site traffic") or stop
   printing it until §5.3 lands. Do not leave a 95 % number under a 99 % heading.

Items 1–3 are what a finance team's acceptance turns on. Items 5.1 (auth) and 5.2 (per-tenant targets) are each a
few hours and should ride along; the clustering-aware statistics and the metric expansion follow as scheduled work.
