# F32 — Whole-catalog KV documents and repeated full sorts do not support arbitrary catalog scale

**Independent verification.** Repository `__cloudflare_base`, branch `feature/real-time-personalization`,
HEAD = `c10ccff7303d06492e4acdf932fc70273d7159ac` — **identical to the commit the audit names**, so no
drift is possible between the audited tree and the verified tree. Working tree carries only
`public/meridian/engine.bundle.js` (modified) and two untracked docs; nothing under `src/` differs from
the audited commit.

**Verdict: CONFIRMED.** Every code citation holds. Two of the audit's three measured numbers are
**understated** — both in the direction that makes the finding worse. One line citation drifted by 22
lines inside the correct function. Nothing in the finding is refuted.

## 1 · Evidence claims, checked one by one

### 1.1 `src/config/versionedStore.ts:243` duplicates the document under `value` and `config` — HOLDS, exact line

```
241	  // `config` is written alongside `value` so a build that predates this
242	  // generalization can still read what a newer build wrote.
243	  const body = JSON.stringify({ ...revision, config: value });
244
245	  await env.CACHE.put(keyRevision(kind.name, scope, revisionNumber), body);
246	  await env.CACHE.put(keyCurrent(kind.name, scope), body);
```

The line number is exact. Three things the audit did not say, all verified:

* The read side never uses it. `coerce()` at `:199` is
  `const body = 'value' in envelope ? envelope.value : envelope.config;` — `value` always wins. The
  duplicate is dead weight for every build that writes it.
* `git log -S "config: value"` puts its introduction in **`1877fc6`, 2026-09-02**. Staging was
  provisioned 2026-09-04 and production 2026-09-05 (both after). So the compatibility window this line
  exists for has already closed on every environment this programme runs. *(I could not attest live
  Worker versions — calling `*.workers.dev` is out of scope for this verification.)*
* The same body is `put` **twice** (`:rev:N` and `:current`, lines 245–246), and **no revision body is
  ever deleted** — `versionedStore.ts` contains no `CACHE.delete` and no `CACHE.list`. `INDEX_LIMIT = 50`
  trims the browsable index, not the bodies. Net: **4× the raw catalog in KV per import, forever.**

### 1.2 `src/reflex/contentCompose.ts:116` filters/maps/sorts the live corpus per slot — BEHAVIOUR HOLDS, LINE DRIFTED

Line 116 is `const live = pieces.filter(...)`, which runs **once per call**, not per slot. The per-slot
work the sentence describes is 22–40 lines below, in the same function:

| line | code | cost |
|---|---|---|
| `:116` | `const live = pieces.filter(p => (p.lifecycle?.status ?? 'live') === 'live')` | O(n), once |
| `:119` | `const rank = new Map(pieces.map((p,i) => [p.id, i]))` | O(n), once, over **all** pieces incl. non-live |
| `:138` | `const eligible = live.filter(p => p.slotTypes.includes(slot.slot) && !used.has(p.id))` | O(n) **per slot** |
| `:139–155` | `.map(...)` scoring every eligible piece, allocating a `drivers` array per piece | O(n·dims) **per slot** |
| `:156` | `.sort((x,y) => y.score - x.score \|\| rank … \|\| id)` | O(n log n) **per slot** |
| `:169` | `scored.slice(0, candidateLimit)` — only 10 survive | the full ordering was never needed |

So the claim is true of the function; the anchor should read `contentCompose.ts:138`, `:139`, `:156`.

### 1.3 `src/content/decide.ts:78` also builds full-catalog structures — HOLDS, exact line

```
78	  const eligible = i.pieces.filter((p) => isEligibleAt(p, i.nowMs));
79	  const byId = new Map(i.pieces.map((p) => [p.id, p]));
```

Both are whole-catalog. `:78` is also **redundant with `contentCompose.ts:116`**: `isEligibleAt` →
`isLiveAt` already tests `lifecycle.status === 'live'` (`src/content/lifecycle.ts:19`), and the composer
re-tests exactly the same predicate on the set `decide` just filtered. Two full scans where one suffices.

### 1.4 `/sort` caps candidates at 500 (`src/routes/sort.ts:33`) — HOLDS, exact line, and it is tested

`const MAX_CANDIDATES = 500;` at `:33`, enforced by zod at `:39`. `src/routes/sort.test.ts:62`
("bounds the candidate set, because a page of results is not a catalog") posts 501 candidates and asserts
400. I ran it: 5/5 pass in 118 ms. **The audit's caveat is correct and protected.** Good discipline —
that sentence should survive into the remediation record unchanged.

### 1.5 KV 25 MiB value limit / Worker 128 MB isolate limit — correct as stated

Both are the documented Cloudflare limits, correctly applied. No `[limits]` block exists in
`wrangler.toml`, so plan defaults apply.

### 2.1 Stored envelope size — `sizeProbe.ts`, using the **real** `write()` and the **real** `CONTENT_KIND` validator

| shape | n | pieces array | **KV envelope** | amplification | > 25 MiB |

> The audit is conservative by ~3.4×.

Removing the `config` duplicate alone moves that wall to ~49,500 pieces.

### 2.3 The read path — the cost the audit did not measure

`serveContentDecisions` (`src/content/service.ts:137`) reads the catalog through
`versionedStore.readRevision`, whose isolate cache has a **30-second TTL** (`CACHE_TTL_MS`,
`versionedStore.ts:37`, checked at `:144`). On every miss the decision path **re-parses the whole
envelope and re-runs `validateContentCatalog`, rebuilding every piece object**:

| n | envelope | `JSON.parse` | `validateContentCatalog` | **parse + validate** |
|---|---|---|---|---|
| 10,000 | 8.92 MiB | 139.6 ms | 80.9 ms | **149.0 ms** |
| 100,000 | 89.41 MiB | 520.3 ms | 385.8 ms | **1,438.2 ms** |

This is the dominant cost, and it is not a scale-only problem: it lands on the brief's own open target
(§6, "Decision latency for a new shopper … Target: under 200 ms at P95 on the server").

### 2.4 What the `config` duplicate costs on **read** — `dupProbe.ts`

| n | envelope as written | without `config` | parse as written | parse value-only | duplicate costs |
|---|---|---|---|---|---|
| 10,000 | 8.92 MiB | 4.46 MiB | 85.7 ms | 27.4 ms | **+58.2 ms (+212%)** |
| 50,000 | 44.70 MiB | 22.35 MiB | 362.4 ms | 188.0 ms | **+174.4 ms (+93%)** |

Every isolate-cache miss pays that, to parse a field no current build reads.

### 2.5 Isolate heap — `dupProbe.ts` probe 4b, `--expose-gc`

| n | JSON | retained after parse + validate | bytes/piece |
|---|---|---|---|
| 1,000 | 0.45 MiB | ~1.3 MiB | 1,335 |
| 10,000 | 4.46 MiB | ~11.2 MiB | 1,173 |
| 50,000 | 22.35 MiB | ~49.6 MiB | 1,041 |

**~100,000 pieces retained fills the 128 MB isolate** — and `isolateCache` (`versionedStore.ts:120`) is a
plain `Map` with **no size bound and no eviction**: entries are replaced on re-read but a scope that goes
quiet keeps its full catalog forever. That is one catalog per `(kind, scope)` for every scope the isolate
has ever served. Ten tenants × 20,000 pieces ≈ 230 MB retained → the isolate dies. The audit called this
"a further design risk"; it is a named, measurable mechanism.

`docs/architecture/28-operator-surfaces-evaluation.md:26` states the design scale: *"hundreds of content

|---|---|---|---|---|---|---|
| 200 | 0.18 MiB | no | 1.8 ms | 1.8 ms | 3.6 ms | 1.8 ms |
| 1,000 | 0.89 MiB | no | 4.5 ms | 2.2 ms | 6.7 ms | 2.2 ms |
| 2,000 | 1.78 MiB | no | 10.7 ms | 4.3 ms | 15.0 ms | 4.3 ms |
| 5,000 | 4.46 MiB | no | 22.6 ms | 13.0 ms | 35.6 ms | 13.0 ms |
| 10,000 | 8.92 MiB | no | 53.7 ms | 38.7 ms | **92.4 ms** | 38.7 ms |
| 25,000 | 22.34 MiB | no (one revision short) | 224.1 ms | 113.6 ms | **337.7 ms** | 113.6 ms |

**This is the table the team should act on.** At the launch corpus (hundreds of pieces) nothing is wrong.
The design's practical ceiling is **≈20,000–25,000 pieces per scope**, and the *latency* wall arrives
before the *size* wall.

### 2.7 Is the audit's remedy worth the money? — `topkProbe.ts`

I wrote a top-k selector with the **identical comparator** (score desc → catalogue order → id) and
compared it to the shipped full sort:

| n | shipped (full sort) | top-k selection | speedup | identical output |
|---|---|---|---|---|
| 10,000 | 44.5 ms | 8.0 ms | **5.5×** | decisions ✓ candidates ✓ |
| 100,000 | 348.0 ms | 87.8 ms | **4.0×** | decisions ✓ candidates ✓ |
| 300,000 | 1,267.3 ms | 348.1 ms | **3.6×** | decisions ✓ candidates ✓ |

The winners and the recorded candidate sets are **byte-identical**. The audit's "top-k rather than full
ordering" is validated.

**Honest caveat the team must carry:** my top-k ranks on the base tag score only. The shipped composer
applies `ScoreAdjust` (`contentCompose.ts:154`) — lift^γ, external model, merchandising, journey stage,
freshness, fatigue — *inside* the per-piece map, and those can reorder. With any of them configured,
top-k becomes a **two-stage retrieve-then-rerank**, which can change what is served when the adjustment
promotes a piece from outside the base top-K. That is exactly the audit's phrase "candidate-preserving
edge reranking", and it needs a quality test, not just a benchmark. It is not a free optimisation.

## 3 · What the audit got wrong

1. **`contentCompose.ts:116` is not the per-slot line.** It is the once-per-call live filter. The per-slot
   filter/map/sort is `:138`, `:139`, `:156`. Fix the anchor before the remediation ticket is cut, or an
   engineer will look at line 116 and see an O(n) pass that runs once.
2. **37.42 MiB / 113.52 MiB understate the wall by ~3.4×.** Their synthetic piece is ~392 envelope bytes;
   the real shipped catalog's pieces are ~1,059. The 25 MiB limit is crossed at ~24,700 pieces, not
   ~67,000. The audit's own numbers are internally consistent — they simply used a thin synthetic piece
   and did not calibrate against `public/data/coach-content.json`.
3. **502.1 ms for a 300,000-piece ranker run is understated by 2.5–6.5×.** Over the shipped three-slot
   home page with a real tag shape: 1,586 ms (one slot type per piece) to 3,297 ms (all three).
4. **"Size: M–L" over-scopes what actually needs doing.** Shards, slot/locale/eligibility indexes and ANN
   retrieval are L and nothing currently committed needs them. The part that closes the real risk is
   S–M (see §6).
5. **Nothing is overstated.** Every correction I found makes the finding worse, not better. The `/sort`
   caveat is scrupulously fair and is backed by a passing test.

## 4 · What the audit missed (adjacent, same code path)

1. **The read path is the dominant cost, and it was not measured.** Parse + re-validate the whole catalog
   on every 30-second isolate-cache miss: 92 ms at 10,000 pieces, 1,438 ms at 100,000
   (`versionedStore.ts:144`, `:148`, `:200`). This collides directly with the brief §6's open 200 ms P95
   target — which makes F32 relevant *now*, not only at "arbitrary scale".
2. **The `config` duplicate is a read-path cost, not just a storage cost:** +58 ms parse at 10,000 pieces,
   +174 ms at 50,000, for a field `coerce()` never reads when `value` is present.
3. **Every revision body is retained forever.** `write()` puts the same body to `:rev:N` and `:current`
   (`:245–246`) and nothing ever deletes a revision. A nightly re-import of a 20 MiB catalog adds ~40 MiB
   of KV permanently. `INDEX_LIMIT = 50` hides the growth, it does not stop it.
4. **`isolateCache` is unbounded and never evicts** (`versionedStore.ts:120`, `:155`). One full catalog
   retained per `(kind, scope)` for every scope the isolate has served, at ~1.0–1.3 KB/piece against a
   128 MB ceiling. This is the concrete multi-tenant OOM path.
5. **The server-paged operator routes are worse than the audit says.** `src/routes/decisions.ts:98`,
   `:169` and `:239` each build a **full-catalog `Map`** per request just to join `title` and
   `customerContentId` onto at most `limit` rows. The cursor pages the lift snapshot; it never pages the
   catalog.
6. **A third full-catalog structure on the decision path:** `src/content/service.ts:201` builds
   `catalog.pieces.map(p => ({ id, tags }))` for the external-model call whenever any slot on the page
   weights the external term.
7. **A redundant whole-corpus scan:** `decide.ts:78` (`isEligibleAt`) and `contentCompose.ts:116`
   (`lifecycle.status === 'live'`) test overlapping predicates over the same set, back to back.
8. **The write and read routes have no cap and echo whole documents.** `PUT /content/:kind`
   (`src/routes/content.ts:110`) returns the entire stored document in its JSON response;
   `GET /content/:kind` (`:63`) returns it whole; the merge import (`:129–133`) reads the current catalog,
   merges, and writes — several full copies live simultaneously in the 128 MB isolate. `write()`'s three
   `CACHE.put` calls are unguarded, so a >25 MiB catalog fails with a raw KV error through
   `app.onError` (`src/index.ts:89`), with nothing telling the merchandiser that the catalog is too big.
9. **A second document with the same wall, sized worse:** `PRIORS_KIND` (`src/learn/priors.ts:15`) is a
   whole-document KV value whose rows are **slot × item × cell** — a cross product, not a list. It reaches
   25 MiB far faster than the catalog does. It is read inside `LearnStats`
   (`src/durable-objects/LearnStats.ts:121`), off the request path, so it is less urgent — but it is the
   same defect, and F32 names only the content catalog.
10. **No test asserts any catalog-size bound or envelope size.** `src/routes/content.test.ts` exercises
    PUT and import with one or two pieces, so the write path is proven only at a scale where none of this
    is visible. It does not pass for a *wrong* reason — it simply never asks the question.

## 6 · Severity, size, and the smallest safe fix

**Severity: fix before the next customer — I agree with the audit,** and its hedge ("earlier if the agreed
content corpus is large") is doing real work and is correct. Reasoning against the brief's scale:

* It does **not** block the Coach launch. At the documented launch corpus — doc 28's "hundreds of content
  pieces per brand" — the whole decision costs 2–7 ms of CPU. Nothing breaks.
* It **is not** merely a portability nicety either. The programme has no documented supported envelope, no
  size guard, and no test at scale; the customer-facing proposal
  (`docs/Tapestry-Content-Personalization-Proposal.md:71`) promises CMS/DAM ingestion "at your scale". A
  merchandiser who imports a large feed gets a raw KV 500. That is what must close before the pilot, and
  it is cheap.

**Size: S–M for the part that matters; L only for the full remedy as written.** I disagree with M–L as the
headline: it will get the whole finding deferred as a rewrite when four small changes close the risk.

**The smallest safe fix (S, roughly 1–2 engineer-days):**

1. **Delete `config: value` from `src/config/versionedStore.ts:243`** and invert the one test that pins it,
   `src/config/versionedStore.test.ts:215` ("writes both field names, so an older build can still read a
   newer write"). Nothing else in the repository depends on it — `coerce()` at `:199` still reads
   `config` on the way *out*, so every document already stored keeps working. This alone halves the stored
   envelope, halves the KV write volume, and removes 58–174 ms of parse from every isolate-cache miss.
   Confirm first that no Worker version deployed before 2026-09-02 is still serving; staging (2026-09-04)
   and production (2026-09-05) both postdate the change.
2. **Guard the write.** Refuse a document over ~20 MiB in `write()` with a named error, and surface the
   catalog's byte size and piece count in the console. A merchandiser must never discover the ceiling as
   a 500.
3. **Bound `isolateCache`** to a few entries or a byte budget, evicting least-recently-used. Today it is
   an unbounded `Map` against a 128 MB isolate.
4. **Publish the supported envelope** from the §2.6 table — "up to N pieces per scope, measured" — so the
   next customer conversation starts from a number rather than from an assumption.

**Then (M, and only then):** top-k selection in `composeContentDetailed` (measured 3.6–5.5× with identical
output, but a *two-stage* rerank once `ScoreAdjust` is configured, so it needs a decision-parity test, not
just a benchmark), and collapse the redundant liveness scans and the full-catalog `Map`s in
`src/routes/decisions.ts`.

**Defer (L, not needed by anything currently committed):** immutable catalog shards, slot/locale/eligibility
indexes, and semantic/ANN retrieval. The audit is right that these are where the architecture goes if a
customer's corpus is genuinely six figures. Nothing in the Tapestry contract requires them today, and
building them now would be the expensive answer to a problem the four cheap changes above already push
past 50,000 pieces.
