## 3 · What the audit missed

**(a) The third defect, in the same three lines, and it is worse than the one reported.**
`views-config.js:341-342` fall back to the *maximum-effect* value when the field is emptied:

```js
st.stage.outOfStage = v ?? 0;   // :341 — 0 = the piece is removed from the slot entirely
st.stage.inStage    = v ?? 1;   // :342 — 1 = a full point added, the largest legal value
```

The engine's own "off" values are the opposite: `decide.ts:106` treats the rule as absent when
`(outOfStage ?? 1) >= 1 && (inStage ?? 0) <= 0`. **The form's empty-field fallbacks are exactly inverted
from the engine's off-defaults.** Reproduced in the JSDOM harness (§2.2 file, same run):

```
>>> inStage box value as shipped: "1.2" min= 1 max= 3
>>> AFTER CLEARING THE BOX, error banner present: false
>>> SAVED DOCUMENT stage BLOCK: {"outOfStage":0.5,"inStage":1}
```

Clearing the box **saves silently**, passes the validator, and applies the maximum bonus. Every other rule
on the screen falls back to "off" or to its shipped default (freshness `?? 0` / `?? 14`, fatigue `?? 0` /
`?? 24` / `?? 3`, diversity `?? 2`, merchandising `?? 0` / `?? 2` / `?? 0.5`). Only the two stage fields
fall back to extremes. This is the launch-relevant half: the reported bug *blocks* and is loud; this one
*ships* and is silent.

**(b) A second test that passes for the wrong reason.** `scripts/acceptance-run.mjs:80` — the scripted
20–30-image acceptance run, ledger 19 row 26's evidence for the customer's acceptance bar — writes
`stage: { outOfStage: 0.3, inStage: 0.2 }` by API. Hand-authored, valid, and it never touches the console.
The one script that is supposed to prove the acceptance bar bypasses the surface the acceptance bar is about.

**(c) No readback, not just no editor.** `src/learn/rows.ts:176` strips the weight values server-side. The
audit says a merchandiser "cannot perform the tuning"; in fact they cannot *see* the current weights
anywhere in the console. Any remedy must change that route, not only add a form.

**(d) Unsaved-edit loss on navigation.** `shell.js:322` calls `view.enter(S)` on every hash change;
`views-config.js:319` `enter()` calls `loadRules()`, which resets `rules.draft = copy(rules.doc)` with no
prompt. Changing the slot in the rail silently discards an unsaved draft. Adjacent, cheap, separate.

**(e) Two copy defects on the same screen.** `views-config.js:318` says "four rules" — there are five
`ruleCard`s (stage, freshness, fatigue, diversity, merchandising). And `views.js:293` lists "merchandising"
in the Slots grid's rules column whenever `Object.values(s.merchandising).some(v => v)` is truthy
(`src/learn/rows.ts:169`) — the shipped default `{season:0, promotion:0, margin:0, maxBoost:2, minBoost:0.5}`
makes that true while `decide.ts:98` correctly treats it as off. The grid reports a rule the engine ignores.

**(f) Unregistered dimension names validate.** `kinds.ts:151-153` checks only that a weight is a number
0..1; a typo (`lien` for `line`) saves cleanly and `decide.ts:201` / `contentCompose.ts:143` simply never
read it. Overlaps F27's registry point; belongs in the same fix.

## 4 · What the audit got wrong

Nothing factual. Three points of calibration:

1. **`views.js:320` is a comment line**, not code. The citation lands on the Dials module banner. Harmless,
   but a reader checking line-by-line will hit it.
2. **"Public staging JavaScript contains that same value"** is a true sentence carrying almost no
   consequence. It reads as a security note beside F01 and is not one; the point is only that the defect is
   deployed. Say that.
3. **The remedy is over-scoped for the evidence.** "Deliver per-slot dimension weights, pins, and
   exclusions… Separate business scoring, learned-lift trust, exploration and autonomy controls."
   *Exclusions do not exist in the content model at all* — no `exclude`, `blocklist` or equivalent anywhere
   in `src/content/`. That is a new capability, not a missing form, and it is not in the acceptance sentence.
   Pins exist (`pinnedPieceId`, validated at `kinds.ts:155`) and only need an input where `:336` today prints
   a read-only row. Re-separating the four control families is a console information-architecture project.
   Bundling all of that under one **M** understates the remedy as written and overstates the fix the
   acceptance bar needs.

**One honest ambiguity, which the audit does not acknowledge.** "Weight configurability" in the acceptance
sentence is not self-evidently `SlotStrategy.weights`. The console *does* ship weight configurability —
action weights (`views-config.js:63-73, 168-176`) and per-dimension τ/K/θ (`:215-242`). A defender will say
the bar is met. The reason that defence fails: what those dials tune is how an interest *builds and fades*,
not how much a given interest *counts for a given placement*. "20–30 images on the homepage served
differently… on the agreed dimensions" is a statement about the homepage hero's ranking, and the only number
that controls it is `SlotStrategy.weights`. Put that sentence in the remediation ticket, because it is the
argument that will be had.

## 5 · Severity and size

**Severity: blocks the pilot.** I agree with the audit. `docs/architecture/19:17` is the customer's own V1
acceptance sentence, the audience is a head of platform with data scientists, and `docs/architecture/20:66`
B4 already says the criterion must be met or renegotiated. The engine delivers: weights are settable through
the authenticated versioned `PUT /content/slots` with validation, history and rollback, so a solutions
engineer can demonstrate the behaviour. The merchandiser cannot. That is a pilot blocker, not a launch
blocker — no live-data safety or reliability issue is involved.

The invalid form is on the same screen and is hit in one click, so it inherits the severity. The silent
`?? 1` fallback (§3a) is the piece I would raise hardest: it can put an engine into production that ignores
affinity, with no error anywhere.

**Size: S + S, not M.** I disagree with the audit's M overall.

- **Invalid form: S**, and small within S — four lines in one file plus a real-validator test. Hours.
- **Weights editor: S–M**, roughly 2–4 engineer-days. Every hard part is built: `weights` is on the document
  the rules screen *already holds in the browser* (`rules.draft` from `C.content('/slots')`), the validator
  exists, `POST /content/slots/validate` exists, `PUT /content/slots` exists, versioning, history and
  rollback exist, and the merchandising card at `:365-370` is a working template for a dimension-weight card.
  The one server change is `src/learn/rows.ts:176`, to carry values as well as names for the grid readback.

The audit's **M** is defensible only for the remedy *as it wrote it* (pins + exclusions + control-family
re-separation), which is a different and larger piece of work than the finding's evidence supports.

## 7 · Remedy assessment and the smallest safe fix

**Smallest safe fix that closes the pilot-blocking part — one file, four lines, no server change:**

```js
// public/console/views-config.js:340
(on) => toggle('stage', on, { outOfStage: 0.5, inStage: 0.2 }, st),

// :342 — bounds match kinds.ts:176; empty means "no bonus", matching decide.ts:106
st.stage ? n('A piece for her stage gets a bonus of',
  'Added to its score. 0 is off. 1 is a whole point and will outrank almost any other signal.',
  st.stage.inStage, (v) => { st.stage.inStage = v ?? 0; ruleCheck(); },
  'stage.in', { min: 0, max: 1, step: 0.05 },
  `+${dec(st.stage.inStage)} on a score that is usually below 1`) : null));

// :341 — same reasoning: empty means "off", not "delete the piece"
st.stage.outOfStage = v ?? 1;
```

Then delete the stub at `src/console/console.render.test.ts:187` and call the real `validateSlotCatalog`
there, and update the assertion at `:544`. That single change converts the whole console suite into a
form-to-API contract test and would have caught this on the day it was written. It is the highest-leverage
line in this finding.

**Then, in order:**
1. A dimension-weights card on the rules screen, modelled on the merchandising card, reading and writing
   `st.weights` from the draft already in the browser; make `pinnedPieceId` an input while there.
2. `src/learn/rows.ts:176` to carry weight values so the Slots grid shows the numbers, not just the names.
3. Reject weights naming a dimension outside the active reflex registry (shared with F27's registry work).

**Defer, and say so to the customer rather than shipping silently:** exclusions (a new capability, absent
from the model and from the acceptance sentence) and the re-separation of business / trust / exploration /
autonomy controls into distinct screens (a console IA project). Close ledger 20 row B4 with a name and a
date at the same time — the audit found the same gap the builders had already written down and left open.
