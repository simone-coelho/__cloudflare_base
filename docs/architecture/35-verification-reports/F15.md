## 2 · Reproductions

All scratch harnesses live under `/tmp/audit-verify/F15/`, run from the repository root with `npx tsx`.
They import the **actual modules** (`src/config/versionedStore.ts`, `src/content/kinds.ts`,
`src/reflex/configStore.ts`) against an in-memory KV that is strongly consistent and immediately
visible — the friendliest possible store, i.e. every result below is a **lower bound** on the real
platform's behaviour.

Two isolates are modelled by two byte-identical copies of `versionedStore.ts`
(`md5 18b673180544ae0cb491a9d86dbdc333`, identical to the tracked file) in `isoA/` and `isoB/`, so each has
its own module-level `isolateCache`. `tsx` collapses `import('…?query')` cache-busting under its CJS
transform, so file copies were the only faithful way to get two module instances; verified with
`A.invalidateCache === B.invalidateCache → false`.

### Probe 1 — the audit's own probe, reproduced exactly (`repro.ts`)

Seeded `learn` for scope `coach` with `slots.hero.gamma = 0`, `slots.hero.exploration.share = 0`
(revision 1), then `Promise.all` of two `patch()` calls: γ → 0.5 (actor `alice`) and ε → 0.1 (actor `bob`).

```
alice(gamma=0.5) -> ok, revision 2, version learn-default+r2
bob(eps=0.1)     -> ok, revision 2, version learn-default+r2
PERSISTED current: gamma=0 eps=0.1 version=learn-default+r2
PERSISTED rev:2  : gamma=0 eps=0.1 actor=bob note="raise exploration to 0.1"
AUDIT INDEX (2 entries): [{"r":2,"v":"learn-default+r2","a":"bob"},{"r":1,...,"a":"seed"}]
```

The audit's sentence — "Both writes returned revision 2, overwrote the same supposedly immutable revision,
and persisted γ=0, ε=0.1" — is **exactly right**. Identical at 0 ms and at 2 ms of simulated KV latency.
One thing the audit did not report: the **audit index lost a row** (two entries for three writes), so the
history does not even record that alice's change was attempted.

### Probe 1b — the real operator tuning path (`repro4.ts`)

Same race through the actual customer-facing surface: `PATCH /v1/config/reflex` →
`patchReflexConfig` (`src/reflex/configStore.ts:462`) → `versionedStore.patch`.

```
alice -> HTTP 200 {ok:true, revision:2, version:"reflex-demo-v1+r2"}
bob   -> HTTP 200 {ok:true, revision:2, version:"reflex-demo-v1+r2"}
persisted weights.product_view = 1    (alice asked for 0.9)
persisted weights.add_to_cart  = 0.8  (bob asked for 0.8)
persisted config.version       = reflex-demo-v1+r2
```

Both operators are told **200 OK, revision 2, version `reflex-demo-v1+r2`**. One slider is discarded with
no error and no audit row. `config.version` is stamped into every decision record's `config_label`
(`src/content/service.ts:228`, `src/content/decide.ts:283`), so two materially different configurations
carry the same label on the ledger.

### Probe 2 — **no concurrency required** (`repro3.ts`)

This is the result that matters most, and the audit does not contain it. Isolate A publishes revision 1 and
serves a decision, caching it. One second later isolate B publishes revision 2 (γ = 0.9). **Twenty-eight
seconds later** — no overlap, no race — isolate A publishes again:

```
isolate A published revision 1
isolate A serves a decision at t0 and caches revision 1 for 30 s
isolate B published revision 2 (gamma 0.9) 1 s later; B invalidated only B's cache
rev:2 body: gamma=0.9 actor=bob note="r2: gamma 0.9"
isolate A publishes 28 s after B and is told it wrote revision 2
rev:2 body AFTER: gamma=0.2 actor=alice note="gamma 0.2"
current pointer : revision 2 gamma=0.2 actor=alice
audit index: [{"r":2,"a":"alice",...},{"r":2,"a":"bob",...},{"r":1,"a":"seed",...}]
```

Bob's revision 2 is destroyed in `current` **and** in history. The audit index ends holding **two different
rows both numbered 2**, so `POST /content/learn/rollback/2` can only reach one of them and there is no way
to say which. The exposure window is the full `CACHE_TTL_MS` (30 s), not a request overlap — and on the real
platform the team has already measured the second half of this: doc 21 line 339, "on the real platform KV
answers a read with what it held up to a minute ago". Isolate cache (≤30 s) plus KV read staleness (≤~60 s)
means **ordinary sequential operator edits inside a ~90-second window collide**. This is not a rare race;
it is what a tuning session looks like.

### Probe 3 / Probe 6 — a transient KV read failure destroys the version history (`repro.ts`, `repro6.ts`)

`readRevision` catches a KV read error, logs "serving fallback", and returns `null`
(`versionedStore.ts:149–154`). `write` cannot distinguish "read failed" from "nothing stored"
(`:234 (previous?.revision ?? 0) + 1`). Three good revisions, then one transient read failure on
`reflex:config:coach:current` during a full `PUT`:

```
wrote revision 1 product_view=0.11
wrote revision 2 product_view=0.22
wrote revision 3 product_view=0.33
rev:1 body before: product_view=0.11 note="r1"
next PUT reported revision 1 version reflex-demo-v1+r1
rev:1 body after : product_view=0.44 note="r4 after a transient read failure"
audit index: [{"r":1,"a":"op4",...},{"r":3,...},{"r":2,...},{"r":1,"a":"op1",...}]
```

The counter **rewinds to 1**, revision 1's immutable body is destroyed, the version label on every
subsequent decision goes **backwards** (`+r3` → `+r1`), and the index carries two rows numbered 1 so
`rollback/1` restores the wrong document. The next write then reuses 2, and so on down the history.
The same happens whenever the `current` key is momentarily unreadable — including KV's negative caching of
a key written seconds earlier in another colo, which is exactly the condition during seeding and rehearsal.

### Probe 5 — one transient read failure silently reverts all tuning (`repro5.ts`)

Five ordinary tuning sessions through `patchReflexConfig`, then a sixth where the read of `current` fails
once. `patch` (`versionedStore.ts:264`) merges the operator's slider onto `read(...)`'s **fallback**, which
for this kind is the compiled default (`compiledDefaultFor`, `configStore.ts:306`):

```
after five tunes: reflex-demo-v1+r5
  product_view=0.9 add_to_cart=0.8 search=0.7 category_view=0.6
tune 6 -> HTTP 200 {ok:true, revision:6, version:"reflex-demo-v1+r6"}
after tune 6 : reflex-demo-v1+r6
  product_view=1 add_to_cart=3 search=undefined category_view=undefined
audit index: [{"r":6,"a":"op6"},{"r":5},{"r":4},{"r":3},{"r":2},{"r":1}]
```

Every tuned weight is silently reset to the compiled default. The response is **200**, the revision counter
is **monotonic**, and the audit index is **clean**. Nothing anywhere says a revert happened. This needs no
concurrency and no second operator, and it is the worst behaviour in the file: it is invisible.

### Probe 4 — partial write (`repro.ts`)

`write` has **no try/catch**. With `put(keyCurrent)` failing:

```
write() THREW: Error: KV put failed
rev:2 exists after the failure: true gamma=0.6
index rows: [1]           (the failed write left no audit row)
retry returned revision 2
rev:2 body now gamma=0.7 actor=bob
```

The comment at `versionedStore.ts:222–224` — "The immutable revision body is written BEFORE the current
pointer moves, so a failure between the two leaves the pointer on a revision that is known to exist" — is
true and is also the smaller half of the story: it leaves an **orphan body under a number that the next
write silently reuses**, and it throws out of the store into the Hono route handler
(`src/routes/content.ts:108`, `src/routes/config.ts:135/152`), which has no catch either.

### Probe 6b — the audit index loses rows (`repro3.ts`)

audit index holds 2 rows: [{"r":2,"a":"op4"},{"r":1,"a":"seed"}]

Five publishes, two audit rows, one distinct revision number for four changes.

## 3 · What the audit got wrong

1. **Framed as a concurrency defect.** It is not only concurrent. Probe 2 collides two publishes **28
   seconds apart** with no overlap, and Probes 5/6 destroy data with **one writer and no race at all**.
   The audit's own remedy list ("test concurrent operators/autonomy") would not have caught the transient-read
   failures.
2. **Severity is too low.** "Blocks the pilot for trustworthy tuning/rollback" is right for the collision.
   The transient-read reset is silent production data loss on the operator's own configuration with a clean
   audit trail — that is the brief's *production reliability* bar, i.e. **blocks launch**.
3. **"Immediately effective" is the audit's phrase, not the builders'.** Doc 22 §13 says "applies without a
   deployment". Attribute the claim correctly or the finding invites a definitional argument that distracts
   from the real defect.
4. **Sub-line drift on two citations** (`:233` is the read, the increment is `:234`; `:264` is the read, the
   merge is `:265`). Cosmetic; both statements are on the cited lines.
5. **Size M–L is over-scoped** for what is actually needed. See §5.
6. Nothing in the finding is refuted. The probe reproduces verbatim.

## 4 · What the audit missed, adjacent to the same code path

1. **`patch` merges onto the compiled default when the read fails** — silent full revert, HTTP 200,
   monotonic counter, clean index (`versionedStore.ts:264` + `:149–154`). Probe 5.
2. **A failed read renumbers history** — `write` cannot tell "read failed" from "nothing stored"
   (`:234`), so it emits revision 1 and overwrites revision 1's body; the version label regresses. Probe 3/6.
3. **The audit index is itself an unguarded read-modify-write** (`:248` → `:254`): rows vanish, and it can
   end up holding two rows with the same revision number and different actors, which breaks
   `POST …/rollback/:n` as an addressing scheme.
4. **`write` has no try/catch**; a failed `put` throws out of the store into the route handler and leaves an
   orphan revision body that the next write silently replaces (Probe 4).
5. **Replay reads by revision number.** `src/learn/replay.ts:50` resolves a receipt's documents with
   `readVersion(kind, scope, revision)`. A collided body makes doc 22 §12.3's determinism proof compare
   against the wrong document — it can report `equal: true` for the wrong reason, or a spurious diff that
   sends an engineer hunting a non-existent nondeterminism.
6. **`decideProposal` makes two non-atomic writes** (`src/learn/cycle.ts:94` SLOTS then `:99` PROPOSALS).
   A failure between them leaves a slot change applied while the proposal still reads `proposed`; a second
   approval applies the same move twice. `runCycle` (`:73`, `:76`) has the same shape, and it runs on the
   `0 3 * * *` cron (`wrangler.toml:212`) *and* on demand from `src/routes/decisions.ts:292` — two writers to
   the same scope with no coordination, in production, without two humans.
7. **`importInto`** (`src/routes/content.ts:126–133`) is a read-modify-write of the entire catalog: two
   concurrent CSV imports lose one wholesale. Same class, much larger blast radius than a dial.
8. **KV's one-write-per-second-per-key limit** applies to `:current` and `:index`. The audit cites it in F14
   but not here; a rapid tuning session or a burst of proposal approvals can hit it, and the failure surfaces
   as the uncaught throw of item 4.
9. **The correct pattern already exists in this repo.** `src/durable-objects/LearnStats.ts` publishes the
   lift snapshot through `this.serialize(() => this.publish())` (`:62`, `:84`) with the version counter in DO
   storage and an immutable per-version archive object (`liftArchiveKey`, `src/learn/fan.ts:18`). The lift
   path is single-writer-safe; the configuration path, which is the one a customer touches, is not. That
   asymmetry is the strongest argument that the fix is small.

## 5 · Severity, size, remedy

**Severity: blocks launch.** The collision half alone is "blocks the pilot", as the audit says. The
transient-read half is silent loss of the customer's own tuning, with a receipt trail that certifies
something that did not happen — the brief's production-reliability bar. Doc 22 §11's "a rollback is a
version pointer" is currently a false representation: the pointer's target is mutable.

**Size: M** for the audit's whole remedy as scoped, **S** for the launch-blocking subset. The audit's "M–L"
assumes new infrastructure. Seven Durable Object classes are already bound in `wrangler.toml:41–79`, and
`LearnStats` already demonstrates the serialize-and-publish pattern, so the coordinator is a day or two,
not weeks. The L half of "M–L" is the content-addressed bodies plus manifest activation — genuinely useful
(it is the only thing that fixes mixed activation, Probe 7) but not launch-blocking, and it should be
scheduled separately rather than bundled into the same estimate.

### Remedy assessment

The audit's remedy is directionally right and over-scoped as one unit. Taking its four clauses:

- *"Serialize publication per scope through a transactional coordinator with expected-revision
  preconditions; reject stale writes."* — **Right, and the smallest thing that actually fixes it.** A
  `ConfigPublisher` DO keyed `{kind}:{scope}` owning the counter and doing the three puts. Writes are rare
  (operator actions, one daily cycle), the read path is untouched, and the counter leaves KV entirely, so
  KV staleness stops mattering for allocation. Expected-revision preconditions are worth adding at the same
  time, but note they are **not sufficient on their own**: with a 30 s isolate cache the client's expected
  value is itself stale, so a precondition without the coordinator just converts silent loss into spurious
  409s.
- *"Store immutable content-addressed/versioned bodies and atomically activate a manifest."* — Right for
  mixed activation (Probe 7) and for making "immutable" true by construction, but this is the L, and it can
  follow.
- *"Publish a defined propagation bound and last-good behaviour."* — Right and nearly free. The bound today
  is 30 s (`CACHE_TTL_MS`) plus KV read staleness the team has already measured at up to a minute; it is
  written down nowhere in `docs/architecture/`.
- *"Test concurrent operators/autonomy, partial publication, cache propagation, rollback, reproducibility of
  old receipts."* — Right, and **add a failed read and a failed put**, which is where the silent losses are.

### The smallest safe fix that closes the launch-blocking part

About 30 lines in `src/config/versionedStore.ts`, one file, no new binding, no schema change — do this
first, today, regardless of when the coordinator lands:

1. **Fail closed on a read error.** Give `readRevision` a way to say "the read failed" as distinct from
   "nothing is stored" (an out-parameter, a sentinel, or a sibling `readRevisionStrict`). In `write` and
   `patch`, if the read failed, **return `{ ok: false, errors: ['configuration is temporarily unreadable;
   the change was not applied'] }`** rather than treating the store as empty. This alone kills Probes 3, 5
   and 6 — the silent full revert and the history renumbering.
2. **Never reuse a revision number.** Compute `n = max(previous?.revision ?? 0, index[0]?.revision ?? 0) + 1`
   from the index that is being read anyway at `:248`, then `get(keyRevision(n))` before writing it; if it
   exists, bump and retry (bounded, say 5 attempts) and fail if it still collides. This makes the bodies
   genuinely immutable and turns the remaining conflict into a truthful last-writer-wins on `current`
   instead of destroyed history. It kills Probe 2's history destruction and Probe 4's orphan replacement.
3. **Bypass the isolate cache for the read inside `write`/`patch`.** The read at `:233` currently consumes a
   30 s cache; a decision path may, a publish path must not. Shrinks the collision window from ~90 s to
   KV's own staleness.
4. **Wrap the three puts in try/catch** and return `{ ok: false, errors: [...] }` so a KV failure is a 5xx
   the operator sees, not an unhandled throw.

That is roughly one engineer-day including tests, and it converts every failure in this finding from
*silent and destructive* to *visible and recoverable*. It does **not** make publication atomic — two
operators can still last-writer-win on `current` — so the `ConfigPublisher` DO (a further 1–2 days) is still
required before anyone is told that concurrent tuning is safe, and the manifest work is still required
before anyone is told a decision reflects one coherent published set.
