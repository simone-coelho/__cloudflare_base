## 1 · Evidence claims, one by one

### 1.1 "`src/durable-objects/LearnStats.ts:93` accepts each caller's latest configuration while retaining the same counters" — **holds (with 2-line drift)**

Line 93 is the signature `private async load(tenant, brand, slot, config?)`. The behavior named is at
lines 94–98:

```ts
93  private async load(tenant: string, brand: string, slot: string, config?: SlotLearnConfig): Promise<Stored> {
94    const existing = await this.loadIfAny();
95    const cfg: SlotLearnConfig = config ?? existing?.config ?? { reward: 'click', stats: DEFAULT_STATS };
96    if (!existing) this.data = { tenant, brand, slot, config: cfg, stats: emptyStats() };
97    else existing.config = cfg;   // the latest configuration a caller sent is the one in force
98    return this.data!;
```

`existing.stats` is never touched. Both write paths route through it: `/exposures` (line 39) and
`/credits` (line 49). A remediator reading line 93 alone sees only a signature; the correct anchor is
95–97.

### 1.2 "`:97` simply replaces the configuration" — **holds, verbatim**

Line 97 is exactly `else existing.config = cfg;`, and its own trailing comment states the intent:
*"the latest configuration a caller sent is the one in force."* The behavior is deliberate and asserted
in the source, not accidental.

### 1.3 "`src/learn/route.ts:31` resolves the current learning policy" — **holds in substance, imprecise line**

Line 31 is `const rev = await readRevision(env, LEARN_KIND, scope);` — it resolves the *learn document*.
The policy is derived at line 33 through `policyOf(learn)` (defined at lines 16–19), and the per-slot
objectives at line 24 through `slotConfigsOf`. The document read is the right place to point at; the
sentence would be exact as "resolves the learn document, from which the current policy and per-slot
objective are taken (lines 24, 33)."

`readRevision` is re-read per outcome, so an operator's change takes effect on the next event, bounded
only by the 30 s isolate cache (`src/config/versionedStore.ts:37,144`) plus KV propagation.

### 1.4 "Existing sufficient statistics do not preserve the original objective/decay/policy generations" — **holds**

`StatsState` (`src/learn/stats.ts:41-48`) is `{ items, slot, events, updatedAt }`. `Counter`
(`:39`) is `{ n: ReflexEntry; s: Partial<Record<RewardType, ReflexEntry>> }`, and `ReflexEntry` is a
scalar `{ s, t }`. There is no objective, no τ, no policy fingerprint, no generation id anywhere in the
persisted `Stored` (`LearnStats.ts:18`) other than the single latest `config`. A pooled scalar cannot be
decomposed after the fact.

Fairness: the *platform* does retain what a rebuild would need — the immutable NDJSON ledger carries
`OutcomeRecord.value / margin / currency / products / type / ts` (`src/ledger/records.ts:12-31`) and the
decision records, `liftArchiveKey` archives every published snapshot by version
(`LearnStats.ts:114`), and the learn document is revision-versioned. The audit's claim is true of the
sufficient statistics; it is not true that the information is gone from the system. That is what makes
the remedy tractable.

### 1.5 "A local sequence of a unit-valued purchase followed by a revenue-valued 400 purchase yielded a revenue-labeled total of 401" — **reproduced exactly**

Ran `/tmp/audit-verify/F19/probe1.ts` with `npx tsx` from the repository root, using the real
`creditWeight`, `recordSuccess`, `buildSnapshot`, `liftFor` and `outcomeFromAction`:


successes where two occurred.

## 3 · Verdict, severity and size

**Verdict: confirmed.** Not partly — every sub-claim holds and the numeric probe is exact.

**Severity: blocks the pilot**, agreeing with the audit, with the trigger sharpened. It fires whenever a
slot's `objective`, `reward`, `stats.tauLearnMs` (or n₀/nMin/clamps) or the learning policy changes after
the slot has banked evidence. Doc 22 §13 lists all of these as operator dials that "apply without a
deployment," and the tuning UI commitment makes mid-flight changes the expected mode of use, not an edge
case. It is not "blocks launch" on the brief's scale — nothing here is a live-data safety or production
reliability defect — but it does put a false representation on the customer-facing receipt
(`src/learn/receipts.ts:65` prints *"N succeeded, weighed by revenue"* over a mixed-unit scalar), and it
defeats the one thing a money-objective pilot exists to prove.

One mitigation the audit does not mention: γ defaults to 0 (`decide.ts`: `base * Math.pow(look.lift, gamma)`),
so on a slot at trust 0 the mixed number is reported but not served. That bounds today's blast radius to
reported numbers — and a pilot that leaves γ at 0 is not testing configurable objectives at all.

**Size: M.** The audit's "M–L" is defensible but L is not warranted: the machinery for a rebuild already
exists. `src/learn/report.ts:87-122` and `src/learn/hourly.ts:250-280` already reconstruct sufficient
statistics from ledger decisions and outcomes under an arbitrary policy *and* objective; the archive and
publish plumbing (`liftKey`, `liftArchiveKey`) already exists. What is missing is a generation stamp and
a promote step. The guard-only fix that closes the pilot-blocking part is **S** (§7).

## 4 · What the audit got wrong

1. **`LearnStats.ts:93` is a function signature.** The behavior is at 95–97. Two-line drift; harmless to
   the argument, mildly annoying for the remediator.
2. **`route.ts:31` reads the learn document, not the policy.** The policy is resolved at line 33 via
   `policyOf` (lines 16–19) and the objective at line 24 via `slotConfigsOf`.
3. **"Size M–L" over-states the upper bound.** See §3.
4. **The remedy's "Expose reset/backfill/maturity status" ignores what exists and what it cannot do.**
   A per-item reset route already ships (`POST /v1/:tenant/learn/items/reset`,
   `src/routes/decisions.ts:493-507`). It is not a repair: `LearnStats.ts:68-79` deletes only
   `stats.items[item]` and its own comment says *"The slot's own counters keep what they saw."* Since
   `lift = p̂ / p0` and `p0` comes from `st.slot[key]`, resetting every item still leaves every
   denominator mixed. The DO's whole-slot `/reset` (`LearnStats.ts:65`) is reachable from no HTTP route.
5. **Nothing in F19 is overstated.** The 401 is exact and the consequences are real. The audit
   *under*-states in three places: it never shows the ranking can invert, never notes the γ=0 mitigation,
   and never notes that the autonomy cycle can act on the corrupted snapshot (§5.6).
6. **"without the promised historical recomputation" gives no citation.** The promise is verbatim in
   `docs/architecture/22-outcome-learning-design.md:178-180`: *"Promoting a reporting policy to the
   learning policy is a configuration change. The statistics are recomputed from the ledger under the new
   policy and published as a new lift version. The old version remains available."* Nothing implements
   it. Quoting it turns the finding from a design opinion into an unmet written commitment.

## 5 · What the audit missed (adjacent, same code path)

### 5.1 The contamination is pre-loaded: it needs no objective change at all

`DecisionRing.outcome` (`DecisionRing.ts:82-95`) forwards credits for **every** reward type to
`LearnStats`, weighted by the slot's current objective. The batch paths do filter — `report.ts:110` and
`hourly.ts:266` both carry `if (c.reward !== reward) continue; // the slot learns against one reward` —
but the online path does not. So while a slot learns `click`/`unit`, `s['purchase']` quietly fills with
unit weights (proved in §2.5: `{"purchase":{"s":1}}`). The day the slot is moved to `purchase`/`revenue`
— the *only* legal way to enable a money objective, since `validateLearnConfig`
(`src/content/kinds.ts:325`) refuses revenue on a `click` reward — it reads a series that is already part
unit. First-day revenue read 101 where the truth was 1000; a $900 order counted as $1.

**Consequence for remediation:** "do not change the objective mid-flight" is *not* a workaround. Every
slot that turns revenue on for the first time is already contaminated. This is the strongest single
reason the fix cannot wait for a rebuild path.

### 5.2 `margin ?? value` mixes units with no configuration change whatsoever

`creditWeight` (`policy.ts:65`): `const v = objective === 'margin' ? (outcome.margin ?? outcome.value) : outcome.value;`
This is deliberate and documented (doc 22 §13: *"a feed that has not yet been taught margin degrades to
revenue rather than to silence"*), but it means the unit of a `margin` counter is decided **per event by
feed completeness**. A feed that starts populating `data.margin` mid-week silently switches the counter
from gross revenue to margin, permanently, with no operator action, no config revision and no audit
trail. This is a fourth route to the same failure and it is invisible to every control the remedy
proposes.

### 5.3 Currency is never read, and a refund can never subtract

`creditWeight`'s parameter type is `Pick<OutcomeRecord, 'value' | 'margin'>` — `currency`, which the
ledger *does* carry (`records.ts:25`), is structurally out of scope. A multi-brand, multi-region tenant
sums JPY and USD into one scalar. And `v > 0 ? v : 0`, plus `DecisionRing.ts:90`'s
`.filter((c) => c.weight > 0)`, means learned revenue is monotonically non-decreasing: there is no
refund/return reward type in `RewardType` and a negative value is dropped. For Coach, where returns are
material, "revenue per exposure" is gross-of-returns, single-currency-assumed. This makes the audit's
closing sentence ("Revenue is not profit…") concrete and testable rather than rhetorical.

### 5.4 `learn.stats` is one tenant-wide object

`slotConfigsOf` (`route.ts:22`) hands the *same* `learn.stats` to every slot, and
`validateLearnConfig` (`kinds.ts:290-300`) exposes only one `stats` block per document. Changing τ to
tune one slot silently re-bases every slot's counters in the tenant at once. The blast radius of a decay
change is the tenant, not the slot.

### 5.5 No test exercises the mutation

The only `LearnStats` DO test (`src/learn/learn.test.ts:124-128`) passes one constant `cfg` to both
`/exposures` and `/credits`. `objective.test.ts` builds each snapshot from a fresh `emptyStats()` under a
single objective. Deleting line 97 would not fail the suite. Both files pass today; neither covers the
line whose comment asserts the intended behavior.

### 5.6 The autonomy cycle acts on the corrupted snapshot

`src/learn/cycle.ts:56` reads `liftKey` and hands the snapshot to `proposeFor`
(`src/learn/autonomy.ts:74-99`), which derives per-dimension spread from those lifts. In `autonomous`
mode `runCycle` writes a **new slots revision** (`cycle.ts:74-77`) from that evidence. So mixed-unit
statistics do not merely mis-serve; they propagate into the tenant's configuration, with a note in the
audit trail that reads as if it were justified.

### 5.7 A config change can never be atomic

`readRevision`'s isolate cache is 30 s (`versionedStore.ts:37,144`) on top of KV eventual consistency
(the brief's own §6 flags KV consistency as a live risk). For at least ~30–60 s after a flip, concurrent
isolates weight credits under both objectives into the same counter. Even a disciplined "pause traffic,
flip, resume" procedure cannot produce a clean boundary. The fix must therefore be *in the object*, at
the point of write — not in an operator runbook.

### 5.8 A config-catalog row is claimed configurable and is hardcoded

Doc 22 §13 lists "Pooling ladder order and n_min" as a data-science dial and §5.4 (line 313) states *"A
team that believes region matters more than channel reorders the ladder and the statistics recompute."*
`levelKeys` (`stats.ts:33-36`) is a fixed six-key function and no ladder field exists in the stats
validator. Neither half of that sentence is built — and were the first half built, it would land in
exactly this trap, since reordering the ladder re-keys every counter.

## 7 · Remedy assessment and the smallest safe fix

### The audit's remedy

Directionally right and complete on the science: version statistics by objective/policy/horizon/schema,
rebuild a generation from immutable events, promote atomically, expose status, property-test the
transitions. Three gaps to close in it:

1. It must also **filter the online credit path to the slot's configured reward**, as the batch path
   already does (`report.ts:110`), or fold `reward` into the generation key — otherwise §5.1's pre-loaded
   contamination survives the fix.
2. The promotion must write **`liftKey`** — the only key `src/content/service.ts:48` reads — and archive
   the superseded version, not merely produce a report grid.
3. The reset it exposes must cover **`stats.slot`**, not only `stats.items`, or the lift denominator stays
   mixed (§4.4).

It is not over-scoped in substance, only in size: L is unwarranted (§3).

### Smallest safe fix that closes the launch/pilot-blocking part — **S, 1–3 engineer-days**

Stamp a generation on the counters and start a fresh one when the generation changes.

- `Stored` (`LearnStats.ts:18`) gains `gen: string` and `restartedAt: number`, where `gen` is a hash over
  `{ objective, reward, tauLearnMs, n0, nMin, liftMin, liftMax }` — and, once the policy is passed
  through, a policy fingerprint too.
- `load()` (`LearnStats.ts:93-99`): on `existing.gen !== fp`, replace `stats` with `emptyStats()`,
  set `restartedAt = now`, keep the previous generation's last published snapshot in the R2 archive
  (already written at `:114`), and log the transition. Do **not** silently keep the counters.
- `LiftSnapshot` (`stats.ts:88-100`, returned at `:164`) gains `generation`, `restartedAt` and
  `exposuresSinceRestart`; `receipts.ts:65` says *"learning restarted <when> after a configuration
  change; N exposures since"* instead of asserting a unit it cannot vouch for.

This degrades safely with no serving cliff: `liftFor` (`stats.ts:185`) already refuses any level below
`nMin`, so a fresh generation simply returns `null`, the receipt says *"Nothing learned yet for this
piece in this shopper's context"* (an existing string), and the engine serves base scores until evidence
rebuilds. Roughly 40–60 lines across three files plus the tests that are missing today: a mid-stream
objective flip, a mid-stream τ change, a reward flip over a pre-loaded series, and an assertion that a
snapshot's `objective` label matches the generation that produced its counters.

The doc 22 §4.2 promise — rebuild from the ledger under the new policy, publish as a new lift version,
keep the old one — then follows as the **M** piece, reusing `report.ts` / `hourly.ts` rather than new
machinery. Until it lands, the honest operator-facing statement is that a configuration change restarts
learning rather than reinterpreting it.
