## 2 · Reproductions

All run with `npx tsx` from the repository root against the real exported functions — no reimplementation.

### A. The audit's own probe — `/tmp/audit-verify/F18/repro.ts`

chronological n = 1.367879

### B. What a single late event costs — same file
1,000 exposures accumulated, then one arrival back-dated by Δ, read at the same instant:

| Δ | n before | n after | expected | evidence destroyed |
|---|---|---|---|---|
| 1 min | 1000.000 | 1000.966 | 1001 | 0.03 |
| 1 h | 1000.000 | 999.015 | 1001 | 1.99 |
| 24 h | 1000.000 | 954.450 | 1001 | 46.6 |
| 7 d | 1000.000 | 717.247 | 1001 | 283.8 (**28%**) |

Mechanism: `bump` calls `effectiveScore(entry, ts, tau)` with `ts < entry.t`; core.ts:234 clamps `dt` to 0, so the existing mass is returned undiscounted and the counter's clock is then rewound to `ts`. On the next read the whole accumulated pile is aged by Δ. **A late event retroactively ages all prior evidence at that key by its own lateness.**

### C. How much delivery order actually matters — `/tmp/audit-verify/F18/magnitude.ts`
450 exposures over a fortnight, order-independent truth **329.149**:

| delivery | n | error |
|---|---|---|
| perfectly chronological | 329.149 | 0% |
| jitter ±1 s | 329.149 | 0.00% |
| jitter ±60 s | 328.840 | −0.09% |
| jitter ±1 h | 320.243 | −2.71% |
| jitter ±24 h | 84.900 | **−74.21%** |
| one day replayed last (catch-up shape) | 176.496 | **−46.38%** |

And over 200 random permutations of a 525-event set (`fix.ts`): HEAD produces n ∈ **[3.20, 10.11]** against a true 109.72 — an 11–34× under-count with a 68% spread. The audit's single 1.368/0.736 datum understates the worst case by an order of magnitude and overstates the steady-state online case, where the error is under 0.1%.

### D. The rounding half — `/tmp/audit-verify/F18/round.ts`, `round2.ts`
At the root key the shrinkage is algebraically a no-op — `(s + n₀·(s/n))/(n + n₀) = s/n` — so the published root rate *is* the raw rate, and `r3` is the only quantization. Below 0.0005 it is zero.

10,000 exposures, varying purchases, `objective: 'unit'`, reward `purchase`:

| purchases | true rate | published p0 | item p̂ | **served lift** |
|---|---|---|---|---|
| 6 | 0.00060 | 0.001 | 0.001 | 1.199 |
| 5 | 0.00050 | 0.001 | 0.001 | 1.000 |
| 4 | 0.00040 | **0** | 0.001 | **1.000** |
| 3 | 0.00030 | **0** | 0.001 | **1.000** |

`lift = p0slot > 0 ? … : 1` (stats.ts:159). When the rounded slot rate is 0, **every item at every level gets lift exactly 1**. `liftFor` still answers at level 5 with `lift: 1`, `decide.ts:179` applies `Math.pow(1, γ) = 1`, and learning is a silent no-op. In the 4-purchase case the item is genuinely 2× better: with full internal precision its lift is **1.994**.

Off-grid quantization, same slot size:

| true rate | published p0 | error | published lift | full-precision lift | error |
|---|---|---|---|---|---|
| 0.00160 | 0.002 | 25.0% | 1.298 | 1.621 | 19.9% |
| 0.00240 | 0.002 | 16.7% | 1.895 | 1.580 | 19.9% |
| 0.00350 | 0.003 | 14.3% | 1.861 | 1.596 | 16.6% |
| 0.00540 | 0.005 | 7.4% | 1.716 | 1.589 | 8.0% |

This is not confined to purchases. `slotRate` memoises the **rounded** rate and each child level shrinks toward it with strength n₀ = 30 (stats.ts:120–121), so the quantization propagates down all six levels. At level 5, where a cell is sparse, the `30·p0` term dominates the estimate, so the parent's quantization is most of the fine answer — and level 5 is the level that answers for a known shopper. Content click-through of 0.2–0.5% per rail item is ordinary; that is the 20% error row.

Is a rare rate configured today? `scripts/seed-coach-content.mjs:57` seeds Coach as `story: { reward: 'purchase', objective: 'revenue' }`. Revenue weighting makes `s` dollars, so dollars-per-exposure is large and the collapse is *accidentally masked*. `objective: 'unit'` with `reward: 'purchase'`, `wishlist` or `video_complete` is a valid configuration (kinds.ts:322–325) and is one operator dial away from the collapse.

### F. The path the audit missed: client-controlled timestamps — `/tmp/audit-verify/F18/poison.ts`
```
src/routes/realtime.ts:85    timestamp: z.number().optional()      no bound, no skew clamp
src/routes/realtime.ts:101   timestamp: validatedEvent.timestamp || Date.now()
src/ledger/records.ts:131    ts = any finite client timestamp, else Date.now()
src/learn/policy.ts:95       Credit.ts = outcome.ts
src/durable-objects/LearnStats.ts:50   recordSuccess(..., Number(c.ts) || Date.now(), ...)
```
`attribute()` bounds the backdate to the reward's window (policy.ts:76–77), which is 7 days for a purchase — precisely the interval that costs 28% of a counter. Exposure timestamps are safe (`ts: i.nowMs`, decide.ts:260/282, server-side).

Measured: an item with 296.4 units of honest accumulated purchase evidence; an attacker drives their own visitor id, takes one served decision, then posts purchases dated `now − 7 d + 1 s` naming the served item, interleaved with a normal day of real traffic:

| crafted events | evidence at HEAD | honest run would be |
|---|---|---|
| 1 | 240.1 | 324.4 |
| 3 | 170.8 | 380.4 |
| 10 | 104.9 | 576.4 |

**81.8% of the item's purchase evidence destroyed by ten crafted events** — and each one is itself credited as a purchase, so it reads as favourable traffic. The counters are slot-wide and item-wide (`st.slot[k]`, `st.items[item][k]`), so one visitor id poisons the learned statistics every shopper of that tenant/brand/slot is served from. This is the ordering defect turned into an unauthenticated data-integrity attack, and the audit does not name it.

Related: because core.ts:234 clamps, a counter whose `t` is ahead of `now` does not decay at all until its next event. A single future-dated event freezes that counter's decay.

## 3 · Where the consequence does **not** reach

Stated so the team fixes the right place:

- **The day report is already order-independent.** `mergeEntry` (hourly.ts:143–148) decays both operands to `Math.max(a.t, b.t)` — exactly the audit's remedy — and `reportFromHours` sorts hours and folds them through `mergeBrand`/`mergeStats` (hourly.ts:291–293). Cross-hour ordering cannot corrupt the day report.
- **Batch fold skew is bounded by one hour.** `foldDecisions` accumulates into a fresh `emptyStats()` per hour and ledger objects are read in time order (hourly.test.ts:206). Worst case ≈ −2.7% per the table in §C.
- **Decision replay is not broken.** `src/learn/replay.ts` fetches the *archived* snapshot by recorded version (`liftArchiveKey`, replay.ts:15/72/77), so doc 22 §12.3 determinism holds. The audit's "a data scientist cannot reproduce online results from an event-time replay" is true **of the lift table**, not of the receipt replay; left as written it invites a refutation that would discredit the whole finding.
- **Steady-state online jitter is immaterial.** Exposures post immediately after serving and credits immediately after attribution; ±1 s skew gives 0.00% error. There is no live backfill path into `LearnStats` — I grepped every caller of `/exposures` and `/credits` (only `fan.ts:79` and `DecisionRing.ts:93`).

## 4 · Verdict, severity and size

**Confirmed.** Every evidence claim holds at HEAD; both reported measurements reproduce exactly.

**Severity: blocks the pilot** — I agree with the audit for the finding as scoped. Two independent reasons:
1. With `objective: 'unit'` on a rare reward the learned lift is silently 1.000 everywhere while the operator UI, receipts and day report present it as a learned result. That is a representation that a contracted capability is delivered when it is not.
2. It is not gated by γ. Every slot defaults to γ = 0 (kinds.ts:381), so lift does not move serving today — but it is on every receipt, in the day report grids and in the operator's evidence view from day one. The pilot's *numbers* are wrong before the dial is ever raised.

The client-timestamp path in §F I would raise as its own finding at **blocks launch** under the brief's "live-data safety" clause. It is not F18 as written, but it is the same code path and it is the reason F18 cannot be deferred.

**Size: S for the code, S–M with the state migration** — I agree with the audit's S–M, weighted to S. The correct primitive already exists in the repository (`mergeEntry`), the change is seven lines, and I verified it is output-identical on same-timestamp data so all 59 `src/learn` tests stay green. What makes it M is the two things the remedy omits: the persisted `StatsState` and the property-test suite.

## 5 · What the audit got wrong

1. **`stats.ts:51` is the signature, not the statements.** The behaviour is on 52–53. Trivial, but a reader who opens line 51 sees a function header.
2. **"Queue reordering/backfill changes learned truth" is not the live vector.** No backfill path into the online counters exists, and steady-state reordering is sub-0.1%. Presenting the toy 1-τ example as the consequence invites the team to measure the online path, find 0.09%, and dismiss the finding. The live vectors are client-supplied timestamps (§F), catch-up/replay shapes (−46%), and the batch fold (−2.7%).
3. **"Alter smoothing/lift" understates the rounding.** It does not perturb the lift; below 0.0005 it forces lift to exactly 1 at every level and disables learning for that slot silently. Measured 1.000 where the truth is 1.994.
4. **The reproducibility sentence is too broad** and reads as impugning doc 22 §12.3 replay, which is unaffected (§3).
5. **The remedy has no migration step.** `Stored.stats` is persisted in the LearnStats DO (LearnStats.ts:18, 88–90). Fixing `bump` does not repair counters whose `t` is already skewed; those objects must be reset and refolded, or rebuilt from the ledger.
6. **The remedy does not mention `mergeEntry`.** Naming it turns "property-test all permutations, historical backfill, near-zero rates and numerical decay invariants" from a research task into a seven-line edit.

## 6 · What the audit missed, adjacent to this finding

1. **The fix is already written, 90 lines away.** `mergeEntry` (hourly.ts:143) is exactly the remedy; hourly.ts:8 documents it as the module's invariant. `bump` is the only accumulator in the codebase that does not obey it — and it is the one that feeds the object serving live lift.
2. **Client-controlled timestamps** (§F): 81.8% of an item's purchase evidence destroyed by ten crafted events, slot-wide, from one self-served visitor id.
3. **A future-dated event suspends decay** for that counter until its next event (core.ts:234 clamp).
4. **The receipt becomes self-contradictory** when p0 rounds to 0 (§E) — and *stays* imprecise after the precision fix, because the published `p0` still prints `0.000` while lift reads 1.994. Display rounding must become significant-digit based, not fixed 3 dp.
5. **Quantization compounds down the six-level ladder** because `slotRate` memoises the rounded value and each child shrinks toward it with n₀ = 30. Measured 20% lift error at a 0.0016 true rate.
6. **Nobody measured the skew sensitivity.** The table in §C is the number the team needs to prioritise; it did not exist.
7. **The test that gives false confidence.** `src/learn/learn.test.ts:75–91` ("decays on the long horizon, shrinks a thin sample toward its parent, and clamps") stamps all 480 events with the same `T0`. It validates the decay algebra and is structurally incapable of detecting order dependence. All 59 `src/learn` tests pass at HEAD; there is no ordering or rounding test anywhere in the repository.
8. **`Number(c.weight) || 1`** (LearnStats.ts:50) converts a weight of 0 to 1. Unreachable today because DecisionRing.ts:90 filters `weight > 0`, but a live trap for any future producer of credits — the same `||` idiom as `Number(e.ts) || Date.now()` two lines up.

## 8 · Remedy assessment and the smallest safe fix

The audit's remedy is **directionally right and slightly over-scoped in framing, under-scoped in operations**. "Keep each counter at a monotonic reference time; discount late contributions to that time rather than moving the clock backward" is precisely correct — and is `mergeEntry`. "Preserve full precision internally and round only for presentation" is precisely correct. Neither needs a new model architecture, as the audit says. What is missing is the state migration and the input clamp.

**Smallest safe fix that closes the launch-blocking part** — two edits in `src/learn/stats.ts`, plus one operational step and one input clamp. Verified: order-independent over 200 permutations, and byte-identical output on same-timestamp data, so no existing test changes.

```ts
// src/learn/stats.ts, replacing lines 51-54
function bump(entry: ReflexEntry | undefined, ts: number, w: number, tau: number): ReflexEntry {
  if (!entry) return { s: w, t: ts };
  const t = Math.max(entry.t, ts);                     // the counter's clock never moves backward
  return { s: effectiveScore(entry, t, tau) + w * Math.exp(-(t - ts) / tau), t };
}
```
```ts
// src/learn/stats.ts, inside buildSnapshot: memoise the exact rate, round only into the published record
const exactRate = new Map<string, number>();
const slotRate = (key: string): number => {
  if (exactRate.has(key)) return exactRate.get(key)!;
  ...
  const exact = Number.isFinite(rate) ? rate : 0;
  exactRate.set(key, exact);
  slotRates[key] = { n: r3(n), s: r3(s), rate: r3(exact) };
  return exact;                                        // full precision to children, to p_hat, to lift
};
```
Then:
- **Rebuild the persisted counters once.** `POST /reset` each `LearnStats` object and refold, or rebuild from the ledger. Without this the skewed `t` values survive the code fix.
- **Clamp the client timestamp** at `src/routes/realtime.ts:85`: bound `timestamp` to a small skew window around server time (reject or replace outside, say, ±5 minutes). One line of zod. This closes §F and is the part that would otherwise be a live-data-safety issue at launch.

Follow-on, not launch-blocking: a property test asserting `buildSnapshot` is invariant under permutation of the event stream and under an event-time replay of the same ledger; a near-zero-rate test asserting lift is not forced to 1; and significant-digit display rounding on the receipt so `p0` is legible below 0.001.
