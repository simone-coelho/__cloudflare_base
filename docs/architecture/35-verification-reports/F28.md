## 3 · Severity and size

**Blocks the pilot — agreed.** Not because the demo is broken (it is not, §5), but because:

* `docs/architecture/18-content-affinity-engine.md:92` states the contract: *"Cross-slot invariants at assembly:
  dedupe (no content twice per page), non-personalizable slots excluded per tenant config, absent decision →
  customer default."* The pin path breaks the first clause using the second.
* `docs/architecture/26-btie-requirements-gap-review.md:152` tells the customer, against requirement **D11**, that
  *"Within one page a piece is used once"* is **already in the design**; `:194` repeats it; `docs/architecture/21-tapestry-gap-closure-plan.md:144`
  marks D11 ✅ Built. A claimed-closed customer requirement is falsified by an ordinary page layout.
* `src/reflex/contentCompose.ts:12` — the module's own header — names DEDUPE as the invariant it exists to enforce.
* The trap is the *documented* authoring path, not an exotic one: `src/content/types.ts:75` and
  `docs/kit/02-api-reference.md:78` both describe the array as **page order**, while the composer treats it as
  **priority order**. A hero above a pinned campaign band is the most ordinary merchandising layout there is.

Not *blocks launch*: no live-data safety issue, no production reliability issue, and it is a defect inside a
delivered feature rather than a claim that an undelivered capability exists.

**S for the deduplication, M for the constraint contract — agreed.** The reservation itself is four lines
(probe 5); S is the right bucket once the negative tests, the receipt/monitor signal and the demo bundle rebuild
are counted. M for the precedence contract is right, and understated if the schema gains exclusions/off-limits and
the operator UI has to explain them.

## 4 · What the audit got wrong

1. **It omits that no shipped configuration triggers this.** Every slot document in the repository puts the pinned
   slot **first** — `scripts/seed-coach-content.mjs:40`, `scripts/import-content.mjs:45`,
   `public/meridian/meridian.js:245` — and each pins a piece whose `slotTypes` are `['merch']` only
   (`public/data/coach-content.json`, CCH-026), which no ranked slot can select. `DEFAULT_SLOTS`
   (`src/content/kinds.ts:229`) has no pins at all, and the Coach storefront does not even render `merch`
   (`public/storefront.js:287–288` subscribes to `chero` and `story`). A reader could take F28 to mean the demo is
   duplicating today. It is not. This matters for a *blocks the pilot* rating and should be stated: the defect is
   armed by customer configuration, and the configuration that arms it is the one the kit documents.
2. **"does not … check the used set"** is imprecise: the pin branch *writes* to `used` (`:130`), which is why
   pin-first ordering is safe. The defect is the absence of a *reservation pass*, not the absence of tracking.
3. **"no … default-handoff policy"** is right about the slot schema and wrong if read as behaviour: the SDK
   already hands a slot back to the page's own default when it has no decision (`src/sdk/listen.ts:20–27`, an
   empty array per slot), and no-arbitrary-fill holds (probe F). What is missing is the ability to *declare* a
   handoff, and any signal that one happened.
4. **The remedy's "reject contradictory pins" cannot be a write-time guarantee.** `validate` is document-pure and
   the catalog is a separate versioned document (`src/config/versionedStore.ts:229`); the next catalog revision can
   invalidate a pin that validated cleanly. Intra-document contradictions (two slots, one pin) are checkable at
   write time; referential ones must be handled at decision time regardless. The remedy should say so.

## 5 · What the audit missed (same code path)

1. **Two slots pinning the same piece duplicate it with no ranking at all** (probe C), and the validator accepts
   the document (probe 4). This is the same failure without the ordering subtlety, and it is the cheap half to
   reject at write time.
2. **A pin overrides `slotTypes`, which is the only slot-eligibility control the schema has.** So the governance
   gap is worse than "no off-limits list": the one gate that exists is bypassed by the pin path (probe D).
3. **A pinned slot ignores `take`.** `take:3` + a pin serves one piece; two positions are permanently unfillable,
   with no note and no error, and `validateSlot` accepts `take` 1..50 alongside a pin (probes E and 4).
4. **A dead pin silently deletes the slot** — missing id, `draft`, expired window, or `inStock:false` — with no
   decision, no candidates entry, no receipt note and no monitor signal (probes F and 2). A stock feed flipping one
   flag can blank the merchandiser's campaign band and nobody is told.
5. **The duplicate contaminates measurement, not just the page.** One click on the hero credits the pinned slot as
   well (probe 3), because `attribute()` credits one entry per slot and ignores `OutcomeRecord.slot`; two exposures
   are also fanned. The pinned slot's measured lift for that item rises on an interaction it never received — a
   page-governance bug leaking into the "we can prove lift" claim. The same ring inflation feeds the CW30 fatigue
   counter twice for one page view (`src/learn/fan.ts:50–60`).
6. **The tests pass for the wrong reason.** `src/demos/meridian/contentCompose.test.ts:8–18` places the pinned
   `merch` slot **last** — the exact risky order — but pins a piece whose `slotTypes` are `['merch']`, so nothing
   can collide; its DEDUPE assertion only exercises the ranked path. `src/reflex/contentCompose.test.ts:18` and
   `src/content/decide.test.ts:20` both put the pin first. No test anywhere asserts page-wide uniqueness in the
   presence of a pin.
7. **A second promise line.** `docs/PS-Implementation-Delivery-Guide.md:167` sells CRePE parity as reimplemented,
   including *"slot eligibility/exclusions, per-slot fallbacks, cross-page dedupe"*. Cross-**page** dedupe does not
   exist at all (the `used` set lives inside one decision; the nearest thing is the soft, per-slot fatigue penalty),
   and per-slot fallbacks do not exist for a pinned slot.
8. **`items: { mode: 'reject' }` is not an exclusion.** `docs/architecture/26:64` lists "Pins, blocks" as the
   governance layer; the `reject` control (`src/content/decide.ts:170`) only ignores the *learned lift* for an item.
   Nothing in the product excludes an item from a slot.

## 7 · Remedy assessment and the smallest safe fix

The remedy is right in direction and slightly over-scoped for the launch-blocking part; it also under-specifies
where validation must live (§4.4). Split it:

**Smallest safe fix (hours, ships alone).** In `composeContentDetailed`, before the slot loop:

```ts
const reserved = new Set<string>();
for (const s of slots) if (s.pinnedPieceId && live.some((p) => p.id === s.pinnedPieceId)) reserved.add(s.pinnedPieceId);
```

then `!reserved.has(p.id)` in the `eligible` filter at `:138`, and `if (p && !used.has(p.id))` at `:129`. Order
stops mattering, contradictory pins collapse to first-wins, and existing fixtures are byte-identical (probe 5).
Add four negative tests: pin after a ranked slot, two slots one pin, dead pin, pinned slot with `take > 1`. Rebuild
`public/meridian/engine.bundle.js` so the demo runs the fixed function.

**Then, in the M bucket, in this order of value:**
1. A receipt note and a monitor signal when a pin does not resolve, and when a pinned slot cannot fill `take`
   (today both are silent).
2. Write-time rejection of intra-document contradictions (two slots, one pin), plus a *warning* pass that reads the
   catalog revision in force and reports pins that do not resolve or that name a slot outside the piece's
   `slotTypes` — advisory, because the catalog moves independently.
3. Decide and document the precedence: lifecycle → window → stock → slot eligibility → pin → diversity → default
   handoff; say in the operator UI and the contract that diversity is a soft preference that relaxes rather than
   leave a hole, and that a pin overrides slot eligibility.
4. Only then, the schema work for declarative exclusions / off-limits / per-slot fallback that
   `docs/PS-Implementation-Delivery-Guide.md:101` and `:167` promise.

**One documentation correction is owed either way:** `docs/architecture/26-btie-requirements-gap-review.md:152`
and `:194` tell the customer per-page uniqueness is already in the design. The four-line fix makes that true; until
it lands, the sentence is false.
