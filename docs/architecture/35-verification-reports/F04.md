## 2 · Reproductions

Ran with `npx vitest run --config /tmp/audit-verify/F04/vitest.config.ts` (root outside the repo, `@/…` aliased to the repo's `src/`;
nothing in the tree was written). Files: `/tmp/audit-verify/F04/f04.probe.test.ts` (mine), `/tmp/audit-verify/F04/f04.adjacent.test.ts` (mine),
and the audit's own harness `/tmp/audit-verify/F04/f04.test.ts`, which I re-ran unmodified.

**A · Account proof is optional even on an enforced stamp.** Env shaped like `provision-stamp.sh`'s output
(`AUTH_MODE:'enforced'`, `IDENTITY_SALT` set, `SDK_KEYS` set, **no** `IDENTITY_SECRETS`):

- `verifyAssertion(env,'coach',{visitorId:'vis-attacker',accountId:'acct-victim'})` → `{ok:true, assurance:'site'}`.
- `POST /coach/identity/link {visitorId:'vis-attacker', accountId:'acct-1001'}` (no assertion) → **200**,
  `assurance:'site'`, `carry: sh_48ffc559…` = the victim's shopper id, `audiences:["line_tabby_affinity"]` — i.e. the
  victim's live profile handed to a stranger's browser. The audit's own run hands back `line_maternity_affinity`, its planted marker.
- Control: with `IDENTITY_SECRETS:'coach:s3cret'` the same call → **401** `identity assertion required for this tenant`.
  So the only thing standing between a public site key and any customer's account is one unset variable that no script sets and no check reports.

**B · Logout resurrects the previous shopper.** Sequence: seed `session:s-BROWSER` owned by `vis-A` with a
Maternity/Tabby affinity → `POST /identity/link {vis-A, acct-1001}` (browser record gets `forwardTo: <person session>`) →
`POST /identity/detach` (200; clears eight cookies, `nothing server-side changes`) → new anonymous visitor `vis-personB`
presents the **same** `s-BROWSER` (the SDK never rotated it):

```
getOrCreateSessionFromCookies(null, 'vis-personB', undefined, 's-BROWSER')
→ { returnedSessionId:'s-BROWSER', isNewSession:false,
    userId:'sh_48ffc559…',                      ← the PREVIOUS shopper
    identity:{shopperId:'sh_48ffc559…'},        ← the private profile marker
    segments:['line_tabby_affinity','new_user'], attributes:{product_views:3} }
```

Through the whole decision path (`serveContentDecisions`, audit harness P3): the carried session explains
`drivers:[{dim:'line',value:'Maternity',a:0.6093}]`; an identical request on a clean session explains
`"no signal yet — the slot default"`. Shopper B is personalised as shopper A.

**C · The SDK.** Driving the real `createCore` + `createIdentity` against a memory host:
`sessionBefore = s-M0GCGMIO0F0F0F`, after `identify()` and `logout()` → `sessionAfter = s-M0GCGMIO0F0F0F`,
`opt_session` in storage unchanged, `visitorId` rotated to a fresh `vis-…`. `src/sdk/listen.ts:75` puts
`sessionId: core.sessionId` on every snapshot and `src/routes/decisions.ts:329,336` feeds it to `serveContentDecisions`.
The loop is closed end to end.

**D · The 409 retry.** With `IDENTITY_SECRETS:'coach:s3cret'`, a browser carrying the previous person's shopper id and a
site-signed assertion: attempt 1 → **409**, detach → 200, attempt 2 → **401 `assertion does not verify`** (the assertion
names the old visitor id). Legitimate re-login on a shared machine fails. My first version of this test passed for the wrong
reason (a constant-uuid fake host), which is itself a caution: the fake must vary the uuid.

## 3 · What the audit got wrong

1. **Line drift** on four citations (above). Cosmetic, but the remediating engineer will look at the wrong line in `assertion.ts`
   (`secretsFor`, not the fall-open) and in `provision-stamp.sh` (an `echo`).
2. **The 409 claim is narrower than it reads.** "The signed-identify retry also fails" is true **only for a tenant that has a
   secret**. On every stamp `provision-stamp.sh` produces there is no secret, so the retry **succeeds** (probe X5: 409 → detach →
   200 `linked`). The defect is invisible in demo, staging and production as provisioned today, and appears the moment a customer
   turns on the very control that F04 says they must. Worth stating: fixing half A surfaces defect D.
3. **The remedy "rotate the browsing session on logout" is necessary but not sufficient**, because of the miss below.
   Shipping only the audit's remedy would leave a working resurrection path.

Nothing in the finding is overstated. The consequence ("breaks the account boundary on shared devices") is, if anything, understated:
the same mechanism leaks the profile **live, before any logout**, into a second tab.

## 4 · What the audit missed (adjacent, same code path)

1. **A second resurrection path with no session id and no cookie.** `absorbIntoShopper` writes
   `user:{browserVisitorId} → personSessionId` (`SessionManager.ts:434-436`), and
   `getOrCreateSessionFromCookies` falls back to `resolveSessionIdByUserId(userId)` (`RealtimeSegmentEngine.ts:897-906`).
   Probe X1: after link **and** detach, `getOrCreateSessionFromCookies(null, 'vis-A', undefined, undefined)` returns the
   person (`userId: sh_91a8…`, `segments:['line_maternity_affinity','new_user']`, `isNewSession:false`).
   **Rotating the session and clearing cookies does not close this.** It is the pointer, not the session, that must be revoked.
2. **A live cross-tab leak, before any logout.** The SDK has **no `storage`-event listener** (grep of `src/sdk/*.ts`: none);
   `setVisitorId` updates only the calling tab. A tab opened before sign-in keeps sending `vis-A` forever, and after the link
   `user:vis-A` resolves to the person — so that tab personalises as the signed-in person. On a shared device the same
   in-memory id belongs to whoever sits down next.
3. **The forwarding pointer is renewed, so it never lapses.** `resolveRecord` (`SessionManager.ts:332-339`) rewrites
   `user:{raw.userId} = raw.forwardTo` and re-puts the browser record every 24 h on an ordinary read. Probe X4: I deleted
   `user:vis-A`, aged the record three days, made **one** `getSession('s-BROWSER')` call, and the pointer came back.
   The 30-day TTL never expires it on an active device.
4. **The session id is a bearer credential for a person's record** — read and write, unauthenticated beyond the
   browser-distributed site key:
   - `GET /realtime/session/s-BROWSER/analytics` → **200**, `segmentHistory:["line_maternity_affinity","new_user"]` (probe X2).
   - `POST /realtime/session/s-BROWSER/preferences {trackingConsent:false, personalizationEnabled:false}` → **200**, and the
     **person's** record now reads `{trackingConsent:false, personalizationEnabled:false}` (probe X7). `createOrUpdateSession`
     resolves the forward at `SessionManager.ts:200-201` and pins the person's id at :204, so the write lands on the person.
     A stranger can silently switch off a real shopper's tracking and personalisation. This straddles F04 and F05.
5. **Those session ids are weak.** `mintSessionId` (`src/sdk/identity.ts:56-58`) is `s-` + a ms timestamp in base36 +
   **six hex characters** = 24 bits of randomness, and since CW39 the client's id **names** the server session. A bearer
   credential with 24 bits is not a credential.
6. **Detach cannot revoke anything even in principle.** `identityRoutes.post('/:tenant/identity/detach')`
   (`src/routes/identity.ts:98-105`) ignores the body entirely — the SDK sends `{visitorId}` at `identify.ts:47` and the
   route never reads it — and its only action is `clearCookieHeaders()`. The comment at `SessionManager.ts:660-661` states
   the design: *"nothing server-side changes."* That is the root cause of the whole second half of F04.
7. **The SDK rotates the visitor even when detach fails.** `logout()` (`identify.ts:45-50`) calls `setVisitorId` without
   checking `res.ok`. On a blocked/offline/4xx detach the person's `opt_session_id` cookie survives, and the next request from
   the fresh anonymous visitor lands on the person **directly by cookie** (probe B6) — a third path.
8. **Two tests that pass for the wrong reason** (all 50 identity tests pass at HEAD):
   - `src/routes/identity.test.ts` — *"a shared computer, second account without a logout: the second person inherits nothing,
     the first stays whole"* reads as shared-device coverage and passes. It only covers the second person **signing in**
     (which takes the `repoint` branch and is genuinely safe). It never covers the second person **browsing anonymously**,
     which is the failing case.
   - `src/sdk/identify.test.ts:63` — *"logout detaches, mints a fresh anonymous id, and reconnects under it"* asserts the
     visitor id, both stores and the socket, and asserts **nothing** about `opt_session`.

## 6 · Severity, size, remedy

**Severity: blocks launch.** Agreed. The brief's scale reserves that label for live-data safety, and both halves are
account-boundary failures against real shoppers. Half A also makes a stronger statement than the audit does: the platform
as provisioned has *no* account authentication at all, and the only artefact that records the difference (`assurance:'site'`)
is written to a store nothing reads.

**Size: M.** Agreed, for the whole remedy. The audit's own remedy list is correctly scoped — it is not over-scoped — but it is
**under-scoped in one specific place**: "rotate the browsing session on logout" does not close the `user:{visitorId}` pointer
path (miss 1) or the live cross-tab path (miss 2). Add "revoke the browser→person pointer on detach" to it.

**Smallest safe fix that closes the launch-blocking part (S, ~2–3 engineer-days including tests):**

1. **Fail closed on account proof.** In `verifyAssertion` (`src/identity/assertion.ts:98-99`), return
   `{ok:false, reason:'identity verification not configured'}` instead of `assurance:'site'` when
   `AUTH_MODE === 'enforced'` (or behind a new explicit `IDENTITY_ASSURANCE=site|required`), and add
   `IDENTITY_SECRETS` to `scripts/provision-stamp.sh` beside `IDENTITY_SALT` (line 49). Surface it in
   `/v1/:tenant/monitor` so a stamp missing it reports unready rather than silently accepting claims.
2. **One ownership guard, which closes every read and write path at once.** In
   `RealtimeSegmentEngine.getOrCreateSessionFromCookies` (and in the two `/realtime/session/:sessionId/*` handlers),
   after resolving, refuse a record whose `identity.shopperId` is set and is not the requesting `userId` — treat it as a
   new session instead. Because `getSession`, `getSessionAnalytics`, `updateUserPreferences` and `createOrUpdateSession`
   all funnel through `resolveRecord`, this single check closes the carried-session path, the `user:`-pointer path, the
   cross-tab path, the failed-detach cookie path and the analytics/preferences bearer paths.
3. **Make logout mean something.** Have `POST /identity/detach` read the `visitorId` the SDK already sends, delete
   `user:{visitorId}`, and strip `forwardTo` from that browser's own session record; and have `logout()` in
   `src/sdk/identify.ts` mint a new browsing session as well as a new visitor id (a `core.newSession()` beside
   `setVisitorId`).

Items 1 and 2 are the launch gate. Item 3 is correctness and hygiene and can follow within the same week.
Defer to the F01/F03 workstreams: authenticating `/realtime/session/*` properly, and replacing the 24-bit client-minted
session id with a server-minted one — but note that the guard in item 2 is what makes those merely defence in depth
rather than the only control.
