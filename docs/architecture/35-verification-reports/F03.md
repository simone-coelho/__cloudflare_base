Detail:

- **`edgeAccess.ts:115–127`.** `sdkKey()` reads `const tenant = (c.req.param('tenant') ?? '').trim() || null`
  (122) and calls `verifySdkKey(key, tenant, c.env)` (123). On success it calls `next()` (124) and throws
  `verdict.tenant` away. `verifySdkKey` is called from exactly one place in the whole source tree; its
  `tenant` field is never consumed anywhere.
- **`verifySdkKey` (96–105).** With `tenant === null` it accepts *any* recognised key: `if (tenant && …)`
  short-circuits. So the gate on `/realtime/*` answers only "is this a key we issued to somebody".
- **`tenancy/middleware.ts:74–95` → `tenant.ts:127–149`.** `resolveTenant` precedence is explicit → header
  → host, restricted to `provisioned`. The module's own comment (`tenant.ts:104–116`) states the hazard:
  *"WITHOUT THIS, `X-Tenant` IS AN UNAUTHENTICATED BRAND SELECTOR."* The mitigation is a scope limit
  (provisioned brands only), not authorization.
- **`sdk/core.ts:15–22, 121, 126, 213`.** `DEFAULT_PATHS.action/ws/reflex` are `/realtime/*` — no
  `{tenant}` token, so `url()`'s substitution (121) never fires for them. `headers()` (126) sets only
  `X-SDK-Key`. `socketUrl()` (213) carries `userId` and `sdkKey`. `envelope()` (130–143) carries no brand.
  `resolveConfig` keeps `cfg.brand` (43) but the transport never sends it.
- **`auth/store.ts:9–24`** `UserRecord` = id, email, name, roles, permissions, password fields. No tenant.
  **`routes/auth.ts:37–40`** `mintAccess` signs `{ sub, email, name, roles, permissions }`. No tenant claim.

## 3 · Severity and size

**Severity: blocks launch. I agree with the audit.** The brief's §5.12 claims "a tenant with brands … One
worker serves every tenant of a stamp"; scope appendix §1.7 promises "hard data isolation between brands …
a provisioning exercise rather than another build". The code cannot honour that: provisioning the second
brand is the exact moment isolation fails. Under the brief's own definition — "representations that the
full contracted capability is delivered" — that is blocks-launch, independent of whether anyone has yet
been harmed. And the attacker's cost is nil: `public/edge-auth.js:30` reads the site key from
`<meta name="edge-sdk-key">`, so "a verified key for brand A" means View Source on brand A's storefront.

**Size: M–L. I agree**, with one correction of emphasis. The audit presents one L-shaped programme. It
contains an **S-shaped launch blocker** (the gate, the SDK's two lines, the tests) that can ship in days,
and an M–L remainder (scoped operator memberships, one immutable context threaded to every store and
connector, cross-surface tests) that can follow — *provided* no second brand is provisioned first.

## 4 · What the audit got wrong

1. **It overstates today's exposure by omission.** The consequence paragraph reads as a live breach. It is
   not: `TENANTS` is unset on both deployed stamps, so only `coach` is provisioned and `X-Tenant` is inert
   (probe 7). This is a latent defect that arms on provisioning. Say so, or the first question from the
   architecture team ("are we breached now?") gets the wrong answer.
2. **`edgeAccess.ts:122`** is where the URL tenant is read; the check is 123. Trivial, but a reader
   grepping line 122 for a comparison will not find one.
3. **`config.ts:123`** is the write-gate's opening line; `jwt({required:true})` is 125. More substantively
   the audit *under*-describes it: `scopeOf` (`config.ts:45–50`) takes the scope from a caller-supplied
   **query parameter**, and `versionedStore.ts:113–115` writes `reflex:config:{scope}:current` straight
   into `env.CACHE` with **no `TenantKV`, no tenant prefix at all**. `configStore.ts:48` says CW1 "makes it
   `{tenant}:{surface}`" — future tense; it was never done. The reflex config is not weakly tenant-bound,
   it is entirely tenant-blind.
4. **The SDK fall-back is described too gently.** "Can fall back to Coach" is true; what it means is that a
   non-default brand's shopper state is written into the **default, unprefixed** key space — Coach's
   production keys — silently, with nothing recording which brand meant to write, so it is not separable
   afterwards.

Nothing in the finding is refuted.

## 5 · What the audit missed (adjacent, same code path)

1. **The operator-token branch bypasses the one working gate.** `edgeAccess.ts:119–120`: no site key + any
   Bearer token → `jwt({required:true})`, and the tenant param is never consulted on that branch. Probe 3.
   A second, independent route to the same failure, on `/v1/:tenant/*` where the key binding otherwise
   holds. The audit notes the missing membership model but never connects it here.
2. **Split-brain tenancy inside one request.** `decisions.ts:332–337` documents it as deliberate: "Two
   names, on purpose … the path names the SCOPE the documents are read under; the tenancy middleware names
   the brand whose shopper state … this request belongs to." Downstream, `content/service.ts:155` reads the
   shopper under `stateTenant` while `:200`, `:212` (`readRing`) and `:225` stamp records and read the
   visitor ring under the **path** tenant. So one request can serve brand B's catalogue and slots from
   brand A's affinity vector and session, and write ledger rows stamped `tenant: B` (R2 prefix
   `B/{date}/{hh}`, `ledger/records.ts:48`) built from A's behaviour. **This needs no second provisioned
   brand**: `decisions.ts:320` only shape-checks the path slug (`TENANT.test`), never against
   `provisioned`. It is live today for anyone holding the wildcard demo key or any operator token.
3. **Blast radius unquantified. 24 of 37 `/v1/:tenant/*` routes** take the tenant from the URL behind
   `jwt({required:true})` alone: the ledger export (`decisions.ts:355`, `:416`, `:434`), erasure
   (`:388`, `:399`, `identity.ts:175`), identity resolution (`identity.ts:108`, `:120`, `:130`), per-visitor
   receipts (`:223`) and recent activity (`:270`), the learning cycle and publish (`:288`, `:513`). One
   path segment is the entire authorization decision for another customer's export or erasure.
4. **The shipped default `SDK_KEYS='*:demo-site'`** (docs/deployment/01-deploy.md:34, wrangler.toml:149,
   `.dev.vars`) makes even the working `/v1` binding a no-op. Probe 4. Any remedy must refuse `*` when
   `AUTH_MODE==='enforced'` and more than one brand is provisioned.
5. **Two tests that pass for the wrong reason.** `edgeAccess.test.ts:76` asserts
   `verifySdkKey('k-kate', null, e) === {ok:true, tenant:'kate'}` — the *helper* computes the owner
   correctly and the *middleware* (`:124`) discards it; no test anywhere asserts which tenant a request was
   served as. `tenancy/middleware.test.ts:76–78` — "lets the header override the host, which is how an
   operator tool reaches a brand" — codifies the crossing as intended behaviour. 84/84 green.
6. **An implementation trap in the remedy.** `X-Tenant` is not in the CORS `allowHeaders` at
   `src/index.ts:74` (`Content-Type, Authorization, X-Request-Id, X-SDK-Key`). Making the SDK send the
   brand as a header without changing that list fails every cross-origin preflight.
7. **No provisioning path for a second brand's key.** `provision-stamp.sh:50` runs
   `printf '%s' "$TENANT:$SITE_KEY" | wrangler secret put SDK_KEYS`, which **replaces** the secret.
   Provisioning brand two on a stamp deletes brand one's key. §5.12's multi-brand stamp has no tooling.

## 7 · Remedy assessment

Directionally right and correctly scoped to the contract. "Resolve one canonical customer/brand context,
authorize the key or operator against that exact context, and pass it immutably to every store and
connector" is exactly the right sentence. Three corrections:

- **Sequencing, not scope, is the problem.** As written it reads as one L programme; the launch-blocking
  part is S and should not wait behind the membership model.
- **Under-scoped in two places:** it does not say to refuse the `*` wildcard in enforced multi-tenant mode,
  and it does not name the operator-token bypass in `sdkKey()` — a reader could implement the whole remedy
  and leave `/v1/:tenant/*` open to any token.
- **"Reject conflicting header/path/host/SDK identities" is the right instruction** and is the single
  highest-value line in it; it also happens to close the split-brain in §5.2 as a side effect.

### Smallest safe fix that closes the launch-blocking part

In `sdkKey()` (`src/middleware/edgeAccess.ts:115–127`), authorize against the **resolved** tenant instead of
only the path parameter, and refuse disagreement:

```ts
const ctx  = tenantForRequest(c.env, c.req.raw);          // one canonical context
const path = (c.req.param('tenant') ?? '').trim();
if (path && path !== ctx) return c.json({ ok:false, error:'tenant mismatch' }, 409);
const verdict = verifySdkKey(key, ctx, c.env);            // was: verifySdkKey(key, path||null, …)
```

plus (a) apply the same `ctx` check on the Bearer branch at line 119 rather than accepting any token, and
(b) refuse a `SDK_KEYS` entry of `*` when `AUTH_MODE==='enforced'` and `provisioned.length > 1`.

Probe 6 shows this returns 403/409 on all three crossings and the split-brain, and 200 on both legitimate
cases and both demo-wildcard cases. It must ship **together with** the SDK sending its brand —
`X-Tenant: cfg.tenant` in `headers()` (`sdk/core.ts:126`) and `tenant=` in `socketUrl()` (`:213`) — and
`X-Tenant` added to `allowHeaders` (`src/index.ts:74`); otherwise a brand on a shared hostname turns from
silently-Coach into a loud 403. Roughly S: 1–3 engineer-days including negative tests that assert *which
tenant a request was served as*, through HTTP, the SDK and the socket, using two non-default brands.

The membership model for operator accounts (a `tenants` column on `UserRecord`, a claim in `mintAccess`, an
`authorizeTenant(c, tenant)` on the 24 jwt-only `/v1/:tenant/*` routes) remains M and is shared work with
F02. Threading one immutable context to every store and connector remains L. Neither blocks the fix above.
