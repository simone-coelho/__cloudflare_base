### 2.4 The SQL policy (`probe-sql.ts` through the real tool; `probe-sqlite.mjs` through real SQLite)

`getOpalTools(env).queryData.execute(...)` with a `DB` stub that records what reaches `prepare()`:

| Input | guardSelect | Reaches `env.DB.prepare` |
|---|---|---|
| `SELECT * FROM operator_accounts LIMIT 5` | refused | no |
| `SELECT * FROM"operator_accounts" LIMIT 5` | **passed** | **yes** |
| `SELECT * FROM/**/operator_accounts LIMIT 5` | **passed** | **yes** |
| `SELECT * FROM [operator_accounts] LIMIT 5` | **passed** | **yes** |
| `SELECT password_hash, email FROM--c⏎operator_accounts LIMIT 5` | **passed** | **yes** |
| ``SELECT * FROM`operator_sessions` LIMIT 5`` | **passed** | **yes** |

All five then **execute** against a real SQLite engine (`node:sqlite`, D1's engine) and return rows, e.g.
`{"email":"ops@example.com","password_hash":"pbkdf2$100000$…"}` and `{"jti":"j1","token_hash":"sha256-abc"}`.

The defect class: the ref extractor at `tools.ts:34`
(`/\b(?:from|join)\s+["'`]?([a-zA-Z_][a-zA-Z0-9_]*)["'`]?/gi`) requires whitespace after `FROM` and an
unbracketed leading identifier character. When it fails to match, `refs` is empty and **nothing is checked** —
the guard fails **open**, not closed.

## 3 · Why this blocks launch, stated for the record

* Both customer stamps exist and both set `AUTH_MODE = "enforced"` (`wrangler.toml` `[env.staging.vars]`,
  `[env.production.vars]`). "Enforced" is therefore a claim the team makes about those hosts, and §2.1 shows
  it covers two prefixes out of roughly twenty-five mounts.
* `[env.staging.assets]` and `[env.production.assets]` both set `directory = "public"` — **361 files, 74 MB**
  of demo storefront, Opticon/Meridian, Bright Hour and console pages are part of the customer deployable.
  `public/storefront.html:6` and `public/operator-console.html:6` carry `<meta name="edge-sdk-key"
  content="demo-site">`, the same example key doc 32 §7 says staging accepts.
* The `OpalAgent` Durable Object binding is declared in **both** customer stamps, and its `DB` binding is the
  same D1 database migration `0010_operator_accounts.sql` puts `operator_accounts.password_hash` and
  `operator_sessions.token_hash` in.
* The harm is bounded in one useful way: `CDPService` is used only by `/cdp/*`, so profile poisoning does not
  reach the decision path. It is an anonymous read/write PII store on the customer's own host, not corrupted
  personalization.

## 4 · What the audit got wrong

1. **`src/index.ts:85` gates both prefixes.** It gates `/realtime/*`; line 86 gates `/v1/:tenant/*`. Trivial.
2. **"General agent-binding exposure is a source/installed-dependency finding, not a remotely demonstrated
   compromise."** Half right. It is *not* a dependency defect: the application calls
   `routeAgentRequest(request, env)` at `index.ts:185` with no options and before auth, and the SDK documents
   `onBeforeRequest`/`onBeforeConnect` hooks that were not used. And it is demonstrable — locally, in workerd:
   three `101` upgrades and a working rate-limiter write (§2.1). "Not *remotely* demonstrated" is fair and
   should stay; "source/installed-dependency finding" should go.
3. **"no real account data was read"** is true of their probe but reads as reassurance. The tool's `DB` is the
   database that holds the operator credential table. The right sentence is: the guard fails open, and the
   table it is protecting the caller from is in the same database.
4. **The remedy leads with the expensive half.** "Ship an explicit customer route/binding allowlist" is
   correct but reads as a project. The launch-blocking part closes with ~25 lines that are *inert* while
   `AUTH_MODE = 'open'` (§7), so the demo worker and the Opticon stage cannot break.
5. **Nothing in F01 is refuted.** Every claim I could check, held.

## 5 · What the audit missed, adjacent to the same finding

1. **The credential store is in the agent's database.** `migrations/0010_operator_accounts.sql` puts
   `operator_accounts` (PBKDF2 hashes) and `operator_sessions` (refresh-token SHA-256) in the same D1 the
   `queryData` tool queries, in every environment. Chain: unauthenticated `/agents/opal-agent/<name>` → chat
   turn → `queryData` → one of the five bypasses → credential hashes. This is the escalation that makes F01
   and F02 one story rather than two.
2. **Five named bypasses, and a fail-open parser.** Not "could pass a request" — `FROM"t"`, `FROM/**/t`,
   `FROM [t]`, `FROM--c⏎t`, ``FROM`t` ``, all valid SQLite. See §2.4.
3. **A second WebSocket door around the SDK-key gate.** `ShopperReflex.fetch` (line 243) and
   `PersonalizationWebSocket.fetch` (line 56) test `Upgrade: websocket` **before** routing on pathname, so
   `/agents/shopper-reflex/<name>?userId=x` and `/agents/personalization-websocket/<name>?userId=victim`
   return `101` — the shopper socket the `/realtime/*` gate is supposed to guard, reached around it. Frames
   of `{"type":"action"}` on the reflex socket run the same reducer as `POST /ingest`.
   **The corresponding bound, which the audit also did not establish:** the HTTP doors of those objects
   (`/snapshot`, `/ingest`, `/reset`, `/identity/*`) are **not** reachable this way, because the DO sees the
   path `/agents/…` and 404s. `StateManager`, `DecisionRing`, `LearnStats`, `RegionTrend` are inert for the
   same reason. Say both halves or the finding will be argued down.
4. **`RateLimiter.fetch` ignores the pathname entirely** (`src/durable-objects/RateLimiter.ts:10`), so
   `/agents/rate-limiter/<CF-Connecting-IP>` is a working, unauthenticated, targeted denial of service on
   that caller's `/api/*` budget — reproduced (second call `allowed:false`). Note also that `/api/*` is the
   only rate-limited prefix in the worker: `/sort`, `/cdp/*`, `/ai/*`, `/track/*` have no limiter at all.
5. **Operator *reads* are open in enforced mode by design.** `operatorWrites()`
   (`src/middleware/edgeAccess.ts:140`) passes every `GET`/`HEAD`/`OPTIONS`. On the customer stamp
   `GET /operator/insights` and `GET /operator/audiences` answer `200` to anyone. That is a recorded decision
   ("reads stay open"), but on a customer host it publishes audience definitions and aggregate analytics.
6. **`/live/ops-api/*` is an unauthenticated demo *operator* surface.** `POST /live/ops-api/reset` returned
   `200 {"reset":3}` in enforced mode. The audit lists demo *shopper* and AI routes; it does not name the
   Bright Hour Offer Desk write surface, nor `/meridian/api` (`index.ts:111`).
7. **`/webhook/segment` and `/webhook/custom` verify nothing.** Only `/webhook/optimizely-datafile` checks
   `X-Hub-Signature`, and only when `OPTIMIZELY_WEBHOOK_SECRET` is set (`src/routes/webhook.ts:63`). Anonymous
   event injection into the customer's event pipeline.
8. **The brand is caller-selected on ungated routes** via `X-Tenant` (§2.3) — any *provisioned* brand, which
   on a Tapestry-wide stamp is the point.
9. **The key-bearing pages ship with the stamp** (§3, third bullet). Doc 32 §7's staging key is not just a
   secret to rotate; the deployable contains the pages that publish it.
10. **No test enumerates the real route table.** §2.5.

## 7 · Remedy assessment, and the smallest safe fix

The audit's remedy is **right in direction and over-scoped as one unit of work.** It bundles five things of
very different sizes: deny-by-default routing (small), authenticating agent dispatch (small), removing demo
surfaces from customer stamps (medium), replacing free-form reporting SQL with scoped views and
least-privilege storage (medium, and the correct fix), and route/scope/workload rate limiting plus a negative
authorization test matrix (medium). Estimating that as one **M** hides that the launch blocker closes in a
day and the rest is hygiene that can follow on a schedule.

**Smallest safe fix (S — roughly 1–3 engineer-days including the negative tests). Two edits, both inert while
`AUTH_MODE = 'open'`, so the demo worker and the Opticon stage cannot regress.**

1. `src/index.ts`, before the route table — deny by default in enforced mode:

```ts
// Enforced stamps serve the customer surface and nothing else. Open mode is untouched.
const CUSTOMER_SURFACE = [/^\/health\b/, /^\/auth\//, /^\/v1\//, /^\/realtime\//,
                          /^\/sort\b/, /^\/content\//, /^\/config\//, /^\/operator\//, /^\/track\//];
app.use('*', createMiddleware<{ Bindings: Env }>(async (c, next) => {
  if (authMode(c.env) === 'open') return next();
  const p = new URL(c.req.url).pathname;
  return CUSTOMER_SURFACE.some((r) => r.test(p)) ? next()
       : c.json({ ok: false, error: 'not available on this stamp' }, 404);
}));
```
   This alone removes `/cdp/*`, `/ai/*`, `/experiment/*`, `/live/*`, `/meridian/api`, `/funnel*`, `/signals`,
   `/geo`, `/webhook/*`, `/optimizely/*`, `/pixel/*` and `/api-info` from the customer stamps. Then extend
   `app.use(..., sdkKey())` to `/sort` and `/track/*` so what remains is gated, not merely reachable.

2. `src/index.ts:185` — do not dispatch to agents on a customer stamp:

```ts
const agentResponse = authMode(env) === 'open' ? await routeAgentRequest(request, env) : null;
```
   If the agent must live on a customer stamp later, it needs **both** halves: an operator-JWT
   `onBeforeRequest`/`onBeforeConnect`, **and** a namespace allowlist (`opal-agent` only) — because the
   router otherwise publishes every Durable Object binding in the environment, including the shopper socket.

Then, before any customer connection (separately sized, **M**): replace `queryData`'s free-form SQL with a
fixed set of parameterised reporting operations; give the agent a database that does not contain
`operator_accounts`; and add the negative-authorization test that walks the *real* route table plus every
`/agents/<binding>/…` namespace in enforced mode — the test `edgeAccess.test.ts` only pretends to be.
Complete deployable separation (a customer stamp built without `public/`, without demo agents, without the
demo D1) remains **L**, and I agree with the audit that it is the destination.
