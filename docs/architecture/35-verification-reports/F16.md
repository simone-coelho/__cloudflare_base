## 3 · Verdict, severity and size

**Confirmed.** Every evidence claim holds at HEAD; both stated consequences reproduce; the mechanism is
ordinary at-least-once queue semantics plus an application that never wrote the corresponding dedup.

**Severity: blocks the pilot** — I agree with the audit's label. The learning numbers, the day report, the
exploration audit and the holdout comparison are all derived by counting rows, and all of them move on a
delivery accident. Two qualifiers a Managing Principal should hold:

- **It does not change what is served today.** Every slot's `gamma` defaults to 0 (`src/content/service.ts:220`,
  applied at `src/content/decide.ts:179`: `base * Math.pow(look.lift, gamma)`), so a corrupted lift is displayed, not
  applied. The moment an operator raises the dial — or `learn/cycle.ts` autonomy raises it — corrupted
  evidence starts changing the page.
- **The "lose" half is closer to blocks launch than the audit says.** There is no dead-letter queue on any
  environment and `max_retries = 2`; three failed attempts and the rows are gone from the customer's system of
  record with a single `console.error`. The producer-side `catch` is silent even of that. For a ledger that
  also backs erasure receipts and the warehouse export, silent unbounded loss is a production-reliability
  representation, not a reporting nuisance.

**Size: M**, and I would split it rather than quote "M–L":
- **S (~2–3 days):** read-time dedup in the two loaders, a dead-letter queue, a logged/counted producer
  failure, an `res.ok` check in `fan.ts`. This closes everything that blocks acceptance of the report,
  the holdout and the export.
- **M (~1–2 weeks):** online idempotency in `DecisionRing` + a nightly online-vs-batch divergence check.
- **L:** only if the team takes the transactional-outbox architecture the remedy asks for.

## 4 · What the audit got wrong

**4.1 The causal story behind `DecisionRing.ts:69` / `:82` is thin, though both lines are right.**
Reading the two together implies a duplicated append doubles a credit. It cannot: `attribute()`
(`src/learn/policy.ts:88–97`) collapses eligible entries with `bySlot`, one credit per slot per outcome, so a
duplicated ring entry cannot double-pay. What it actually does is inflate the CW30 fatigue count
(`fan.ts:50–59`; probe 2.3 shows `served = 2` for one real impression) and burn the 200-entry ring cap.
Further, the platform's online path never retries anything — `post()` has no retry, and the SDK's `send()`
returns `null` on failure (`src/sdk/core.ts:167`) — so identical *decision* appends do not arise from the
platform's own machinery. The realistic online duplicate is a re-posted **outcome**, and that one does
double-credit (probe 2.3: `credits 1 / 1` for one `outcome_id`).

**4.2 "Stable event/decision-set/outcome IDs" is already delivered; the remedy implies it is missing.**
`decision_id` is minted at decide time (`src/content/decide.ts:259`) and `outcome_id` at event time
(`src/ledger/records.ts:134`), both carried into every NDJSON row and every ring entry. Probe 2.1 shows the two
duplicate rows are byte-identical, same `outcome_id`. The work is to *use* the ids, not to introduce them —
which is the difference between an L and an S.

**4.3 "Idempotent storage" via object naming will not work, and the remedy as worded invites it.**
The obvious reading — content-address the batch object instead of `Math.random()` — does not close the defect,
because a Queues retry does not guarantee the same batch composition: the redelivered messages can be
regrouped with different companions, producing a different digest and therefore a different key again. And
per-message object naming would undo doc 31's whole point (one object per hour/stream per batch instead of
thousands). The reliable idempotency point on this path is the **read**, not the write.

**4.4 The export consequence is overstated by omission.** "R2 remains a good durable export substrate; its
object naming does not provide end-to-end exactly-once effects" is true, but every exported row already
carries a stable primary key, so the customer's warehouse can dedupe on `decision_id`/`outcome_id` today —
the standard at-least-once-into-exactly-once-in-the-warehouse pattern. What is missing is the **contract**:
doc 22 §12.4 says "The R2 partitions are the export… nothing is transformed on the way out" and never
mentions duplicates or a dedup key. One paragraph in the export contract converts the export half of this
finding from a defect into a documented property.

Nothing else: no wrong line, no wrong file, no misattributed behavior.

## 5 · What the audit missed, adjacent to F16

**(a) No dead-letter queue anywhere.** `wrangler.toml:29–34`, `:250–255`, `:348–353` set `max_retries = 2`
with no `dead_letter_queue`. Three failed attempts and the ledger rows are dropped forever — the concrete
mechanism behind the finding's own word "lose", and a one-line config fix per environment.

**(b) The producer swallows silently.** `src/ledger/enqueue.ts:19–21` is an empty `catch` with a comment; a
queue outage loses ledger rows with no log, no counter, no Analytics point. Probe 2.5 is exactly this failure.

**(c) `post()` never checks `res.ok`** (`src/learn/fan.ts:21–27`). A Durable Object answering 400 or 500 is
recorded as delivered by every caller.

**(d) `DecisionRing` reports credits it may not have applied.** `:93` fires the credit posts with
`.then(() => undefined, () => undefined)` and `:97` returns `credits.length` regardless, so a `/outcome`
response of `{ok:true, credits:2}` is not evidence that `LearnStats` received anything.

**(e) Duplication also causes loss, through the caps.** `MAX_HOUR_OBJECTS = 600` (`hourly.ts:46`) and
`REPORT_CAP = 50_000` (`report.ts:183`) are counted over duplicated objects and rows, so duplicates can push a
legitimate hour into `truncated: true` and silently drop real records from the fold.

**(f) `consumeLedger` mis-reports a partial batch** as `written: 0, objects: 0` when objects have already
landed (probe 2.2).

**(g) Unplaceable messages are dropped with only a `console.warn`** (`consume.ts:20`, `index.ts:264`). There is
no dead-letter copy of a row the writer could not place, so a malformed id removes a record from the ledger
permanently and invisibly.

**(h) A test that passes for the wrong reason.** `src/learn/hourly.test.ts:108` — "an hour built again is not
folded twice, and its aggregate still counts everything" — and the doc comment on `buildHour` ("Re-running an
hour never doubles it") read as idempotence coverage. They only prove the *ring* is not re-folded, via
`folded = ctx.from > state.through` (`hourly.ts:231`). Duplicate rows *inside* one hour are counted twice by
`foldDecisions` (`:199`) and re-attributed by `foldShard` (`:244`, `:260`). No test in the repository sends the
same row twice through either loader.

**(i) The acceptance run cannot detect this class of defect.** `scripts/acceptance-run.mjs` asserts
`counts.decisions >= 14`, `counts.outcomes >= 2`, `credited >= 1`, `s - before >= 0.99` — lower bounds, all of
them, so duplication passes. The single exception is the revenue-objective check `near(..., 250, 1)` at
`:202`, which a double-credited purchase would fail. If the team wants a gate, that is the shape it must have.

**(j) The opposite defect, which any dedup must handle.** `outcome_id = {tenant}:{ts36(ts)}:{userId}:{event}`
(`records.ts:134`) carries no nonce. Two genuinely distinct outcomes of the same event type from the same
visitor in the same millisecond share one id, so a naive dedup would *drop a real event*. Conversely a client
that re-fires an event with a fresh timestamp produces a new id that no dedup can catch. The dedup work must
come with a decision about both — a per-event nonce in the id, or an accepted, documented collapse.

## 7 · Remedy assessment and the smallest safe fix

The audit's remedy is directionally right and **over-scoped at the front and under-specified in the middle**:
the stable ids it asks for already exist (§4.2), the idempotent object naming it implies will not hold (§4.3),
and the transactional outbox is a genuine L that no pilot needs in order to accept a report.

**Smallest safe fix that closes the launch-blocking part (S, ~2–3 engineer-days):**

1. **Deduplicate on read, in two places.** In `loadDay` (`report.ts:157–180`) and `loadHourRecords`
   (`hourly.ts:350–369`), keep a `Set<string>` of `decision_id` / `outcome_id` and skip a row already seen;
   count the skips into the report as `duplicates_dropped` so the rate is visible instead of silent. Probe 2.6
   shows this restores the exact clean numbers, and it costs one Set of at most `REPORT_CAP` strings.
2. **Add a `dead_letter_queue`** to the three `[[queues.consumers]]` blocks, and alert on its depth. Rows the
   consumer cannot place stop vanishing.
3. **Stop swallowing the producer.** Log and count `sendAll`'s failure (`enqueue.ts:19`) and the `skipped`
   path (`consume.ts:20`); emit one Analytics point per drop so the gap in the ledger is discoverable.
4. **Check `res.ok` in `post()`** (`fan.ts:21–27`) and count the failures.
5. **One paragraph in doc 22 §12.4** stating that rows are at-least-once and that `decision_id` /
   `outcome_id` are the dedup keys, so the customer's warehouse job is correct by contract.

**Then, before learning is trusted (M):** carry a bounded set of recently credited `outcome_id`s in
`DecisionRing`'s stored state — the object already persists a 90-day id index, so the pruning exists — and drop
a repeat before `attribute()`; put `decision_id` back into the `/exposures` payload (`fan.ts:81`) so
`LearnStats` can do the same; and run a nightly comparison of the published lift snapshot against the day
report's learning grid, alerting past a threshold. That last check costs a day and is the only thing that would
have caught the disagreement in probe 2.5.

**Defer (L):** the transactional outbox / durable ingestion log with downstream state derived from it. It is
the right end state for "one event, one truth", and it is not what unblocks a pilot.
