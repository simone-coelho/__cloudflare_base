## 2 · Reproductions

All run from the repository root with `npx tsx`; scratch files under `/tmp/audit-verify/F22/`. Nothing in the
tree was modified; no network, no wrangler, no deploy.

### 2.1 The audit's own example (`repro-coupled.ts`)

Two pieces `a`, `b`, both eligible for `hero` and `rail`, equal base score 0.4, catalogue order `a` first.
A hero snapshot (version 11) gives `b` lift 2 at γ = 1. Rail's snapshot (version 7) is empty and changes nothing.

```
SERVED page:
  hero[0] = b  score_final=0.8 lift_v=11
  rail[0] = a  score_final=0.4 lift_v=7

REPLAY hero: ok=true equal=true    served=b  replayed=b
REPLAY rail: ok=true equal=false   served=a  replayed=b
  DIFF item_id   "a" -> "b"
  DIFF candidates [{"contentId":"a","score":0.4}] -> [{"contentId":"b","score":0.4}]
```

Exactly the audit's sentence. Note the shape: **the first ranked slot on a page always replays; every slot
after it is exposed.** The archive in this harness holds *both* snapshots — replay simply never asks for the
sibling's.

### 2.2 The same failure at γ = 0 — the audit missed this (`repro-explore.ts`)

γ = 0 on every slot (shadow mode, the brief's stated default), so the lift channel is inert. `hero` has
`exploration: { mode: 'rotation', share: 1, floor: 50 }`. At serve time hero's snapshot shows n = 400 ≥ floor,
so `explorationPick` (`src/learn/explore.ts:110-115`) finds nothing under-observed and returns null; hero
serves `b`. On replay hero's snapshot is `undefined`, `observationsOf` (`explore.ts:49-51`) returns 0 for
everything, every item is under-observed, and rotation picks `a`:

```
SERVED page (gamma = 0 everywhere):
  hero[0] = b explored=false lift_v=21
  rail[0] = c explored=false lift_v=22

REPLAY hero: ok=true equal=true    served=b replayed=b
REPLAY rail: ok=true equal=false   served=c replayed=b
  DIFF item_id, explain.score_base (0.5 -> 0.9), explain.score_final, explain.drivers, candidates
```

Thompson mode is worse: with no snapshot every draw is Beta(1,1) (`explore.ts:92-96`), so the earlier slot's
whole ranking is randomised on replay. **Conclusion: this is not gated on turning learning on.** Any earlier
slot with `rotation` or `thompson` exploration breaks every later slot's replay while γ is still zero.

### 2.3 The archive gap is permanent (`repro-archive.ts`)

Instantiated the real `LearnStats` Durable Object class with stub `state`/`env`, made `STORAGE.put` throw once:

```
publish #1  version = 1788716902641
  KV keys : [ 'lift:coach:coach:hero' ]
  R2 keys : []                          (R2 failing)
publish #2  version = 1788716902647     (R2 healthy)
  R2 keys : [ 'lift/coach/coach/hero/1788716902647.json' ]
  is version 1788716902641 archived now? -> false
```

Every decision stamped `versions.lift = 1788716902641` in that window is permanently unreplayable; the replay
returns `ok:false, "lift snapshot … is not in the archive"`. The comment at `LearnStats.ts:114` —
"the next publish archives again" — is wrong, because `version` is `Date.now()`.

## 3 · What the audit got wrong

Nothing factual. Four calibration points:

1. **Understates when it fires.** The example reads as a consequence of turning the lift on. §2.2 shows it
   fires with γ = 0 across the board, through exploration on an earlier slot. Shadow mode is the pilot default,
   so "we'll turn learning off for the pilot" is not a mitigation.
2. **Understates the archive gap.** "may have no durable archive at all" reads transient. It is permanent for
   the affected version, and the code comment claiming self-healing is false (§2.3).
3. **Remedy names work already done.** "state/context time" is already recorded — `served.ts` is the
   `nowMs` passed to `decideContent` (`replay.ts:88`). "Stochastic seed/policy" is already recoverable —
   `explorationPick` is a pure function of `visitorId`, `slot`, `hourKeyOf(nowMs)`, the ranked list, the
   snapshot and the config, all of which are recorded or fetched. Listing them implies missing work that is
   not missing, and inflates the estimate.
4. **"Persist a decision-set ID" is hygiene, not the load-bearing fix.** A set key is already derivable:
   `decision_id` is `` `${tenant}:${nowMs.toString(36)}:${visitorId}:${page}:${slot}:${position}` ``
   (`src/content/decide.ts:255`), and the records also carry `tenant`, `visitor_id`, `page`, `ts` as fields.
   `findById` (`src/ledger/writer.ts:87`) already opens exactly the objects holding the siblings.

The closing paragraph on causal offline evaluation is correct but is a *different* problem (F23 territory).
Bundling it into F22's remedy is what turns an S into an M.

## 4 · What the audit missed

1. **The exploration channel (§2.2).** Rotation and Thompson read `learning.snapshots[slot]`, so replay can
   *invent* an exploration pick on an earlier slot that never happened, or suppress one that did — at γ = 0.
2. **The blast radius is the launch configuration, not a contrived one (§2.4).** 21 of 26 Coach pieces are
   multi-slot; 7 of 9 home-page positions sit downstream of the first learning slot.
3. **The only test of replay passes because both preconditions for the defect are absent.**
   `src/learn/phase3.test.ts:147-176` is the sole caller of `replayDecision` in the repository. Its page is
   `slots = [{ slot: 'hero', take: 1, … }]` — **one slot** — and its `ReplayDeps.archive` is
   `async () => null` with `versions.lift = 0`, so the archive branch never executes. The suite is green
   (`npx vitest run src/learn/phase3.test.ts` → 10 passed) and proves nothing about multi-slot pages.
4. **Pinned, non-personalizable decisions are stamped with a lift version they never used.**
   `decide.ts:260` sets `lift: learning?.snapshots[d.slot]?.version ?? 0` for every record including pins,
   and `service.ts:212` reads a snapshot for *every* slot on the page. Probe (`repro-pinned.ts`):
   a `merch` record with `authority = pin`, `explain.lift = null`, `versions.lift = 909` →
   `replay ok=false, "lift snapshot 909 is not in the archive"`. A decision learning could not have touched
   is refused.
5. **Nothing exercises the endpoint.** `scripts/acceptance-run.mjs` never calls `/v1/:tenant/replay/`
   (its one mention of "replay" is a comment on the fatigue counts), and no console asset links it. That is
   why this survived to the audit.
6. **The `candidates`-only failure mode** produces `equal:false` on receipts whose served item is correct —
   noisy, and hard for a support engineer to triage without knowing this finding.

Two things I checked that are **not** defects, so the team does not chase them: `candidateLimit` —
`replay.ts:92` uses `Math.max(10, served.candidates.length)` while the service passes nothing (default 10 at
`decide.ts:192`), so the two agree today; and the regional block — `regionalOf` only pushes an explain driver
and never changes a score, so reconstructing it from the target record alone is safe.

## 5 · Severity and size

**Severity: blocks the pilot.** I agree with the audit. Serving is unaffected — this is a read-only diagnostic
endpoint — so it is not live-data safety or production reliability, which is what the brief reserves
"blocks launch" for. But replay is the artefact behind "explains every decision" and doc 22 §12.3's
"equality is the proof that the explain record is the truth rather than a narrative about it". Shipping an
endpoint that calls 32% of honest receipts unequal is worse than not shipping it: it manufactures evidence
of tampering. The elevation argument — the brief's "representations that the full contracted capability is
delivered" — is available if the customer's acceptance criteria name auditability of a decision; I did not
take it, because the capability exists and is wrong only on multi-slot pages.

**Size: S for the defect (audit says M for the remedy list).** The audit's M is defensible for everything it
lists, but three of its five remedy items are already satisfied (§3.3) and the off-policy-evaluation paragraph
is a separate piece of work. The launch-blocking core is 1–3 engineer-days including tests.

## 7 · Remedy assessment and the smallest safe fix

**Right on two items, over-scoped on three.** Correct and load-bearing: *per-slot lift/prior versions*, and
*durably archive dependencies before making their manifest serveable*. Already satisfied: state/context time,
stochastic seed/policy. Hygiene rather than fix: the decision-set ID. Separate problem: causal offline
evaluation, support and propensities, an agreed estimator — that belongs with F23 and the holdout, not here.

**Smallest safe fix that closes the launch-blocking part (S, ~1–3 days):**

1. **`src/content/decide.ts`** — carry the page's per-slot snapshot versions on every record, e.g.
   `versions.page_lift: Record<slot, {lift, prior}>` built once from `i.learning.snapshots`
   (a handful of integers; the record already carries a ~1 KB `inputs` block). This removes any dependence on
   finding sibling records.
   *Cheaper alternative if the schema must not move:* have `replayDecision` collect the siblings —
   `findById` already scans the exact objects that hold them — matching on
   `(tenant, visitor_id, page, ts)`, and read each slot's `versions.lift`/`versions.prior` from them.
2. **`src/learn/replay.ts:68-94`** — fetch the archive for **every** slot on the page at that slot's recorded
   version and pass the full `snapshots` map to `decideContent`. When a sibling's archive is missing, fail with
   a reason that **names the slot** (`fail(served, 'the archive for slot X version N is missing; this page
   cannot be replayed')`) instead of silently replaying with a hole.
3. **`src/durable-objects/LearnStats.ts:107-116`** — write R2 **before** KV, and skip the KV publish if the
   archive throws, so no served snapshot version can ever be unarchivable. The alarm is a 30-second coalescing
   background job, so the added latency is free. Re-arm the alarm on that path (`arm()` today only fires from
   `/exposures` and `/credits`), otherwise a quiet slot stalls until the next event.
4. **`src/content/decide.ts:260`** — stop stamping `versions.lift`/`prior` where the snapshot could not have
   applied (`authority === 'pin'`, or `arm === 'default'`), or make replay skip the archive fetch for those.
   Closes the false refusal in §4.4.
5. **`src/learn/phase3.test.ts`** — add a multi-slot replay case with a real archive: two slots sharing a
   piece, an earlier-slot lift that flips the earlier pick, assert the later slot replays `equal: true`.
   Add the γ = 0 rotation case from §2.2. The existing one-slot test cannot fail and must not be the gate.

Items 1–3 close the defect. Item 4 is a five-line correctness tidy in the same path. Item 5 is what stops it
coming back.
