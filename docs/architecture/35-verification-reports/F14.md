## 2 · Reproductions

All run from the repository root with `npx tsx`, scratch files under `/tmp/audit-verify/F14/`. Every harness uses the real modules (`SessionManager`, `RealtimeSegmentEngine`, `getConnectors`) with only the KV binding stubbed, and — except where stated — a **strictly visible** in-memory KV, i.e. kinder than the real store.

### R1 · Lost update at the session manager (`repro1.ts`)
Seed `session:s1` with `product_views: 3`; two overlapping event-shaped updates, each reading then writing the whole record.
```
product_views after two concurrent views: 4   (a correct authority would say 5)
A_seen present: true | B_seen present: true
writes per key: { 'session:s1': 3, 'user:v1': 3 }
```
The loss is **selective and silent**: because `:226` re-merges `existingSession.attributes` at write time, keys the loser did not compute survive, while every value derived from the stale read (counters, `reflex`, `segments`, `engagementScore`) is clobbered. The record looks consistent and is not.

### R2 · The same through the real engine (`repro2.ts`)
Two `product_view` events for two different products, same session, concurrent, through `RealtimeSegmentEngine.processActionEvent`.
```
product_views: 1   (two views happened)
reflex: {"dims":{"line":{"Tabby":…},"category":{"Handbags":…}, …}}   — one product only
```
The second view leaves **no trace at all**: no counter, no affinity dimension, no engagement.

### R3 · The realistic burst (`repro8.ts`)
`src/sdk/emit.ts:101` fires `void track('content_impression', …)` per newly visible slot — un-awaited, so a page paint is N concurrent POSTs. Eight concurrent views on one session:
```
writes to session:<id> in that burst: 7   (Cloudflare documents 1 write/second/key)
product_views recorded on the session: 1 of 8
affinity values accumulated: 8            — one product's dimensions
```
**Seven of eight signals are lost**, at seven times the documented per-key write rate.

### R4 · KV traffic per event (`repro4.ts`)
```
COLD event  writes { session:<id>: 2, user:<id>: 2, audience:*: 47, reflex:audgen:v1: 1 }
            reads  { session:<id>: 5, user:<id>: 1, profile:v1: 1, audience:*: 10, … }
WARM event  writes { session:<id>: 1, user:<id>: 1 }
            reads  { session:<id>: 5, user:<id>: 1, audience:*: 10, reflex:audgen:v1: 1 }
```
Five separate reads of the same session key per event, each a network round trip in production. This is the mechanism behind doc 32's 1,731 ms action median, and the 1.7 s is also the width of the lost-update window.

### R5 · Read-after-write turns into a 500 (`repro5.ts`)
KV that **acks** a put and makes it visible 500 ms later (the documented behaviour; Cloudflare allows up to 60 s):
```
Error processing action event: Error: Failed to update session data
RESULT: the event route THREW -> Failed to update session data
```
`RealtimeSegmentEngine.ts:572–574` → `src/routes/realtime.ts:241` → **HTTP 500**. `emitOutcome(result.sessionId)` is never reached, so a click or purchase that raced KV visibility is **dropped from the learning ledger** while `captureDemoEvent` has already recorded it in D1. Learning under-counts rewards asymmetrically (the events most likely to race are the ones inside a burst).

### R6 · The CW39 seam on the event route (`repro3.ts`)
```
DECISION session   : sdk-abc
EVENT session      : sdk-abc            (strictly visible KV — the pointer saved it)
UNPROPAGATED  decision: sdk-xyz | event: 8b8e9ae3-… (DIFFERENT)
```
With any propagation lag, the decision names the session from the SDK id and the event mints its own — **the exact split CW39 says it closed, still reachable through `:1003`**. On the session host the two records then hold different halves of the visit, and `user:<id>` points at whichever wrote last.

### R7 · What CW39's regression test actually proves (`repro6.ts`)
```
no client id -> same session: true | second isNewSession: false
CONCURRENT, no client id -> same session: false  (a22cd064 vs d44ce891)
CONCURRENT, with client id -> same session: true (sdk-1)
   both isNewSession: true true  -> two creations of one session, last write wins
```
The CW39 test in `src/services/sessionDefer.test.ts` runs its "two requests arriving together" **sequentially**, and two of its three assertions (`b.sessionId === a.sessionId`, `b.isNewSession === false`) pass without CW39 at all, delivered by the `user:<id>` pointer. CW39 does buy a real property — concurrent cold requests carrying the same client id agree on the name — but both still report `isNewSession: true` and both write the whole record: **one name, two creations, last write wins.** The audit's title is precisely right.

### R8 · One missed pointer read orphans the whole profile (`repro7.ts`) — *not in the audit*
```
after three views, session a2f86c8b holds product_views = 3 | affinity dims = 6
pointer user:v1 -> a2f86c8b…
a single cookie-less request with ONE KV miss created session b840692f | isNew: true | affinity dims = 0
pointer user:v1 now -> b840692f…
the NEXT cookie-less request lands on b840692f | product_views = undefined | affinity dims = 0
the old record is still in KV, unreferenced: true
```
`getOrCreateSessionFromCookies` creates a session when it cannot read one, and `createOrUpdateSession` unconditionally rewrites `user:<visitorId>` to point at it. A single missed read — eventual visibility, a negatively cached lookup, a colo that has not seen the write — **permanently repoints the shopper at an empty record**. The accrued vector is still in KV and nothing will ever read it again. Triggers available today: a cross-site request with no cookie (the session cookie is `SameSite=Lax`, `SessionManager.ts:571`, so an SDK on a customer domain never sends it), a server-to-server `POST /sort`, or ordinary KV lag. This is the "days and weeks of return memory" commitment failing silently.

### R9 · CW37's deferred write can erase a visit (`repro9b.ts`) — *not in the audit*
Decision route creates the session and hands the put to `waitUntil` (`src/content/service.ts:154`, `SessionManager.ts:297`). Two events then write real state. The deferred put — dispatched with the **empty** body — commits last:
```
after two views                 -> product_views: 2 | affinity dims: 6
after the deferred create lands -> product_views: undefined | affinity dims: 0
```
The audit says deferring "cannot establish the state revision used by the next decision". It is stronger than that: **the deferred write can destroy state committed after it was dispatched.** Frequency in production depends on KV commit ordering and was not measured here; the mechanism is unconditional.

### R10 · The identity link splits a person (`repro10.ts`) — *not in the audit*
`SessionManager.absorbIntoShopper` (CW25, scope-ledger row 2, `POST /:tenant/identity/link`) reads `user:<shopperId>`, merges two profiles, then makes **three or four separate, non-atomic puts**. Two links for one person that arrive together:
```
two canonical person sessions minted: true (76752ebf / f5e0e45c)
user:person-1 -> f5e0e45c | product_views = 9 | segments = ["b"]
the person actually viewed 13 products across the two devices
   record 76752ebf product_views = 4 | pointed at: false
vp -> 76752ebf | vl -> f5e0e45c
```
Both records claim identity `person-1`; the phone's pointer still names the orphan, so the two devices see two different "linked" profiles forever. `src/routes/identity.test.ts:93–94` covers the two-device case **sequentially**, so it passes. This is the highest-value state in the system and the same root cause.

## 3 · Verdict, severity and size

**Verdict: confirmed.** Nothing in F14 is refuted. One citation is imprecise; every behavioural claim reproduces.

**Severity: I would raise it from "blocks the pilot" to "blocks launch."** The brief defines blocks launch as covering production reliability and representations that the contracted capability is delivered. What reproduces here is not degraded real-time quality:
* seven of eight signals from one page paint are discarded (R3);
* a single missed KV read erases a shopper's accumulated profile permanently (R8);
* a deferred decision write can erase a visit that was already recorded (R9);
* KV lag returns HTTP 500 on the event route and silently drops the outcome from the learning ledger (R5);
* two logins for one person produce two permanently divergent "linked" profiles (R10).

"Behavioral Targeting and Intelligence" is sold on behaviour accumulating across a visit and returning across visits. On the stamps as configured (`REFLEX_HOST = "session"`, both files) that accumulation is unreliable under exactly the traffic shape a retail listing page produces. The label difference does not change the order of the work — it changes whether a January launch can run on the session host. It cannot.

**Size: L for the authoritative-host transition — agreed.** But the audit gives no smaller step, and there is one: see §5.

## 4 · What the audit got wrong, and what it missed

### 4.1 Wrong or imprecise
1. **`:535`/`:554` are alternative branches**, not two writes in one pass. The real multiplicity is `getOrCreateSessionFromCookies` → `:419` → `:554` (measured: two `session:<id>` writes on a cold event, one on a warm one). The conclusion is unaffected; the citation should be corrected before this goes to the delivery team, because an engineer reading it will look at two lines that cannot both execute.
2. **`:307` is module scope, not the class.** `ensureAudiencesSeeded` is an exported function shared with the object host; the per-instance part is `:373` `this.seeded` and `:375`.
3. **"Configuration/audience work per instance" badly understates `:363`.** `new CatalogService()` runs `buildAffinityGraph`, an O(N² log N) all-pairs precompute, in the constructor — and `src/demos/registry.ts:177–180` memoizes the same object precisely because "the constructor runs the O(N²) item-item precompute, **which must never run per event**". `RealtimeSegmentEngine`'s constructor does not use that memo, and eleven call sites build one engine per request (`src/content/service.ts:112`, `src/routes/sort.ts:74`, `src/routes/realtime.ts` ×9, `src/routes/live.ts:276`). Measured on this machine:

   | catalog size | `new CatalogService()` |
   |---|---|
   | 71 (bundled Coach) | 5 ms median, 24 ms first |
   | 250 | 59 ms |
   | 500 | 209 ms |
   | 1,000 | 775 ms |
   | 2,000 | 2,980 ms |

   Today it is ~5 ms of CPU on every decision and every event. Doc 28 says the operator application is "written for thousands of products". At 2,000 products this is three seconds of CPU per request, which is not a latency regression but an outage. It is a one-line fix (use the registry's memo).
4. **The consequence "cannot establish the state revision used by the next decision" is too mild** for the deferred write. R9 shows it can erase state committed in between.

### 4.2 Missed, adjacent, same root cause
1. **Pointer orphaning (R8).** One missed read of `user:<visitorId>` permanently detaches a shopper from her profile. This is the single most damaging path in the finding and it is not mentioned.
2. **The identity link (R10).** `absorbIntoShopper` has the same read-merge-write shape with a three-to-four put non-atomic commit, on scope-ledger row 2 (identity stitching, a contracted capability). A partial commit or a concurrent link leaves a person split across two records, each pointed at by a different device.
3. **KV lag becomes a 500 and a dropped outcome (R5).** The audit treats the `:572` read as a consistency smell; it is an availability and learning-integrity defect.
4. **`SameSite=Lax` (`SessionManager.ts:571`) makes the cookie useless for the integration the product is sold on.** The SDK sends `credentials: 'include'`, but a `Lax` cookie is not sent on a cross-site XHR, so for an SDK on a customer domain calling the worker domain **every** request falls through to the `user:<id>` pointer — the exact path that orphans (R8) and the one CW39 does not cover on events (R6). The whole KV-consistency exposure is therefore the normal case in a real integration, not the edge case.
5. **`POST /sort` mutates shopper state.** It is documented as a pure ranking call, and on the session host it performs two KV writes per request and can repoint the visitor (`sort.ts:74–75` → `getOrCreateSessionFromCookies` with no `defer`). Ignoring the body's `sessionId` is not merely a missed personalization opportunity: it is a write on a read path. On the object host (`sort.ts:63–72`) it is correctly read-only — the two hosts disagree about whether sorting has side effects.
6. **No test in the repository asserts concurrent-update safety.** `Promise.all` appears in exactly two test files, neither of them over shopper state. The two tests that name the property — CW39's "two requests arriving together" (`sessionDefer.test.ts`) and the two-device link (`identity.test.ts:93–94`) — both run sequentially and both pass for the wrong reason (R7, R10). 1,092 green tests do not touch this failure mode.
7. **Fixing F14 by flipping `REFLEX_HOST` makes F13 worse.** On the object host `readShopper` returns `sessionId: null, isNewSession: null` (`src/content/service.ts:106`), so `cellFor`'s `visitNumber` is permanently null. The host transition must carry visit number, entry channel and session identity into the object, or the F13 remedy regresses the day the F14 remedy lands. Neither finding says this.

## 5 · Remedy assessment

**The audit's remedy is right in shape and correctly sized (L).** One transactional shopper authority owning identity, session, consent, ordered signal updates and a state revision; a committed revision on the acknowledgment; dependent decisions referencing it; config/catalog shared and immutable; regeneration and connector enrichment off the event path; parity proven before `REFLEX_HOST` changes. `ShopperReflex` already exists with `/ingest` and `/snapshot` and gives per-shopper serialization by construction, so this is finishing and qualifying an object that is written, not new architecture — which is why L (multi-week, parity across SDK, identity, consent, sort, fatigue, migration, erasure, rollback), not XL.

Two things the remedy should add:
* **Carry visit number, entry channel and the session identity into the object** (see 4.2.7), or the transition silently regresses F13.
* **Name the identity link as part of the same authority.** The remedy says "identity/session"; R10 shows the link is a separate multi-put commit that must move too, not a consequence of moving the session.

### The smallest safe fix
There is no small fix that gives read-after-write consistency or serializes concurrent updates on KV — that is the finding, and it is correct. But there is an **S-sized subset that removes the destruction paths while the transition is qualified**, and it should be done this week regardless of the host decision:

1. **Thread the client's session id on the event route.** `src/routes/realtime.ts:165` already has `sessionId` in scope (`:111`); pass it to `processActionEventWithSession` and on to `getOrCreateSessionFromCookies` at `:1003`. Closes R6 deterministically, ~10 lines, no API change.
2. **Stop re-reading at `:572`.** `createOrUpdateSession` already returns the merged record; use its return value and delete the `getSession`. Removes the 500 and the dropped outcome (R5) and one KV round trip per event.
3. **Make `/sort` read-only.** Honour the body's `sessionId`, and resolve the session without creating one. Removes two KV writes and one orphaning trigger per sort call.
4. **Never repoint `user:<visitorId>` from a session the request just invented.** Write the pointer only when the record was genuinely absent *and* the request supplied no id of its own. This narrows R8 sharply; it does not close it, because there is no conditional write in KV. Say so in the ledger rather than calling it fixed.
5. **Use the registry's memoized catalog in the engine constructor** (`:363`). One line; removes 5 ms of CPU per request today and a cliff at customer catalog sizes.

Items 1–3 and 5 are unambiguously safe and independently testable. Item 4 is a mitigation, not a fix. **None of them makes KV a correct authority for hot shopper state**, and the ledger should not record them as closing F14 — they buy time for the object-host transition, which remains the fix.
