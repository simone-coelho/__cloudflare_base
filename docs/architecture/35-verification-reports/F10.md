### 1.4 "`src/ops/monitor.ts:26` accepts decision latency up to 1,500 ms, versus the interim 200 ms target"

**Holds, exact line, exact number.** `src/ops/monitor.ts:26`:

```ts
export const DEFAULT_THRESHOLDS: Thresholds = { decisionMs: 1500 };
```

The target is `docs/architecture/32-latency-numbers.md:63` — "a decision under 200 ms at P95 on the server and an event under 300 ms". The threshold is **7.5× the target** and roughly **2× the current measured worst case** (`GET /v1/:tenant/decisions/snapshot`, never-seen shopper: P95 716.2 ms wall, 708 ms P99 in-worker). A regression that doubles today's worst case still reads green.

Three further facts, none of which the audit states:

- `problemsOf` (line 34) applies a latency bound **only to the check named `decision`**. Verified by probe: `problemsOf({ kv: {ok:true, ms:4000}, database: {ok:true, ms:9000}, decision: {ok:true, ms:10} })` → `[]`. A four-second KV read and a nine-second D1 query are not problems as long as they answered.
- The comparison is strictly greater (`c.ms > t.decisionMs`), on **one sample every five minutes**. It is not a percentile and cannot become one at that cadence.
- **The timed path is not the envelope's path.** The monitor's synthetic visitor refuses consent, so `armUnder` forces `arm === 'default'`, and in `src/content/service.ts` that skips the regional trend read (line 177 `regionalCfg.enabled && arm !== 'default'`), the external-model call (line 197 `arm !== 'default'`) and the DecisionRing read (line 211 `arm !== 'default'`); the session write is deferred out of the timed window (lines 154–156, 239–241). The monitor times `documents + shopper + lift + decide` on the cheapest arm the engine has. **Lowering 1,500 to 200 would still not measure the operating envelope.**

### 1.8 "Scheduled work uses different tenant lists: `src/index.ts:213` and `:240` default trend/autonomy work to Coach, while other work discovers provisioned tenants"

**Holds at the exact lines; the consequence is prospective, not present.**

- `src/index.ts:213` (cron `0 3 * * *`, the autonomy cycle) and `:240` (cron `0 * * * *`, the trend rollup): `(env.TREND_ROLLUP_TENANTS ?? 'coach').split(',')…`
- `src/index.ts:193` (monitor), `:201` (hourly fold), `:222` (day report), `:230` (erasure rewrite): `tenantConfig(env).provisioned`

Two different sources of truth, confirmed.

**Precision the audit does not give.** `TREND_ROLLUP_TENANTS = "coach"` appears only in the top-level `[vars]` (`wrangler.toml:174`); `vars` is a non-inheritable key in Wrangler, and neither `[env.staging.vars]` nor `[env.production.vars]` re-declares it — so on both deployed stamps the variable is undefined and the code default `'coach'` applies. Today the two lists are identical and **no customer is currently omitted from any job**. State it as a latent defect on the exact next step, not a present omission; a reader who checks production and finds nothing missing will otherwise discard the finding.

### 1.9 "shared cron and queues create noisy-neighbor/lag risks"

**Holds as a design fact.** `[triggers] crons = ["*/5 * * * *", "0 * * * *", "0 3 * * *"]` is declared once (`wrangler.toml:211–212`); `triggers` is inheritable, so every stamp runs the same three schedules for every tenant. The 03:00 handler fans out three `ctx.waitUntil` jobs per tenant (autonomy cycle, day report, erasure rewrite) inside one invocation's CPU and subrequest budget, with no concurrency cap across tenants. Per-tenant work *is* bounded (the fold takes two hours per run and caps an hour at 600 objects; the erasure rewrite is capped per run and resumes) — credit where due; the unbounded dimension is the number of tenants, not the work per tenant. One queue per environment (`events-production`, `max_batch_size 100`, `max_concurrency 6`) is shared by every tenant.

## 2 · What the audit got wrong

1. **"A healthy object-host deployment *may* also fail the monitor's consent assertion."** It *will*, deterministically, on every run, for every tenant. "May" invites a reader to treat it as a race. It is not one.
2. **"Customers can be omitted from jobs."** True prospectively; false today. Both staging and production resolve both tenant lists to `['coach']`. Say "the moment a second brand is provisioned", or the finding will be checked against production and dismissed.
3. **"The brief's six lint errors … were not reproduced because lint never reached analysis."** Accurate about what the auditor did, but the measurement is available for the cost of a `sed`: **5 errors, 324 warnings**. Leaving it unmeasured makes the remedy look bigger than it is; it is the cheapest launch-blocking item in the whole audit.
4. **The remedy's "build once, test the actual Worker/SDK artifact, and promote that artifact"** does not name a mechanism, and on Cloudflare Workers `wrangler deploy` compiles from source at deploy time by default — a team could reasonably conclude artifact promotion is not available. It is: `wrangler deploy --dry-run --outdir` to produce and hash a bundle, and `wrangler versions upload` + `wrangler versions deploy` for staged/percentage promotion. Name it, or this item will not land.
5. **Under-scoped in one place, over-scoped in another.** The remedy omits the two monitor write-side defects in §3.1–3.2 and the dead-letter gap in §3.3, all of which sit in this exact code path. Meanwhile "test migrations forward and recovery/rollback with compatible state", "hot-object saturation" and "a tested 03:00 runbook with named owners" are correct but are not what makes F10 launch-blocking; bundling them into one M–L estimate is what will cause the cheap, sharp part to be deferred.

Nothing in F10 is factually wrong. Every file, line number and number checks out.

## 3 · What the audit missed, adjacent to this finding

### 3.1 On the object host, the monitor injects synthetic exposures into the tenant's live learning statistics (most serious)

`runChecks` does not await `out.afterResponse`, and on the object host `consent.tracking` reads as `true`, so `src/content/service.ts:242` calls `fanDecisions` **before** line 69 throws. Reproduced: `coach:monitor-<id> POST /append` to `DECISION_RING` and `coach:coach:hero POST /exposures` to `LEARN_STATS`.

`fanDecisions` (`src/learn/fan.ts:77`) posts exposures for every record with `arm === 'personalized'`. The default holdout share is 0.05 (`src/content/kinds.ts:378`), so ~95 % of runs qualify. At `*/5` that is ~274 synthetic exposure batches per tenant per day across the three `home` slots (`hero` take 1, `story` take 2, `rail` take 5 in `DEFAULT_SLOTS`) — on the order of **2,000 synthetic exposures per tenant per day that can never convert**, recorded at every level of the pooling ladder including `'*'`, everyone (`src/learn/stats.ts:33–35`, `recordExposure` at `:58–63`). Exposures are the denominator of the lift the platform learns from, reports, and lets the 03:00 autonomy cycle act on. It also creates one new `DecisionRing` Durable Object per run (unique visitor id), never cleaned up.

This is live-data corruption of the evidence system, caused by the monitoring code, on the host the brief says is the intended one once acceptance passes (`docs/architecture/33-…md` §5.7, §6). It is worse than anything F10 names and it shares a one-line fix with F05 (see §5).

### 3.2 On the session host, the monitor writes two KV keys per run and never reclaims them

`src/ops/monitor.ts:2–4,67` says "nothing is written". Not true even on the green path. Reproduced with `REFLEX_HOST='session'`:

```
SESSION decision: {"ok":true,"ms":9,"detail":"1 decisions from 2 pieces"}
SESSION KV(SESSIONS) puts: ["session:monitor-mtq3025f","user:monitor-mtq3025f"]
```

`SessionManager.createOrUpdateSession` (`src/services/SessionManager.ts:269–288`) deliberately persists the refusal instruction — correct behaviour for a real shopper, wrong for a synthetic one whose id is unique per run (`monitor-${now.toString(36)}`). At `expirationTtl = 30 days` (`:151`) and 288 runs/day: ~576 writes/day/tenant and **~17,000 dead keys resident per tenant** in the `SESSIONS` namespace. Small money, real noise, and it falsifies a comment the team relies on.

### 3.3 No dead-letter queue: ledger loss is silent

All three `[[…queues.consumers]]` blocks (`wrangler.toml:31–34, 252–255, 350–353`) set `max_retries = 2` with **no `dead_letter_queue`**. `src/index.ts:262` retries a failed ledger batch; after the third failure Cloudflare Queues discards it with nowhere to go. `src/index.ts:263` acknowledges and drops unplaceable messages with a `console.warn`. Decision and outcome records are the platform's evidence and the input to every lift claim; they can be lost with no metric, no alert, and no monitor check for ledger completeness. F10's remedy names "queue age/dead letters" abstractly; this is the concrete instance, and it is configuration, not code.

### 3.4 A test that passes for the wrong reason

`src/ops/monitor.test.ts` (3 tests) covers only `problemsOf`, `alertPayload` and `alert` — the pure parts. **`runChecks` has no test at all**, which is why the object-host failure in §1.7 and the zero-decision acceptance in §1.5 both ship green.

Worse, `src/content/consent.test.ts` — the suite that exists to prove CW31 consent — passes `cookieHeader: null` on every call (line 41) and sets consent only inside the DO snapshot. **No test anywhere in the repository passes a non-null `cookieHeader` to `serveContentDecisions`** (verified by grep across all `*.test.ts`). The one mechanism the self-monitor depends on for "nothing is written" is completely untested, on both hosts.

### 3.5 Documentation drift on the deploy path

`docs/deployment/01-deploy.md:56` still states that `[env.production]` "declares only a name", which has been false since `0fbf87e`. The documented production deploy command (`bash scripts/deploy.sh production`) cannot run at all. If release gates are the finding, the release documentation is part of it.

## 5 · Severity, size, and the smallest safe fix

**Severity: blocks launch. I agree**, on the brief's "production reliability" limb, for three independent reasons, in order:

1. On the object host the monitor **corrupts the learning statistics it is meant to watch** (§3.1) — live-data integrity, on the exact upgrade path the team is committed to.
2. "Monitor green" is the only continuous evidence anyone has that the platform is serving, and it is green with zero content, zero decisions, a broken write path, and a decision seven and a half times slower than the stated target, timed on an arm no real shopper takes (§1.4, §1.5, §1.6).
3. The documented deploy command cannot execute, and the command that can (`npm run deploy`) runs no gate at all; nothing attests that what is deployed is what was tested — and one served bundle at HEAD demonstrably is not (§1.2, §1.10).

**Size: L for the remedy as written** (build/promote artifacts, migration forward-and-rollback tests, six new tenant-scoped synthetics, error-budget and queue alerting, a provisioned-customer registry, checkpointed jobs, a tested 03:00 runbook with owners). The audit's M–L is optimistic for that list. But F10 bundles at least four separable items and the audit's own rule — "overlapping findings share work" — should be applied: the consent fix is shared with F05, and the tenant-registry fix is shared with F01's containment work.

**Smallest safe fix that closes the launch-blocking part — S, roughly 1–3 engineer-days with tests:**

1. **`.eslintrc.json`**: `"@typescript-eslint/recommended"` → `"plugin:@typescript-eslint/recommended"`. Fix four trivial errors; give `src/reflex/core.ts:296` an inline `no-control-regex` disable with a reason (it is deliberate). Pin the baseline with `eslint src --ext .ts --max-warnings 324` so it is blocking and cannot grow, and ratchet down later. Add `npm run lint` to `.github/workflows/ci.yml`. Result: `bash scripts/deploy.sh <env>` runs end to end for the first time — and reaches the test suite it has never reached.
2. **`src/content/service.ts:100–110`** (`readShopper`, `do` branch): fold `consentFromCookies(r.cookieHeader)` into the object's consent, most-restrictive-wins, matching the session branch. One expression. Closes the false red *and* the synthetic-exposure write in one move, and is the same edit F05 needs.
3. **`src/ops/monitor.ts`**: fail the decision check when `out.sources.slots.count > 0 && out.records.length === 0` (slots configured but nothing decided — a green empty tenant stays green legitimately). Time a *personalized* probe with the write suppressed by the caller rather than by the shopper's consent, and set `decisionMs` from the stated envelope rather than 1,500. Give `runChecks` its first test.
4. **`wrangler.toml`**: add `dead_letter_queue` to all three consumer blocks.
5. **`src/index.ts:213` and `:240`**: use `tenantConfig(env).provisioned`, keeping `TREND_ROLLUP_TENANTS` as an optional narrowing override. Two lines, before the second brand is provisioned.
6. **`npm run deploy`** (package.json): make it call `scripts/deploy.sh`, or delete it, so there is one deploy path.

Everything else in F10's remedy — artifact build-and-promote, migration rollback tests, the full synthetic suite, error budgets, the 03:00 runbook — is correct and can follow the launch-blocking set. When it is scheduled, name the mechanism: `wrangler deploy --dry-run --outdir` to produce and hash the bundle, `wrangler versions upload` / `wrangler versions deploy` to promote it, and a CI step that rebuilds `public/sdk/*` and `public/meridian/engine.bundle.js` and fails on any diff against the committed files (§1.10).
