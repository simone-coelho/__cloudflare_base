## 3 · What the audit got wrong

1. **The chosen example conflates two causes.** The audit's row is `n_equiv = 20`, and
   `src/learn/stats.ts:185` requires `st.n + prior.n >= snap.nMin` with `nMin = 30`. With the split fixed,
   that row *still* returns null — legitimately, on the evidence threshold. The finding is nonetheless
   proven by rows at or above the threshold; isolated:

   ```
   DEPTH-2 prior, n_equiv 50 (>= nMin 30):
     HEAD  items=["b","a|c=direct"]  liftFor(a) = null
     FIXED items=["b","a"]           liftFor(a) = level 2, p_hat 0.02, lift 0.5, n0 50, prior {p:0.02,n:50}
   ```
   Reviewers who retest with the audit's exact numbers will see a null that survives the fix and may
   wrongly conclude the fix failed. Use `n_equiv >= 30`.

2. **"Root-level `*` priors do not expose this case" understates what works.** Depth-1 (`c=direct`)
   priors work too. The correct statement is "levels 0 and 1 work; levels 2–5 do not."

3. **The title names the lesser harm.** A phantom item id is cosmetic pollution. The damaging half is
   that the *real* item silently loses its estimate, and that four of six ladder levels of the priors
   feature are dead.

4. **The money consequence is understated** — see §1.5. It is not "cannot silently stand for"; it is
   "actively demotes the item to the lift floor with strength `n_equiv`".

Nothing in the finding is factually wrong. The line numbers, the mechanism, the reproduction and the
remedy direction are all correct.

## 4 · What the audit missed (adjacent, same code path)

1. **Coarse + fine together serves a wrong number, not a missing one.** With
   `('a','c=direct',0.12,50)` and `('a','c=direct|v=1',0.02,400)` imported, the fine row is dropped and
   the coarse row answers: `level 1, p_hat 0.12, lift 2.0, n0 50` — the opposite direction from the
   belief the DS actually expressed for that cell (0.02, worth 400 observations). Doc 22 §8's "a finer
   prior overrides" is inverted. This is worse than a null, because it is confident and auditable-looking.

2. **A second manifestation: warm item, wrong cell.** An item with live exposures only in
   cell(search) and a prior for cell(direct) at depth ≥ 2 gets `liftFor(a, cell(direct)) = null` and a
   phantom. The prior never applies anywhere.

3. **The blast radius is bounded, and the audit does not say so.** `priorFor`
   (`src/learn/stats.ts:133-139`) *constructs* the key and never splits it, so an item with live evidence
   at the prior's exact key does get the prior (verified: level-5 prior + 2 live exposures →
   `level 5, n 2, n0 100, prior {0.3,100}`). Only the no-live-evidence-at-that-key case — i.e. the cold
   start the feature exists for — is broken. This matters for triage: no *warm* item has been served a
   wrong prior-derived lift by this defect.

4. **Operator surfaces publish the phantom.**
   - `src/learn/rows.ts:57` `rowsOf` emits `item: "a|c=direct"`, `key: "v=1"`, `level_words: "channel"` into
     the lift grid and its CSV export (`public/learning.js:252` `gridCsv`).
   - `src/learn/rows.ts:118` `exploringRows` and `public/learning.js:261`: the phantom has no `'*'` key, so
     `n = 0 < floor` and it lands **first** in "Under the floor" — the list that tells a merchandiser what
     exploration should serve next, naming an id that is not in the catalog.
   - `src/routes/decisions.ts:139` and `:212` report `evidence.items = Object.keys(snap.items).length`,
     inflated by one per mis-indexed prior.
   - Safe: `src/learn/autonomy.ts:59` skips items with no `'*'` key or `n <= 0`, so the autonomy cycle is
     not polluted. Freeze/Reject/Reset controls render only on `key === '*'` rows, so no operator control
     can be attached to a phantom.

5. **A brand-new slot publishes nothing at all.** `src/durable-objects/LearnStats.ts:109`:
   `if (!d || d.stats.events === 0) return null;`. A slot with imported priors and zero live events never
   publishes a snapshot, so *no* prior — not even a `'*'` one — reaches KV until the slot has recorded at
   least one exposure. Doc 22 §8 promises "an item with a prior and no live events yet has an estimate".
   Fixing the split does not fix this; it is an independent second way the same promise fails.

6. **`/reset-item` inherits the bug.** `LearnStats.ts:68-79` implements doc 22 §12.2 "discard an item's
   evidence and start again from the prior". If the item's only prior is at depth ≥ 2, after the reset the
   item disappears from the snapshot entirely and the merchandiser's Reset button silently deletes the
   item from the lift table instead of restarting it from the prior.

7. **The cell grammar is not the ladder grammar.** `src/learn/priors.ts:20`
   `CELL = /^(\*|[a-z_]+=[^|]*(\|[a-z_]+=[^|]*)*)$/` accepts any `k=v` pairs in any order. All of these
   validate, version, and can never match a ladder key or a parent of one — silently, forever:
   `stage=early`, `zzz=1`, `v=1|c=direct` (wrong order), `c=direct|v=1|r=US-NY` (stage skipped).
   This matters now: **CW29 (`6a84fc9`) moved the stage ahead of the region in `levelKeys`**, so any prior
   file exported by the DS before that commit — `c=…|v=…|r=…|a=…` — is silently dead at HEAD. The audit's
   remedy names grammar validation but not this live migration hazard.

8. **The green test passes for the wrong reason.** `src/learn/phase3.test.ts:28` asserts
   `[...indexPriors(csv,'hero').keys()] === ['a|*', 'b|c=direct|v=1']` — it asserts the exact encoding the
   split cannot invert, and then never carries `b`'s deep prior into `buildSnapshot`. Both snapshot-level
   prior tests (`:36`, `:126`) use cell `'*'`, the one depth that works. All 10 tests pass at HEAD.

9. **Nothing automated would catch it.** No script under `scripts/` exercises priors; `acceptance-run.mjs`
   does not touch `PUT /content/priors` or the priors document.

10. **The offline grids ignore priors entirely.** `src/learn/hourly.ts:303` and `src/learn/report.ts:122`
    both call `buildSnapshot(..., null, ...)`. The day report's lift grid and the policy-comparison grids
    are therefore built with no priors at all, so a data scientist reconciling the report against the live
    table sees a different `p̂`, `n₀` and `lift` for every prior'd item, at every depth including `'*'`.
    Replay is unaffected — `src/learn/replay.ts:54` reads the archived snapshot and `:78` even asserts the
    archived `priorVersion` matches the receipt.

## 5 · Severity and size

**My severity: blocks the pilot.** I agree with the audit's label and would **drop its conditional.**
`docs/architecture/20-scope-truth-ledger.md` row 4 records requirement §1.8 — "data science surfaces:
explain export, decision/outcome egress, **priors import**, debug endpoints" — as **"Closed 2026-09-03
(code, Phase 3)"**, to be exercised "With the DS working sessions".
`docs/architecture/26-btie-requirements-gap-review.md` §A.3.5 answers the customer's
"Cold content starts with a prior from similar content" with "priors import exists per item and per
coarser key", and §61 answers "similar users like similar things (cold start from lookalikes)" with
"population priors … the pooling ladder by cell". Contextual priors are therefore already represented to
the customer as delivered. The first DS working session that imports a per-segment prior file will find
the feature does not work at the depths it was sold at, and will find it silently.

**Not blocks launch.** `EMPTY_PRIORS` is the compiled default; with no priors document nothing changes.
The default arm, live counts, attribution and the decision path are untouched. No shopper is served a
wrong number *unless* a priors document exists. (I could not check whether staging or production carries
one — no network calls were permitted — so that should be confirmed before the risk is closed.)

**My size: S for the fix that closes the failure; M for the audit's full remedy.** The audit's "S–M" is
right in aggregate but should be split so the S part is not held hostage to the M part:

- **S (hours):** the item-indexing fix + the 7-case regression test. Below.
- **M (1–2 engineer-weeks):** typing priors by objective and unit; validating the canonical ladder
  grammar and versioning it against the CW29 reordering; the `events === 0` publish gate; prior-aware
  offline grids; `/reset-item` coverage; the DS-facing documentation of what a prior means on a money slot.

## 7 · Remedy assessment

The audit's remedy — "use structured/nested keys or an unambiguous encoding, validate the canonical cell
grammar, and type priors by objective/unit" — is **the right direction and slightly over-scoped for the
part that blocks the pilot**. Changing the key encoding is unnecessary: the encoding is only ever *read
back* in one place, and the structured rows that produced it are still in hand two frames up the stack.
Re-encoding would touch archived snapshots and the replay equality check at `src/learn/replay.ts:78` for
no benefit.

The remedy is also **under-scoped in two places**: it does not cover the `events === 0` publish gate
(§4.5), which defeats the same cold-start promise on its own, and it does not name the CW29 ladder
reordering as a migration that already invalidates older prior files (§4.7).

### The smallest safe fix

Two edits, ~6 lines, no change to the stored document, the flat key, `priorFor`, receipts, archived
snapshots, or replay:

```ts
// src/learn/priors.ts — indexPriors already has the structured rows; keep them.
export function indexPriors(doc: PriorsDoc | null | undefined, slot: string): { index: PriorIndex; byItem: Map<string, string[]> } {
  const index: PriorIndex = new Map();
  const byItem = new Map<string, string[]>();
  for (const r of doc?.rows ?? []) if (r.slot === slot) {
    index.set(priorKey(r.item, r.cell), { p: r.p_prior, n: r.n_equiv });
    byItem.set(r.item, [...(byItem.get(r.item) ?? []), r.cell]);
  }
  return { index, byItem };
}

// src/learn/stats.ts — replace lines 140-146 with:
const priorItems = priors?.byItem ?? new Map<string, string[]>();
```

`src/durable-objects/LearnStats.ts:119-123` already returns `indexPriors(...)` whole, so the call sites
change only in shape. Verified in `/tmp/audit-verify/F20/fix.ts`:

```
FIXED *        items=["b","a"]  liftFor(a) = level 0 p_hat=0.1  lift=2 n0=200
FIXED depth 1  items=["b","a"]  liftFor(a) = level 1 p_hat=0.12 lift=2 n0=50
FIXED level 5  items=["b","a"]  liftFor(a) = level 5 p_hat=0.3  lift=2 n0=100
FIXED depth 2 (n_equiv 50)      liftFor(a) = level 2 p_hat=0.02 lift=0.5 n0=50
FIXED coarse+fine               prior {p:0.02,n:400}  <- the finer prior now overrides
```

Ship it with the regression test at `/tmp/audit-verify/F20/f20.regression.test.ts` (one case per ladder
depth plus the override rule; 5 of its 7 cases fail at HEAD), and with one import-time guard so the fix is
not silently re-opened by hazard 7: reject any `cell` that is not `'*'` or a prefix of the canonical
ladder key order `c=, v=, s=, r=, a=`. That guard is ~5 lines in `validatePriors` and it turns three of the
four silent-no-op grammars into an import error the DS sees immediately.

Everything else — money-typed priors, the `events === 0` gate, prior-aware day-report grids — is real work
that should be scheduled, but it does not have to block the DS session that the S fix unblocks.
