# F13 · Independent verification

**Finding:** "Visit/channel context and customer journey/memory behavior are not implemented as claimed"
(`docs/architecture/34-independent-adversarial-audit.md:137-146`)

**Verifier:** independent, adversarial, both directions.
**Checkout:** `feature/real-time-personalization`, HEAD = `c10ccff` — the audited commit itself. The only
working-tree modification is `public/meridian/engine.bundle.js`; no file in F13's path differs from HEAD,
so every line number below is HEAD's own.

**Verdict: CONFIRMED.** Every cited line is correct, every factual claim about behavior holds, and I
reproduced each of the four consequences locally. Severity **blocks the pilot** and size **M plus customer
calibration** are both right. The audit is, if anything, one notch too gentle: it did not find that the
stored entry channel is itself written wrong for the exact integration its own kit documents, and that the
decision path never advances the visit boundary — two defects that would make a naive implementation of the
audit's own remedy ship a *wrong* channel and a *stale* visit number.

## 2 · Reproductions

All probes are read-only and were run from the repository root with
`npx tsx --tsconfig <repo>/tsconfig.json /tmp/audit-verify/F13/probe.ts` (and `probe5.ts`). They import the
real modules — `serveContentDecisions`, `SessionManager`, `RealtimeSegmentEngine`, `cellFor`, `levelKeys`,
`decideContent`, `stageFromCounters`, `reflex/core` — with in-memory KV and stub Durable Object namespaces,
`REFLEX_HOST='session'` (what staging and production run per brief §5.7).

**Probe 1 — a fourth-visit, paid-social shopper asks for a decision.** Four visits written through
`SessionManager.createOrUpdateSession` with a 6-hour gap between each and a tagged entry on the first:

```
stored metadata = {"visitCount":4,"entryChannel":"paid_social", …}
decision cell   = {"channel":"unknown","visit_bucket":"unknown","region":"US-NY","affinity":null,"stage":"unknown"}
ladder keys     = ["*","c=unknown","c=unknown|v=unknown","c=unknown|v=unknown|s=unknown",
                   "c=unknown|v=unknown|s=unknown|r=US-NY","c=unknown|v=unknown|s=unknown|r=US-NY|a=none"]
```

The platform holds the right answer and the decision throws it away. Levels 2 and 3 of the six-level
pooling ladder (`src/learn/stats.ts:33-36`) carry no information: `c=unknown` partitions nothing, so the
advertised six-level ladder is a four-level ladder in production.

**Probe 1b — the reachable values.** A brand-new shopper yields `visit_bucket:"1"`. Nothing on the decision
path can ever produce `2-3` or `4+`, the two values `docs/kit/03-payload-schemas.md:49` publishes to the
customer. A free-text channel is taken verbatim: `channel=Not-A-Channel-At-All` becomes cell channel
`not-a-channel-at-all` — `cell.ts:63` lowercases and truncates to 32 characters against no vocabulary.

**Probe 2 — return memory under the shipped default.** Three views 5 s apart, then time:

```
a(line:Tabby) = [["at once",0.6058],["+1 min",0.3612],["+10 min",0.0001],["+1 hour",0],["+1 day",0],["+7 days",0]]
```

τ = 60 s (`core.ts:202`), decay `exp(-Δt/τ)` (`core.ts:233-236`). Cross-visit memory on the launch brand's
effective config is **exactly zero** an hour after the last event. "Picks up where you left off, remembers
what you were considering" (`docs/architecture/tapestry_requirements.txt:152`) is not what this configuration
does.

**Probe 3 — the stage heuristic against the customer's own example.** `stageFromCounters({product_views:1})`
= `early`/exploring; `{product_views:2}` = `mid`/**considering**; `{wishlist_adds:1}` = considering;
`{purchases:3}` = `late`/deciding. The customer's Click 3 (`tapestry_requirements.txt:121`) is a shopper who
has viewed **two** crossbodies and is explicitly labelled *exploring* "with 89% confidence". Our engine
labels that same shopper *considering*. The audit's claim is exact.

**Probe 4 — what the cell actually moves.** With γ = 0 (`service.ts:220` `gammaOf … ?? 0`;
`kinds.ts:380-384` "Every slot runs at γ = 0 (shadow)"), two opposite contexts produce byte-identical output:

```
paid_social / visit 4 → ["b:0.4","a:0.2"]
direct      / visit 1 → ["b:0.4","a:0.2"]
```

`decide.ts:179` is `base * Math.pow(look.lift, gamma)`; at γ=0 that is `base * 1`. Channel and visit bucket
reach the score through the learned lift and through nothing else. The audit's sentence — "a learning-cell
field alone does not implement an immediate seeded context effect at learning weight γ=0" — is verified.
**Worth stating for balance:** the *stage* field of the same cell **does** have a seeded effect
(`decide.ts:105`, `:132-141`, the CW29 slot rule). My probe shows `stage=early → ["a:0.7","b:0.04"]` versus
`stage=late → ["b:0.9","a:0.02"]`. So the cell is not decorative as a whole; channel and visit are.

## 3 · Severity and size

**I agree: blocks the pilot. Size M plus customer calibration.**

Nothing here is a live-data-safety or reliability defect, so it is not "blocks launch" on those limbs of the
scale. It is squarely "a feature claimed in that pilot": two of the dimensions Mandeep named — `visit.ts:1-4`
calls them "the two dimensions Mandeep named and the two levels doc 22's pooling ladder leans on hardest" —
do not reach the contracted decision, and the customer's own three-visit narrative
(`tapestry_requirements.txt:121-125`, `:152-153`) cannot be demonstrated on it.

One limb of the scale does touch "representations that the full contracted capability is delivered":
`docs/architecture/26-btie-requirements-gap-review.md:48` marks Unified Customer Profile **✅** citing "CW7
visits and entry channel", and the **customer-facing** kit publishes a cell example
`{"channel":"direct","visit_bucket":"1"}` (`docs/kit/02-api-reference.md:92`) and the values `2-3`/`4+`
(`docs/kit/03-payload-schemas.md:49`) that the documented integration cannot produce. Doc 26 is internal, so
this does not lift the whole finding to "blocks launch" — but the two kit lines are wrong on a page a
customer reads, and correcting them is an hour's work that should not wait on the engineering schedule.

On size: the *truthfulness* half is S (about a day — see §6). The *capability* half — a seeded scoring effect
for channel and visit, agreed stage transitions, a post-purchase state, production decay horizons, and the
verification scenarios — is M and needs the customer in the room. The audit's "M plus customer calibration"
is the right net number.

## 4 · What the audit got wrong

Very little. Three points of precision, none of which changes the verdict:

1. **`src/sdk/listen.ts:75` — "the kit does not supply a channel on ordinary hydration" is true of the
   *documentation*, not of the SDK.** Line 75 already forwards `channel: o.channel`, and the SDK **already
   computes** the entry signals it would need: `entrySignals(host)` (`src/sdk/identity.ts:65-72`) reads
   `utm_medium`/`utm_source`/referrer at page load, `core.ts:96` stores them, and `core.ts:140` puts them on
   **every event envelope**. The SDK has the campaign in hand at hydrate time and simply does not send it on
   the snapshot. This makes the SDK half of the remedy nearly free (one default in `listen.ts`), which the
   audit's remedy wording ("carry authoritative visit/channel metadata into decisions on both hosts") makes
   sound larger than it is.
2. **"the advertised second/fourth visits" is loose.** The customer's paper advertises the **second and
   third** visit (`tapestry_requirements.txt:124-125`); `2-3` and `4+` are the *platform's own* published
   bucket values (`docs/kit/03-payload-schemas.md:49`). Both are unreachable, so the point stands; the
   citation should be the kit, not the customer paper.
3. **"campaign context is lost" is true of the content contract, not of the platform.** The channel does
   reach the legacy decision seam (`RealtimeSegmentEngine.ts:702` → `decideAll` at `:712-717`) and ODP. The
   audit says as much elsewhere in the same paragraph; a reader skimming the consequence line could
   over-read it.
4. **`core.ts:201` is the comment; `:202` is the value.** Immaterial — the comment is the evidence.

I found **no** wrong line, no wrong claim about behavior, no overstated consequence, and no remedy step that
would not work.

## 5 · What the audit missed

Eight adjacent items, in order of how much they would hurt a remediation that took the audit at face value.

**A. The stored entry channel is itself wrong for the integration the kit documents.** Reproduced
(`probe5.ts`). The kit's ten lines call `hydrate()` first (`docs/kit/01-integration-guide.md:56-57`), and the
SDK sends no auto page-view on init. So the snapshot is the first request; it creates the session through
`RealtimeSegmentEngine.getOrCreateSessionFromCookies` → `createOrUpdateSession(…, entry = undefined)`
(`:925-944`), and `SessionManager.ts:218-220` therefore stores `entryChannel: 'direct'`. The first tagged
event arrives seconds later carrying the real utm — and cannot correct it, because `openingNewVisit` is now
false and the branch keeps `existingSession.metadata.entryChannel`:

```
after the snapshot,             stored entryChannel = direct
after the first tagged EVENT,   stored entryChannel = direct   visitCount = 1
```

A shopper who clicked a TikTok ad is stored as `direct` for the whole visit. `visit.ts:12-17` argues, in its
own header, that a *wrong* level is worse than a missing one — "It attributes a real outcome to a cell the
shopper was never in, and nothing surfaces as an error." Plumbing the stored channel into the cell without
fixing this ships exactly that failure, at scale, for paid traffic — the population the customer names as
its #1 predictor (`docs/architecture/18-content-affinity-engine.md:68`).

**B. The decision path never advances the visit boundary.** Reproduced (`probe5.ts`, probe 6). After three
hours idle, a decision request leaves `visitCount` at 1 and `isNewSession` false; the boundary rule
(`nextVisitCount`, `visit.ts:67-78`) would say 2. Only the *event* path writes. So a remedy that simply reads
`sessionData.metadata.visitCount` at decision time reports the **previous** visit's number on the first
decision of every return visit — the precise request the whole feature exists to serve. The fix must apply
`nextVisitCount(stored.visitCount, stored.lastSeen, now)` at read time, the same pure function the writer uses.

**C. The object host has no visit or channel state at all.** `readShopper`'s DO branch (`service.ts:100-109`)
returns `isNewSession: null` unconditionally, so `visit_bucket` there is permanently `unknown` — not even the
`1` the session host can produce. `ShopperReflex` stores neither a visit count nor an entry channel
(`ShopperReflex.ts:1035`: "touches nothing about visits or lastSeen"). Brief §5.7 calls the object host the
preferred target shape and three times faster; flipping `REFLEX_HOST` would silently regress the one visit
value that works today. The audit says "on both hosts" but does not say that one host has nothing to carry.

**D. Two visit-bucket implementations disagree, and the legacy one asserts instead of admitting.**
`src/services/visit.ts:84-89` `visitBucket(undefined) === '1'`; `src/content/cell.ts:43-48`
`visitBucketOf(undefined) === 'unknown'`. `RealtimeSegmentEngine.ts:701-702` uses the first and pairs it with
`entry_channel: sessionData.metadata.entryChannel ?? 'direct'`. So the attributes fed to the flag/decision
seam and onward claim "visit 1, direct" for shoppers whose context is genuinely unknown, while the content
cell correctly records `unknown` for the same shopper at the same moment. Two surfaces of one platform
disagree about one shopper, and the legacy one commits the error `visit.ts`'s own header warns against.

**E. The channel is unvalidated free text and becomes a statistics key.** `cellFor` (`cell.ts:63`) applies no
vocabulary check against the six-value `EntryChannel` (`visit.ts:36-37`), and `levelKeys`
(`stats.ts:33-36`) makes the value levels 2 and 3 of the pooling ladder. The repo's own evidence scripts
already exploit it: `scripts/acceptance-run.mjs:115` passes `channel=acceptance` and `src/ops/monitor.ts:68`
passes `channel=monitor`. The acceptance run therefore writes a junk cell (`c=acceptance`) into the learning
statistics — and never exercises the ordinary channel-less path at all. Any customer page can fragment the
ladder into a cell per campaign by passing a campaign id here.

**F. The tests in this area pass for the wrong reason.** `src/services/visit.test.ts`,
`src/content/cell.test.ts`, `src/services/JourneyStage.test.ts`, `src/services/SessionManager.visit.test.ts`
= 46 green assertions (I ran them: 4 files, 46 tests, all pass). None of the four calls
`serveContentDecisions`. `visit.test.ts:70-75` asserts `visitBucket(2)==='2-3'` and `visitBucket(97)==='4+'`;
`cell.test.ts:26` asserts `visitBucketOf(9)==='4+'` — values no production caller can generate. The
end-to-end script asserts `cell.stage` (`acceptance-run.mjs:137`, `:163`) and never `cell.channel` or
`cell.visit_bucket`. The suite proves the cut points are right and says nothing about whether a number ever
arrives.

**G. The kit publishes an unreachable example.** `docs/kit/02-api-reference.md:92` shows
`"cell": {"channel":"direct","visit_bucket":"1", …}` next to a ten-line integration
(`01-integration-guide.md:56`) that sends no channel; a customer who follows the guide gets
`"channel":"unknown"`. `03-payload-schemas.md:49` publishes `2-3` and `4+` as values of a field that cannot
take them. This is the one customer-facing artifact in the finding.

**H. `classifyEntryChannel` maps the most common Meta tagging convention to paid search.** I hit this by
accident on the first probe run: `utm_medium=cpc&utm_source=facebook` → **`paid_search`**, because
`visit.ts:139-141` decides on the medium before the source is ever consulted, and `cpc` is in
`PAID_SEARCH_MEDIUMS` (`:93`). Meta's own default tagging is `utm_medium=cpc`. Once the channel actually
reaches decisions, paid-social spend pools into the paid-search cell — the same class of reconciliation
argument the visit-count fix was written to avoid.

**I. The journey stage latches.** `stageFromCounters` is a pure function of `sessionData.attributes`
counters, which `applyEventToAttributes` only ever increments (`RealtimeSegmentEngine.ts:183-228`,
`inc(key, by) => attributes[key] = num(attributes[key]) + by`) and `createOrUpdateSession` merges forward
unconditionally (`SessionManager.ts:226-229`). No code path resets them, per visit or otherwise, and the
record's TTL is 30 days (`SessionManager.ts:151`). So two product views on day 1 make a shopper *considering*
for thirty days, and one purchase makes her *deciding* for thirty days. The audit's "purchase to late with no
post-purchase stage" is right; the sharper statement is that the stage does not merely lack a post-purchase
value, it cannot leave `deciding` for a month. This matters more than the missing enum value because stage is
the **one** cell field that already has a seeded scoring effect (`decide.ts:132-141`).

## 7 · Remedy assessment

The audit's remedy is **correctly scoped and correctly ordered**, and it is right to insist that the seeded
scoring effect be specified *separately* from learned pooling — that is precisely the distinction probe 4
measures. Two amendments:

- **It is missing its own prerequisites.** Steps A and B above must land *before* "carry authoritative
  visit/channel metadata into decisions", or the remedy ships a wrong channel and a stale visit number with
  the platform's full authority behind them.
- **The SDK half is smaller than implied**, because `entrySignals` already exists client-side (§4.1).

### Smallest safe fix

The pilot-blocking part splits cleanly. The following is roughly **one engineer-day** and makes the platform
*truthful* — the receipts, the ledger and the pooling ladder start carrying the context the platform already
holds:

1. `src/content/service.ts` — add `visitNumber: number | null` and `channel: string | null` to `ShopperRead`
   (`:77-86`). In the session branch (`:114-119`) set
   `visitNumber: nextVisitCount(sessionData.metadata.visitCount, sessionData.metadata.lastSeen, now)` and
   `channel: sessionData.metadata.entryChannel ?? null`; DO branch returns nulls. At the `cellFor` call
   (`:158-165`) use `channel: r.channel ?? shopper.channel` and
   `visitNumber: shopper.visitNumber ?? (shopper.isNewSession === true ? 1 : null)`.
2. `src/services/SessionManager.ts:220` — stop writing `'direct'` when nothing is known; leave
   `entryChannel` undefined so the first tagged event of the visit can still set it. (One line, and it
   removes the whole of defect A.)
3. `src/sdk/listen.ts:75` — default the hydrate channel from the entry signals the SDK already holds.
4. `src/content/cell.ts:63` — validate against the six `EntryChannel` values; anything else is `unknown`.
   Then fix `scripts/acceptance-run.mjs:115` and `docs/kit/02-api-reference.md:92` /
   `03-payload-schemas.md:49`.
5. One integration test that drives `serveContentDecisions` for a stored fourth-visit paid-social shopper and
   asserts `cell.channel === 'paid_social'` and `cell.visit_bucket === '4+'` — the test that does not exist.

**Be honest about what that does not close.** At γ = 0 the cell still moves no score, so step 1-5 delivers
correct *evidence*, not the promised behavior ("first visit → romance imagery; return visit → detail +
reviews", `docs/architecture/18-content-affinity-engine.md:68`). Delivering that needs a seeded rule for
channel and visit modelled on the CW29 stage rule (`decide.ts:132-141`, `journeyStageFit` on the piece,
`stage` dials on the slot) plus agreed decay horizons — the M half, and the half that needs the customer.
Until then the capability should be reported as evidence-only, not as delivered.
