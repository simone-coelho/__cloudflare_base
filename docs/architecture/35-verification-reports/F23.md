## 3 · What the audit got wrong

**3.1 A wrong line, trivially.** `:96` builds the ranking; the return that carries it is `:99`.

**3.2 One claim overstated in framing.** "It returns a whole sampled ranking, not just a budgeted first-position
alternate" reads as an undeclared surprise. The whole-ranking shape *is* documented: doc 22 §7 says Thompson
"samples each item's rate from its posterior and ranks by the sample". What is undocumented is that the share
does not apply to it, and that the same §7 table lists `share` for every mode with no exception. This matters for
the remedy: the reconciliation is between the code, that table row, and the UI dial — not a rediscovery of intent.
The code's own comment at `explore.ts:88` ("Every decision ranks on a sampled rate; the sample is the
exploration") shows the builder knew. This is a contract divergence, not a coding slip.

**3.3 One consequence stated in the wrong direction for the case the finding is named after.** The headline
consequence — 50 of 100 visitors displaced at share zero — is the **unit-objective** failure. Under the *money*
objective the failure inverts. Because `s` carries dollars and `n` carries exposures, `max(0, n − s)` is 0 for
every item that has earned anything, the Beta collapses to Beta(s+1, 1), and 1995/2000 draws round to exactly
1.000 at line 94's three-decimal rounding. The sampled ordering degenerates into a tie broken by the raw score:
997 of 1,000 visitors saw the merchandiser's leader. Thompson on a revenue slot does not over-explore — it
**stops exploring silently**, and the direction it does resolve is by *total* revenue rather than revenue per
exposure, so the item earning $5.95 per exposure outdraws the one earning $29.70 per exposure 1343/2000 times.
A rich-get-richer preference dressed as a bandit. Both failure modes belong in the finding; the current text
only carries one.

**3.4 The severity condition is already met.** "if Thompson exploration is offered/enabled" — it is offered
today, in two operator interfaces, in the validated config schema, and in a customer-facing payload document.
It is not enabled anywhere by default.

## 4 · What the audit missed, adjacent to this finding

**4.1 The ledger under-reports its own exploration, and the verification report cannot see it.**
`decide.ts:254` sets `wasExplored` only when `position === 0`. Thompson replaces the ranking for the *whole*
slot. Measured over 200 visitors on a take-4 rail: 278 rows changed item because of the sample, 82 carry
`explored: true`. **196 sampled placements — 71% of the reordering — are written to the ledger as ordinary
personalized decisions.** Doc 22 §7's "Every exploration pick is flagged in the decision record" is false.
`report.ts:144` and `hourly.ts:202` both count position 0 only, so the "realized against configured" table the
same section promises ("so the exploration share can be verified rather than trusted") is blind to it.
There is a second way the flag lies: `explore.ts:98` returns `null` when the sample agrees with the score order,
so a decision that *was* made by a random draw is recorded as not explored.

**4.2 The recorded candidate set is truncated after the sampled reorder.** `contentCompose.ts:169` slices
`scored` to `candidateLimit` *after* line 162 has re-sorted it by the sample. With `candidateLimit: 3`, 82 of 200
visitors got a logged candidate list that no longer contains the top-scored candidates — p3 (score 0.667) fell
out and p4 (0.5) entered. That list is the input F22's replay and any future offline estimator would read. The
audit's remedy asks for "logged selection probabilities/support" without noticing that the support itself is
already being corrupted by this same code path.

**4.3 Merchandiser item controls are bypassed.** `decide.ts:170` implements `control: 'reject'` as "learned lift
ignored for this item" and `receipts.ts:59` prints "A merchandiser rejected the learned lift for this piece; it
competes on its base score alone." Thompson re-ranks on `snapshot.items[id]['*']` and never consults `controlOf`.
A rejected item is ranked by learned counters after all, and the receipt sentence is untrue. `freeze` is bypassed
the same way.

**4.4 An imported prior is not merely ignored; its value is irrelevant.** A prior of p=0.30/n=800 and a prior of
p=0.005/n=800 both produce Beta(1,1) and both serve the primed piece first 908/1000 times. A piece a customer
imported as *known-poor* — which the scoring path correctly discounts to lift 0.5 — is promoted to first position
91% of the time. This is the cold-start feature the priors work (CW23) was built for, inverted.

**4.5 Thompson is anti-contextual, not merely non-contextual.** An item converting at 50% in one cell (level 5,
p_hat 0.369, lift 2 — the scoring path finds it) but 2% overall was served first **0 of 1,000 times in exactly
that cell**, because the root counters say 0.02. Thompson does not simply lose the context; it systematically
prefers the item the context says is worse.

**4.6 A documented dial does not exist.** Doc 22 §7's settings table lists `cooldown` — "Minimum time between
exploration picks of the same item for one visitor", default "Session". There is no `cooldown` field in
`ExploreConfig`, none in `kinds.ts` validation, and no implementation anywhere in `src/`. This affects all three
modes, not only Thompson.

**4.7 The one Thompson test passes for the wrong reason.** `src/learn/phase2.test.ts:45-59` is the only test of
this mode. It pins `share: 1`, so no assertion in the suite can observe the gate. Its acceptance band is
`flagged > 20 && flagged < 180` out of 200 — a policy that explores on 100% of decisions satisfies it. The test's
own comment (lines 46-47) records that the fixture was repaired once already for a related reason
("only passed because the seeds were poorly mixed"). The suite passes: 7/7.

**4.8 Provenance, which explains the shape of the fix.** `src/learn/explore.ts` has two commits: `0c9e367`
(CW21, exploration, 2026-09-03) and `a819a3c` (holdout). Imported priors landed afterwards in `67e6e3d`
(CW23, 2026-09-03) and the value objective in `28639df` (CW27, 2026-09-04). Neither touched `explore.ts`.
The Bernoulli model predates both of the features it now contradicts. This is a missed follow-up, not a
misunderstanding, and it points at a review rule: a new reward semantic must sweep every consumer of `s` and `n`.

**Two smaller notes.** The receipt records `bucket: 0.884` on a Thompson pick where the bucket governed nothing.
Doc 22 §7 promises the Thompson explain record "shows the sampled value alongside the mean"; `decide.ts:268`
writes `sample` only, and the mean (`p_hat`) rides in the `lift` block only when the item clears `nMin` at some
level.

## 5 · Adversarial checks that did NOT produce a finding

Reported so the team does not re-walk them.

- `LearnStats.ts:50` reads `Number(c.weight) || 1`, which would count a valueless purchase as $1 on a revenue
  slot. It cannot fire: `DecisionRing.ts:90` filters `weight > 0` before forwarding.
- The holdout arms are protected. `decide.ts:88` sets `exploreOf: undefined` for the `no_learning` arm and
  `learning = null` for `default`, so Thompson cannot contaminate the incrementality comparison.
- Pinned slots are protected. `contentCompose.ts:127` returns the tenant's piece before scoring and before the
  explore hook runs.
- Under a `unit` objective `s ≤ n` holds in normal operation: `report.ts:102` records one exposure per decision
  row and `:116` one credit per attributed outcome, so the Beta parameters stay non-degenerate. The money case
  is the one that breaks the model, exactly as the finding says.

## 7 · Severity, size, and the remedy

**Severity: blocks the pilot** — I agree with the audit, with the condition tightened. Thompson is *offered*
today (two operator UIs, validated schema, published payload doc), so the condition is already satisfied; it is
not *enabled* anywhere, which is why this is not blocks-launch. The default mode, `rotation`, honours the share
(measured 6/100 at share 0.1 against 7/100 eligible buckets), so nothing on the default path is affected.

**Size: M for the audit's full remedy; the launch-blocking part is S.** I agree with M. Reconciling the budget,
replacing the posterior with a reward-appropriate model, logging selection probabilities and support, and
building the test matrix the remedy names is one to two engineer-weeks.

**Remedy assessment.** Right direction, correctly scoped for the complete fix, under-scoped in three specifics
and mis-sequenced in one.

- Under-scoped (a): it asks for "logged selection probabilities/support" without noting that the `explored` flag
  is already wrong for 71% of Thompson's reordering (§4.1) and that the logged candidate support is already
  corrupted (§4.2). Both must be fixed *before* propensity logging means anything.
- Under-scoped (b): it does not name the merchandiser item controls (§4.3), which a Tapestry merchandiser will
  discover the first time a rejected piece leads a slot.
- Under-scoped (c): it does not name the unimplemented `cooldown` dial (§4.6), which is a documented setting that
  does not exist in any mode.
- Mis-sequenced: "Reject unsupported objective/mode combinations" and "Keep unsupported exploration off during
  pilot acceptance" are, together, the entire launch-blocking fix and cost hours. The reward-appropriate model
  and the causal logging are the M-sized follow-on. Presenting them as one gate makes an S-sized safety change
  look like a two-week commitment it is not.

**Smallest safe fix that closes the launch-blocking part (S, roughly half a day including tests):**

Withdraw the mode rather than repair it, in three places, with no change to the decision path:
1. `src/content/kinds.ts:330` — remove `'thompson'` from the accepted `exploration.mode` values, so a config
   naming it is rejected with a message rather than served.
2. `public/learning.js:384` and `public/console/views.js:406` — remove the `thompson` option from both selects.
3. `docs/kit/03-payload-schemas.md:150` and `docs/architecture/22-outcome-learning-design.md:402` — strike
   `thompson` from the published values and mark it not delivered, per the brief's rule that a disabled capability
   must be reported as undelivered.

If Thompson must remain available for the pilot, the alternative is two lines in `src/learn/explore.ts`, and it
closes only the budget half:
- move `if (bucket >= share) return null;` (currently `:102`) above the `if (cfg.mode === 'thompson')` block at
  `:87`, so all three modes share one gate;
- return `{ mode, pieceId: top, reason, bucket, samples }` **without** `ranking`, so only first position moves and
  `decide.ts:254`'s position-0 flag becomes truthful again.

That restores the documented share and the honest receipt. It does **not** fix the money model: a
`revenue` or `margin` objective must still be rejected in combination with `thompson` (a three-line check beside
`kinds.ts:325`, which already ties the objective to the reward type) until a reward-appropriate posterior exists.

**The regression test that would have caught this**, and which the suite still lacks: assert that
`explorationPick` returns `null` for every visitor whose `bucketOf(...) >= share`, parameterised over all four
modes — not `share: 1` alone, as `phase2.test.ts:49` does today.
