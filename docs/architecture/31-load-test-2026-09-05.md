# 31 · The first load test, 2026-09-05: what held, what did not, and who fixes what

Internal. Three runs against staging with `scripts/load-test.mjs`, the same afternoon, from one machine
in the eastern United States against the Atlanta edge. Each shopper is a new visitor asking for the home
page's decisions; four in ten then send a product view and a click on the hero they were served, as the
SDK does. Latency is the server's own time from its `Server-Timing` header where it says so, else the
round trip from the client.

What held, in every run: forty shoppers a second sustained to the second, no request failed for load,
and every slot's statistics object received every exposure it was owed (the hero 4,555 of 4,800 in run
1, the five percent holdout not being fed by design; the carousel five per shopper; the stories two).

## 2 · Where the time goes

One decision on the session host, from the server's own header, a new visitor:
`documents 4 ms, shopper 637 ms, trend 2 ms, lift 4 ms, decide 0 ms`. The same visitor a minute later:
`shopper 12 ms`, total 12 ms. The shopper stage on the session host creates or updates the session in
KV on the request path, and a KV write costs half a second or more from a Worker; the first repeat still
paid it, the third read came from KV's edge cache. Everything else on the path is a few milliseconds once
the isolate's caches are warm, and about a hundred cold.

One event on either host, from the server's own header: `engine 6,477 ms` and `2,306 ms` on the
session host; `object 5,383 ms`, `3,010 ms`, `1,263 ms` on the shopper object. The event pipeline
resolves the surface's catalog, the reflex configuration and the audience seeding before it touches the
event, on every event, on both hosts; the first event on a cold isolate or a cold object pays seconds,
and a warm one still pays above a second on the session host.

The target for a pilot, stated once: a decision under 200 ms at the 95th percentile on the server, an
event under 300 ms. The decision stage that is ours (`decide`) is 0 ms; the engine's terms are not the
cost.

## 3 · What broke, and what is fixed

**The day report answered 500 after run 1** (two seconds). A Worker may open only so many storage
objects in one request, and the day held thousands, because the ledger wrote one R2 object per ten
records: run 1 alone made about 4,300 objects in one hour. Fixed the same afternoon, ours:

- the producer sends a decision set as one message and the consumer expands it (`expandLedgerMessage`);
- the queue's consumer takes a hundred messages or three seconds per batch (`wrangler.toml`);
- run 3's objects are 0.6 to 1.8 MB each, so an hour of that load is dozens of objects, not thousands;
- the report route counts the day's objects first and answers 413 with the reason past eight hundred;
- the 03:00 job builds yesterday's report for every provisioned tenant and `GET` reads it.

At the design's volume (a million decisions a day, doc 22 §14.1) even hundred-record objects are
thousands a day, so the report can no longer be a day a request reads. **Done the same evening
(`src/learn/hourly.ts`):** five minutes after an hour closes, the five-minute job folds that hour's
ledger objects into one aggregate under `aggregates/{tenant}/{date}/{hh}.json`, oldest missing hour
first, two per run, and a day is the sum of its hours. Every number in the report is a count or a
decayed accumulator, and both add exactly, so the day built from hours equals the day built from
records (the test asserts it, grid for grid). Attribution needs each visitor's earlier decisions, so
those are carried hour to hour in sixty-four ring shards by visitor, pruned to a two-day horizon and to
the online ring's capacity of two hundred; a click at 13:01 on a hero served at 12:59 credits it, a
purchase two days after the story no longer does in the batch, and the report says so (`hours.horizonMs`).
An erased visitor leaves the shards at the next fold; the aggregates hold no visitor id. The day report
for today is refreshed after every fold, so `GET learn/report` answers through the last closed hour, and
the 413 remains only for custom reporting policies, which are computed over the records. Past a two-day
horizon at that volume the batch ring would need a database, not objects: the next step if a customer's
numbers ask for it, not before.

**The shopper object refuses the content events.** Every `content_click` answered 400 at the object's
`/ingest` in run 2, and the stage the object derives never reached the decision's context cell, which is
why the acceptance run failed at its second snapshot there. The object host is the one built for the
path and it is faster (192 ms median decisions against 632), but the loop is wrong on it. Staging is
back on the session host until the object host passes the acceptance run. Delivery session.

## 4 · Who fixes what

| Finding | Owner | What |
|---|---|---|
| Session host writes KV on the request path: 580 to 720 ms per decision for a visitor KV has not cached | delivery | the session write moves after the response (`waitUntil`), or the object host takes the path |
| Event pipeline resolves catalog, configuration and seeding per event: seconds cold, above a second warm | delivery | resolve once per isolate or per object and reuse; the seeding is a provisioning step, not a request step |
| Object host's ingest refuses `content_click` (and, untested, the other content events and the purchase) | delivery | accept the first-class event types the session host accepts |
| Object host: the stage does not reach the cell | delivery | the snapshot's `journeyStage` is on the cell only when the object has derived one; check the ingest path sets it |
| Ledger objects per hour, report on demand at volume | outcome-learning | done: set messages, batches of a hundred, 413 with the reason, nightly build |
| Report at the design's volume | outcome-learning | done: hourly aggregates folded by the five-minute job, the day as their sum, the batch ring in shards with a two-day horizon (§3) |
| Cloudflare refuses Python's default user agent with 403 | note | tooling uses curl; a customer's server-side integration sets its own agent |

## 5 · How to run it again

```
node scripts/operator-seed.mjs --email <you>@<brand> --admin --env staging      # once; the password is shown once
node scripts/load-test.mjs --base https://<stamp> --sdk-key <site key> --rps 40 --seconds 120 --token <operator jwt>
```

The script prints the achieved rate, latency per request kind, errors by status, then after forty-five
seconds the exposures gained per slot and the ledger's decision count against what was sent. Read the
server's own numbers with `curl -D -` on one request: the decision answers `documents, shopper, trend,
lift, decide`, the event `engine` or `object`.
