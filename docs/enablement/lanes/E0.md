## 3. What "assets-only worker" means

A Cloudflare worker is normally a small program that runs on Cloudflare's servers, close to whoever opens the page, and decides what to send back. An assets-only worker has no program at all. It is a labelled folder of finished pages that Cloudflare stores and hands out, one file per address, exactly as written, at an address of its own. Because nothing runs, there is nothing to break into, nothing to patch, no database to leak and nothing that can call another system on anyone's behalf, which is why it is the safest and cheapest way to publish internal reading material. The trade-off is that the site cannot do anything clever by itself: it cannot ask who you are, search, or remember you. Anything like that, the sign-in included, has to be placed in front of the site rather than built into it.

## 4. Check list after the deploy

As for every demo deploy, verify through the responses, not by whether a page opens. Run items 1 to 5 before the sign-in is added. Once it is on, an anonymous `curl` sees the redirect, so use a signed-in browser's DevTools for items 1 to 4.

1. **The page answers 200.** `curl -sI https://edge-platform-enablement.expedge.workers.dev/` shows `200` and `content-type: text/html`.
2. **An address that does not exist answers 404 with the page.** `curl -s -o /dev/null -w "%{http_code}\n" https://edge-platform-enablement.expedge.workers.dev/no-such-page` prints `404`, and the body is the not-found page. Note: `/404` itself is the file `404.html`, so it answers 200 with the same page (measured with wrangler's asset handling). That is not a defect; use any other address for this check.
3. **The headers are on every response, the 404 included.** `content-security-policy` starting `default-src 'none'`, `x-content-type-options: nosniff`, `referrer-policy: no-referrer`, `cache-control: private, no-store`, `strict-transport-security`, `x-robots-tag: noindex, nofollow, noarchive`.
4. **No request leaves the page on load.** Open DevTools, Network tab, tick Disable cache and reload: exactly one request, the page itself, and no other host, font, script or image. Console: no message beginning "Refused" (if someone edits the CSS and not the hash, the page loads unstyled and the console says it refused the inline style). Application tab: no cookie, local storage or session storage set by the page. Once the sign-in is on, its own session cookie will appear; that is the sign-in's, not the page's.
5. **There is one address only.** Preview URLs are off (`preview_urls = false`), so no `<version>-edge-platform-enablement.expedge.workers.dev` address should answer, and the worker's settings in the dashboard show Preview URLs disabled.
6. **The sign-in, once the lead adds it.** In a private window, `/` and `/no-such-page` both redirect to the sign-in instead of answering 200 or 404; an email outside Optimizely is refused; `curl -sI` with no session shows the redirect, not the page; after signing in, items 1 to 4 hold.

## 5. What was checked before handover

- **The preflight:** `node enablement/check-site.mjs` passes all 38 checks. Eleven mutations of scratch copies (an inline script, a link to another address, a style attribute, a remote `@import`, `unsafe-inline` in the policy, a stale style hash, a `[vars]` table, a `main` entry, preview URLs on, a credential in a comment, the package name written twice) each fail for the right reason, and the unmodified copy passes.
- **Served by wrangler 4.105.0's own asset handling** (run inside WSL, because `node_modules` carries the Linux `workerd`; from a scratch copy of the site and config). It parses the `_headers` rule. `/` answers 200; `/index.html` redirects to `/`; unknown addresses (`/no-such-page`, nested paths, `/_headers`, `/.env`, `/robots.txt`, `/favicon.ico`, an encoded traversal) answer 404 with the page and the full header set; query strings are not reflected; a POST answers 405. Cloudflare's edge may differ in detail, for example the redirect's 307 against 308, so items 2 and 3 above stay in the list.
- **Headless Chrome**, two pages by four widths (320, 375, 768, 1280) by light and dark, 16 scenarios, all passing. Exactly one request each (the page); no console message; no horizontal scroll at any width; every text and background pair meets WCAG AA (lowest 5.12:1 in light, 9.52:1 in dark, 13.27:1 on the not-found page); no cookie, local storage or session storage; the brief's strings match exactly; the cards stack below 880 px and sit three across above it; the first Tab stop is the skip link (landing page) or the button (not found), each with a 3 px focus ring.
- **The policy is enforced, not just present.** In the page, an injected `<style>`, an injected `<script>`, an outbound `fetch` and a remote image were all refused by the browser.

## 6. Design notes and open points for the lead

- **Colours and type follow the current green-led Optimizely brand guidelines** (Dark Fir, LFGreen, Grass, Light Blue and Neutral 3; 32 px corners, smoothed where the browser supports it; no gradients), not the Vantage red (a customer skin) and not the older teal of the Affinity page. The structure follows the house pages: tokens on `:root`, a skip link, mono captions, light and dark through `prefers-color-scheme`. Type is a system stack that names the brand's sanctioned Roboto family first, so it shows where installed and nothing is fetched. Headlines are sentence case, with the brand's tight tracking.
- **The Optimizely logo is not on the page.** No logo asset was available and the guidelines forbid recreating the wordmark. The tab icon is a plain green tile, an inline data URI in the two `<link rel="icon">` lines; swap in the real icon there if wanted (it is outside the `<style>`, so no hash changes).
- **Dark mode** uses Mid Fir for card surfaces. The guidelines discourage tertiary colours as backgrounds, but their own template uses Mid Fir for its dark content slide. If brand review objects, the alternative is Dark Fir for both the page and the cards, with spacing instead of a fill to separate them.
- **The package name** is written once, in `<h1 id="package-name">`. The tab title reads "Optimizely enablement" so it holds no second copy, and the preflight fails if the name appears anywhere else. The brand's verbal identity asks for American English on global-facing material ("Behavioral personalization engine"); the brief's string is used exactly as given.
- **The policy lists a SHA-256 for each page's inline style, not `unsafe-inline`**, because the platform standard treats `unsafe-inline` as no protection. After editing the CSS in either page, run `node enablement/check-site.mjs --hashes` and paste the result into `_headers`; the preflight fails until you do. Wrangler reads `_headers` when it starts, so a local `wrangler dev` needs a restart after that edit. Moving the CSS to a same-origin file and using `style-src 'self'` is the alternative if hash upkeep becomes a burden.
- **The sign-in:** nothing on the site depends on how it is done. A sign-in applied in front of the worker's address needs no change here. If it is added as worker code in front of the pages, the config needs a `main` and `run_worker_first`, and the config allow-list at the top of `check-site.mjs` should be widened on purpose.
- **Not done, by instruction:** no git change, no install, no deploy, and no edit to any file outside `wrangler.enablement.toml`, `enablement/` and this note. One incidental write: the local wrangler runs started from the repo root, so wrangler made and removed its own temporary folders under the git-ignored `.wrangler/tmp`; nothing remains there from this lane. Its state and logs went to a scratch folder.
