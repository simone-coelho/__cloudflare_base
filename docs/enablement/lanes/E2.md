## 2. What the gate is, and what it is not

- **It is one shared passphrase.** Anyone who is told it can open the site. It cannot tell one person from another, so it cannot say who read what, and it has no second factor. It keeps the pages away from people who were not given the passphrase. It is not an identity check.
- **It is temporary.** The owner approved it on 2026-10-02 as a stopgap, because Cloudflare Access's one-time codes were not reaching the owner. It ends when the Microsoft sign-in replaces it.
- **Its rate limit slows guessing; it does not stop it.** The limit counts failures per address in one isolate's memory. Cloudflare runs many isolates and recycles them at will, so a patient or distributed guesser is held back mainly by the passphrase's length. That is why the gate refuses to run with a passphrase under 15 characters (the floor NIST SP 800-63B-4 sets for a single-factor password). The owner's current one is longer.
- **Signing out only clears the cookie on that browser.** A copied cookie stays valid until it expires (seven days at most). The only way to end every session at once is to rotate `COOKIE_SECRET`.
- **Measured against the Optimizely secure-coding checklist.** Where it applies, the gate meets it: constant-time comparison, no secret in code, response or log, `HttpOnly; Secure; SameSite=Lax` on a `__Host-` cookie, server-side expiry, strict headers and CSP, rate limiting with a fixed delay, a validated redirect, no reflected input, generic errors and a capped body. Two items it cannot meet, and both are why it is temporary:
  - the checklist asks for a central identity provider (OAuth or OIDC) rather than custom sign-in logic, with MFA;
  - the checklist asks for authentication events to be logged, but the brief said to log nothing by default. The gate therefore logs nothing unless `AUTH_EVENT_LOG` is `on` (section 3).

## 3. How it works

| Request | Answer |
|---|---|
| `GET` or `HEAD /auth` | The sign-in page: one password field (`autocomplete="current-password"`), a hidden return path, a button, no script. A visitor already signed in is sent straight on to the return path. |
| `POST /auth` | Reads the form (`application/x-www-form-urlencoded`, at most 4 KB). It compares SHA-256 digests of the typed and the stored passphrase with a fixed-length XOR loop. Right: sets the cookie and answers 303 to the return path. Wrong: waits a fixed second, then answers 401 with the same page and "That passphrase was not accepted." |
| `GET` or `HEAD /logout` | Clears the cookie (`Max-Age=0`) and answers 302 to `/auth`. |
| Any other path, valid cookie | The page from `env.ASSETS.fetch(request)`, with the security headers added where the page lacks them. `Cache-Control: private, no-store` is always forced, so no shared cache keeps a gated page. |
| Any other path, no valid cookie | 302 to `/auth?return=<path>`. Known and unknown addresses answer alike, so nothing about the site shows. |
| Any other method | 405 with `Allow`. `POST` is accepted only on `/auth`. |
| Either secret missing or too short | 503 "Site not configured" to every request, and nothing else. |

- **The cookie:** `__Host-enablement_session=<expiry>.<signature>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800`. The signature is base64url HMAC-SHA256 of the expiry under `COOKIE_SECRET` (Web Crypto). The gate checks the expiry first (in the future, and never later than one session from now), then the signature, in constant time. There is no session store.
- **The return path** must be a path on this site. It starts with one `/` and holds only letters, digits, `-`, `.`, `_`, `~`, `/` and percent escapes. It never contains `//`, a backslash, a scheme, a space, a control character, a query or a fragment, and it is never `/auth` or `/logout`. Anything else becomes `/`. It is checked when it fills the hidden field and again when the form returns. It is the only value from the request that ever reaches the page, and it is escaped all the same.
- **The rate limit:** five failures per address in any ten minutes. The sixth attempt answers 429 with `Retry-After` and the page says how long to wait. While an address is held back, even the right passphrase is not checked. Failures are counted before the comparison, with no `await` between the check and the count, so guesses sent in parallel cannot overtake the limit. A right passphrase takes its own count back. Addresses come from `CF-Connecting-IP`; IPv6 is counted per /64.
- **Headers on every response the gate makes:**
  - `Content-Security-Policy: default-src 'none'; style-src 'sha256-1pCAVB9WnT/49lTVcGYDLmy3zh0qcyLYC33TYzYmbOc='; img-src data:; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`;
  - `nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store`, `X-Robots-Tag: noindex, nofollow, noarchive`, `Strict-Transport-Security: max-age=31536000; includeSubDomains`;
  - `X-Frame-Options: DENY` and the same Permissions-Policy as `_headers`.

  `img-src data:` is beyond the brief: it lets the page show the site's inline tab icon. Without it, the browser asks for `/favicon.ico` through the gate instead.
- **The style hash** is a constant, `STYLE_HASH`, in `worker.mjs`. A test recomputes it from the served page. After editing `STYLE`, the failing test prints the value to paste.
- **Beyond the brief, on purpose:**
  - a form posted from another site (`Sec-Fetch-Site: cross-site` or `same-site`) is refused with 403 before it is read; a client that sends no such header (curl, an older browser) is judged on the passphrase alone;
  - a non-form body answers 415 and an oversized one 413.
- **Logging:** nothing by default. With `AUTH_EVENT_LOG` set to `on`, the gate writes one JSON line per outcome (`success`, `failure`, `locked`, `logout`, `error`) to `console.log`. Each line holds the time, the address and the ray id, and never the passphrase, the cookie, the form or the path. To turn it on: `npx wrangler deploy --config wrangler.enablement.toml --var AUTH_EVENT_LOG:on`, then `npx wrangler tail edge-platform-bti`.

- **Order:** deploy first, then the secrets. Until both secrets exist, the new worker answers 503 to everything, so nothing is served in between. `secret put` on a worker that does not exist yet would offer to create a draft worker instead.
- **The values** live only in the owner's local `.dev.vars` (as `ENABLEMENT_PASSPHRASE` and `ENABLEMENT_COOKIE_SECRET`) and in the worker. The preflight confirms that the local values meet the gate's minimums before they are set.
- **To rotate the passphrase:** put the new one (15 characters or more) in `.dev.vars` as `ENABLEMENT_PASSPHRASE`, run the preflight, then set `ACCESS_PASSPHRASE` again with either form above. `secret put` deploys a new version carrying the secret at once; a later `wrangler deploy` keeps it, because deploys never delete secrets. Sessions already granted stay valid until they expire.
- **To sign everyone out at once** (for example, if the passphrase leaked), also rotate the key. Run `sed -i "s/^ENABLEMENT_COOKIE_SECRET=.*/ENABLEMENT_COOKIE_SECRET=$(openssl rand -hex 32)/" .dev.vars`, then set `COOKIE_SECRET` again the same way.
- **A local run** needs its own values: `npx wrangler dev --config wrangler.enablement.toml --port 9311 --env-file <file with ACCESS_PASSPHRASE and COOKIE_SECRET>`. With `--env-file`, wrangler 4.105 does not load the repository's `.dev.vars` at all. Without it, wrangler would load that file's unrelated secrets into this worker and still answer 503, since the gate's two names are not in it.
