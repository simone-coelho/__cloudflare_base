# Lane W4: the Word converter gains in-document links and figures

**Status:** done 2026-10-01, with one follow-up the same night. One file changed, `scripts/md2docx.mjs` (final hash `0b2159ee…`); nothing under `docs/` touched by this lane.
**Why:** the technical note's new shape (a three-page walk whose sections link to the detailed sections and
back, with one figure) needs links inside the document and a picture at text width. The owner prefers Word
with working links over an HTML document.

## What an author writes

| Feature | Syntax | Notes |
|---|---|---|
| In-document link | `[link text](#anchor)` | Works in paragraphs, list items, table body cells and `>` callouts; literal inside headings, table header rows, code fences and inline code. Rendered like the existing external links (Calibri 10.5 pt, 0B5CAD, underlined) as a `w:hyperlink w:anchor`, the same element the contents entries use. |
| Figure | `![caption](relative/path.png)` alone on its line | Path relative to the markdown file (`%20` for a space); PNG or JPEG checked by bytes; centred at the text width (9,360 twips, 12,960 landscape), aspect kept, capped at 8 in tall (5.5 in landscape); caption beneath in Calibri 9 pt grey and stored as the picture's description. |

**The anchor rule is GitHub's exactly:** take the heading text without its markup, trim, lower-case, delete
every character that is not a letter, digit, underscore, hyphen or space, turn each space into a hyphen
(spaces are never collapsed, so `## 4. The walk — in brief` is `#4-the-walk--in-brief`), suffix duplicates
`-1`, `-2`, with GitHub's rule for a suffix already taken. Position-based ids were rejected because they
renumber silently when a heading is added above; a heading's anchor changes only when its own text changes,
and then the build fails loudly. The same links work on GitHub and in VS Code's preview.

A link to a missing anchor, or a figure that cannot be read, fails the build, writes no file, and lists
every problem at once with line numbers and a near-match suggestion. Renaming a heading breaks the links to
it until they are updated; that is intended.

## Proof

- Both existing Word documents build byte-identically before and after the change, with the exact W2 and
  W1 arguments: `word/document.xml` and `word/numbering.xml` hashes equal (the one-pager
  `d761f049…` / `38be9fd6…`, the technical note `2a51ca0d…` / `1fa40374…`), every other part identical except
  the build timestamps in `docProps/core.xml`. Because the `docx` library gives each external link a random
  id, the proof is run with a seeded random preload (converter header rule 13); `build-pair.sh` in lane W4's
  scratchpad folder reproduces it for any later converter change.
- 18 slug fixtures pass; the 24 GitHub-style links in
  `docs/architecture/tapestry-requirements-extraction-2026-09-18.md` all land on the right heading in a
  scratchpad build, double-hyphen cases included.
- Figure tests: a 600×300 PNG renders at 6.5 × 3.25 in; a 390×844 PNG is held to 8 in tall; a JPEG with
  EXIF renders at 6.5 in square; relationships, media parts and unique picture ids present.

## Follow-up: unique bookmark ids

The review of the built documents (R2 round 4) found every heading bookmark carrying `w:id="1"`, the `docx`
library's default; names were unique, so every link resolved, and Word desktop tolerates it, but ECMA-376
defines the id as a unique annotation identifier and Word Online and PDF export could not be tested here.
The converter now numbers each bookmark's start/end pair 1, 2, 3 … in document order (header rule 12,
rewritten; the same rule already gave each figure its own id). Proof on both current documents with the
seeded build pair: the only change in `word/document.xml` is the bookmark id values (the one-pager 8 of 10
attributes, the technical note 50 of 52; the first pair was already 1), zero other changes, every start
matched by its end, `word/numbering.xml` unchanged. Both Word copies were rebuilt in place afterwards.

## Not verified, and known limits

- Ctrl+Click in Word desktop and links surviving a PDF export were not machine-verified (Word may not be
  automated on this machine, and there is no LibreOffice). The evidence is structural: the links are the same
  element type as the contents entries, which work. The owner is asked to Ctrl+Click one link and try Save as
  PDF on the first real build.
- JPEG EXIF rotation is ignored; save photos upright. A figure with no alt text gets a warning and no caption.
- Older, unchanged: a markdown file with CRLF line endings fails on its first heading; repo markdown is LF.
  The fix is `md.split(/\r?\n/)` and belongs to a later converter change with its byte-identical proof.
