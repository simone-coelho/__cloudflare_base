# Lane K4: the SE path, proven by scaffolding the LG demo

**Opened 2026-10-02 by the lead; starts when the LG demo's two-letter name is chosen**, because the slug sets every path the scaffold writes. Design: [Demo-Kit-Design.md](../Demo-Kit-Design.md) §2.3, §2.4, §2.5 and the decisions log (worker `edge-platform-<slug>`, queue `events-<slug>`, the beat documents as data, the products-file check). The first consumer's requirements: [LG-Understanding-and-Use-Cases.md](../../lg/LG-Understanding-and-Use-Cases.md) §5.

## Scope

1. **`scripts/demo-kit/new-demo.mjs --config public/<slug>/demo.config.json`** writes, from templates under `scripts/demo-kit/templates/`:
   - the worker config through `build-demo-worker-config.mjs` (`--name edge-platform-<slug> --queue events-<slug> --dev-port <port>`), refusing a slug whose worker or queue already exists in the repository;
   - `src/demos/<slug>.config.ts` and a thin `src/routes/<slug>.ts` built by the kit factories, plus the mount lines for `src/index.ts` printed for the lead to apply (the scaffolder does not edit `src/index.ts`);
   - `public/<slug>/`: `index.html` and a product page shell on the kit modules, `<slug>.css` with the palette tokens from the config, `<slug>.js` with empty renderers and a `facts` skeleton, `beats.json` with the three-to-five beats named in the config as data, `beats/` with an `anchor.json` and the opening documents, `catalog.json`, the products file as given, `img/MANIFEST.json`;
   - `scripts/demo-kit/configs/<slug>.json` with the two suites of kind page and dom, and two suite files for the vertical's outcomes with the arrival checks already written;
   - `docs/<slug>/` with the design document, presenter script and resume skeletons, each carrying the decisions-log table and the morning routine;
   - a printed list of the secrets the worker needs, by name only, and the deploy command.
2. **`demo.config.json`** as the design describes it (name, slug, tenant, worker, queue, dev port, palette, fonts, pages and slots, dimensions with τ, the beats file, the products file and its attribute map, the imagery manifest, the regional vocabulary, asserted context names, report slots, flags, sign-in demo accounts by name). The validator in `lib/config.mjs` grows to cover it, with the products-file check: a seed refuses when a beat document's product facts disagree with the products file.
3. **`docs/demo-kit/HOWTO.md`**: from a customer brief to a hosted demo, in the order the work happens: the research lanes, the design document with its decisions log, the config, the products and imagery, the beats, the suites, the deploy on the owner's go from a WSL worktree, the morning routine. Written for a solutions engineer who has never seen the repository.
4. **`.claude/skills/new-demo/SKILL.md`**: invoked as `/new-demo`, it interviews for the customer, the fictional name, the palette, the product source and the story in three to five beats, writes the config, runs the scaffolder, dispatches build lanes for the renderers, the catalog pieces and the imagery with the kit's path-ownership rules, runs `check-demo`, and writes the resume. It never deploys; it prints the deploy command for the owner.
5. **The proof:** scaffold the LG demo with its chosen slug, the LG palette, and TVs, laundry and the kitchen path as its categories; the scaffold builds, its suites run against a local rig on its own port and state directory and pass their arrival checks, `check-demo` passes, and nothing it writes collides with Vantage or Top Offers.

## Definition of done

The scaffold of the LG demo exists under its slug with every file above; `node --test` green with the scaffolder's and validator's new tests; `check-demo --config <slug>` green against a local rig; the Vantage suites untouched and still green through `check-demo --config vantage`; the HOWTO and the skill reviewed by reading them as the SE would, start to finish; the Report section written.
