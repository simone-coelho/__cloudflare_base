# Lane H2: hosting a demo's own worker as one command

**Opened 2026-10-02 by the lead.** The Vantage hosting sequence (`docs/verizon/RESUME-vantage.md`: migrations with the remote 0012 workaround, the secrets through `wrangler secret put`, the deploy from a clean WSL worktree, `wrangler triggers deploy`, the hosted seed with a minted operator token, the region seed, the morning routine) becomes `scripts/demo-kit/host.mjs --config <slug>`. The steps are explicit, there is a `--dry-run` that prints every step with values redacted, and the command stops at the first failure and names the step. Design: [Demo-Kit-Design.md](../Demo-Kit-Design.md) §2.3, §2.5 and the decisions log; the worker's cloud list is K4's Report.

## What it does

```bash
node scripts/demo-kit/host.mjs --config <slug> --dry-run                                  # anywhere: every step printed, nothing run
node scripts/demo-kit/host.mjs --config <slug> --confirm edge-platform-<slug>             # from WSL, on the owner's go: all six steps
node scripts/demo-kit/host.mjs --config <slug> --step <name> [--confirm edge-platform-<slug>]   # one step
node scripts/demo-kit/host.mjs --config <slug> --from <name> --confirm edge-platform-<slug>     # one step and the ones after it
node scripts/demo-kit/host.mjs --config <slug> --step secrets --only IDENTITY_SECRETS --confirm edge-platform-<slug>
```

Before any step runs, it **refuses** a config it must never host: the shared worker `edge-platform`, the customer stamps (named here and also read from `wrangler.toml`'s own `[env.*]` sections), a worker other than `edge-platform-<slug>`, a worker config other than `wrangler.<slug>.toml` (never `wrangler.toml`), a worker config that names another worker, carries stamp environments, runs a `DEPLOYMENT_PROFILE` other than `demo` or names a queue other than `events-<slug>` and its dead-letter queue, and seed operators that the hosted TENANTS would not grant. A real run is refused from Windows (worktree line endings) and needs `--confirm <worker name>` for any step after preflight.

**Why the seed step deploys, and in this order.** `seed.mjs` re-anchors every window to now and rewrites `public/<slug>/beats/`. The worker applies a beat from its own ASSETS copy of those documents, so until a deploy ships the rewritten copies, a beat would publish a different document from the one just seeded. The seed runs inside a worktree of the head, so the re-anchored documents land in that worktree, the redeploy ships exactly them, and the shared checkout (with other lanes' uncommitted beat files) is never written. The redeploy comes straight after the seed and before the region seed. That keeps the window of mismatched assets as short as possible (the region seed takes about 11 minutes hosted), and the region seed writes no file under `public/`. This is the order Vantage's checklist uses.

**The secrets.** Values exist only in the process. They go to wrangler on stdin, never as an argument and never in a child's environment. They are never printed and never written to disk. Every line the command prints, including its children's output, passes through a redactor that holds each value, its JSON-escaped form and each minted token, and replaces them with a label. The sha256 prefix (8 hex digits) lets the lead tell two runs apart. TENANTS provisions the tenant alone and grants it to `<slug>-demo`, `seed-<slug>` and `seed-<slug>-region`. SDK_KEYS is `<tenant>:demo-site`, the public site key the pages send. RETENTION carries the tenant's own policies when `.dev.vars` has a complete set, else the first complete set (the rig's rule, made strict: the worker throws on a category it has no policy for, so an incomplete set is refused rather than copied).

**The JWT secret across runs.** The hosted seed's tokens are minted from the worker's `JWT_SECRET`. A secret generated by a run lives only in that run's memory: its own seed step can mint, and once it ends nothing can until the secret is put again. So when the owner keeps one, as `<SLUG>_REMOTE_JWT_SECRET` in the environment or in `.dev.vars` (Vantage already does: `VANTAGE_REMOTE_JWT_SECRET`), the secrets step puts that one instead of generating, and `--step seed` alone mints from it. That makes `--from seed` the morning routine for any hosted demo. For a new demo, the dry run prints the one-line way for the owner to create the kept secret before the first run. The command never writes it.

**The tokens.** They are minted in memory with `scripts/lib/tool-token.mjs` `resolveToolToken`, exactly as the resume's `mint()` does: subject the config's operator, roles `operator`, 30 minutes, issuer and audience read from the worker config's `[vars]`. Each is passed to its seed as `OPERATOR_TOKEN` in the child's environment, never as `--token` on a command line, which any process on the machine can read. `seed.mjs` and `region-seed.mjs` read that variable when no `--token` is given.

**If a run is interrupted** inside a worktree, the worktree is left under `/tmp/edge-host-<slug>-<step>-<stamp>`: `unlink <it>/node_modules`, then `git worktree remove --force <it>` from WSL.

### The tests

The derivations: TENANTS, SDK_KEYS and RETENTION equal what `rigVars` passes for the same `.dev.vars`, with the tenant's own complete policies preferred and an incomplete set refused. The six secrets come in order, each accepted by the worker's own `readSigningConfig`, `safeIdentitySecret` and `parseIdentitySecrets(…, true)`, the kept JWT secret read from the environment before `.dev.vars`. The redaction: raw and JSON-escaped forms, a failing `secret put` whose stderr echoes its value, a seed whose streamed line echoes its token and the JWT secret. The readers: pending migrations in file order (an unreadable list stops the step), whole-name queue matching (`events-oh` is not `events-oh-dlq`), the version id, porcelain, the recipe, the worktree name. The steps: `--step`, `--from`. The refusals: every case above, and a run refused before the runner is touched (no or wrong `--confirm`, from Windows, two step choices, an unknown step, `--only` outside the secrets). The dry run: six headers in order, every command, the seed then the redeploy then the region seed, no value. A full run on the fake runner: the exact 30-call order, every secret only on stdin and absent from every argument, child environment and printed line, both worktrees of the same head with autocrlf input, the links unlinked, the tokens verified with `jose` against the JWT secret the run put (subject, role, 30 minutes, issuer and audience), the scratch copy and its directory removed. The stops: a missing migration (the recipe printed, never run, nothing after the step), a missing queue, a failed deploy (the worktree still cleaned up), a stale worker config, a head without the mount. Each step alone: the seed without a kept secret stops before making a worktree, and with one it mints from it; `--only`; verify outside WSL and without `node.exe`. The seed's worktree is left, not forced, when it holds a change no step made.

### Choices beyond the brief, for the lead's ruling

1. **The owner's kept JWT secret** (`<SLUG>_REMOTE_JWT_SECRET`, environment then `.dev.vars`) is used instead of a generated one when present. Without it, a generated secret dies with the run, and the morning reseed (and `--step seed` alone) could never mint. This follows Vantage's practice and never writes the secret.
2. **The tokens travel as `OPERATOR_TOKEN` in the seed's environment, not `--token <minted>`**, so they never appear in a process list. The seeds already read that variable.
3. **The redeploy comes between the seed and the region seed**, not after both, for the reason above. It is still after the seed, which is the rule.
4. **`--confirm <worker>`** for every step after preflight, so a slug typo cannot point the secrets or a deploy at the wrong demo; **`--from`** to go on after the owner applies what step 3 printed; **`--only`** so a hosted worker can gain IDENTITY_SECRETS for P3's sign-in without rotating IDENTITY_SALT, which re-keys every visitor id and receipt audit reference made before it.
5. **Preflight also checks that the head mounts `/<slug>/api`.** The deploy ships the head, and a head without the mount lines is exactly the failure AGENTS.md records: every page 200, every API 404.
6. **The queues are checked in step 3** (read-only, with the create commands printed), because a deploy to a worker whose queue does not exist fails, and K4's cloud list names both queues while the brief's steps do not create them.
7. **Verify runs check-demo's suites only, through `node.exe`.** Preflight already ran the bundles, typecheck and grep, and from WSL the DOM suite finds no Chrome.

- **OH cannot be hosted from the current head.** `src/index.ts` at `9b3dafa`/`ef32f7b` does not mount `/oh/api` or `/oh/api/coldstart`; the working tree does, uncommitted. Preflight refuses until the lead commits the mount lines (K4's Report has them).
- **"Byte-equal to the builder's output" holds only under the same file name.** The builder's header line 4 (`# Deploy (owner's go only): npx wrangler deploy --config <file>`) takes the output file's own basename, so a comparison copy written as `host-oh-<pid>.toml` differs at byte 320 although the configs are identical. My first real preflight caught exactly that. The command now builds into `/tmp/host-<slug>-XXXXXX/wrangler.<slug>.toml`, and both configs compare byte-equal.
- **RETENTION's source.** For OH, `.dev.vars` has no `oh` policies, so the derivation copies the first complete set, which is `coach`'s (the rig does the same). Vantage's hosted RETENTION was copied from `shn` in September. The policies are the same seven categories either way. A demo that wants specific durations adds its own tenant's set to `.dev.vars` and the command takes that.
